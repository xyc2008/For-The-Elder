# 迭代记录

本文件按轮次记录每一次迭代。每一轮固定四小节：**目标 / 产出 / 问题与解决 / 验证**。

「验证」一节只写**真正跑过**的东西，并附可复核的原始数据；没跑的一律显式写「未验证」。
数字来自 Gradle 的 XML 报告、`adb` 的 UI 层级转储、`logcat`，不来自记忆或推测。

轮次的划分标准是「交付了一个可独立验收的增量」，不是「写了多少文件」。

## 第 1 轮：需求基线

**目标**：把 `新建 DOCX 文档.docx` 里的产品思路(「懂节制的陪伴者」)变成可验收的工程语言，
划清范围，并锁定后续所有轮次的技术基线与里程碑。

**产出**

- `docs/00-项目章程与需求计划书.md`(11,694 字节)
  - 立项背景(引原文)、业务目标 G-01~G-06、交付目标与 10+10 轮里程碑
  - 范围与**明确不做清单**；负面需求 NR-01~NR-05(零推销 / 不打扰 / 不制造焦虑 /
    不替用户判断 / 不索取无关权限)
  - 用户画像(含两条铁律：不用「老人模式」这类称呼；不用问卷收集偏好)
  - 假定 A-01~A-04、约束 C-01~C-06、角色分工、7 条项目级验收准则、风险 R-01~R-03
- `docs/01-需求规格说明书.md`(21,533 字节)
  - 术语表 10 词(每词都写明「不是什么」)、需求编号规则
  - 用户故事 US-01~US-10
  - 功能需求 FR-01~FR-14，每条带验收准则(AC)表、当前证据、边界与异常
  - 非功能需求 NFR-01~NFR-17、数据需求 DR-01~DR-09
  - 轮次追溯矩阵、需求变更规则、**遗留缺口诚实清单 GAP-01~GAP-05**

**问题与解决**

- 原始 docx 是「产品思路」不是「需求」，很多句子是立场而非可测行为。
  解决办法是把每条立场拆成「负面需求」并给出可测的判据，例如
  NR-02「不打扰」落到「刻意不申请 POST_NOTIFICATIONS、不使用前台服务唤起」这种可以
  用「权限数为 0」直接核对的程度。
- 出现过一个自我加戏的风险：把「趣味脑力互动」写成认知训练/健脑。
  已在 docs/01 术语表里明确**严格剥离医疗宣称**，定为「趣味大脑体操」。

**验证**

- 文档存在与体积：`stat` 实测 `docs/00`=11,694 字节、`docs/01`=21,533 字节。**已验证**。
- 文档与代码的一致性：**未验证**(当时还没有代码；后续轮次逐条回填证据)。

## 第 2 轮：工程骨架与最小可运行链路

**目标**：把技术基线落地成能构建、能装机、能跑通一条真实链路的工程，
并交付第一批有实际行为的功能(引导、问候、字号、设置)，不允许出现空壳页面。

**产出**

**(1) 构建与工具链**

- Gradle 8.13 wrapper + AGP 8.7.3 + Kotlin 2.0.21 + KSP 2.0.21-1.0.26
- `gradle/libs.versions.toml` 版本目录统一管版本
- 单模块 `:app` + 包分层(core / data / domain / ui)，**手工 DI 不用 Hilt**
- compileSdk / targetSdk 35、minSdk 26、versionCode 1、versionName `0.1.0`
- `applicationId` 为 `com.fortheelder`(debug 变体加 `.debug` 后缀，可与正式版共存)
- `debug`/`release` 之外不建无意义的变体

**(2) 数据层(DataStore)**

  `AppSettings`、`settings` 流、`ensureFirstLaunchRecorded` / `setAddress` / `setFontSize` /
  `completeOnboarding` / `resetToDefaults`
- `data/prefs/SettingsDataStore.kt`：Preferences DataStore 实现

**(3) 领域层(问候引擎)**

- `domain/engine/greeting/GreetingEngine.kt`：按一天里的时段产出问候语与提示语
- `core/time/AppClock.kt`：集中时间取值，让引擎可以在测试里注入固定时间

**(4) UI 层**

- `ui/common/ElderComponents.kt`：`ElderScreen` / `ElderHeader` / `SectionCard` / `SectionTitle` /
  `BulletLine` / `QuietNote` / `PrimaryWideButton` / `SecondaryWideButton` / `ActionRow`
- `ui/onboard/OnboardingScreen.kt`：两页直上直下(不用横滑分页)，第一页讲「不会做什么」
- `ui/home/`：`HomeScreen` + `HomeViewModel`
- `ui/settings/SettingsScreen.kt`：改完立即生效不设「确定」；仅「清空设置」需确认对话框
- `ui/nav/MainNav.kt`：只登记 `HOME` 与 `SETTINGS` 两个**已完成**的目的地，不预埋空壳页面

**(5) 隐私立场**

- `AndroidManifest.xml`：`allowBackup="false"`；**申请权限数 = 0**
- 刻意**不写** `backup_rules.xml` / `data_extraction_rules.xml`

**问题与解决**

- `TopAppBar` 在 55 岁以上用户的实际观感里偏「工具感」，且大字重下标题容易被状态栏压住。
  改为自绘 `Row` 表头，配合 `safeDrawingPadding()` 处理状态栏/导航栏/刘海/键盘四类遮挡。
- 只用 `safeDrawing` 不加 `imePadding`：`safeDrawing` 已包含 IME，重复加会在键盘弹出时
  把内容顶得过高。

- 单测(JVM)实测 24 例全绿(第 3 轮用 `--rerun-tasks` 复核过，见下)。
- APK 产出：`app/build/outputs/apk/debug/app-debug.apk` = **18,410,122 字节**。
- 装机与启动：`adb install -r` → Success；`am start` 进入主界面，`logcat -b crash` 无输出。

## 第 3 轮：字号可访问性缺陷修复与渲染级测试体系

**目标**：字号档位是本项目最核心的可访问性承诺之一(`docs/01` 中一条 AC 就是「不用去改手机设置也能放大字」)，
但此前只有「渲染不崩」的证据。本轮要查清「点一下真的大了吗」，补齐渲染级测试，
并把 UI 层端到端链路实测一遍。

**产出**

**(1) 查清并修复一个真实缺陷：档位越高、放大越被压制**

原实现用「替换 `LocalDensity.fontScale`」来放大字号。仪器化探针实测发现，
在 API 35 上 `Density(density, fontScale)` 工厂内置**非线性字体换算**，`sp→px` 不是线性的：
字号越大、放大被压制得越狠。原始数据见 `records/04-质量与验证记录.md`。

后果是 30sp 以上的标题在「更大」档**完全不放大**——正文变大了、标题没变，
这是一个用户一眼就能看出来的假功能。

修复方式：改为**按档位换一套排版表**(把倍率直接乘进每个 `sp`，行高同步乘，字距与字重不乘)，
不再替换 `LocalDensity`。落在：

- `ui/theme/Type.kt` —— 整文件重写，新增 `elderTypography(scale: Float = 1f)`，15 个 style 逐个列出数值
- `ui/theme/Theme.kt` —— 删掉 `LocalBaseFontScale` 与 `LocalDensity` 替换，只剩
  `remember(fontSize) { elderTypography(fontSize.scale) }`
- `ui/onboard/OnboardingScreen.kt` —— 更新 `FontPreviewCard` 的说明

**(2) 建立渲染级测试**

- 新增 `app/src/test/.../ui/theme/TypographyScaleTest.kt`(纯 JVM，5 例)：
  标准档基准值、每档全量字号与行高按倍率同步、字重与字距不随档位变、
  大档行高能容纳放大后的文字、同档重复调用等价但非同一实例
- 重写 `app/src/androidTest/.../ui/theme/ThemeFontScaleTest.kt`(5 例)：
  用 `TextLayoutResult.size.width` 量**原始像素**，容差 3%
  - 教训：第一版用 `getUnclippedBoundsInRoot()` 量 dp，得到的倍率恒偏低
    (标称 1.15 量出 1.097)。原因是那个接口把像素换算成 dp 时用的 density **本身就带 fontScale**，
    被试和量尺是同一个东西，比值被部分抵消。
  - 错误做法：对平台做它不承诺的线性假设。第一版断言「系统 1.5 × 应用内 1.3 线性相乘」，
    实测不成立。已改写为断言两条真正要保证的性质：**应用不抹平系统设置**、
    **应用内档位在该环境下仍然显著放大**。实测倍率打印出来归档。

**(3) UI 层端到端实测(关闭 GAP-01)**

用 `adb` + `uiautomator dump` 走完整条链路，见 `records/04` 的完整证据表。
结论：`docs/01` 中 FR-13 的 AC-13.1 / AC-13.4 此前只在数据层验证过，**现在已在 UI 层跑通**。

**问题与解决**

- 诊断用的 `FontScaleDensityProbeTest` 是**故意 `fail()`** 的探针(用失败信息带回测量值)，
  留着会让整个 `connectedDebugAndroidTest` 变红。已确认删除。
- `DensityImpl` 没有实现 `equals`，在 `setContent` 里每次重组新建实例会让下游读取者反复失效。
  合成 density 必须 `remember` 住。
- `adb` 无法输入中文(`input text` 只支持 ASCII)，所以 UI 层用 ASCII 称呼走链路。
  中文称呼的持久化由 `SettingsStoreTest` 覆盖(见 `records/04` 的 GAP-02)。

**验证**

- `./gradlew :app:testDebugUnitTest --rerun-tasks` → **BUILD SUCCESSFUL in 29s**，26 tasks executed(强制真跑)。
  XML 报告实测：`SettingsStoreTest` **tests=9 failures=0**、
  `GreetingEngineTest` **tests=10 failures=0**、`TypographyScaleTest` **tests=5 failures=0** → **合计 24 例全绿**。
- `./gradlew :app:connectedDebugAndroidTest -P...class=...ThemeFontScaleTest` → **BUILD SUCCESSFUL in 39s**，
  `Finished 5 tests on Elder_API35(AVD)`，**5 例全绿**。
- 实测倍率(logcat 原始行)：
  `FONTSCALE-PROBE plain=320 syntheticStandard=419 syntheticExtra=461 systemOnlyRatio=1.309375 appTierRatio=1.1002387`
  即：系统字号 1.5 在本平台只带来 1.309×；在其之上再选应用内「更大」，只额外带来 1.100×
  (标称 1.30×)。**这是平台行为，不是缺陷**，但**它意味着系统字号调大以后，应用内档位的区分度会明显下降**——
  作为已知限制记入 `records/03` 的 ADR-004 与 `records/CHANGELOG` 的 Known Issues。
- UI 端到端 12 步全部实测通过，`logcat -b crash` 全程无输出。
- `MainNav` 的 HOME ↔ SETTINGS 导航**首次在 UI 层实测**(此前只有代码，无运行证据)。
- 系统字号非 1.0 的真机/模拟器整体观感：**未验证**(只在测试里用合成的 density 验证过行为)。
