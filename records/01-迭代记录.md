# 迭代记录

本文件按轮次记录每一次迭代。每一轮固定四小节：**目标 / 产出 / 问题与解决 / 验证**。

「验证」一节只写**真正跑过**的东西，并附可复核的原始数据；没跑的一律显式写「未验证」。
数字来自 Gradle 的 XML 报告、`adb` 的 UI 层级转储、`logcat`，不来自记忆或推测。

轮次的划分标准是「交付了一个可独立验收的增量」，不是「写了多少文件」。

## 第 3 轮：字号可访问性缺陷修复与渲染级测试体系

**目标**：字号档位是本项目最核心的可访问性承诺之一(`docs/01` 中一条 AC 就是「不用去改手机设置也能放大字」)，
但此前只有「渲染不崩」的证据。本轮要查清「点一下真的大了吗」，补齐渲染级测试，
并把 UI 层端到端链路实测一遍。

**产出**

**(1) 查清并修复一个真实缺陷：档位越高、放大越被压制**

原实现用「替换 `LocalDensity.fontScale`」来放大字号。仪器化探针实测发现，
在 API 35 上 `Density(density, fontScale)` 工厂内置**非线性字体换算**，`sp→px` 不是线性的：
字号越大、放大被压制得越狠。原始数据见 `records/04-质量与验证记录.md`。

后果是 30sp 以上的标题在「更大」档**完全不放大**——正文变大了、标题没变，
这是一个用户一眼就能看出来的假功能。

修复方式：改为**按档位换一套排版表**(把倍率直接乘进每个 `sp`，行高同步乘，字距与字重不乘)，
不再替换 `LocalDensity`。落在：

- `ui/theme/Type.kt` —— 整文件重写，新增 `elderTypography(scale: Float = 1f)`，15 个 style 逐个列出数值
- `ui/theme/Theme.kt` —— 删掉 `LocalBaseFontScale` 与 `LocalDensity` 替换，只剩
  `remember(fontSize) { elderTypography(fontSize.scale) }`
- `ui/onboard/OnboardingScreen.kt` —— 更新 `FontPreviewCard` 的说明

**(2) 建立渲染级测试**

- 新增 `app/src/test/.../ui/theme/TypographyScaleTest.kt`(纯 JVM，5 例)：
  标准档基准值、每档全量字号与行高按倍率同步、字重与字距不随档位变、
  大档行高能容纳放大后的文字、同档重复调用等价但非同一实例
- 重写 `app/src/androidTest/.../ui/theme/ThemeFontScaleTest.kt`(5 例)：
  用 `TextLayoutResult.size.width` 量**原始像素**，容差 3%
  - 教训：第一版用 `getUnclippedBoundsInRoot()` 量 dp，得到的倍率恒偏低
    (标称 1.15 量出 1.097)。原因是那个接口把像素换算成 dp 时用的 density **本身就带 fontScale**，
    被试和量尺是同一个东西，比值被部分抵消。
  - 错误做法：对平台做它不承诺的线性假设。第一版断言「系统 1.5 × 应用内 1.3 线性相乘」，
    实测不成立。已改写为断言两条真正要保证的性质：**应用不抹平系统设置**、
    **应用内档位在该环境下仍然显著放大**。实测倍率打印出来归档。

**(3) UI 层端到端实测(关闭 GAP-01)**

用 `adb` + `uiautomator dump` 走完整条链路，见 `records/04` 的完整证据表。
结论：`docs/01` 中 FR-13 的 AC-13.1 / AC-13.4 此前只在数据层验证过，**现在已在 UI 层跑通**。

**问题与解决**

- 诊断用的 `FontScaleDensityProbeTest` 是**故意 `fail()`** 的探针(用失败信息带回测量值)，
  留着会让整个 `connectedDebugAndroidTest` 变红。已确认删除。
- `DensityImpl` 没有实现 `equals`，在 `setContent` 里每次重组新建实例会让下游读取者反复失效。
  合成 density 必须 `remember` 住。
- `adb` 无法输入中文(`input text` 只支持 ASCII)，所以 UI 层用 ASCII 称呼走链路。
  中文称呼的持久化由 `SettingsStoreTest` 覆盖(见 `records/04` 的 GAP-02)。

**验证**

- `./gradlew :app:testDebugUnitTest --rerun-tasks` → **BUILD SUCCESSFUL in 29s**，26 tasks executed(强制真跑)。
  XML 报告实测：`SettingsStoreTest` **tests=9 failures=0**、
  `GreetingEngineTest` **tests=10 failures=0**、`TypographyScaleTest` **tests=5 failures=0** → **合计 24 例全绿**。
- `./gradlew :app:connectedDebugAndroidTest -P...class=...ThemeFontScaleTest` → **BUILD SUCCESSFUL in 39s**，
  `Finished 5 tests on Elder_API35(AVD)`，**5 例全绿**。
- 实测倍率(logcat 原始行)：
  `FONTSCALE-PROBE plain=320 syntheticStandard=419 syntheticExtra=461 systemOnlyRatio=1.309375 appTierRatio=1.1002387`
  即：系统字号 1.5 在本平台只带来 1.309×；在其之上再选应用内「更大」，只额外带来 1.100×
  (标称 1.30×)。**这是平台行为，不是缺陷**，但**它意味着系统字号调大以后，应用内档位的区分度会明显下降**——
  作为已知限制记入 `records/03` 的 ADR-004 与 `records/CHANGELOG` 的 Known Issues。
- UI 端到端 12 步全部实测通过，`logcat -b crash` 全程无输出。
- `MainNav` 的 HOME ↔ SETTINGS 导航**首次在 UI 层实测**(此前只有代码，无运行证据)。
- 系统字号非 1.0 的真机/模拟器整体观感：**未验证**(只在测试里用合成的 density 验证过行为)。

## 第 4 轮：作息感知引擎(纯 Kotlin 领域层 + 单测)

**目标**

把 `docs/01` 的 FR-04 拆成两半，本轮做**不碰 Android 的那一半**：从「亮屏/解锁/充电」
这类信号里推断出作息画像。目标是 AC-04.1(引擎不依赖任何 Android API，可在 JVM 单测里充分验证)
与 AC-04.2(同一份输入永远得到同一份输出)。采集器、权限向导留到第 6 轮(原写「第 5 轮」是排期估算偏差，
第 5 轮实际做的是落库)，落库在第 5 轮完成。

这样切分的理由是：推断逻辑是这一块唯一有难度的地方，把它做成纯函数就能在 JVM 上用合成数据
把边界情况全跑一遍，不用等模拟器；采集部分则全是平台细节，放在一起会互相拖累。

**产出**

- 新增 `app/src/main/java/com/fortheelder/domain/engine/rhythm/RhythmSignal.kt`(37 行)
  - `RhythmKind`：`SCREEN_ON` / `SCREEN_OFF` / `USER_PRESENT` / `CHARGING_START` / `CHARGING_END`。
    只有这五种，因为它们都能从**运行时注册的系统广播**拿到，不需要读其他应用的使用记录。
  - `isPresence` 把 `SCREEN_ON` 也当成「人在场」：目标用户里相当一部分不设锁屏密码，
    那种情况根本收不到 `USER_PRESENT`。代价是兜里误触亮屏也算在线，靠每天最少信号条数兜住。
- 新增 `RhythmInference.kt`(274 行)：`RhythmConfig`(阈值全部有默认值) +
  `RhythmInference.infer(signals): RhythmResult`。
  - 作息日按凌晨 4 点分界 → 每天至少 20 条在场信号才算有效天 → 有效天不足 3 天返回 `Gathering`
    → 起床/睡前取中位数 → 醒着不足 6 小时返回 `Inconsistent`
    → 按 30 分钟桶统计日均密度，低于 `max(均值×0.35, 0.5)` 的桶算安静
    → 连续安静段还要同时满足「≥1 小时」「离起床 ≥45 分钟」「离睡前 ≥45 分钟」才成为空窗候选。
- 新增 `DailyRhythm.kt`(89 行)：`TimeSpan`(半开区间，允许跨子夜)、`DailyRhythm`(画像)、
  `RhythmResult`(三态)。
- 新增 `app/src/test/java/.../rhythm/RhythmInferenceTest.kt`(337 行，23 例)：见 `records/04`。

**问题与解决**

1. **自己写的第一版里有两条「看起来在做事、其实恒不生效」的逻辑**，写测试前就删掉了：
   一处算出结果后再除以 1 的噪声运算，一处恒为 0 的 `centerBonus` 加分项。
   留着它们会让人以为置信度算法比实际复杂——**这也是「不要存在假功能」的一条**，
   只不过假在内部而不是界面上。
2. **`edgeGuardMinutes` 一开始是个装饰性阈值**。原实现是「把起止桶裁掉再判断」，
   但起止桶按定义必然有信号，裁剪永远不会生效——阈值写在那里却不产生任何行为差异。
   改成**真实的丢弃规则**：安静段若落在起床后 45 分钟内或睡前 45 分钟内，整段丢弃。
   并配了两条互相反证的用例守着它(起床后 07:00–08:00 的安静段不报；
   同样长度但挪到 07:30–08:30 就报出来)。
3. **单测里有一条期望值是我算错的，代码是对的**。`起床时刻散乱时置信度下降` 一开始
   7 天里有 2 天被引擎判成无效天，因为「起床越晚、一天剩下的桶越少」——
   那些天每个桶只放 1 条信号，桶数一少就低于每天 20 条的在场门槛，
   于是 `sampleDays` 变成 5 而不是 7，置信度实测 **0.48214287** 而非期望的 0.5。
   修改的是**测试数据**(每桶放两条)而不是引擎，并把 `sampleDays == 7` 也断言上，
   免得以后又悄悄退化成「测的不是散乱而是稀疏」。这条失败如实留在记录里：
   它证明了那道门槛真的在起作用。

**验证**

  26 tasks executed(强制真跑，不吃缓存)。XML 报告实测：

  | 测试类 | tests | failures | errors |
  |---|---|---|---|
  | `data.prefs.SettingsStoreTest` | 9 | 0 | 0 |
  | `domain.engine.greeting.GreetingEngineTest` | 10 | 0 | 0 |
  | `domain.engine.rhythm.RhythmInferenceTest` | 23 | 0 | 0 |
  | `ui.theme.TypographyScaleTest` | 5 | 0 | 0 |

- 静态证据(AC-04.1)：`grep -rn "android\.\|androidx\." app/src/main/java/com/fortheelder/domain/engine/rhythm/`
  → **无匹配**。引擎只用到 `java.time`，所以能在 JVM 上跑。
- 静态证据(AC-03.5 的延伸)：`grep -rn "LocalDateTime.now\|LocalDate.now\|System.currentTimeMillis"`
  全仓 → **无匹配**(只有 `core/time/AppClock.kt` 里有，已排除)。引擎不看「现在几点」。

  (`4 executed, 34 up-to-date`)，产物 `app/build/outputs/apk/debug/app-debug.apk`
  **18,432,832 字节，时间戳 05:57:51**。说明第 3 轮末尾那两处 KDoc 改动没有碰到代码。

  都是**从需求推导的估计值，没有真实用户数据支撑**。它们能保证「不乱报」，

## 第 5 轮：作息数据落库与真实设备上的链路验证(FR-04 的第二半)

**目标**

第 4 轮的引擎只能吃内存里的 `List<RhythmSignal>`：算得出来，但关掉应用就没了。
本轮把它接到真实存储上——信号进 Room、画像算出来也落库、重启后读得回来，
并且**在真实设备(模拟器 `Elder_API35`)上**证明这条链路走得通，而不是只在 JVM 单测里成立。
顺带清掉上一轮留下的两笔工程债：三个声明了却全仓零引用的依赖、以及一个比预期大得多的 APK。

采集器(系统广播)**本轮没做**，排到第 6 轮。第 4 轮记录里**两处**把采集器写成「第 5 轮」
是排期估算偏差，已在原地改为「第 6 轮」(修正处：本文件第 4 轮小节、`records/04` 第 4.5 节、
`records/CHANGELOG` 的说明行与 `Unverified` 一节)。

**产出**

  - `RhythmSignalEntity.kt`(34 行)：一次亮屏/解锁/充放电事件。存 **UTC 绝对时刻 + 采集时的时区偏移**，

  - `DailyRhythmEntity.kt`(32 行) / `DailyRhythmDao.kt`(36 行)：画像每天一行，主键就是作息日的 `epochDay`，

1. **带空格的方法名让编译产物文件名非法**。Kotlin 给测试方法里的 lambda 生成匿名类时，

   `RhythmRepositoryTest$入睡锚点看不出规律时读回来仍是 null$1.class` 这种**带空格的文件名**，
   在文件系统 / dex 环节过不去。处理办法是把方法名里的空格去掉(那句改成「读回来仍是空」)，
   **全仓共改 4 处**。这类名字读起来顺口，但只有不含空格的才安全。

2. **三个依赖声明了却从没用过**。`okhttp`、`kotlinx-serialization-json`、`androidx-work-runtime-ktx`

3. **两条仪器化断言是我写错的，代码是对的**。两条都留在记录里：

## 第 6 轮：作息采集从「算得出来」走到「真的收得到」(FR-04 收口)

**目标**

第 5 轮结束时，整条作息链路在设备上是**死的**：`signalCount` 恒为 0，
「已记录 N 条」那句界面文案从来没出现过。本轮把系统广播接上，让「亮屏 / 灭屏 / 解锁 /
插电 / 拔电」真的落进 Room，并且把采集这件事的**同意闸门**放到引导第 3 页——
先问、再采，拒绝也能照常使用全部功能。

同时处理一个容易被做假的地方：采集器「看起来在跑」和「真的收到系统广播」是两件事。
本轮为此专门写了**能收到真广播**的仪器化用例，并且把断言收紧到「行是采集器写的」，

## 第 7 轮：意愿识别能听懂、也敢说听不懂(FR-06 收口)

**目标**

前六轮把「常伴知道您什么时候醒着」这件事做通了，但**它还不知道您想干什么**。
本轮做 FR-06：从用户说的一句话里，听出三类意愿——**想做的事**（兴趣）、
**现在的状态**、**想找人帮的事**（请求），并且给出「是听哪几个字听出来的」证据。

这一轮刻意给自己限死三条：

1. **不联网、不引模型。** 用户说的话不离开设备，权限数继续是 0。
2. **听不出来就说听不出来**，绝不猜、绝不硬凑一个推荐。
3. **不留死代码。** 引擎做完必须有一条**真实可达**的界面链路，否则这一轮等于没做。

**产出**

- 新增 `domain/engine/intent/IntentLexicon.kt`(7,539 字节)：**纯数据**的词表。
  - `data class IntentTerm(term, phrases)`：一个规范词 + 用户在口语里可能说的若干说法。
  - `sentenceBreaks = "。！？；!?;\n\r"`——**逗号不在里面**（「我想学书法，也想学画画」
    是一句话里的两件事，不该被切成两句丢掉后半句；这条边界在本轮有单测守着）。
  - `interestCues`：19 个提示词短语（想学 / 想学学 / 学着 / 一直想 / 早就想 / 打算学 /
    有点兴趣 / 琢磨着想 / 感兴趣 / 愿意学 / 想了解 / 想看看 / 想试试 / 想试 / 想练 /
    想玩 / 喜欢 / 爱好 / 想）。长短都收，因为「一直想学书法」里真正表意的是「一直想」。

    它们更多是「东西」而不是「想做的事」。
  - `statePhrases`：7 个（睡不好 / 身上疼 / 一个人在家 / 记性不如从前 / 没事做 /
    吃饭不规律 / 心里闷）；`requestPhrases`：2 个（想找人搭把手 / 想打听一件事）。

  连带 `android.*` 的影子都没有，所以整层逻辑能在 JVM 上逐条断言。
  - `enum IntentKind { INTEREST, STATE, REQUEST }`；
    `data class IntentHit(kind, term, cue, evidence, start, endExclusive)`。
  - `sealed interface IntentScan { data class Recognized(hits); data object NotRecognized }`
    ——拒答是**类型上必须处理**的一个分支，调用方想「忘了它」都编不过。
  - 算法分四步：`forEachSentence`（按 `sentenceBreaks` 切句，**偏移是相对原文的绝对值**，
    所以每句单独剃空白不会让偏移错位）→ `scanSentence`（否定标记命中则**丢掉这一句的兴趣命中**，
    状态与请求不受影响）→ `occurrences()`（
    按词长降序贪心匹配，配 `BooleanArray taken` 防重叠，于是「一直想」先落座，
    把「想学」和「想」的位置占掉）→ `nearestCue()`（取距离最近的提示词，
    同距取更长的、再取更靠前的，保证同一输入永远同一个结果）。
  - `interestHit` 的证据取 **cue 与 topic 的最短包住片段**——所以「我一直想学书法」
    给出的证据是「一直想学书法」，而不是「一直想」也不是「书法」。
  - 结果按 `(start, endExclusive, kind.ordinal)` 排序后 `distinctBy { kind to term }`，
    同一件事在一句话里说两遍只报一次。
- 新增 `ui/talk/TalkViewModel.kt`(3,465 字节) 与 `ui/talk/TalkScreen.kt`(4,386 字节)：

**问题与解决**

1. **设备侧的采集器用例挂了——而且它挂得**对**：两个采集器在写同一张表。**
   第 7 轮重跑 `connectedDebugAndroidTest` 时，第 6 轮那条最严的用例
   `屏幕开关广播真的能从系统收到` 失败：

   but was:<[2026-03-10T09:00:12.345, 2026-11-21T00:12:34.765, 2026-11-21T00:12:34.833]>`。
   那两条**真实时钟**的行不是测试写的，是**应用进程自己的采集器**写的：

2. **中文测试名不能带空格（第 6 轮那条经验的又一次应用）。** 本轮新增的设备侧用例

## 第 8 轮：意愿不再只是听着——真输入框、确认闸门与落库(FR-07 收口)

**本轮做了什么**

第 7 轮结束时，「常伴听懂了您想学书法」**只显示在屏幕上，不落库、不推荐**——
意愿识别是只读的。本轮把这条链路接完：用户能自己打一句话进来，常伴听懂了要**问一句**
才敢记，用户点头之后这件事**真的进库**，并且**随时能删**。

- **真输入框（FR-06 的欠账）**。说两句页从「只能点示例句」变成「能自己打字」：
  `TalkScreen` 顶部是 `OutlinedTextField`（`说一句` + 占位「比如：我一直想学书法」），
  底下是 `说完了` 按钮。示例句**保留**，从「唯一入口」降级为「不知道说什么时的备选」，
  小标题改成「不知道说什么，点一句试试」。第 7 轮 `adb shell input text` 送不进中文
  这条限制（GAP-02）**没有消失**，但本轮找到了绕过办法：设备侧的 `TalkInputTest`
  用 Compose 的 `performTextInput` 注入中文（那是真的把字符送进文本框，不是伪造状态），
  手工验证则用英文串 `hello` 走「听不明白」这条路。
- **确认闸门**。新增 `domain/wish/Wish.kt`(4,321 字节)：`WishStatus{PENDING,CONFIRMED,
  DECLINED}`、`WishDecision{CONFIRM,DECLINE}`、`StoredWish(kind,term,evidence,sentence,
  status,heardAtEpochMilli,decidedAtEpochMilli)`，以及 `object WishGate`：
  `mayOffer` 只放行 `CONFIRMED`，`mayBringUp` 只放行 `PENDING`，`bringUpable()` 筛列表，
  `decide(from, decision)` 是**唯一的**状态转移入口，状态不变时返回 `null`（这样不会把
  用户第一次表态的时刻覆盖掉）。
  - **`DECLINED + CONFIRM → CONFIRMED` 是刻意的**。AC-07.3 要挡的是「常伴主动提起
    用户拒绝过的事」，不是「用户自己改主意」——后者是用户的动作，不是常伴的推销。

    唤醒，也不会进任何推荐。

    想显示，显示了用户就会读成「常伴在数我来过几次」。

**问题与解决**

本轮在真机上**红过两次、崩过一次**，且都不是靠「再跑一遍」蒙过去的。

1. **`WishDaoTest > 同一件事记两次只留一条` 断言写错了。** 用例第二次插入时断言
   `rowId > 0`，但 `INSERT OR IGNORE` 撞唯一索引时**本来就应该**返回 -1。
   这不是产品缺陷，是**测试笔误**：把「忽略」当成了「更新」。改成
   「第一次 `rowId > 0`、第二次 `assertEquals(listOf(-1L), …)`、`count() == 1`」后绿。
2. **`TalkInputTest > 点了先不用之后不再问但用户自己还能改主意` 崩掉，还带走了 8 例。**
   异常是
   `android.database.sqlite.SQLiteException: no such table: wish (code 1 SQLITE_ERROR):
   , while compiling: SELECT * FROM wish ORDER BY id ASC`，崩在
   `WishDao_Impl$10.call → CoroutinesRoom$createFlow → Dispatchers.Main.immediate`，
   异常打崩了整个测试进程，所以同一个类里排在它后面的用例**根本没跑**。
   取证链：
   - 干净装机 + `am instrument` 全包跑 → **必现**；
   - 事后 `run-as … cat databases/elder.db` 取回 12,288 字节的库，用 Python `sqlite3`
     读出 `user_version = 0`、tables 只有 `['android_metadata']`、**没有
     `room_master_table`**——是个**空壳库**；
   - 设备上已经有一份健康 `elder.db` 时跑同一条命令，只 1 例失败、**不崩**；
   - `TalkInputTest` 单独跑（干净装机）4 例全跑完，**不崩**。
   **根因结论**：同一个测试进程里，四个数据用例反复 `deleteDatabase("elder.db")` 再重开，
   而应用自己那个 `AppContainer` 的 Room 实例**一直活着**——两者**共用一个文件**。
   Room 的实例缓存与文件被删之间对不上，于是建表语句没跑、查询打在空壳上。
   **产品代码不会在自己的进程里删自己的库**，所以这是**测试环境问题**，不是产品缺陷。
   修法就是上面那条「测试库文件与产品的库文件分家」。
   **如实说明**：SQLite 文件级的逐帧时序**没有取证**，所以这里只能写到
   「已定位到共用库文件这条路径」，不写成「已完全解释」。
3. **`TalkInputTest > 全部清空要先问一次再真的清掉` 抛
   `java.lang.AssertionError: Semantic Node has no parent layout with a Scroll
   SemanticsAction`**（`ActionsKt.scrollToNode` ← `tap(TalkInputTest.kt:79)`）。
   原因是测试的 `tap()` 无条件先 `performScrollTo()`，而 `AlertDialog` 的按钮在**另一个
   窗口**、没有可滚动的祖先。新增 `tapInDialog()`（只点、不滚）后绿。
   这是**测试工具的假设不成立**，不是界面缺陷。
4. 题外现象（**未改代码**）：`logcat -b crash` 里当时能看到 01:58 / 01:08 / 01:13 三次
   **历史**的 `no such table: wish`（设备时钟 2026-11-21）。这是失败 2 的历史残留。
   `adb logcat -b crash -c` 清空后重启复跑，收尾时再查一次**仍为空**，见「验证」。

- **纯函数决策层**，新增 `domain/engine/intervention/InterventionWindow.kt`(212 行，
  **零 Android 依赖**，只用 `java.time`)：
  - `InterventionConfig(minGapMinutes=30, backoffStepMinutes=180, maxGapMinutes=1440,
    fallbackWakeAt=07:00, fallbackSleepAt=22:30)`，`init` 里三条 `require` 把不可能的
    配置挡在构造期(`backoffStepMinutes >= 0`、`maxGapMinutes >= minGapMinutes`、
    `minGapMinutes > 0`)。
  - `ThrottleState(lastSpokenAt, lastAnsweredAt, ignoredStreak)` + `pendingSpeak`：
    「上次开口之后用户还没接过话」才算一次未回应，所以 `afterSpoken` 才 +1，
    `afterAnswered` 清零并记下接话时刻(**不动** `lastSpokenAt`，否则间隔会从接话那一刻
    重新起算，等于用户一接话就把自己往后推一档)。
  - `decide(rhythmResult, now, throttle, config)` 只分三段：①`now` 落在安静时段
    (睡下到起床) → `StayQuiet(SLEEP_HOURS)`，并给出**下一次可以说话的最早时刻**
    (`nextOccurrence(quietSpan.end, now)`)；②距上次开口不足当前间隔 → `StayQuiet(TOO_SOON)`
    (+ `spoken.plusMinutes(gap)`)；③其余 → `Speak(basis)`。
  - `RhythmBasis{LEARNED, ASSUMED_NOT_ENOUGH_DATA, ASSUMED_INCONSISTENT}`：画像还不成形
    时**不装成知道**，退回 `fallbackWakeAt/fallbackSleepAt`，并在结果里如实标注是哪一种
    「不知道」。界面据此换一句话(见下)。
- **`gapMinutes(ignoredStreak)` 的上限是 24 小时，不是「永久沉默」**：
  `minGap + step × streak` 最后 `coerceAtMost(maxGapMinutes)`。一次都不回应 → 最多一天
  一次(AC-05.3)，但**永远不会变成「再也不说话」**——那和一个坏掉的按钮没区别，
  而且用户没有任何办法把它叫回来。计算全程走 `Long` 中转防溢出。
- **节流状态落盘**，新增 `data/intervention/InterventionStore.kt`(87 行)：用**独立**的
  `preferencesDataStore(name = "intervention")` 文件，而不是挤进设置那个文件。理由是
  设置页有「恢复默认」，那一处走的是 `prefs.clear()`：两者的键放在同一个文件里，

**问题与解决**

1. **主源首次编译没过，逐条改完后 `BUILD SUCCESSFUL in 26s`。** 两处可查证的错误：
   - `InterventionStore` 里 `prefs[KEY] = spoken?.toEpochMilli()` 通不过——DataStore 的
     `set` 对 `Long` 键**不接受可空值**。改成显式分支：有值就
     `prefs[KEY] = spoken.toEpochMilli()`，没值就 `prefs.remove(KEY)`。
     这不只是绕开类型检查：写成 `0L` 会把「从没记过」变成「记过一次、时刻是 1970 年」，
     两者在 `ThrottleState` 上是**不同的状态**。所以必须是 `remove`。
   - `SettingsScreen.kt:303 Unresolved reference 'wakeSleepSummary'`：那是定义在
     `InterventionWindow.kt` 里的扩展属性，补 import 后通过。
2. **一个设计问题，在写代码时就想到了、并且留了守卫**：`LifecycleRegistry.addObserver`
   会**同步补发** `ON_CREATE` / `ON_START` / `ON_RESUME`。如果直接在 `ON_START` 里
   `open()`，冷启动会**判两次**——第一次判出 `Speak` 并记下 `last_spoken_at`，紧接着
   补发的那次读到刚刚写下的时刻，立刻翻成 `TOO_SOON`。用户看到的就是「第一句话一闪
   而过，只剩『先不重复招呼了』」。处理办法是 `HomeViewModel.leftSinceLastOpening`：
   只有**真的离开过**（`onStop` 置位）再回来才重新判。设备实测冷启落在 `TOO_SOON`
   是**因为确实刚说过话**（见验证第 5 步），不是这个竞态。
3. **我原计划的验证步骤本身是错的，这里如实改掉。** 我原本打算「接话 → 重开 → 应该
   恢复问候」。实测**不会恢复**，仍然是「先不重复招呼了。」——因为 `decide` 的第二段
   只看 `MINUTES.between(lastSpokenAt, now) < gapMinutes(streak)`，而 `afterAnswered`
   **故意不动** `lastSpokenAt`（`streak` 清零只把间隔从 210 分钟缩回 30 分钟）。
   这是设计正确的行为：如果接话让间隔从那一刻重新起算，用户**越回应、被搭话越晚**，
   正好和 AC-05.3 想教出来的方向相反。**记为设计而非缺陷**，见本节「遗留」第一条。
4. 本轮 JVM 与设备测试**首次运行即全绿**（无红、无崩、无跳过）。这与第 5、6、7、8 轮
   不同，所以**没有**「本轮真实的红」这一节可写——不编。

**遗留**

- **接话后 30 分钟内不说话是设计，不是缺陷。** 见「问题与解决」第 3 条。`afterAnswered`
  不动 `lastSpokenAt`，否则用户越回应、被搭话越晚。**这条不许当成「接话没反应」的 bug 去修。**
- **本版本没有通知通道（RC-008）。** FR-05 的产出只作用在「用户打开应用时迎上来说话」。
  用户不打开应用的时候，常伴**什么也不做**——没有通知、没有前台服务、没有闹钟，
  manifest 里 `<uses-permission>` 与 `<receiver>` 都是 0。这是刻意的边界，接的也是
  「不催促」的立场；但它意味着**「用户不开应用」这个场景完全没有被覆盖**，记为 GAP-06。
- **`gapMinutes` 的上限是 24 小时**，所以最坏情况下常伴一天仍会说一次。这是有意的：
  一个能自己彻底安静下去的陪伴者，用户没有任何办法把它叫回来。上限而不是「永久沉默」
  是这一轮明确选的边。
- **说出来的话只有两行**（`Opening(headline, note)`）。真正的「说什么」在 FR-08/FR-09；
  在那之前不放任何充场面的字。
- **`ignored_streak` 的语义边界**：它由 `afterSpoken` 递增、`afterAnswered` 清零，
  而 `pendingSpeak` 的定义是「上次开口之后还没接话」。所以**同一个 `streak` 只在
  「连续多次开口都没得到回应」时才增长**——这条在 JVM 层有 11 例守着，但**没有真实
  用户数据验证过这个定义在人身上是合理的**。
- 老账照旧：第 8 轮那处「示例句点不动」未查明；用户还不能和常伴来回说话；
  `RhythmConfig` 阈值；`RhythmMaintenance.pruneIfDue()` 跨天路径；进程被杀后的丢失量；
  GAP-03（性能基线，第 10 轮）、GAP-04（文案集中化，第 16 轮）、GAP-05（TalkBack，第 17 轮）。

## 第 10 轮：低门槛行动卡与生活锚点(FR-08/09/10 收口，第 1 次推送)

**本轮做了什么**

第 9 轮结束时，常伴已经会判断「该不该说话」，也能从「一直想学书法」里听出意愿、当面问一句
「要不要常伴替您记着」。但用户答「愿意了解」之后**什么都没有**——第 8 轮只做到「记住了」。
这一轮补上「记住之后呢」，也就是 FR-08 / FR-09 / FR-10 三件事，并第一次把仓库推上 GitHub。

- **低门槛行动卡：一个纯数据 + 纯函数的目录。** 新增 `domain/companion/StarterOptions.kt`
  (448 行)，里面只有两样东西——13 个主题的目录数据，以及查目录的纯函数。
  - 覆盖 `interestTopics` 的 13 个主题(书法 / 京剧 / 乐器 / 绘画 / 摄影 / 园艺 / 游泳 /

    `prep`(要准备什么)。**目录结构里没有字段能填「连续多少天」「完成几次」**——
    AC-08.4 是靠数据结构守的，不是靠人记得别写。

**问题与解决**

1. **第 9 轮写下的迁移测试缺陷，在版本升到 3 的那一刻当场炸了。**

2. **`chess-square` 是不存在的 id，是测试写错，不是产品缺陷。**

   id 实际是 `chess-solo`。改用例后绿。**产品代码一行没动**——这条要记清楚，
   免得以后有人看到 `chess-square` 这个词以为目录里少了一项。
3. **首页没有显示锚点行，是设计决策，不是缺陷。**

### 第 10 轮补记：第一次推送到 GitHub（逐字真实输出）

推送**之前先查，再推**，因为「远端是不是空的」不能假设：

- `git ls-remote origin` →
  `8286376afafb6d71e1eb4ffabfa742405a8eaca1  HEAD` 与
  `8286376afafb6d71e1eb4ffabfa742405a8eaca1  refs/heads/main`。
  远端**不是空的**：GitHub 建仓时生成了 `8286376 Initial commit`，`git ls-tree -r origin/main`
  只有一行 `README.md`。
- `git merge-base main origin/main` **失败** → 两侧是**不相关历史**，
  直接 `git push` 会被拒（non-fast-forward）。
- `git config --get-all credential.helper` → `manager`，即 Git Credential Manager，
  凭据存在 Windows 凭据管理器里。

**处理**：`GIT_EDITOR=true git rebase origin/main`，输出
`Successfully rebased and updated refs/heads/main.` 8 个提交（第 1~3 轮基线 … 第 10 轮）
全部重放到那条 `Initial commit` 之上，**没有冲突**——远端只有 `README.md`，
本地从未创建同名文件；重放前后工作区 `git status --short` 都是干净的。
重放后本地 `HEAD` = `1afc687 第 10 轮：低门槛行动卡与生活锚点(FR-08/09/10 收口)，补齐 docs/02 与 records 记录`。

在这次 rebase 后**都已失效**，第 9 轮现在是 `aa2a797`。

```
To https://github.com/xyc2008/For-The-Elder.git

branch 'main' set up to track 'origin/main'.
```

`1afc687345d41c5053dd64dc431658a0972a9902`，与本地 `git rev-parse main`

## 第 11 轮：脑力互动框架与舒尔特方格(FR-11/FR-12 收口)

**本轮做了什么**

第 10 轮把「愿意了解一下」之后的事补齐了：起点卡、记成日常、鼓励。用户手上终于有了
一件可以做的事。这一轮加的是另一条路——**手上想有点事、但不想跟人说话的时候**。
`docs/00` 第 6 节给这个模块的定位是一句话：「严格剥离医疗宣称」，范围外清单里点名
「脑力训练的『延缓认知衰退』等疗效宣称」；`docs/01` 的 DR-09 又加了一条硬要求：
单局结果**不落库**，随进程结束。

- **框架的形状：数据类 + 出局函数，不是接口。** 新增 `domain/play/PlayGame.kt`(125 行)，
  里面三个类型：
  - `enum class PlayHint(val text: String)`：只有 `NONE("")` / `ALREADY_DONE("这个已经点过了，换一个")` /
    `NOT_YET("这个还在后面，不急")` 三态。**没有第四态能记下「错了几次」**，
    提示是一次性的，下一次点对就被清掉。
  - `data class PlayRound(gameId, cells, order, step = 0, hint = PlayHint.NONE)`：
    `cells` 与 `order` 装的是**同一批字**，只是顺序不同；这一层不认识「数字」，
    只认识「相等」与「先后」。派生值 `target` / `total` / `finished` / `passed(label)`
    全部现算——「这个格子点过没有」用 `order.indexOf(label) in 0 until step` 算，
    **不存已点集合**(存两份状态迟早显示自相矛盾的东西)。
  - `data class PlayGame(id, name, howTo, columns, longestSeconds, deal: (Random) -> PlayRound)`：
    加第二个游戏 = 往 `PlayCatalog.games` 多写一条，不新增类型。**刻意不做成
    `interface PlayGame`**——本项目的规则是「只有一个实现的接口不写」(`docs/02` 第 2.2 节 /
    `docs/01` NFR-14)，理由写在 `records/03` ADR-015。
  - `tap(index)` 三分支：已完成 → 原样返回；下标越界 → 原样返回；
    点对 → `step + 1` 且清提示；点错 → **只改 `hint`**，`step` 单调不减。
    5×5 的 25 个格子走 3b/3c 两个分支时**步数一点都不动**，本轮装机走查实测过。
- **舒尔特方格。** 新增 `domain/play/SchulteGrid.kt`(48 行)：`ID = "schulte-5x5"`、
  `SIDE = 5`、`numbers = (1..25).map { it.toString() }`，
  `deal(random) = PlayRound(gameId = ID, cells = numbers.shuffled(random), order = numbers)`
  ——`shuffled` 返回新列表，`numbers` 本身不动，所以同一份 `order` 在每一局之间是稳定的。
  `howTo = "格子里是打乱的 1 到 25，按从小到大的顺序挨个点一遍。点错了也不要紧，接着点就是。"`，
  `longestSeconds = 180`(**是上限不是目标也不是及格线**，不做倒计时，到点不打断)。
- **注册表。** 新增 `domain/play/PlayCatalog.kt`(20 行)：`games = listOf(SchulteGrid.game)`、
  `first = games.first()`，**没有 `byId`、没有占位条目、没有 `enabled` 开关**。
  首页「玩一会儿」直接进这个唯一的游戏，**不做游戏选择页**——一个游戏做一个选择页
  是纯多余。第 12~14 轮的三个新游戏届时只需往 `games` 里多写一条。
- **宣称词表与扫描。** 新增 `domain/play/PlayWords.kt`(53 行)：
  `banned` 15 词(训练 / 改善 / 提升 / 延缓 / 评估 / 认知能力 / 疗效 / 疗程 / 治疗 /
  预防 / 诊断 / 康复 / 大脑退化 / 记忆力 / 变聪明)；`allowedWords = listOf("玩", "试试", "大脑体操")`
  ——它**不参与判定**，作用是不让后来者把「大脑」整词加进 `banned`；
  `checkWords(text, words = banned) = words.filter { text.contains(it) }`；
  `violations(text)` 连空串也报一条。扫描是**朴素子串**，所以自己也不能写否定式
  ——「这不叫练脑子」照样会被扫出来，这是存心的。
- **界面三件套。** 新增 `ui/play/PlayVoice.kt`(85 行) / `PlayViewModel.kt`(92 行) /
  `PlayScreen.kt`(187 行)：
  - `PlayVoice` 是**唯一**放用户可见文字的地方：`title = "玩一会儿"`、`startLabel = "开始"`、
    `leaveLabel = "回去歇会儿"`、`doneNote = "用时只在这里显示，关掉就没了。"`、
    `promise(game) = "一局最多 N 分钟。不用计时，也没有分数跟谁比。"`、
    `nextTarget(round) = "现在点 X"`、`doneLine(round, seconds)`、
    `duration(seconds)`(45 → "45 秒"、60 → "1 分钟"、125 → "2 分 5 秒")。
    `PlayScreen.kt` 里**没有任何用户可见字面量**。
  - `PlayViewModel(clock: AppClock)` 是三个状态的 `sealed interface`：
    `Ready` / `Playing(game, round, startedAt)` / `Finished(game, round, seconds)`。
    **没有 `viewModelScope`、没有 repository、没有一处写入**；全程只读时钟**两次**
    (start 一次、完成那一次 `tap()` 里一次)，中间每次点击**不读时钟**——所以界面上的
    用时不会因为点得慢而跳数字。
  - `PlayScreen` 用 `ElderScreen(title = PlayVoice.title, onBack)`，三状态 `when` 三个面板；
    格子用 `round.cells.chunked(game.columns)` × `Row` × `Modifier.weight(1f)`；
    每个格子是 `Surface(onClick, ...)`，高度用 `heightIn(min = ElderDimens.minTouchTarget)`
    **而不是 `aspectRatio`**——大字号档下 25 个格子必须全部在屏内且不裁字(下面实测)；
    点过的格子压暗但**仍然可点**(点了会说「这个已经点过了，换一个」)。
- **接线与首页入口。** `ui/nav/MainNav.kt`(64 行) 的 `Route` 由 3 个常量变 4 个
  (`HOME` / `SETTINGS` / `TALK` / `PLAY`)，新增 `composable(Route.PLAY)`；
  `ui/home/HomeScreen.kt`(163 行) 第 4 个入参 `onOpenPlay`，新增一节
  「手上想有点事的时候」+ 一行「玩一会儿」，位置在「您自己的节奏」之前。
- **需求收窄。** 三件看起来都不是坏主意、但会把「玩一会儿」变成考核的事，本轮全部不做：
  结束卡不放「再来一局」、不留历史最好成绩、框架不预埋没做完的游戏。
  理由与实测证据写在 `records/02` RC-010；结构性的守法写在 `records/03` ADR-015。
- **文档**：新建 `docs/03-详细设计说明书.md`(8 章，35,468 字节)；`docs/00` 第 7 节里程碑表
  按「计划轮次 / 主题 / 状态 / 实际落地」四列重写，并如实记下**一处里程碑偏移**；

**问题与解决**

1. **三个「自然但会变味」的做法，写代码时才发现必须提前挡掉。**
   结束卡上放「再来一局」是所有游戏的标准做法，记下最好成绩是所有脑力游戏的标准做法。
   但 `docs/00` 把模块定位成「玩一会儿」，一旦有比较对象，它立刻就变成了考核。
   处理：不放按钮、不留成绩(前面三条收窄)，并且**守法方式从「记得别写」换成
   「结构上写不出来」**——`PlayRound` 里没有 `score` 字段、没有 `wrongCount`，
   `PlayViewModel` 里没有 `viewModelScope`。这是 ADR-011 / ADR-014 的同一思路，
   本轮第一次用在「类」上而不是「表」上。
2. **大字号档下 25 个格子会不会裁字，是设计时就必须回答的问题。**
   第一版想用 `aspectRatio(1f)` 做正方形格子，但正方形格子在大字号下要么被压扁
   要么把数字裁掉。改成 `heightIn(min = ElderDimens.minTouchTarget)`：
   格子可以变高，`ElderScreen` 的内容区本来就能滚。实测三档字号下
   25 格、5 行**全部在屏内**且数字高度随档递增(见「验证」第五节)。
3. **走查脚本里 `has 分` 是个假阳性，记录时必须说清楚。**
   完成卡上按 `分` 查，命中的是「这一局用了 1 分 37 秒」里的**分钟**，
   **不是分数**。记录里不能写成「检测到分数」，所以下面第五节的走查输出
   照抄原文，并在旁边注明这一条。
4. **APK 字节数与第 10 轮记录完全相同(11,012,408)，这是个矛盾。**
   已实测排除「新代码没打进 APK」：`unzip -p app-debug.apk classes15.dex | grep -ac schulte`
   = **1**；新源文件 mtime 全在 11:35~11:44、晚于第 10 轮提交 11:30；
   `git ls-tree d769c69` 确认第 10 轮提交里**没有** play 相关源文件。
   所以新代码确实在包里。推测第 10 轮那次 `assembleDebug` 是 UP-TO-DATE、
   其体积数字的可靠程度存疑。**本轮没有跑 `--rerun-tasks` 复核**(预算放在走查与字号实测上)，
   如实记为未验证，第 12 轮补一次再定论。
5. **宣称词表出现了两张，是本轮自己制造的新缺口。**
   第 10 轮的 `StarterRules.medicalWords`(9 词)与本轮新写的 `PlayWords.banned`(15 词)
   重叠 8 词、前者少 6 词，而 AC-11.1 是**全 App**规则。本轮**不**合并——
   合并要改 `app/src/`，一改就让本轮全部测试与走查证据失效。
   记为 GAP-07，第 12 轮收口到单一来源。

## 第 12 轮：第二个游戏「找出一样的」与三处缺口收口(FR-15 交付 / GAP-07/08/09 关闭)

**本轮做了什么**

第 11 轮把脑力互动的框架建起来了，但只放了一个游戏，所以当时那句「加游戏 = 往
`PlayCatalog.games` 多写一条」**只是设计意图，没有证据**。这一轮真的加第二个游戏，
把这句话变成实测数字——答案是**部分不成立**（见下面「问题与解决」第 1 条）。
同时把第 11 轮记下的三处缺口（GAP-07/08/09）收口。

- **第二个游戏：找出一样的。** 新增 `domain/play/FindPair.kt`(66 行)：`object FindPair`，
  `ID = "find-pair-4x4"`、`SIDE = 4`、20 个**两个字**的日常物件词（桔子 / 苹果 / 白菜 /
  豆腐 / 茶壶 / 蒲扇 / 毛衣 / 布鞋 / 象棋 / 毛笔 / 藤椅 / 凉席 / 算盘 / 棉被 / 雨伞 /
  桂花 / 月饼 / 核桃 / 花生 / 石榴——四列摆下来不会挤成两行，彼此没有一个是另一个的一部分），
  `game = PlayGame(name = "找出一样的", howTo = "格子里有 16 个字，其中两个是一样的。
  把这两个找出来。点错了也不要紧，再看看别的。", columns = 4, longestSeconds = 120, deal = ::deal)`。
  `deal(random)`：`words.shuffled(random).take(15)` 铺 15 格，再从这 15 个里挑一个字补成
  第 16 格 → 盘面**恰好**一对。用带种子的 `shuffled(random)` 而不是 `shuffled()`，
  同一个种子出同一局，测试才能造出确定的局面。
  **为什么选它**：动作最少（只有「看」和「找」）。记一记（翻牌）要求「第一张翻开来停多久
  再盖回去」，得让领域层持有时间；反应速度要计时；连续减七要输入数字——这三条都会破坏
  DR-09「领域层不认识时钟」，所以顺延，不在这一轮冒充。
- **`PlayRound` 从 `data class` 改成 `sealed interface`**（本轮最实的发现）。加第二个游戏时
  发现「一局的状态」在不同游戏里根本不是同一个形状：舒尔特要记「点到第几个了」，
  找一样要记「先点中的是哪一张、成没成」。硬塞进一个类里就会长出几个对某个游戏永远
  无意义的字段，而那正是「两个字段能互相矛盾」的来源。改型后：
  - 公共五件事定下来：`gameId` / `cells` / `hint` / `finished` / `stepsToFinish`，
    外加 `tap(index)` 与 `markOf(index)`；
  - 两个实现：`OrderRound`（舒尔特，就是原来那个 `PlayRound` 改名）与 `FindPairRound`；
  - `OrderRound.target` / `passed(label)` 仍是派生值，**没有另存「已点集合」**；
  - 两个实现的 `tap` 都把返回类型**收窄**成自己的具体类型（Kotlin 允许重写时变窄），
    调用方不用强转。
  改动面实测：`PlayGame` 的**六个字段一个都没动**、`PlayCatalog.games` 只多一条，
  但 `PlayRound` 必须改型。所以 `records/03` ADR-016 的结论是
  「加一个**规则已经存在**的游戏确实只加一条；加一个**新规则**的游戏要动三处」。
- **`CellMark` 三态：界面不再自己算规则。** 新增 `enum class CellMark { PLAIN, PICKED, DONE }`。
  理由：第二个游戏进来之后「压暗」的判据变了——舒尔特比的是「格子的字排在第几位、
  点过没有」，找一样比的是「这张牌是不是要找的那张字」。界面要是自己算，它就得同时懂
  两套规则，每加一个游戏都要动界面。改成由 `PlayRound.markOf(index)` 说给界面听，
  界面就只剩「三种样子画成三种颜色」这一件事。
  `FindPairRound.markOf` 按**位置**算不按字算：同样的字在这张盘上出现两次，
  按字查会把两张一起改掉，第一张刚点下去就看着像成了。
- **`PlayHint` 加第四态** `NOT_THIS_ONE("不是它，再看看")`。找一样里点别的字只说这一句，
  已经点中的那张**不动**——用户不需要先把错的取消掉；点同一张两次复用 `ALREADY_DONE`。
  枚举仍然是穷举的：每个取值都被词表扫一遍（用例在 `ClaimWordsTest` 里）。
- **`PlayVoice` 按规则分支，不再共用一个句式。** `nextTarget(round)` 改成
  `headline(round)`：舒尔特「现在点 X」、找一样「找出一样的那两张」——找一样没有顺序可讲，
  反复说「现在点 3」反而是错的话。`doneLine(round, seconds)` 也分支：舒尔特说
  「25 个都点到了。这一局用了 1 分 38 秒。」，找一样说「那两张「棉被」都找到了。」
  **找一样不报用时**：它这一局根本没在计时，报一个数就是把不存在的东西说出来。
  两个分支都用 `when` 而不是 `if`，新加一种规则时编译器会在这里报出漏掉的分支。
  新增 `chooseTitle = "挑一个"`、`chooseNote = "点一个进去，里面会说怎么玩。"`。
- **选择页只在有两个以上游戏时出现。** `PlayViewModel` 新增 `data class Choose(games)`，
  首次进入 `if (games.size == 1) Ready(games.first()) else Choose(games)` ——第 11 轮
  「一个游戏做一个选择页是纯多余」这条判断在有两个游戏之后自然反过来，**不需要开关**。
  `ChoosePanel` 每张卡上只有游戏名字，规则留到进去之后说，这里不重复。
- **GAP-07 收口：词表合一。** 删除 `domain/play/PlayWords.kt`(53 行)与其用例
  `PlayWordsTest.kt`，新增 `domain/voice/ClaimWords.kt`(52 行)。原先两张表

**问题与解决**

1. **ADR-015 那句「加游戏只往目录里多写一条」，本轮被证伪了一半。**
   第 11 轮 ADR-015 的结论是「加第二个游戏 = 往 `PlayCatalog.games` 多写一条，
   不新增类型」。真去加的时候第一步就撞墙：`PlayRound` 是个只服务舒尔特的 data class，
   而找一样的「一局的状态」形状完全不同（要记 `firstPick` 与 `solved`）。
   两条路可选：(a) 往原 `PlayRound` 里加 `firstPick: Int? = null` 与 `solved: Boolean = false`，
   (b) 改成 `sealed interface`。
   选 (b)。理由是 (a) 会让舒尔特的每一局都带着两个永远为 null / false 的字段，
   而这种「对某个游戏永远无意义的字段」正是两个字段能互相矛盾的地方——这一轮的目标恰恰是
   把不确定的地方变成实测，不是把不确定藏起来多一层。
   代价是真实的：`PlayRound` 的改型连带改了 `PlayGame` 的 `deal` 返回类型、
   `PlayCatalog`、`PlayVoice`、`PlayViewModel`、`PlayScreen` 与三份测试。
   记在 `records/03` ADR-016（状态「已采纳（第 12 轮）」），并在 `docs/03` 第 3.2 节
   写成一张「加一个游戏要改多少」的分档表：**规则已存在的** → 只加一条 `PlayGame(...)`；
   **新规则的** → 一个 `PlayRound` 实现 + 目录一条 + 界面一个分支。
2. **界面开始懂两套规则，是改型之后紧接着冒出来的第二个坑。**
   改完 `PlayRound` 之后，`PlayScreen` 里算「这一格要不要压暗」的那段代码要同时判断
   「是舒尔特还是找一样」。要是顺着写下去，每加一个游戏都得动界面。
   解决：把这个判断**下沉到领域层**，`PlayRound.markOf(index)` 只回三种样子
   （`PLAIN` / `PICKED` / `DONE`），界面只剩「三种样子画成三种颜色」。
   实测结果：加找一样时 `PlayScreen.kt` 的**摆格子布局一行没改**（`columns`、`chunked`、
   `weight` 三件事都不用动）；改的只有一处**判据**：`PlayCell` 的入参从 `passed: Boolean`
   换成 `mark: CellMark`，`PlayGrid` 里把 `rowIndex * game.columns + columnIndex` 提成
   `val index`。`git diff --numstat` 实测这一处改动是 `81 insertions / 19 deletions`。
   这条也记进了 `docs/03` 第 3.3 节。
3. **词表搬家之后有旧名残留的嫌疑，查清了。**

## 第 13 轮：接口设计说明书(docs/05)——把「谁调它、保证什么、不保证什么」从代码里抄出来

**本轮做了什么**

**为什么单独花一轮写接口**

`docs/02-概要设计说明书.md` 回答的是「分了几层、层与层为什么这样切」，
`docs/03-详细设计说明书.md` 回答的是「每一处规则的具体形状是什么」。
两者都不回答一个最容易被反复问、也最容易写错的问题：
**某个函数/某个类，到底允许谁调它、调了之后它保证什么、不保证什么。**
这层契约在代码里是隐式的（靠名字、靠可见性、靠零散注释），
一旦有人按自己的想象去调，出问题的地方离原因很远。05 就是把它显式写出来。

**与 TripWear 对照，这一份的形状差别最大**

TripWear 的 05 主体是一张网络 API 清单（路径、方法、请求体、状态码）。
常伴**一个网络接口都没有**——这里没有服务器，也不打算有。
所以本文第 2 节不是「API 清单」，而是「Android 系统服务与平台入口」。
它真正对外打交道的地方只有两处六个面：**三个系统服务面**
（IF-01a 两个 DataStore、IF-01b Room、IF-01c 五个系统广播）加
**三个平台入口**（Application / Activity / Manifest）。

**「刻意没有」也写成接口条目**

第 2.2 节把四个**故意不存在**的服务面单独列出来，每条都附理由：
网络（没有后端，也没有要传出去的东西）、通知（打扰正是要避免的东西，
而且通知要 `POST_NOTIFICATIONS`）、Alarm / WorkManager（定时唤醒就是
「按我们定的钟点去打断用户」，与 FR-03/FR-05 的方向正好相反）、
权限（清单里**一条都没有**，`<receiver>` **零个**）。
写「没有」不是为了凑数：这四个面每一个都是「顺手就能加、加了就违背产品立场」的东西，
把理由写进接口文档，将来谁想加，先得回答这些问题。

**「保证什么 / 不保证什么」逐条写**

第 3~5 节按数据层（IF-03 ~ IF-13，11 组）、领域层（IF-14a ~ IF-14j，10 组）、
界面层（IF-15 ~ IF-19，5 组）三级展开，每组一张小表：
**签名 / 谁调它 / 保证什么 / 不保证什么**。几个例子：

- `SettingsStore.setAddress` 保证写入落在 `settingsDataStore`、`null` 表示清空；
  **不保证**立即落到磁盘（DataStore 是异步落盘），也不保证跨进程可见。
- `RhythmRepository.record(incoming): Int` 保证返回的是**真正新写入的条数**；
  **不保证**按「同一秒只算一条」去重——去重是按 `(时间桶, 类别)` 做的。
- `PlayViewModel` 初值里的 `if (games.size == 1) Ready(...) else Choose(...)`
  **全项目只此一处**（本轮 `grep` 实测：`PlayViewModel.kt:72` 一行命中）。
  这条不是随手记的：它保证「只有一个游戏时不做选择页」这个判断
  不会被第二处悄悄推翻——一推翻就会和 `records/02` RC-010 的三件收窄对不上。

**为什么值得为「风险」单独花一轮**

风险文档最容易写成两种废纸：一种是抄一遍通用模板（「本项目可能遇到人员变动、需求变更……」），
另一种是把设计文档里的取舍换个说法再写一遍。
本文刻意避开了这两条路，改了写法：**每一条风险都要能回答三个问题——它在代码里落在哪个编号上、
我们做过哪一件事来压它、压完之后还剩什么没解决。**
三个问题里只要有一个答不出来，这条就不该收进登记册，或者就该收进去并写明「未落实」。

**为什么这一轮的写法必须与参照项目不一样**

TripWear 的 07 一共 16 条风险，其中 **6 条是外部依赖类**（接口超时、Key 没配、
平台不允许抓、模型编内容、服务端泄露、推送扰民）。
本项目的这三类来源**结构性地不存在**：没有网络调用、没有第三方 SDK、
没有服务端、没有模型、没有通知通道。所以照抄那张表就会变成**凭空捏造风险**。

本文 §0 先把这件事用可复现的判据讲清楚，而不是喊口号：

- 网络面：**宽口径 1 行 / 窄口径 0 行**——那一行出现在 KDoc 文字里，不在业务代码里，一条命令能核。
- 权限 **0 条**、`<receiver>` **0 个**、第三方 SDK **0 个**（`app/build.gradle.kts` 依赖清单）。
- 没有服务端，也没有模型。

真正的结论写在这儿：**本项目不是因为「更安全」才没有这些风险，而是因为「它能做的事更少」。**
这一点必须说破——否则「零风险」听起来像夸奖，实际上是把能力面的窄当成了工程上的好。

**13 条风险是什么，为什么「接受」用得这么多**

登记册 R-01 ~ R-13，每条七项固定：来源 / 类别 / 描述 / 触发条件 / P / I / 等级 / 应对 / 监控信号，
再加两张小表——**「已落实措施」**（每条都指向 ADR / RC / GAP 编号与实测命令）
和**「残余风险」**（压不掉的那部分，不含糊）。

四个等级的分布是 **红 1 / 橙 7 / 黄 4 / 绿 1**：

- **红 1 条：R-09「把不打扰做成没用，用户会卸载」。**
  这是唯一一条 I 也高的：它不是技术缺陷，是**产品立场本身的代价**。
  `ADR-013` 的原话就摆在那儿——「那种应用用户会直接卸载」。
  已经落实的减轻手段是结构化的、能测的：介入上限 24 小时封顶（不永久沉默）、
  三条不依赖任何权限的主动入口、拒绝采集后功能照常且有设备实测、每屏都有退路。
  **但这条风险的判据本身就是「用户还会不会打开」**，而本项目到现在没有过一个真人用户。
  所以它只能是红。§3.1 给它写了明确的落点：**第 15 轮的 `docs/09-用户手册` 要把「怎么用」讲得比界面更清楚。**
- **橙 7 条**：R-01 词表识别漏识、R-02 作息阈值全是推导值、R-03 进程不在收不到广播、
  R-05 目标用户零真人走查、R-10 文档与代码脱节、R-11 功效宣称推向医疗口径、R-12 迁移无备份。
  这七条的共性很清楚：**都是「推理链上有一环没有真人或真数据兜住」**。
- **黄 4 条**：R-04 性能基线未测、R-06 只验过 API 35、R-07 中文手工输入从未验、R-08 零权限立场会被扩展破功——缺的是一次测量或一次环境。
- **绿 1 条**：R-13 行为数据隐私（全部本地、零上传、零备份、30 天保留；本地库未加密）。

「接受」这一策略在本项目用的次数**明显多于**参照项目，§1.4 专门解释了这不是偷懒：
本项目缺的东西**几乎都是「必须有一个真人或真设备才能获得」的**，
不是「再加班写点代码就能补上」的。在这种约束下，唯一诚实的处理就是
**把代价写清楚、把触发信号定下来、把「哪一天要重新判级」写进去**，
而不是编一个缓解措施给自己看。

**问题与解决**

1. **最容易写歪的地方：把「没做」写成「不需要做」。**
   13 条风险里有 5 条的核心内容就是「这件事我们没做」。
   人在写这种句子时手会滑向「暂不涉及」「后续考虑」这类听起来体面的说法。
   本轮的应对是把口径统一成两句：**「已落实措施」只写真的做过、能指到编号或命令的事**；
   压不掉的那部分一律进「残余风险」表，并且**不许用「基本」「大致」这类模糊词盖过去**。
   例如 R-04 只能写「**未关闭**，已欠五轮」——不写任何估算值，因为**在测之前任何数字都是编的**。

2. **§5「刻意不登记的风险」是这一轮最有用的部分，但一开始想省掉。**
   一开始觉得「不存在的风险写它干嘛」。

   将来读的人只会得出两个结论之一——「漏了」或者「本项目特别安全」，**两个都是错的**。
   所以补了 §5：每一类写清「为什么不成立」+「哪一天要补」。
   比如「通知打扰用户」这一类，写的是「没有通知通道，是明确不做（GAP-06 / RC-008）」，
   并且注明**该决定被推翻时本条与 R-08 同时改写**——把「不登记」和「将来要登记」的开关一起留在纸面上。

## 第 15 轮：用户手册(docs/09)——把「怎么用」讲得比界面更清楚一点，兑现对 R-09 的承诺

**本轮做了什么**

这一轮做两件事，一件是文档、一件是证据：

1. **新增 `docs/09-用户手册.md`**（**784 行 / 53,111 字节**，全 LF）。这是 `docs/` 里**第 10 份**，也是原先**缺的两份之一**（另一份 `docs/06-测试计划与用例.md` 仍未写）。
2. 为了写它，**先在设备上做了一遍逐屏证据采集**：`uiautomator dump` 逐屏 + 一次性脚本，**16 屏 / `TAP MISS` 0 / `DUMP FAILED` 0**，498 秒，日志 207 行 / 12,993 字节。

**代码一行未动。** 所以本轮**没有构建、没有跑测试**，也没有任何新的测试数字——下面「验证」里出现的 JVM 342 例、设备 96 例、APK 10,971,528 字节**全部是第 12 轮的**，第 13~15 轮三轮未复核。这一点在 `docs/09` 的修订记录里也写明了。

**为什么这一轮非做不可**

`docs/07:538` 对风险 **R-09**（**红色**等级，全登记册唯一一条红）写的落点原话是：

> 第 15 轮的 `docs/09-用户手册` 要把『怎么用』讲得比界面更清楚一点，第一版手动说明本身就是对这条风险的一次减轻；真人试用是唯一能关闭它的路径（`docs/07:528`）。

也就是说：**第 14 轮已经把话说死了——第 15 轮要是没有这本手册，那句承诺就是空话。** 这轮就是去把它补上。

**写法：先采证据，再动笔**

手册最容易写成两种东西：一种是照着源码「翻译」一遍界面（那读者看界面就够了，何必看它），
另一种是写营销味的使用说明（「轻松上手」「智能陪伴」——本项目一个字都不许用）。
本文走第三条路：**手册里的每一条界面描述，都必须是屏幕上真有的字**。

所以顺序被定死：**先跑采集脚本，把 16 屏的字面落盘；再从落盘的字面里写手册。**
凡是没有实测到、只从源码读出来的（三种 `statusLabel`、`reopen` 按钮、DECLINE 的 `decidedLine`、
设置页大部分常驻说明字），正文里一律标成**「源码字面」**，不与「实测」混用。

采集本身还顺手办了四件事，都写进了 `records/04` 第十三节：

- **结掉一个悬案。** `docs/01:269` 挂着一句「示例句按钮好像点不动，原因未查明」。本轮**未复现**，成因也查清了：上一轮探针挑可点节点的规则（长度 ≥ 6 且含「，」或「。」）挑中的是**说明段文字节点**，不是按钮。改用坐标直点，界面确实变了（出现「我听见的」卡，再点 `愿意了解一下` 真的落库）。**疑点作废。**
- **抓到一个真瑕疵。** 起点卡点「这一步做完了」后屏幕上是：`…留下最顺手的那一支。。这件事是做完了的…`——**双句号**：`firstStep` 正文自带「。」，鼓励语模板又加了一个。**真瑕疵，本轮只记录不修**（本轮声明为纯文档轮；改代码会让「本轮未改代码」这句不成立），修在**第 16 轮**。
- **排掉一个假 bug。** 首页显示「早上好」而宿主机是 15:31——查 `adb shell date` 得 `Sat Nov 21 07:31:12 GMT 2026`，模拟器时区是 `GMT`。**不是 bug**，写进手册 2.1 与 8.4（「只在一种环境里验过」）。
- **两处数字被实测钉死**：`requiredDays = 3`（设置页原话「满 3 天就能用上」）、退避首档 30 分钟（「现在打招呼的间隔：30 分钟」）。

**与 TripWear 那份手册的差别：多了一整节「做不到的事」**

TripWear 的用户手册是写给「用户照着做」的，本项目这本多写了两节：**`## 6. 它刻意不会做的事`** 和 **`## 8. 做不到的事（诚实清单）`**。

- 第 6 节把「能做到但决定不做」的事集中列成一张表，**每一行都给出 ADR / RC 编号当依据**（不建通知通道 = RC-008；零权限零接收器 = ADR-009；不用模型 = ADR-010；不显示打卡积分 = RC-010 / ADR-015；不留最好成绩、不预留半成品游戏 = RC-010；间隔只往上放 = ADR-013；锚点只能亲手建立 = ADR-014）。这样读者能自己分辨「没做完」和「决定不做」。
- 第 8 节把还欠着的账如实摊开：**从未有真人用过**（R-09 仍是红）、**中文打字没被真实输入法验过**（GAP-02）、**快慢没量过**（GAP-03，已欠七轮）、**只在一种 Android 环境里验过**（API 35 模拟器，1080×2400，密度 420，GMT）、**两个已知瑕疵未修**（双句号 → 第 16 轮；引导第 1 页语义标签 0 条 → 第 17 轮 GAP-05），末尾附 GAP-01~09 逐条现状表。

这一段不是自我贬低，是这本手册**唯一诚实**的写法：用户手册如果只讲它能做什么，第一次用卡住的人会觉得是自己笨。

**R-09 怎么兑现的（本轮的核心交付）**

对照 `docs/07:538` 那句话拆开看：

- 「**把『怎么用』讲得比界面更清楚**」——手册不逐字抄屏幕，而是把界面**为什么要这样**讲出来：为什么设置页没有「确定」按钮、为什么玩游戏不会有成绩、为什么安静的时候连「您记下的那件事」都不提、为什么「最多一天一次」只会往上放。这些在原界面里看不出来，只有手册能讲。
- 「**第一版手动说明本身就是对这条风险的一次减轻**」——做到了，`docs/09` 首版落地。
- 「**真人试用是唯一能关闭它的路径**」——**没有做到，也不打算假称做到**。手册 8.1 节把这句原话写在了最显眼的位置，并写明「唯一能真正关闭它的路径是真人试用，而那还没有发生」。

## 第 16 轮：修掉双句号，把 138 处界面文案收进 `*Voice.kt`，并给它配一条机械守卫

**本轮做了什么**

本轮的预算只放两件事：**(a) 修双句号** ＋ **(b) GAP-04 文案归口**。第 15 轮遗留里写着「第 16 轮三件事一起做」，本轮**自主把第三件（第三个游戏）挪到第 17 轮**，理由见下一节。

代码改动共 **11 改 / 5 增**：

**为什么 (a) 和 (b) 非做不可，以及为什么 (c) 被挪走**

(a) 的理由很直白：那句带 `。。` 的原话已经挂在 `records/04` 13.3 与 `docs/09` 里，而第 15 轮白纸黑字写了「修在第 16 轮」。这是自己给自己定的期限，不去做就成了空话。

(b) 的理由是这笔账挂得太久：GAP-04（`NFR-17 文案集中化尚未做`）从第 1 轮挂到第 15 轮，一直是「部分文案在 Kotlin 源码内」。它属于**用户看得见、评审也看得见**的一类欠账：界面代码里散着 138 处中文字面量，谁改一句话都可能漏掉另一处。

**挪走 (c) 是本轮唯一一次「改计划」，理由三条：**

1. **(a)+(b) 本身已经是一轮可独立验证的完整工作**：一条守卫先红（138 处）后绿（0 处），一个覆盖全部 39 条 `firstStep` 的双句号回归。两件事各自都有能摆出来的证据，不需要 (c) 来凑成一整轮。
2. **(c) 的次序是自己定的、且不能压缩**：**先写 ADR-018 → 再改 `docs/03` 第 3 节的形状 → 最后才动代码**。三个候选（记一记/翻牌、反应速度、连续减七）每一个都会让领域层认识时钟，直接破坏 DR-09「领域层不认识时钟」。这是一个**设计问题**，要一整轮的思考和验证预算。
3. **一次迭代塞三件事最常见的结局**是「记账里三件都写了，验证只做了一件」。宁可少做一件并把顺延写清楚，也不做那种记账。

顺延本身记进 `records/02` RC-012；GAP-05（无障碍）连带顺延到第 18 轮。

**双句号怎么修的：只让标点变成条件，不动 `action` 本身**

`Encouragement.forAction` 原来的模板是 `"您刚做完的是：$action。这件事是做完了的…"`。修法**不是**去改 39 条 `firstStep` 的正文——那会动到用户看到的话，也会让 `violations` 的回话原文校验失去依据。真正改的是拼接处：

```kotlin
fun forAction(action: String) =
    "您刚做完的是：$action${terminator(action)}这件事是做完了的，不是想想而已。"

private val sentenceEnds = listOf("。", "！", "？", "…")

private fun terminator(action: String) = if (sentenceEnds.any { action.endsWith(it) }) "" else "。"
```

类注释里写明了理由：**只让标点变成条件，不动 `action` 本身，因为 `violations` 要求回话包含那件事的原文。**

回归不是只测那一条数据，而是**覆盖全量**：`noEncouragementHasDoubledPunctuation` 遍历 `StarterCatalog.all` 的**全部 39 条** `firstStep`（39 用 `grep -c 'id = "' domain/companion/StarterOptions.kt` 复核过），断言拼接结果不含 `。。` / `！！` / `？？` / `，。` / `。，` / `。！` / `。？` 且以「。」结尾；另一例 `forActionAddsAPeriodWhenTheActionHasNone` 管住反向情形（原文没有句末标点时必须补一个）。所以这条修复**没法靠改一条数据糊过去**：以后任何人往目录里加一条自带「。」的 `firstStep`，测试会直接红。

**GAP-04 怎么收口的：进 `*Voice.kt`，不进 `res/values/strings.xml`**

这是本轮最需要解释的决定，写成 `records/03` ADR-017，要点四条：

1. **为什么不搬进 `res/values/strings.xml`**（那才是 Android 的常规做法）：本项目的**禁用词机器扫描（AC-11.1）只扫 Kotlin 源码**——15 个宣称词在 `app/src/main/java/` 里只命中词表定义行、在 `app/src/main/res/` 里 0 行，正是这一点让「0 违规」这句话可机械复核。文案一旦搬进 XML，扫描就覆盖不到了，等于用一次「看起来更规范」的重构换掉一条真实守护。所以落点定为**同包的 `*Voice.kt` 对象**。
2. **搬迁量**：新增 `ui/common/CommonVoice.kt`(44 行) / `ui/home/HomeVoice.kt`(36) / `ui/onboard/OnboardVoice.kt`(97) / `ui/settings/SettingsVoice.kt`(115)；`ui/talk/TalkVoice.kt` 109→171，顺手把 `TalkScreen` 里私有的 `IntentKind.label()` 也并过去，改叫 `TalkVoice.kindLabel`。`ui/` 下 `*Voice.kt` 共 **7 个 / 663 行**。
3. **守卫的机械规则**（`UiCopyPlacementTest`，1 例）：`ui/**/*Voice.kt` 自由写中文；**其余 `.kt` 里出现含中文的字符串字面量即失败**；`copy-ok: 理由` 可显式豁免；注释行不算。
4. **先红后绿**：搬迁前同一条命令报 **138 处**违规（`SettingsScreen` 49 / `OnboardingScreen` 39 / `TalkScreen` 34 / `HomeScreen` 9 / `TalkViewModel` 5 / `StarterCard` 1 / `ElderComponents` 1），138 行**逐条读过、无一误报**，其中 `ElderComponents.kt:94` 那一处是 `contentDescription`——**语义标签也算用户可见文案**；全文落盘 `build/offenders16.txt`（10,774 字节 / 139 行）。搬迁后同一条命令通过。

**防假绿是这条守卫的核心。** 一个「扫不到任何文件」的守卫也是绿的，所以加了三条断言：扫到的 `ui` 文件 **≥ 10**、至少扫到**一个** `*Voice.kt`、扫过行数 **> 500**；并且缺 Gradle 注入的源码根时 `error(...)` **直接失败而不是跳过**。没有这三条，「违规数 = 0」这个数字毫无意义。

**范围如实写清**：守卫只扫 `ui/`。`domain/` 层早就符合「集中常量」（`StarterOptions` / `CompanionVoice` / `InterventionVoice` / `ClaimWords`），但**没有机械守卫**，列**评审项**。所以 GAP-04 的结论是「**`ui/` 层关闭 + `domain/` 层列评审项**」，**不写成已彻底关闭**（`records/02` RC-013）。

- **APK 字节数与第 12 轮一模一样，第一反应是「产物没更新」。** 这是本轮最值得记的坑。字节数相同只有两种可能：构建没生效（假绿），或者巧合。分辨办法**不是再跑一遍构建**，而是换一个**与文件总大小无关的观察点**——解包逐 dex 查类名：本轮新增的 4 个 `*Voice` 类都在，而只存在于测试源码的 `UiCopyPlacementTest` 在所有 dex 里为 0，于是判定产物是本轮 `main` 源码编的。随后补跑的 `--rerun-tasks` 字节与 md5 都没变，与判定一致。**教训：要验证一个「没变」的结论，就换一个维度看，别在同一条证据上反复确认。**
