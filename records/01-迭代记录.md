# 迭代记录

本文件按轮次记录每一次迭代。每一轮固定四小节：**目标 / 产出 / 问题与解决 / 验证**。

「验证」一节只写**真正跑过**的东西，并附可复核的原始数据；没跑的一律显式写「未验证」。
数字来自 Gradle 的 XML 报告、`adb` 的 UI 层级转储、`logcat`，不来自记忆或推测。

轮次的划分标准是「交付了一个可独立验收的增量」，不是「写了多少文件」。

## 第 3 轮：字号可访问性缺陷修复与渲染级测试体系

**目标**：字号档位是本项目最核心的可访问性承诺之一(`docs/01` 中一条 AC 就是「不用去改手机设置也能放大字」)，
但此前只有「渲染不崩」的证据。本轮要查清「点一下真的大了吗」，补齐渲染级测试，
并把 UI 层端到端链路实测一遍。

**产出**

**(1) 查清并修复一个真实缺陷：档位越高、放大越被压制**

原实现用「替换 `LocalDensity.fontScale`」来放大字号。仪器化探针实测发现，
在 API 35 上 `Density(density, fontScale)` 工厂内置**非线性字体换算**，`sp→px` 不是线性的：
字号越大、放大被压制得越狠。原始数据见 `records/04-质量与验证记录.md`。

后果是 30sp 以上的标题在「更大」档**完全不放大**——正文变大了、标题没变，
这是一个用户一眼就能看出来的假功能。

修复方式：改为**按档位换一套排版表**(把倍率直接乘进每个 `sp`，行高同步乘，字距与字重不乘)，
不再替换 `LocalDensity`。落在：

- `ui/theme/Type.kt` —— 整文件重写，新增 `elderTypography(scale: Float = 1f)`，15 个 style 逐个列出数值
- `ui/theme/Theme.kt` —— 删掉 `LocalBaseFontScale` 与 `LocalDensity` 替换，只剩
  `remember(fontSize) { elderTypography(fontSize.scale) }`
- `ui/onboard/OnboardingScreen.kt` —— 更新 `FontPreviewCard` 的说明

**(2) 建立渲染级测试**

- 新增 `app/src/test/.../ui/theme/TypographyScaleTest.kt`(纯 JVM，5 例)：
  标准档基准值、每档全量字号与行高按倍率同步、字重与字距不随档位变、
  大档行高能容纳放大后的文字、同档重复调用等价但非同一实例
- 重写 `app/src/androidTest/.../ui/theme/ThemeFontScaleTest.kt`(5 例)：
  用 `TextLayoutResult.size.width` 量**原始像素**，容差 3%
  - 教训：第一版用 `getUnclippedBoundsInRoot()` 量 dp，得到的倍率恒偏低
    (标称 1.15 量出 1.097)。原因是那个接口把像素换算成 dp 时用的 density **本身就带 fontScale**，
    被试和量尺是同一个东西，比值被部分抵消。
  - 错误做法：对平台做它不承诺的线性假设。第一版断言「系统 1.5 × 应用内 1.3 线性相乘」，
    实测不成立。已改写为断言两条真正要保证的性质：**应用不抹平系统设置**、
    **应用内档位在该环境下仍然显著放大**。实测倍率打印出来归档。

**(3) UI 层端到端实测(关闭 GAP-01)**

用 `adb` + `uiautomator dump` 走完整条链路，见 `records/04` 的完整证据表。
结论：`docs/01` 中 FR-13 的 AC-13.1 / AC-13.4 此前只在数据层验证过，**现在已在 UI 层跑通**。

**问题与解决**

- 诊断用的 `FontScaleDensityProbeTest` 是**故意 `fail()`** 的探针(用失败信息带回测量值)，
  留着会让整个 `connectedDebugAndroidTest` 变红。已确认删除。
- `DensityImpl` 没有实现 `equals`，在 `setContent` 里每次重组新建实例会让下游读取者反复失效。
  合成 density 必须 `remember` 住。
- `adb` 无法输入中文(`input text` 只支持 ASCII)，所以 UI 层用 ASCII 称呼走链路。
  中文称呼的持久化由 `SettingsStoreTest` 覆盖(见 `records/04` 的 GAP-02)。

**验证**

- `./gradlew :app:testDebugUnitTest --rerun-tasks` → **BUILD SUCCESSFUL in 29s**，26 tasks executed(强制真跑)。
  XML 报告实测：`SettingsStoreTest` **tests=9 failures=0**、
  `GreetingEngineTest` **tests=10 failures=0**、`TypographyScaleTest` **tests=5 failures=0** → **合计 24 例全绿**。
- `./gradlew :app:connectedDebugAndroidTest -P...class=...ThemeFontScaleTest` → **BUILD SUCCESSFUL in 39s**，
  `Finished 5 tests on Elder_API35(AVD)`，**5 例全绿**。
- 实测倍率(logcat 原始行)：
  `FONTSCALE-PROBE plain=320 syntheticStandard=419 syntheticExtra=461 systemOnlyRatio=1.309375 appTierRatio=1.1002387`
  即：系统字号 1.5 在本平台只带来 1.309×；在其之上再选应用内「更大」，只额外带来 1.100×
  (标称 1.30×)。**这是平台行为，不是缺陷**，但**它意味着系统字号调大以后，应用内档位的区分度会明显下降**——
  作为已知限制记入 `records/03` 的 ADR-004 与 `records/CHANGELOG` 的 Known Issues。
- UI 端到端 12 步全部实测通过，`logcat -b crash` 全程无输出。
- `MainNav` 的 HOME ↔ SETTINGS 导航**首次在 UI 层实测**(此前只有代码，无运行证据)。
- 系统字号非 1.0 的真机/模拟器整体观感：**未验证**(只在测试里用合成的 density 验证过行为)。

## 第 4 轮：作息感知引擎(纯 Kotlin 领域层 + 单测)

**目标**

把 `docs/01` 的 FR-04 拆成两半，本轮做**不碰 Android 的那一半**：从「亮屏/解锁/充电」
这类信号里推断出作息画像。目标是 AC-04.1(引擎不依赖任何 Android API，可在 JVM 单测里充分验证)
与 AC-04.2(同一份输入永远得到同一份输出)。采集器、权限向导留到第 6 轮(原写「第 5 轮」是排期估算偏差，
第 5 轮实际做的是落库)，落库在第 5 轮完成。

这样切分的理由是：推断逻辑是这一块唯一有难度的地方，把它做成纯函数就能在 JVM 上用合成数据
把边界情况全跑一遍，不用等模拟器；采集部分则全是平台细节，放在一起会互相拖累。

**产出**

- 新增 `app/src/main/java/com/fortheelder/domain/engine/rhythm/RhythmSignal.kt`(37 行)
  - `RhythmKind`：`SCREEN_ON` / `SCREEN_OFF` / `USER_PRESENT` / `CHARGING_START` / `CHARGING_END`。
    只有这五种，因为它们都能从**运行时注册的系统广播**拿到，不需要读其他应用的使用记录。
  - `isPresence` 把 `SCREEN_ON` 也当成「人在场」：目标用户里相当一部分不设锁屏密码，
    那种情况根本收不到 `USER_PRESENT`。代价是兜里误触亮屏也算在线，靠每天最少信号条数兜住。
- 新增 `RhythmInference.kt`(274 行)：`RhythmConfig`(阈值全部有默认值) +
  `RhythmInference.infer(signals): RhythmResult`。
  - 作息日按凌晨 4 点分界 → 每天至少 20 条在场信号才算有效天 → 有效天不足 3 天返回 `Gathering`
    → 起床/睡前取中位数 → 醒着不足 6 小时返回 `Inconsistent`
    → 按 30 分钟桶统计日均密度，低于 `max(均值×0.35, 0.5)` 的桶算安静
    → 连续安静段还要同时满足「≥1 小时」「离起床 ≥45 分钟」「离睡前 ≥45 分钟」才成为空窗候选。
- 新增 `DailyRhythm.kt`(89 行)：`TimeSpan`(半开区间，允许跨子夜)、`DailyRhythm`(画像)、
  `RhythmResult`(三态)。
- 新增 `app/src/test/java/.../rhythm/RhythmInferenceTest.kt`(337 行，23 例)：见 `records/04`。

**问题与解决**

1. **自己写的第一版里有两条「看起来在做事、其实恒不生效」的逻辑**，写测试前就删掉了：
   一处算出结果后再除以 1 的噪声运算，一处恒为 0 的 `centerBonus` 加分项。
   留着它们会让人以为置信度算法比实际复杂——**这也是「不要存在假功能」的一条**，
   只不过假在内部而不是界面上。
2. **`edgeGuardMinutes` 一开始是个装饰性阈值**。原实现是「把起止桶裁掉再判断」，
   但起止桶按定义必然有信号，裁剪永远不会生效——阈值写在那里却不产生任何行为差异。
   改成**真实的丢弃规则**：安静段若落在起床后 45 分钟内或睡前 45 分钟内，整段丢弃。
   并配了两条互相反证的用例守着它(起床后 07:00–08:00 的安静段不报；
   同样长度但挪到 07:30–08:30 就报出来)。
3. **单测里有一条期望值是我算错的，代码是对的**。`起床时刻散乱时置信度下降` 一开始
   7 天里有 2 天被引擎判成无效天，因为「起床越晚、一天剩下的桶越少」——
   那些天每个桶只放 1 条信号，桶数一少就低于每天 20 条的在场门槛，
   于是 `sampleDays` 变成 5 而不是 7，置信度实测 **0.48214287** 而非期望的 0.5。
   修改的是**测试数据**(每桶放两条)而不是引擎，并把 `sampleDays == 7` 也断言上，
   免得以后又悄悄退化成「测的不是散乱而是稀疏」。这条失败如实留在记录里：
   它证明了那道门槛真的在起作用。

**验证**

  26 tasks executed(强制真跑，不吃缓存)。XML 报告实测：

  | 测试类 | tests | failures | errors |
  |---|---|---|---|
  | `data.prefs.SettingsStoreTest` | 9 | 0 | 0 |
  | `domain.engine.greeting.GreetingEngineTest` | 10 | 0 | 0 |
  | `domain.engine.rhythm.RhythmInferenceTest` | 23 | 0 | 0 |
  | `ui.theme.TypographyScaleTest` | 5 | 0 | 0 |

- 静态证据(AC-04.1)：`grep -rn "android\.\|androidx\." app/src/main/java/com/fortheelder/domain/engine/rhythm/`
  → **无匹配**。引擎只用到 `java.time`，所以能在 JVM 上跑。
- 静态证据(AC-03.5 的延伸)：`grep -rn "LocalDateTime.now\|LocalDate.now\|System.currentTimeMillis"`
  全仓 → **无匹配**(只有 `core/time/AppClock.kt` 里有，已排除)。引擎不看「现在几点」。

  (`4 executed, 34 up-to-date`)，产物 `app/build/outputs/apk/debug/app-debug.apk`
  **18,432,832 字节，时间戳 05:57:51**。说明第 3 轮末尾那两处 KDoc 改动没有碰到代码。

  都是**从需求推导的估计值，没有真实用户数据支撑**。它们能保证「不乱报」，

## 第 5 轮：作息数据落库与真实设备上的链路验证(FR-04 的第二半)

**目标**

第 4 轮的引擎只能吃内存里的 `List<RhythmSignal>`：算得出来，但关掉应用就没了。
本轮把它接到真实存储上——信号进 Room、画像算出来也落库、重启后读得回来，
并且**在真实设备(模拟器 `Elder_API35`)上**证明这条链路走得通，而不是只在 JVM 单测里成立。
顺带清掉上一轮留下的两笔工程债：三个声明了却全仓零引用的依赖、以及一个比预期大得多的 APK。

采集器(系统广播)**本轮没做**，排到第 6 轮。第 4 轮记录里**两处**把采集器写成「第 5 轮」
是排期估算偏差，已在原地改为「第 6 轮」(修正处：本文件第 4 轮小节、`records/04` 第 4.5 节、
`records/CHANGELOG` 的说明行与 `Unverified` 一节)。

**产出**

  - `RhythmSignalEntity.kt`(34 行)：一次亮屏/解锁/充放电事件。存 **UTC 绝对时刻 + 采集时的时区偏移**，

  - `DailyRhythmEntity.kt`(32 行) / `DailyRhythmDao.kt`(36 行)：画像每天一行，主键就是作息日的 `epochDay`，

1. **带空格的方法名让编译产物文件名非法**。Kotlin 给测试方法里的 lambda 生成匿名类时，

   `RhythmRepositoryTest$入睡锚点看不出规律时读回来仍是 null$1.class` 这种**带空格的文件名**，
   在文件系统 / dex 环节过不去。处理办法是把方法名里的空格去掉(那句改成「读回来仍是空」)，
   **全仓共改 4 处**。这类名字读起来顺口，但只有不含空格的才安全。

2. **三个依赖声明了却从没用过**。`okhttp`、`kotlinx-serialization-json`、`androidx-work-runtime-ktx`

3. **两条仪器化断言是我写错的，代码是对的**。两条都留在记录里：

## 第 6 轮：作息采集从「算得出来」走到「真的收得到」(FR-04 收口)

**目标**

第 5 轮结束时，整条作息链路在设备上是**死的**：`signalCount` 恒为 0，
「已记录 N 条」那句界面文案从来没出现过。本轮把系统广播接上，让「亮屏 / 灭屏 / 解锁 /
插电 / 拔电」真的落进 Room，并且把采集这件事的**同意闸门**放到引导第 3 页——
先问、再采，拒绝也能照常使用全部功能。

同时处理一个容易被做假的地方：采集器「看起来在跑」和「真的收到系统广播」是两件事。
本轮为此专门写了**能收到真广播**的仪器化用例，并且把断言收紧到「行是采集器写的」，

## 第 7 轮：意愿识别能听懂、也敢说听不懂(FR-06 收口)

**目标**

前六轮把「常伴知道您什么时候醒着」这件事做通了，但**它还不知道您想干什么**。
本轮做 FR-06：从用户说的一句话里，听出三类意愿——**想做的事**（兴趣）、
**现在的状态**、**想找人帮的事**（请求），并且给出「是听哪几个字听出来的」证据。

这一轮刻意给自己限死三条：

1. **不联网、不引模型。** 用户说的话不离开设备，权限数继续是 0。
2. **听不出来就说听不出来**，绝不猜、绝不硬凑一个推荐。
3. **不留死代码。** 引擎做完必须有一条**真实可达**的界面链路，否则这一轮等于没做。

**产出**

- 新增 `domain/engine/intent/IntentLexicon.kt`(7,539 字节)：**纯数据**的词表。
  - `data class IntentTerm(term, phrases)`：一个规范词 + 用户在口语里可能说的若干说法。
  - `sentenceBreaks = "。！？；!?;\n\r"`——**逗号不在里面**（「我想学书法，也想学画画」
    是一句话里的两件事，不该被切成两句丢掉后半句；这条边界在本轮有单测守着）。
  - `interestCues`：19 个提示词短语（想学 / 想学学 / 学着 / 一直想 / 早就想 / 打算学 /
    有点兴趣 / 琢磨着想 / 感兴趣 / 愿意学 / 想了解 / 想看看 / 想试试 / 想试 / 想练 /
    想玩 / 喜欢 / 爱好 / 想）。长短都收，因为「一直想学书法」里真正表意的是「一直想」。
  - `negationMarkers = ["不", "没", "算了", "懒得"]`——**故意不收裸「别」**，
    因为「特别想学书法」里就藏着一个，一收就把这句误杀成否定。
  - `interestTopics`：13 个主题（书法 / 下棋 / 摄影 / 唱歌 / 戏曲 / 跳舞 / 养花 / 钓鱼 /
    打太极 / 出去走走 / 做饭 / 看书 / 用手机）。**不收「相机」「手机」这种单品词**，
    它们更多是「东西」而不是「想做的事」。
  - `statePhrases`：7 个（睡不好 / 身上疼 / 一个人在家 / 记性不如从前 / 没事做 /
    吃饭不规律 / 心里闷）；`requestPhrases`：2 个（想找人搭把手 / 想打听一件事）。
- 新增 `domain/engine/intent/IntentScan.kt`(9,252 字节)：**该文件 import 数为 0**，
  连带 `android.*` 的影子都没有，所以整层逻辑能在 JVM 上逐条断言。
  - `enum IntentKind { INTEREST, STATE, REQUEST }`；
    `data class IntentHit(kind, term, cue, evidence, start, endExclusive)`。
  - `sealed interface IntentScan { data class Recognized(hits); data object NotRecognized }`
    ——拒答是**类型上必须处理**的一个分支，调用方想「忘了它」都编不过。
  - 算法分四步：`forEachSentence`（按 `sentenceBreaks` 切句，**偏移是相对原文的绝对值**，
    所以每句单独剃空白不会让偏移错位）→ `scanSentence`（否定标记命中则**丢掉这一句的兴趣命中**，
    状态与请求不受影响）→ `occurrences()`（
    按词长降序贪心匹配，配 `BooleanArray taken` 防重叠，于是「一直想」先落座，
    把「想学」和「想」的位置占掉）→ `nearestCue()`（取距离最近的提示词，
    同距取更长的、再取更靠前的，保证同一输入永远同一个结果）。
  - `interestHit` 的证据取 **cue 与 topic 的最短包住片段**——所以「我一直想学书法」
    给出的证据是「一直想学书法」，而不是「一直想」也不是「书法」。
  - 结果按 `(start, endExclusive, kind.ordinal)` 排序后 `distinctBy { kind to term }`，
    同一件事在一句话里说两遍只报一次。
- 新增 `ui/talk/TalkViewModel.kt`(3,465 字节) 与 `ui/talk/TalkScreen.kt`(4,386 字节)：
  FR-06 的**最小可达界面**。
  - `TalkUiState` 三态：`Idle` / `Heard(sentence, hits)` / `NotUnderstood(sentence)`；
    `companion object { fun of(sentence, scan) }` 是唯一的状态构造入口，把
    `IntentScan` 直接翻译成界面状态。
  - `TalkExamples.recognized` = 4 句必须识别；`notRecognized` = 1 句必须不识别。
    这 5 句是**产品文案**，有专门两例单测守着它们的真假。
  - `TalkScreen` 三张卡：说明（「常伴只听得懂它学过的那几种说法，也没有联网。
    听不明白的时候它会直接说听不明白，不会瞎猜。」）/「点一句试试」（5 句示例，
    每句整行可点）/ 结果卡。结果卡上「从哪听出来的」那句是
    `BulletLine("是从「${evidence}」这几个字听出来的。")`。
  - `IntentKind.label()` 把三类翻成**人话**：「想做的事 / 现在的状态 / 想找人帮的事」。

**问题与解决**

1. **设备侧的采集器用例挂了——而且它挂得**对**：两个采集器在写同一张表。**
   第 7 轮重跑 `connectedDebugAndroidTest` 时，第 6 轮那条最严的用例
   `屏幕开关广播真的能从系统收到` 失败：
   `java.lang.AssertionError: expected:<[2026-03-10T09:00:12.345]>
   but was:<[2026-03-10T09:00:12.345, 2026-11-21T00:12:34.765, 2026-11-21T00:12:34.833]>`。
   那两条**真实时钟**的行不是测试写的，是**应用进程自己的采集器**写的：
   仪器化用例跑在应用进程里，`ElderApp.onCreate` 已经按用户设置把进程级采集器挂上了，
   而用例里那两次 `input keyevent 26` 是**发给系统的**，所以两个采集器都收到了同一个广播，
   一个用注入的固定时钟写、一个用真实时钟写。
   处理：在 `RhythmCollectorTest.setUp()` 里先
   `(context.applicationContext as ElderApp).container.rhythmCollector.stop()`，
   把「谁在写库」收敛成一个，这才让第 6 轮那条断言（时间戳必须等于注入时钟）站得住。
   修完重跑全绿（数字见下）。
   **顺带说明**：这不是产品缺陷——真实设备上只有一个采集器；这是**测试隔离**问题，
   而它恰好证明了那条断言是有效的：换个时钟写进来的行真的会被抓出来。
2. **中文测试名不能带空格（第 6 轮那条经验的又一次应用）。** 本轮新增的设备侧用例
   全部沿用下划线命名，没有再撞 D8 的 `Space characters in SimpleName`。
   本轮新增用例都在 JVM 侧，这一条只是复述，避免下次忘。
3. **设备上没法用输入法送中文，所以「自由说话」这一轮做不到。**
   `adb shell input text` 送不进中文字符（本轮的 GAP-02），因此设备验证只能走
   **写死的示例句**。这不是把验证偷懒掉——它反过来成了产品设计的一部分：
   界面上那 5 句示例句把「常伴听得懂哪些说法」当面告诉用户，
   其中第 5 句「今天天气还行」**故意**是应拒答样本。代价是这一轮的界面确实薄，
   用户还不能自由打一句自己的话；这条写进遗留。
