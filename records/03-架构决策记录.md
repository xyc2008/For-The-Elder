# 架构决策记录(ADR)

每条 ADR 记录：**背景 / 决策 / 理由 / 代价 / 状态**。
只在「有真实取舍」的地方做记录；显而易见的写法不占篇幅。

状态取值：`已采纳` / `已采纳，含已知限制` / `已废弃`。

## ADR-001：手工依赖注入，不用 Hilt

**背景**：应用需要一个对象图把 `SettingsStore`、问候引擎、`AppClock` 串起来交给 UI。
Android 生态的默认答案是 Hilt。

**决策**：手工 DI。`core/AppContainer.kt` 持有单例并暴露给 `ElderApp` / `MainActivity`，
各 `ViewModel` 用 `viewModel { }` initializer 接住依赖。

**理由**

- 本项目的对象图很小(个位数)，且**没有需要按生命周期销毁的作用域**。
- Hilt 会带来注解处理器、编译期代码生成、`@AndroidEntryPoint` 改造 Activity，
  而它解决的问题(大规模图的装配与作用域)这里不存在。
- 这不是长期排除 Hilt：等对象图长到需要作用域时再换，`AppContainer` 是唯一改动点。

**代价**：新增依赖时要手动改 `AppContainer`。接受。

**状态**：已采纳。

## ADR-002：引导页放在 `NavHost` 之外，作为一道闸门

**背景**：首次启动要显示引导页，引导完成后再进入主界面。

**决策**：引导页**没有 route**。`ui/AppRoot.kt` 直接按 `settings.onboardingDone` 二选一渲染
`OnboardingScreen` 或 `MainNav`。

**理由**

- 把引导页放进 `NavHost` 的常见写法是引导完成后 `popUpTo` 把自身弹掉。这一步写错就会退化成
  「返回键又能回到引导页」，而且是间歇性的，很难在测试里发现。
- 放在外面之后，`onboardingDone` 一翻真，整个分支被替换，**物理上不存在回退路径**。
- 副作用是好的：引导页无法被 deep link 打开，用户的第一次体验顺序有保证。

**代价**：引导页不能使用导航图的转场动画。接受(两页直上直下，本来就不需要)。

**状态**：已采纳。

## ADR-003：`allowBackup="false"`，并且刻意不写备份规则文件

**背景**：Android 默认允许应用数据参与云备份/设备迁移。要拦住它需要写
`backup_rules.xml`(旧)或 `data_extraction_rules.xml`(targetSdk 31+)。

**决策**：`AndroidManifest.xml` 设 `allowBackup="false"`，并且**两个规则文件一个都不写**。

**理由**

- 本项目处理的是「一位退休老人的作息与生活节奏」。这类数据即使在本机是低敏感度的，
  也没有理由被复制到应用的开发者看不到、但平台账号能覆盖的地方。
- 设了 `allowBackup="false"` 之后，规则文件已经不会被读取。再写一份规则文件会给人
  「这里有一套备份策略在被执行」的错觉，属于**描述与实际不符**，比不写更糟。
- 与 `NR-01`(零推销)和 `NR-05`(不索取无关权限)同源：能力和数据都按「先证明需要」来加。

**代价**：换手机时称呼与字号设置需要重新设一遍。已经在设置页明说：
「卸载应用时它们会一起消失，我们这边不会留有副本」。

**状态**：已采纳。

## ADR-004：字号缩放改为「按档位换一套排版表」，且**不干预平台的非线性换算**

**背景**

应用承诺「不用去改手机设置也能放大字」，提供三档：标准 1.0 / 大一点 1.15 / 更大 1.30。

第一版实现是**替换 `LocalDensity` 的 `fontScale`**。这个做法有一个隐蔽后果，
在第 3 轮被仪器化探针查出来(原始数据见 `records/04-质量与验证记录.md`)：

```
density = 2.625 固定，fontScale 变化
case          | 20sp.toPx | 30sp.toPx | 6 字正文 px | 6 字标题 px
fontScale=1.0 | 52.5      | 78.75     | 312         | 468
fontScale=1.5 | 68.25     | 78.75     | 408         | 468
```

同尺寸对照：`fontScale=1.0` 的 30sp = 468px，而 `fontScale=1.5` 的 20sp = 408px。
物理上后者应当不小于前者，实际却小得多。也就是说 **`fontScale` 越大、字号越大，放大越被压制**；
30sp 在 1.5 倍系统字号下**几乎不放大**。

这是 Compose 1.7 的 `Density(density, fontScale)` 工厂**内置非线性字体换算**造成的
(注意：探针测的是手搓的 `Density` 实例，所以非线性来自 Compose 的工厂，不是来自平台 `DisplayMetrics`)。

**决策**：两件事分开处理。

1. **应用自己的档位**不再走 `LocalDensity`，改为**按档位换一套排版表**：
   `ui/theme/Type.kt` 的 `elderTypography(scale: Float = 1f)` 把倍率直接乘进每个 `sp`，
   行高跟着乘，**字距与字重不乘**。选这条路的关键理由是：在 `fontScale = 1.0` 下 `sp→px` 是恒等的，
   这条路径上没有中间环节能丢信息，所以应用自己的 1.15 / 1.30 是**精确**的。
2. **平台的非线性换算不干预**。即：当用户把系统字号调到 1.5 时，应用接受平台对
   大字号施加的压缩，不去替换 `LocalDensity` 把它掰直。

**理由**

- 第 1 点是纯粹的正确性修复：修完之后三档在实测里逐级真实放大，
  并且标题、小标题、正文**都**跟着放大(修之前标题档是假的)。
- 第 2 点是刻意的取舍。平台对系统字号做非线性压缩是 Android 的可访问性策略
  (字号越大越不该继续线性膨胀)。应用把它掰直会**撤销用户手机上的系统级设置**，
  这是已知的可访问性反模式，代价不可接受。
- 替代方案(自建 `Density` 让 `fontScaleConverter = null`)在技术上可行，
  但它是**用应用的行为覆盖系统行为**，与本项目 NR-04「不替用户判断」的立场冲突。

**已知限制(必须如实记录)**

实测：系统字号 1.5 在 API 35 上只带来 **1.309×**；在这个基础上再选应用内「更大」，
只额外带来 **1.100×**(标称 1.30×)。

影响：**用户把系统字号调大以后，应用内三档的区分度会明显下降**。
「大一点」档在系统 1.5 下尤其接近无效。

缓解：默认档「标准」本身就是大字号(正文 20sp，而 Material 默认是 16sp)，
所以即使用户从不碰档位，字也已经比常见应用更大。这条限制记入
`records/CHANGELOG.md` 的 Known Issues 与 `docs/08`。

**状态**：已采纳，含已知限制。

## ADR-005：仪器化测试量**原始像素**，不量 dp

**背景**：要验证「字真的变大了」，需要一个被测的量和一把量尺。

**决策**：用 `TextLayoutResult.size.width`(排版结果的原始像素宽度)做比值，
容差 3%(每个汉字的推进宽度会被取整到整像素，6 个字累计约 1% 抖动)。

**理由**：第一版用 `getUnclippedBoundsInRoot()` 拿 dp 宽度做比值，量出来
「大一点」档的倍率是 1.097(标称 1.15)，`headlineMedium` 的倍率**恒等于 1.0**——看起来像主题坏了，
实际是**这个接口把像素换算成 dp 时用的 density 本身就带 `fontScale`**：
文字放大 1.15 倍、分母也跟着放大 1.15 倍，比值被部分抵消。
**被试和量尺是同一个东西，量出来的结论必然是错的。**

**代价**：测试里要顺着像素宽度推算，不能直接用 dp 断言。接受。

**状态**：已采纳。

## ADR-006：作息推断的时间基准——作息日以凌晨 4 点为界，输入用本地时间

**背景**：要推断「几点起床、几点不再用手机」，先得说清楚「一天」从哪儿算起，
以及引擎拿到的是哪个坐标系里的时间。这两件事定错了，后面所有时刻都不可信。

**决策**

1. **作息日以凌晨 4 点为界**（`RhythmConfig.cutoverHour = 4`）。一天是
   `[04:00, 次日 04:00)`。
2. **引擎的输入是 `LocalDateTime`**（设备本地时间），输出的时刻也是 `LocalTime`。
   时区换算不归引擎管，采集器在落库前换算好。

**理由**

- 第 1 条是被数据逼出来的：按自然日分组时，「晚上 23:30 看一眼手机 + 次日 00:30 又看了一眼」
  会被拆成两天，第二天就变成「00:30 就起床了」——起床时刻直接被一天的尾巴污染。
  往后挪 4 小时，同一夜的活动就归成一天了。4 点这个值选的是「正常人一定在睡」的时刻：
  比 0 点晚，避免跨子夜被切开；比 5 点早，避免把凌晨醒来的活动算进前一天。
  单测里有一条决定性的用例守着它（`跨子夜的深夜活动归到同一个作息日`，
  按自然日分组会得到 22:30，按作息日得到 00:30）。
- 第 2 条是为了让引擎**不依赖任何 Android API**：`java.time` 是纯 JVM 的，
  所以整条推断链路能在 JVM 单测里用合成数据跑（AC-04.1），不需要模拟器。
  时区只在采集的边界处出现一次，比让引擎到处持有 `ZoneId` 更容易查错。
  代价是引擎对「用户改了时区」这件事没有意见——那是采集器要考虑的，见第 5 轮。

**代价**：作息画像里的时刻不能直接和 UTC 时间戳互算，需要采集器提供换算。
边界处的时区处理成为第 5 轮的显式任务，而不是隐式假设。接受。

**状态**：已采纳（第 4 轮）。

## ADR-007：推断结果用三态，不用可空值

**背景**：数据不足时，`infer()` 该返回什么？

**决策**：返回 `RhythmResult` 这个密封接口，三种形态：
`Ready(rhythm)`、`Gathering(validDays, requiredDays)`、`Inconsistent`。

**理由**：如果只给 `DailyRhythm?`，「还在收集（0/3 天）」和「这批数据自相矛盾」会塌成同一个
`null`，界面只能含糊地说一句「还没好」。而这两种情况对界面是两句不同的话：
前者该显示进度让用户知道系统在做什么，后者**不该编**，安静待着就行。
三态让「不编数据」成为类型层面的约束，而不是调用方要记得的约定。

**代价**：调用方要 `when` 三种情况。接受——这正是要让调用方想清楚的地方。

**状态**：已采纳（第 4 轮）。

## ADR-008：作息信号的持久化——存绝对时刻 + 采集时的偏移，时区复原只发生在数据层边界

**背景**：第 4 轮的引擎吃的是 `LocalDateTime`（ADR-006 第 2 条），输出的是 `LocalTime`。
但存进数据库必须能回答「这条信号到底是什么时候发生的」。有两条路：

1. 存本地墙钟时间（`2026-03-10 07:30`）。
2. 存 UTC 绝对时刻（epoch 毫秒）。

**决策**

1. **存 UTC 绝对时刻**（`atEpochMilli`），**外加**采集那一刻的时区偏移（`offsetSeconds`）。
2. **读回来用存下来的偏移还原成本地时刻**，不用当前的系统时区。
3. **引擎完全不碰时区**：采集器交给引擎的仍然是 `LocalDateTime`，时区换算只在
   `data/rhythm/` 这一层出现一次（`RhythmMapping` + `RhythmRepository`）。
4. 作息画像（`daily_rhythm` 表）不存时刻，只存**相对作息日分界点的分钟偏移**
   （`wakeOffsetMinutes` 等），读回时用同一个 `cutoverHour` 还原。

**理由**

- 只存墙钟时间的话，「同一时刻」这件事就丢了。用户出趟差把手机时区换掉，
  库里 7:30 到底是出发地的 7:30 还是家里的 7:30 就无从判断——而作息推断最怕的就是这个。
  存绝对时刻 + 当时的偏移，两个问题一次解决：既能跨时区排序、算间隔，
  又能按当时人的感受还原本地时刻。
- 第 2 条是本 ADR 里最容易被写错的一条。用「当前时区」还原看着更方便，
  但那样用户每换一次时区，**历史作息就会整体平移几小时**——他会看到自己「凌晨 3 点起床」。
  单测 `还原本地时刻用的是存下来的偏移而不是当前时区` 专门守着它。
- 第 3 条延续 ADR-006：时区是脏东西，只让它在一个边界上出现。
  引擎保持纯 `java.time` 无状态，才能在 JVM 单测里跑（AC-04.1）。
- 第 4 条的理由是画像本身**不该绑定时区**：「起床 06:30」是这个人几十年的习惯，
  它跟格林尼治没关系。存成相对分界点的分钟数，换时区也不影响画像的重建。
  代价是**读画像必须知道当初用的 `cutoverHour`**，这个约定由
  `RhythmRepository` 的构造函数参数收口，并有单测反证「按另一个分界点解会错一小时」。

**代价**：多存一个 `offsetSeconds` 字段；画像的读写必须成对使用同一个 `cutoverHour`。
接受——比让历史作息随手机时区漂移便宜得多。

**状态**：已采纳（第 5 轮）。

## ADR-009：作息采集器只在运行时注册广播，且不持有任何权限

**背景**：第 6 轮要把系统广播真的接上。Android 给「持续观察屏幕开关」这件事提供了
至少三条路，选哪条直接决定了权限清单、电池行为和**用户能不能关掉它**：

1. 在 `AndroidManifest.xml` 里静态注册 `RECEIVE_BOOT_COMPLETED` + 一个常驻 receiver，
   再配合前台服务或 `WorkManager` 保活。
2. 只在 `Application.onCreate` / 界面可见时用 `registerReceiver` 动态注册。
3. 完全不注册，改用 `UsageStatsManager` 之类的统计接口。

**决策**

1. **只在运行时注册**（第 2 条路）。manifest 里**没有任何 `<receiver>` 声明**，
   也不申请 `RECEIVE_BOOT_COMPLETED`。进程不在，就收不到广播——接受。
2. **权限数保持 0**。不申请 `PACKAGE_USAGE_STATS`（延续 `docs/01` 的决定），
   不申请 `POST_NOTIFICATIONS`，不用前台服务。
3. **注册用 `RECEIVER_NOT_EXPORTED`**，走 `ContextCompat.registerReceiver` 以兼容 API 26~34 的差异。
4. **广播回调返回 `Job?`，不返回条数**。
5. **拒绝采集后，App 的全部功能照常可用**——作息画像退回「按普通人的作息猜」，
   而不是变成空壳。

**理由**

- 第 1 条与第 3 条是这个 ADR 的核心。静态注册 + 保活意味着**采集一直在跑**，
  用户关掉应用也关不掉它。这正是本应用负面需求 NR-02(不打扰)和 NR-05(不索取无关权限)
  要防止的东西：一个「懂节制」的陪伴应用，自己先变成一个一直在后台偷看屏幕状态的东西，
  说不过去。代价是采集**不连续**——用户不用手机的时候应用本来也不在，丢的事件主要是
  「关机期间」和「杀进程之后」这两段，而这两段恰好是信息量最低的（人在睡觉）。
  这个代价本轮**没有量化**，如实记在 `records/01` 第 6 轮遗留里。
- 第 2 条：三条广播(`SCREEN_ON` / `SCREEN_OFF` / `USER_PRESENT`)和两条充放电广播
  都是系统广播，动态注册就能收到，**不需要任何权限**。既然不需要，就不申请。
  「权限数 = 0」这条还是可以在 `adb shell dumpsys package` 里直接核对的硬判据。
- 第 4 条是为了不制造假接口。落库是异步的，`onBroadcast()` 返回时写入还没完成，
  如果让它返回「写了几条」，返回值只能是 0 或者瞎编。返回 `Job?` 的含义是
  「这个 action 我认，并且已经排了活」/「认不出，没排」——这是调用点当时**真的知道**的事。
  「认不出」用 `null` 而不是抛异常：未知广播是常态(系统会发很多我们不要的)，
  不是错误。
- 第 5 条是产品立场，也是**可测的**：设置页在开关关闭时明确写
  「没有打开。常伴照样能用，只是说话的时机按普通人的作息来猜，可能正好撞上您午睡。」
  这条文案不是安慰话，它描述了代码的真实分支——`AppContainer.startProcessWork()`
  在 `collectRhythm == false` 时不调 `start()`，而问候引擎仍然照常工作
  (第 6 轮实测：拒绝引导第 3 页后首页仍显示「夜深了 / 不着急，什么时候想说都行。」)。

**代价**

- 进程被杀后的事件永久丢失，作息画像的样本量低于「常驻采集」的方案。
- 每轮冷启动会重新注册一次，`start()` 做成幂等的，避免重复注册导致同一事件落两条。
- 无法在后台做定期清理，`pruneIfDue()` 只能挂在启动路径上（同一天只清一次）。

**状态**：已采纳（第 6 轮）。

## ADR-010：意愿识别用词表规则，不用模型；否定按句丢弃；证据保留原话

**背景**：第 7 轮要做 FR-06「从用户说的话里听出他想做什么」。这件事在 2026 年有两条
现成的路：接一个云端大模型做意图分类，或者在本地用规则/小模型做。三条硬约束把选择空间
压得很窄，所以本 ADR 的三条决策其实是同一个立场推出来的：

- **NR-05：不联网、不索取无关权限。** 一旦联网，就要加 `INTERNET` 权限，
  「权限数 = 0」这条硬判据当场作废，用户说的话也要离开设备。
- **NR-02：不打扰，也不制造负担。** 识别错了去推荐一个用户根本没兴趣的东西，
  比识别不出来更打扰。
- **可验证性。** 「识别得对不对」必须能被一个断言说清楚。模型的输出要构造数据集才能断言，
  而这一轮没有真实用户数据。

**决策**

1. **用词表匹配，不引入任何模型、不联网、不加载 native 库。**
   `domain/engine/intent/IntentLexicon.kt` 是纯数据（19 个兴趣提示词、13 个主题词、
   7 个状态说法、2 个请求说法），`IntentScan.kt` 是纯算法，**零 import**
   （连 `kotlin.text` 都不用引，因为是隐式引用的），因此能在 JVM 单测里逐条断言。
2. **否定只在兴趣上生效，且按「整句丢弃」处理，不做逐词消解。**
   `negationMarkers = ["不", "没", "算了", "懒得"]` 出现在同一句里时，
   这一句里的**兴趣**命中全部作废；**状态和请求不受影响**。
   刻意**不收裸「别」**——「特别想学书法」会被它误杀。
3. **证据存「原话里最短包住片段」+ 原文偏移**（`IntentHit.evidence/start/endExclusive`），
   不存归一化后的规范词。
4. **听不出来就明说**（`IntentScan.NotRecognized`），并且**拒答时不给任何推荐**。
   这条是接口形态上的决策：`scan()` 返回 `sealed interface`，调用方**必须**处理
   `NotRecognized` 分支，不可能「忘了处理所以悄悄当成空结果」。
5. **不报置信度。** 界面只显示「想做的事：书法」和「是从「一直想学书法」这几个字听出来的」，
   不显示任何百分比。

**理由**

- 第 1 条：词表匹配的召回一定低于模型，但它的**错误是可读的**——错了就能指着词表说出
  为什么错，下一轮改词表即可。相反，模型在这个场景的错误无法用一条断言复现，
  也就无法保证「不留假功能」。另外，`0 import` 不是洁癖：它使这层逻辑**不依赖 Android**，
  这也是它能以 29 例单测覆盖的原因。选它的代价是词表覆盖率有限
  （口琴、太极剑这类词表外主题一律不识别），已写进 `records/04` 的 Known Issues。
- 第 2 条：逐词消解否定需要句法分析（「我不想学书法，但想学画画」里两个「想」
  一正一负），这套东西靠词表做不出来，做一半反而会产生**看起来很聪明**的错误结果。
  整句丢弃的代价是明确的：`「不错，下棋挺好玩」` 因为有个裸「不」而整句不识别。
  这个代价比「把否定句认成肯定句」小得多——后者会让应用去推荐用户刚拒绝的事。
- 第 3 条：把证据留成原话片段，界面上就能显示**用户自己说过的那句话**，
  而不是我们改写过的词。这既是可解释性的最低要求，也是**纠错入口**——
  用户看到「是从「一直想学」这几个字听出来的」就能立刻判断我们错在哪。
  存规范词（比如统一成「书法」）会让所有来源看起来一模一样，反而丢掉了唯一的纠错线索。
- 第 4 条：`NotRecognized` 做成 `sealed interface` 的一个分支而不是 `null` 或空列表，
  是为了让「听不明白」成为**类型上必须处理的状态**。实测拒答路径上界面只有一句
  「这句我没听明白」，没有任何推荐文案（第 7 轮设备实测）。
- 第 5 条：词表匹配**没有概率**可言，输出一个 `0.87` 只能是编的。宁可没有这个数字。

**代价**

- 召回有限：句内只有主题词、没有提示词时不识别（RC-006 已把这条写进 AC-06.2）。
- 裸「想」在提示词表里，所以「下棋这件事我想想」会被算成兴趣——已知误判，未量化。
- 词表是硬编码的中文短语，扩展要改代码发版，不能热更新（本项目没有服务端，接受）。

**状态**：已采纳（第 7 轮）。

## ADR-011：意愿闸门是独立的一层；拒绝是终止态但可撤回；状态转移用「不变即 `null`」

**背景**：第 8 轮要做 FR-07「意愿确认闸门」。第 7 轮的 `IntentScan` 已经能听出
「想做的事 / 现在的状态 / 想找人帮的事」，但它**不认识用户**——它不知道哪件事已经被
问过、哪件事被拒绝过。于是「问过没有」这件事需要一个归属地。三条既有立场决定了本 ADR：

- **NR-02：不打扰，也不制造负担。** 用户拒绝过的事，一次都不许再主动提。
- **AC-07.4：闸门不碰作息。** 被拒绝的意愿不能因为「检测到用户现在很闲」而被唤醒。
- **可验证性。** 状态机必须能被断言穷举，不能藏在界面里。

**决策**

1. **闸门是独立的一层（`domain/wish/`），不认识 NLU，也不认识作息。**
   `WishGate` 只接受 `WishStatus` 与 `WishDecision` 两个枚举；`StoredWish` 只带
   `IntentKind`（第 7 轮的类型）而不带 `IntentHit`。硬判据：
   `grep -rn "rhythm\|unlock" app/src/main/java/com/fortheelder/domain/wish/` 零命中。
2. **状态转移只有一个入口，且「不变就返回 `null`」。**
   `WishGate.decide(from, decision): WishStatus?`——`null` 表示状态不变。
3. **`DECLINED + CONFIRM → CONFIRMED` 是刻意的**，而 `DECLINED` 本身**不**被
   `WishGate.mayBringUp` 放行。即：常伴不可以主动提起被拒的事，但用户可以自己改主意。
4. **列表里展示已拒绝项（`您说过先不用`）不算「主动提起」。** 只有 `mayBringUp`
   放行的那条路（带闸门按钮的「还没问过您的」）才算。
5. **同一件事在整屏只有一组闸门按钮**，不是列表一处、结果卡一处。
6. **`offerLines()` 只在 `CONFIRMED` 时非空，且内容只有一句真话**
   （「「书法」在下面「常伴记住的事」里，随时能删。」）。AC-07.4 的断言就落在这个「空」上。
7. **写入走 `INSERT OR IGNORE` + 一把 `Mutex`；状态列解不出时兜底 `DECLINED`。**
8. **存 `heardAtEpochMilli` 但界面不显示任何时间，也不存「最近一次提到」。**

**理由**

- 第 1 条：如果闸门去查作息，就必然有一天会写出「他现在闲着，提一句吧」这种代码——
  而这正是 AC-07.4 要挡的东西。**不让它拿到数据，比让写代码的人自律更可靠。**
  这也是第 7 轮「`IntentScan` 零 import」那条决定的同一种做法：**约束靠边界，不靠自觉。**
- 第 2 条：如果 `decide` 返回一个新状态，那么「重复点同一个按钮」就会把
  `decidedAtEpochMilli` 覆盖掉，用户第一次表态的时刻就丢了。返回 `null` 让
  **「没变」成为一个显式结果**，调用方不必去比较字符串。这与 ADR-007「用三态不用可空值」
  并不矛盾：那里空值表示**信息不足**（一个状态），这里 `null` 表示**没有发生转移**
  （一个动作的结果）。
- 第 3 条：AC-07.3 挡的是**常伴主动提起**用户拒绝过的事，不是「用户自己改主意」。
  用户点了 `我现在想了解一下`，那是用户的动作；常伴只是照办。**没有这个入口的话，
  一次误点就是永久生效**，用户没有任何补救办法——对老人尤其糟，误触本来就更常见。
  这条取舍必须写在文档里，否则下一次有人在 AC-07.3 下面看到「DECLINED 能变成
  CONFIRMED」会以为是 bug。
- 第 4 条：如果连列出来都算「提起」，那就只能把被拒的事从界面上抹掉——用户会看到
  「我说过的事不见了」，反而更可疑。**让用户看得到自己说过什么、也看得到自己拒绝过什么，
  是这一页存在的意义。**
- 第 5 条：一个页面上两组按钮，用户会以为要分别点两次；而且「同一件事点了一个按钮
  另一组没变」看起来就是坏了。
- 第 6 条：`offerLines` 是这一轮最容易被写成假功能的地方——确认之后最容易顺手写一句
  「往后我会提醒您」。但这个版本**没有**提醒能力（FR-05 在第 9 轮），写了就是假功能。
  所以本轮的输出只有「它在清单里、能删」这句**当下就成立**的话。
- 第 7 条：`INSERT OR IGNORE` 是对一个真实用户的场景：同一件事说两遍。如果用
  `REPLACE`/`UPDATE`，用户拒绝过的事会因为再提一次而**变回「还没问过您」**，
  闸门就被无限复活了。`Mutex` 同理——闸门按钮与落库之间，用户点得比写入快。
  兜底 `DECLINED` 是这个项目的默认姿势：**宁可不打扰，也不让它变成推销。**
- 第 8 条：存 `heardAtEpochMilli` 是为了排查（用户报「我说过它没记」时能看出是不是
  重复插入被忽略了）；不显示时间、也不存「最近一次提到」，是为了不让一件随口说过的事
  变成被计数的指标（RC-007 已把这条写成需求）。

**代价**

- **闸门与 NLU 之间的类型耦合只剩 `IntentKind`**，所以措辞（`TalkVoice`）成了闸门
  唯一的「内容出口」。措辞里出现一句做不到的话就是假功能——这件事没有编译器帮你挡，
  只能靠单测扫。这是本项目里**约束最弱的一处**，已记进 `records/04`。
- `decide` 返回可空值，调用方要处理 `null`（本轮调用方一律「什么都不做」）。
- 兜底 `DECLINED` 意味着**数据坏掉的方向是「少打扰」而不是「多打扰」**：一条坏行会
  静默地不再出现，排查时容易被忽略。
- 状态转移的**可撤回**让 AC-07.3 的表述必须带上「常伴主动提起」这个限定语，
  文档里多了一段原本不需要的解释。
- 不显示时间 ⇒ 用户无法区分「今天说的」和「上个月说的」；这是刻意的漏（RC-007）。

**状态**：已采纳（第 8 轮）。

## ADR-012：仪器化测试必须用自己的库文件，不能和产品的 `elder.db` 共用一个文件

**背景**：第 8 轮第一次跑 `connectedDebugAndroidTest` 时，
`TalkInputTest > 点了先不用之后不再问但用户自己还能改主意` 崩了，还带走了同进程里
排在它后面的 8 个用例。异常是
`android.database.sqlite.SQLiteException: no such table: wish (code 1 SQLITE_ERROR):
, while compiling: SELECT * FROM wish ORDER BY id ASC`，崩在
`WishDao_Impl$10.call → CoroutinesRoom$createFlow → Dispatchers.Main.immediate`。

取证链（全部实测）：

- 干净装机 + `am instrument` 全包跑 → **必现崩溃**；
- 事后 `run-as … cat databases/elder.db` 取回 12,288 字节的库，Python `sqlite3` 读出
  `user_version = 0`、tables 只有 `['android_metadata']`、**没有 `room_master_table`**
  ——一个**空壳库**；
- 设备上已经有一份健康 `elder.db` 时跑同一条命令 → 只 1 例失败、**不崩**；
- `TalkInputTest` 单独跑（干净装机）→ 4 例全跑完，**不崩**。

**决策**：**仪器化测试用的数据库文件必须与产品运行用的 `elder.db` 分家。**
具体做法：`ElderDatabase.open(context, name: String = FILE_NAME)` 与
`AppContainer(context, databaseName: String = ElderDatabase.FILE_NAME)` 各加一个
**带默认值**的参数；四个数据用例类与 `TalkInputTest` 各自传入 `elder-test-*.db`，
并在 `@Before` 删自己的库、`@After` 关掉自己的 Room 实例再删自己的库。
生产代码的调用点**一个都没变**——仍然只有 `ElderApp.kt:24` 的 `AppContainer(this)`
（已 grep 确认唯一）。

**理由**

- 仪器化用例跑在**应用进程**里，`ElderApp.onCreate` 会按用户设置把进程级的
  `AppContainer` 建起来并**一直活着**。而数据用例又反复
  `deleteDatabase("elder.db")` 再重开——**应用的 Room 实例与测试的删库打在同一个文件上**。
  文件被删之后，Room 缓存的实例没有重建表，查询就打在了空壳上。
- **产品代码不会在自己的进程里删自己的库。** 所以这不是产品缺陷，是**测试隔离**问题。
  判据是那个关键的对照实验：设备上已有健康库时**不崩**，单独跑该用例**不崩**——
  两者都说明「有人在删别人的库」才是变量。
- 为什么用**带默认值的参数**而不是加一个测试专用构造函数/DI 开关：默认值让产品路径
  **一个字都不用改**（也就不可能改错），同时让测试能明确说出自己要用哪个文件。代价是
  产品代码里多了一个「只有测试会传」的参数，这一点由 KDoc 说明（`ElderDatabase.open`
  的类注释里写清了「测试要传自己的库名，两者共用 `elder.db` 会出 `no such table: wish`」）。
- 为什么不在 `@Before` 里删 `elder.db` 前先把应用的容器关掉：那会让测试**依赖产品的
  生命周期**，用例之间互相影响，第一例改了状态、第二例就跟着变。

**代价**

- 产品代码里多了一个只为测试存在的参数（`databaseName`），是**可见的测试让步**。
- 测试库文件留在设备上（`elder-test-*.db`），`@After` 删一次即可，但不保证设备被强杀时
  一定清干净；下次跑到同一个用例时 `@Before` 会再删一次，所以**不会累积到影响结果**。
- 这条路径的**逐帧时序没有取证**。上面写的是「已定位到共用库文件这条路径」，
  不是「已完全解释 SQLite 的每一次文件操作」。因此 `records/01` 与 `records/04` 里
  都**不写**「已完全解释」。

**状态**：已采纳（第 8 轮）。

## ADR-013：介入 = 打开应用时迎上来说话；节流状态单独一个 DataStore 文件；间隔上限 24 小时

**背景**：第 9 轮做 FR-05（低打扰节流）。做之前有三个问题必须回答，而且这三问都没有
现成答案：

1. **「介入」的触发点是什么。** 调度总要有个东西来触发。可选：用户打开应用时判（应用内）、
   到点弹通知、前台服务常驻轮询。
2. **节流状态存哪里。** 第 5、6、8 轮已经有 `settings`（DataStore Preferences）和
   `elder.db`（Room）两处存储。可选的第三个答案是「再开一个 DataStore 文件」。
3. **用户一直不回应时，间隔涨到哪停。** `gap = minGap + step × streak` 一定会增长，
   问题是设不设上限。

**决策**

**一、「介入」只有一个触发点：用户打开应用时，首页判一次要不要说话。**
没有通知通道，不申请 `POST_NOTIFICATIONS`，不建通知渠道，不用前台服务，不注册
`AlarmManager`，manifest 里一个 `<receiver>` 都没有（实测 `<uses-permission>` 0 条、
`<receiver>` 0 条）。决策函数 `InterventionWindow.decide` 的第二个参数就是 `now`，
没有「到点触发」这个概念。

**二、节流状态用独立的 DataStore 文件 `intervention.preferences_pb`**，
三个键 `last_spoken_at`（epoch millis）/ `last_answered_at`（epoch millis）/
`ignored_streak`（Int）。

**三、间隔上限 `maxGapMinutes = 1440`（24 小时），不是「永久沉默」。**

**理由**

**关于一**：

- 用户没打开应用，就说明他此刻不需要常伴。（b）到点通知和（c）前台服务都要求应用
  获得「在自己认为合适的时候打断用户」的能力，而判断「合适」的依据只有屏幕亮灭、
  解锁这类**行为数据**。从行为数据推断「该关心他了」，正是 AC-06.4 禁止的那类推断，
  只是方向相反——一个是从行为推兴趣，一个是从行为推情绪/状态。两者都不该做。
- 代价是结构性的、也是这次真正想要的那部分：**零权限**。没有权限、没有清单项，
  应用在用户没打开的时候**不可能**做任何事。这比「我们保证不发通知」可靠。
- 三问里这一问最容易被含糊过去。含糊的版本是「介入窗口 = 该打扰用户的时间窗」，
  那样写下去，第 10 轮做行动卡时就会顺手加个通知。所以 RC-008 把边界写死在需求里。

**关于二**：

- **`settings` 文件不能放这个状态。** 设置页有「恢复默认」，那一处走的是
  `SettingsStore.resetToDefaults()` → `prefs.clear()`。把节流状态和设置放同一个文件，
  用户点一下「恢复默认」就会把 `ignored_streak` 一起清掉——表现是「重置设置之后常伴
  又开始每次都说」，而用户完全没有把这两件事联系起来。这个 bug 极难查：
  它只在「用户改过设置又刚好重置」时出现。
- **`elder.db` 也可以放**（建一张单行的节流表），但为三个标量开一张表 + 一次 Migration
  （数据库版本要从 2 升到 3）不值得，而 DataStore 已经在本项目里被验证过（第 2、6 轮），
  加一个文件是零风险的。
- 代价是**多了一个文件**：`files/datastore/` 下从 1 个变成 2 个 Preferences 文件。
  收尾时用 `ls -l` 实测确认过确实是两个独立文件（`intervention.preferences_pb` 49 字节、
  `settings.preferences_pb` 120 字节），且两边键名完全不同——不是「看起来分开」。
- 为什么不用同一个文件但换前缀：`prefs.clear()` 清的是**整个文件**，不是某个前缀。
  换前缀解决不了这个问题。

**关于三**：

- 上限而不是永久沉默，理由是**用户没有任何办法把一个永久沉默的陪伴者叫回来**。
  它看起来坏了，而用户不会知道是自己「不理它」导致的。
- 上限取一天一次而不是一周一次：一天一次已经足够低；再低就退化成「几乎不说话」，
  那种应用用户会直接卸载。
- 有了上限，AC-05.3「一次都不回应时必须**降低**频率」就有一个明确的落点：
  30 → 210 → 390 → … → 1440 分钟封顶。

**一个必须配套的细节（`ON_START` 补判但冷启不重复判）**：首页要在「从后台回来」时
重新判一次——不重判的话，用户十分钟前看到的「先不重复招呼了」会一直挂着，而它半小时后
就不成立了。但 `LifecycleRegistry.addObserver` 会把新观察者**同步推进到当前状态**，
依次补发 `ON_CREATE` / `ON_START` / `ON_RESUME`；那时候 `HomeViewModel.init` 刚判过一次，
看到 `ON_START` 就再判，冷启动会**连判两次**——第二次读到的是刚刚写下的「已经招呼过」，
首页于是从问候翻成「先不重复招呼了」，第一句话一闪而过。所以加了
`leftSinceLastOpening`：只有真的先离开过（`onStop` 置位），回来时的 `ON_START` 才算
新的一次露面。**这不是防御性代码，是对一个真实时序的修正**，并且它对应的正是设备上
能看见的观感问题。

**代价**

- 用户不打开应用时，常伴什么也不做；任何形如「提醒吃药」「到点活动」的需求在本版本
  **做不到**。这一点写进 `docs/01` 第 9 节 GAP-06，不是「还没做」而是「明确不做」。
- 多一个 DataStore 文件；如果以后还要加第三个，需要先回答「为什么不能并进已有的」。
- 上限 24 小时意味着最坏情况下常伴一天仍会说一次。用户若连着几周不回应，它不会自己
  彻底安静——这条是有意保留的，不许当成 bug 修。
- `leftSinceLastOpening` 是 ViewModel 里的一个可变字段，**跨进程死亡不保留**：所以
  进程被系统杀掉再恢复时，`init` 会重新判一次，那时读的是磁盘上的节流状态（实测冷启
  确实仍判 `TOO_SOON`），结论正确。但这条「杀进程 → 恢复」的路径**没有专门取证**。
- **「一次不回应 → 间隔变长」这条在真设备上没观察到**：`streak=0` 时间隔就是 30 分钟，
  要看到它涨到 210 分钟得等真实时间。守卫只有 JVM 层（`InterventionWindowTest` 21 例
  含 30 天模拟、`ThrottleStateTest` 11 例）。**不许把它写成「设备上已验证」。**
- 设置页「说话的时机」卡用 `produceState` 调 `rhythmProfileService.current()`，
  画像满 3 天后打开设置页会**触发一次落库**（`RhythmProfileService.current()` 只在
  `Ready` 时 `saveProfile`）。这是**有意**的：设置页显示的是真实缓存，而不是另算一份
  可能不一致的值。代价是「看一眼设置」也会写库，且这条路径在真设备上**没走到**
  （画像一直是 `Gathering`），只有设备侧 `RhythmProfileServiceTest` 的 4 例覆盖。

**状态**：已采纳（第 9 轮）。

## ADR-014：起点目录是纯数据加纯函数；锚点只能由用户亲手建立；鼓励语不落库；锚点表不留任何计数

**背景**：第 10 轮做 FR-08（低门槛行动卡）、FR-09（生活锚点）、FR-10（做完之后的回话）。
动手前有四问没有现成答案：

1. **起点目录（「书法可以这样开始」那一组步骤）是数据还是逻辑。** 三种放法：写死在
   `TalkScreen` 的代码里、放进数据库当一张表、单独做一层。
2. **锚点谁创建。** 用户说过「我一直想学书法」，应用能不能顺手替他记成日常？
3. **做完之后的鼓励语存不存。** 存了以后可以显示「你上次做完是 3 天前」。
4. **锚点表要不要留计数列**（连续天数、完成次数、最近一次做到）。

**决策**

**一、`StarterCatalog` 是纯数据 + 纯函数：39 条起点、13 件事，全在一个 `object` 里
字面量写出，不碰数据库、不碰界面、不依赖任何 Android 类。**
`offerable(kind, term, status)` 是唯一一处放行判据；
`StarterRules.violations(option)` 是机械可判的边界。

**二、锚点只能由用户亲手建立。** `AnchorRepository` 对外只有 `anchors`（读）/
`add`（写）/ `remove` / `dueNow` / `count`；`add` 的唯一入参是 `AnchorDraft`，而草稿
只能由 `AnchorRules.draftOf(optionId, slot)` 从目录里造出来。界面要先显示四个时段按钮、
等用户点下去（AC-09.1），才拿得到那份草稿。

**三、鼓励语不落库。** `Encouragement.forAction(action)` 是唯一入口，签名强制带上
「哪一步」，没有「通用的好话」入口。库中没有完成记录。

**四、锚点表没有任何计数列。** `anchor` 共 6 列：`id` / `term` / `optionId` /
`action` / `slot` / `createdAtEpochMilli`。没有 `streak`、没有 `completedCount`、
没有 `lastDoneAt`（实测 `pragma table_info(anchor)` 输出 6 行，逐行核对过）。

**理由**

**关于一**：

- **放数据库要多一次 Migration 加一张纯只读表**，而目录是随代码一起发布的常量。
  第 10 轮数据库从 2 升到 3 是为了锚点表，不是为目录——目录没有理由占用一次版本升级。
- **写死在界面里，测试就只能靠 UI 测试**。UI 测试要跑设备（本轮 92 例、36 秒），
  而且断言粒度只有「这一行字有没有出现」。放进领域层以后，`StarterCatalogTest` 21 例
  是 JVM 测试，逐条扫 39 个起点的性质：耗时必须在 1~20 分钟、第一步动作至少 10 个字、
  四个词表（要花钱 / 累计施压 / 医疗口吻 / 没法照做的空话）一个都不许命中、`term`
  必须是目录里真的有起点的事。
- 这一层是**可判的**，不只是「分开了」。分层的收益不在文件整齐，在于**加一件事的时候
  性质自动被检查**：新起点只要违反任一条纪律，`StarterCatalogTest` 立刻红。这是
  「不许存在假功能」在文案纪律上的落点——不靠记得去人审。
- `coveredTerms` 是 `byTermIndex.keys` **算出来的**，不是另写一份清单。手写的清单会
  跟实际数据脱节：加了起点忘了往清单里加 `term`，那条起点就永远递不出去，而且不报错。
  算出来的版本不可能脱节。

**关于二**：

- 自动建锚点需要一条完成记录作为触发条件，而 FR-09 自始至终是「用户自己记」
  （RC-009 之二）。自动建还要求应用从「用户提过学书法」推断「他现在想每天写」——
  这正是 ADR-010/011 一路在回避的那类推断，只是换了个方向。
- 更要紧的是**把这条做成结构性的，而不是靠代码规范**：库里没有计数列 → 算不出
  连续天数；`add` 的入参类型只能是目录造出的草稿 → 界面无法伪造一条目录外的锚点；
  `AnchorRules.mayPropose` 还要求来源意愿是 `CONFIRMED`。三条叠起来，即使将来有人
  想加自动创建，也得先改表结构、改入参类型，改不动就会被编译器和迁移测试拦住。
- 唯一索引落在 `optionId` 上，所以「同一件事记两条」在库层就不可能。用户想改时段，
  删掉再记一次——比在同一件事上维护两个时段简单，也不会出现「同一件事上午一条、
  晚上一条」的重复。

**关于三**：

- 存下来就会变成话术库，而话术库迟早被用来做挽留：「您上次是 3 天前来写过的」。
  不存，这种句子在代码里就**写不出来**——没有数据源。
- 鼓励语是当场按「哪一步」生成的，所以每句话都不同，因为它带上了那件事本身
  （AC-10.1）。代价是它不能引用任何历史，这正是想要的。

**关于四**：

- AC-09.2 要求用户中断之后不显示「已中断 N 天」、不归零、不催人恢复。库里没有地方
  能算出 N，界面就不可能显示它。这是这条需求最省事的守法：**把话术的可能性从数据
  模型里拿掉**，而不是在界面上写 `if` 屏蔽它。
- 配套的一条：删掉就是删掉，不追问、不显示「要不要记回来」
  （`AnchorRules.deletionAsksAgain = false`）。

**代价**

- **目录是编译期常量，改文案要重新发版。** 可接受：文案本身是产品的一部分，应当随
  发版一起被审；放进数据库只是把审查推迟到运行期。
- **禁用词是朴素子串扫描**，会误伤。`StarterRules.vagueWords` 里有「了解一下」，所以
  别的文案里只要出现这四个字就会被判违反。这是已知限制，记在 `docs/01` GAP-04
  （文案集中化，第 16 轮）。
- **39 条起点在 13 件事上的分布不均匀**：有的事只有 2 条，有的事有 4 条。补到「每件事
  至少两条、且第一条都不需要准备东西」是第 11 轮之后的事。
- **锚点是本地数据，不联网、不备份**（ADR-003：`allowBackup="false"`），换机就丢。
  这个取舍在第 3 轮已定，本轮不变。
- **首页上锚点行默认看不见**。`InterventionVoice` 只在判定 `Speak` 时才拼出
  `anchorLine`，本轮实测时判的是 `StayQuiet(SLEEP_HOURS)`，所以首页没有锚点行——
  这是设计决策而不是缺陷：一条「今天上午写满一张纸」若在深夜冒出来，就成了催促。
  锚点本身在「跟常伴说两句」页里始终可见、可删。

**状态**：已采纳（第 10 轮）。

## ADR-015：插件式小游戏的落地形状是「数据类 + 出局函数 + 一个 `object` 目录」，不是接口；单局结果不落库，靠「没有地方可落」守法

**日期**：第 11 轮
**关联**：`docs/01` FR-11 / FR-12 / DR-09 / NFR-14；`records/02` RC-010；`docs/03` 第 3 节

**背景**

第 11 轮要加「脑力互动」这个模块，`docs/00` 第 7 节把它拆成「框架 + 三个小游戏」，
三个游戏分三轮（第 12~14 轮）落地。也就是说这一轮必须先把**加第二个游戏的形状**
定下来，否则第 12 轮加游戏时就会顺手改框架，而改框架会牵动已经验证过的舒尔特方格。

同时 `docs/01` DR-09 写了一条硬要求：

> 脑力互动的单局结果**不落库**，随进程结束。

这条要求有两种守法方式：一种是在代码里**记得别写**（写注释、写测试、写 code review
清单），另一种是让**写这件事在结构上做不到**。本项目前几轮一直选后者
（ADR-011 的「不变即 `null`」、ADR-014 的「锚点表不留任何计数字段」），
这一轮延续同一个思路，但落地对象从「表」换成了「类」。

**决策**

**一、游戏不是 `interface`，是一条数据 + 一个纯出局函数。**

形状定在 `domain/play/PlayGame.kt`：

```kotlin
data class PlayGame(
    val id: String,
    val name: String,
    val howTo: String,
    val columns: Int,
    val longestSeconds: Int,
    val deal: (Random) -> PlayRound,
)
```

加第二个游戏 = 往 `PlayCatalog.games` 多写一条 `PlayGame(...)`，
给一个 `deal`，不新增类型、不新增文件间依赖。

**为什么不是 `interface PlayGame { fun deal(): PlayRound }` + 每个游戏一个 `class`：**

- 本项目的判断规则是「**只有一个实现的接口不写**」（`docs/02` 第 2.2 节、
  `docs/01` NFR-14）。第 11 轮只有一个游戏，为它单开一个接口正落进这条规则要避免的情况。
- 更实际的理由是：接口会把「框架」和「游戏」拆进两个文件层级，而这里的「框架」
  一共只有 6 个字段。一个 `data class` 就是能被 `listOf` 装起来、能被 `==` 比较、
  能在测试里直接构造的框架；接口不是。
- `deal: (Random) -> PlayRound` 把随机性**作为入参**交进来，出局函数因此是纯函数：
  测试里给固定种子的 `Random`，同一局每次都一样。这是本项目领域层的既有做法
  （`domain/engine/` 下的纯函数一律不自己取时钟、不自己取随机）。

**注意**：`PlayGame.kt:93` 的 KDoc 把这件事标成了「docs/02 约束 C-04」，
这是**错的**——`docs/02` 的 C-04 是「用户点头之前不提供帮助」。
准确出处是 `docs/02` 第 2.2 节正文与 `docs/01` 的 NFR-14。
源码本轮不动（改 `app/src/` 会让本轮全部测试与走查证据失效），
修正记在 `docs/01` 第 9 节 **GAP-09**，第 12 轮一并改。

**二、一局的状态是一个值，不是一串事件。**

`PlayRound` 的形状：

```kotlin
data class PlayRound(
    val gameId: String,
    val cells: List<String>,
    val order: List<String>,
    val step: Int = 0,
    val hint: PlayHint = PlayHint.NONE,
)
```

- `cells` 和 `order` 装的是**同一批字**，只是顺序不同：`cells` 是屏幕上从左到右
  从上到下的排列，`order` 是正确顺序。这一层不认识「数字」，只认识「相等」与「先后」。
- **没有 `wrongCount`、没有 `score`、没有 `startedAt`、没有 `userId`、没有 `id`。**
  AC-11.2（不给分数评级）与 AC-12.3（点错不扣分不计数不批评）在这里的守法不是
  「界面不显示」，而是**这个类里根本没有字段可以放**。三个点错分支只改 `hint`，
  `step` 单调不减——这一点由 `SchulteGridTest` 的 15 例守着。
- 「这个格子点过没有」**不存**，用 `order.indexOf(label) in 0 until step` 现算
  （`passed(label)`）。理由是：`step` 和「已点集合」是两个能互相矛盾的状态，
  一旦存两份，界面迟早显示自相矛盾的东西（比如某格既亮着又已经点过）。
  25×25 的比较成本在这个场景下可以忽略，用正确换性能划得来。
- 由此，`PlayHint` 只有三态：`NONE("")` / `ALREADY_DONE("这个已经点过了，换一个")` /
  `NOT_YET("这个还在后面，不急")`。**没有第四态能记下「错了几次」**，
  因为提示是一次性的、下一次点对就被清掉。

**三、单局结果不落库，靠的是「没有地方可落」。**

DR-09 的落地检查表（`docs/03` 第 5.4 节）逐项对照的是结构，不是纪律：

| 常见写法 | 本项目的实际情况 |
| --- | --- |
| 建一张 `play_record` 表 | `data/db/` 里**没有**这张表；DB 仍是版本 3，本轮**没有**新增迁移 |
| 把成绩写进 DataStore | `PlayViewModel` 里**没有**注入任何 store / repository |
| 起个协程异步写 | `PlayViewModel` 里**没有** `viewModelScope`，没有 `launch` |
| 结束时上报 | `domain/play/` 不 import 任何 Data 层类型（全目录只有两行 import，都是 `kotlin.random.Random`） |
| 「本次用时」总有地方算吧 | 有，但只活在 `Finished(game, round, seconds)` 这个**界面状态值**里；关掉界面就没了，这正是界面上一句「用时只在这里显示，关掉就没了。」的意思 |

**四、取时钟的次数也被算过。**

`PlayViewModel` 全程只读时钟**两次**：`start()` 一次（记下 `startedAt`），
完成的那一次 `tap()` 里一次（算 `secondsSince()`）。中间的每次点击**不读时钟**。
所以：

- 界面上的用时不会因为点得慢而跳数字（没有倒计时、没有计时器）；
- 「中间退出再进来」在数据上不产生任何痕迹——重进就是新的一次 `start()`，
  步数归零。这一点本轮在模拟器上实测过：中途退出再进入，
  界面回到「现在点 1」。

**五、`object` 目录，不预埋未完成的游戏。**

`PlayCatalog`（20 行）只有两个常量：`games = listOf(SchulteGrid.game)` 与
`first = games.first()`。**没有 `byId`、没有占位条目、没有 `enabled` 开关**。
`PlayCatalogTest` 会遍历 `games` 逐条出局，所以往目录里塞一条不能玩的游戏会让测试红。

**代价**

- **加第二个游戏时如果要新的交互形式**（比如需要按键间隔时间、需要多指触控），
  这个 6 字段的 `data class` 会长胖或需要第二个出局函数类型。届时应当**先改
  `docs/03` 第 3 节的形状再动代码**，而不是在 `SchulteGrid` 里加特例。
- **`PlayRound` 的 `cells` 与 `order` 装同一批字**，这个约束靠约定与测试守着，
  类型系统没有表达它「是同一个多重集合」。代价可接受：出局只有一处（`deal`），
  且 `SchulteGridTest` 有专门的例子。
- **首页只有一个游戏可点**，用户看不出这是个框架。这是 RC-010 第三条接受的代价。
- **`longestSeconds` 是上限不是目标**（`PlayGame.kt:115-121` 的 KDoc 写明了）：
  舒尔特方格取 180 秒，界面上的说法是「一局最多 3 分钟」。它**不做倒计时**、
  到点了也不会打断用户——它唯一的用途是让那句话里的数字有出处。
  这个字段将来很容易被误用成及格线，误用前请先看 RC-010。

**第 12 轮更正**：本条「决策」第二、三点关于 `PlayRound` 形状的部分**已被 ADR-016 取代**——
`PlayRound` 改成了 `sealed interface`（两个实现），点过的格子改由 `markOf(index)` 回答
（三值 `CellMark`），`PlayHint` 扩到四态。因此「加第二个游戏不新增类型」这句话
**不成立**：实测下来要动的是 `PlayRound` 与界面分支；`PlayGame` 那六个字段本身确实一个没动。
本条的其余判断仍然有效：游戏不写成 `interface`、单局结果靠「没有地方可落」守法、
`PlayCatalog` 不预埋未完成的游戏、`longestSeconds` 是上限不是目标。

**状态**：部分被 ADR-016 取代（第 11 轮采纳，第 12 轮更正）。

## ADR-016：单局状态从「一个 data class」改成 sealed interface（第 12 轮）

**背景**

ADR-015 在「代价」里写了这么一句判断：加第二个游戏时不该动框架。
第 12 轮真的加了第二个游戏（找出一样的，`domain/play/FindPair.kt`），
把这句话拿到实测里验一遍。结论是**一半成立**：

| ADR-015 的说法 | 第 12 轮实测 |
| --- | --- |
| `PlayGame` 那六个字段（`id`/`name`/`howTo`/`columns`/`longestSeconds`/`deal`）够用 | **成立**，一个字段没动、一个没加 |
| 加游戏不需要新增类型 | **不成立**，`PlayRound` 必须从 data class 改成 sealed interface |
| `PlayCatalog` 加一行 | **成立**，只加了一行 `FindPair.game` |
| 界面不用动 | **不成立**，`PlayScreen` 多了选择页与按类型分支，`PlayVoice` 从固定句式变成穷举 `when` |

所以 ADR-015 的「决策」第二、三点被本条取代，其余（游戏不写成 interface、
单局结果靠「没有地方可落」守法、`PlayCatalog` 不预埋未完成的游戏、
`longestSeconds` 是上限不是目标）继续有效。

**决策**

**一、`PlayRound` 是 `sealed interface`，不是「一个带可选字段的 data class」。**

第 11 轮它是 `data class PlayRound(gameId, cells, order, step, hint)`。
最省事的改法是往上加字段：`pairLabel: String? = null`、`firstPick: Int? = null`、
`solved: Boolean = false`，然后靠 `order.isEmpty()` 判断这是哪个游戏。**没这么做。**

理由是那两个方向会互相污染：一个只有舒尔特才有的字段，在找一样的里必须带一个
没意义的值——`order = emptyList()`、`step = 0`，于是「步数」这个概念在第二个游戏里
以假数据的形式存活下来。这种字段是**假功能的温床**：任何一处后来写了
「步数 >= 10 就提示一下」，找一样的就会跟着触发，而代码里看不出这不对。
改成 sealed 之后，找一样的**根本没有 `step` 这个属性可以读**，编译器直接拦住。

公共的五件事定在接口上，两个游戏各自带自己的字段：

| 成员 | 是什么 | 谁算出来的 |
| --- | --- | --- |
| `gameId: String` | 哪一局 | 存字段（出局时写入） |
| `cells: List<String>` | 盘面上那几格，按位置 | 存字段 |
| `hint: PlayHint` | 上一句话，没有时是 `NONE` | 存字段 |
| `finished: Boolean` | 这一局是不是完了 | **算出来的**：`OrderRound` 是 `step >= order.size`，`FindPairRound` 是 `solved` |
| `stepsToFinish: Int` | 一共几步 | **算出来的**：`order.size` / 常量 `2` |
| `tap(index): PlayRound` | 点一格，返回新的一局 | 每个实现自己给 |
| `markOf(index): CellMark` | 第 index 格该画成什么样 | 每个实现自己给 |

`finished` 与 `stepsToFinish` 刻意**不存成字段**：存了就有了第二个真相
（`step` 与 `finished` 可以是矛盾的），而算出来的值不可能不一致。

**二、`markOf(index)` 取代「按字查是不是点过」。**

第 11 轮 `PlayGrid` 判断一格是否该压暗的办法是拿它的字去查 `order` 里的位置
（`round.passed(label)`）。这在只有一个游戏时是对的，因为 1~25 每个数只出现一次。
找一样的盘面上**有两个字完全相同**——按字查会把两张一起压暗，
用户点下第一张就会看到「两张都好像成了」，而实际上还差一步。这是会误导人的假反馈。

所以判据从**按字**换成**按位置**：`markOf(index)`，返回三值 `CellMark`
（`PLAIN` / `PICKED` / `DONE`）。`PlayGrid` 那次改动是**一行**：

```kotlin
mark = round.markOf(index),   // 原来是 round.markOf(label)
```

`markOf` 越界返回 `PLAIN`，不抛异常——它是画图时问的，画图不该崩。

**三、`tap` 的返回类型协变收窄。**

`PlayRound.tap(index): PlayRound`，但两个实现把它收窄成自己的类型
（`OrderRound.tap(index): OrderRound`、`FindPairRound.tap(index): FindPairRound`）。
这让纯领域层的测试能直接写 `round.tap(3).step`，不用 `as` 强转；
而界面上拿到的是接口类型，**界面这一层一次强转都没有**。

代价是测试里凡是写 `round.copy(...)` 造状态的断言必须重写——`copy` 是 data class 的
成员，接口上没有。本轮改测试就是这么改的（见 `records/02` RC-011 第七节）。

**四、界面按 `round` 的类型分支，穷举 `when`，不留 `else`。**

`PlayVoice.headline` / `doneLine` / `doneNote` 三处都是 `when (round) { is OrderRound -> ...; is FindPairRound -> ... }`。
不留 `else` 是刻意的：第三个游戏进来时编译器会在**这三处**报出漏掉的分支，
逼着写它的人想一遍「这个游戏该说哪句话」，而不是悄悄沿用上一个游戏的措辞。
「现在点 3」这句话对找一样的就是错的，只是不会崩而已——这类错必须被编译器抓到。

**五、找一样的**不报用时**。

舒尔特的结束卡说「这一局用了 1 分 37 秒」，找一样的只说「那两张「桔子」都找到了」。
不报用时的理由不是偷懒：找一样的**没有计时**（没有倒计时、没有起始目标），
按「从开始到点完的停留时长」报一个数，实际效果是把这件不想让人较劲的事
变成一次计时考核——而用户看得见那个数，就会开始跟自己比。
`PlayVoice.doneLine` 里两个分支的措辞不同，正是这条决策的落点。

**六、选择页只在有两个以上游戏时出现。**

`PlayViewModel` 的 `initialState()`：目录里只有一个游戏时直接进 `Ready`，
两个以上才进 `Choose`。第 11 轮那个「只有一个游戏可点」的形态与文案因此一字未改，
新页面不凭空多出来。这也是 `PlayCatalogTest` 遍历 `games` 的用处：
它保证目录里没有不能玩的条目，而目录的长度决定首页会不会多一步。

**取舍与代价**

- **两个 `PlayRound` 实现的公共代码变多了吗**：没有。共享的是接口的默认语义
  （`markOf` 越界 → `PLAIN`）与 `PlayHint` 枚举，没有共享的实现逻辑。
  如果第三个游戏与舒尔特共用「按顺序点」的规矩，那时才该考虑抽一层基类——
  现在抽是提前抽象。
- **`CellMark` 是三值枚举而不是布尔**：用布尔（点过/没点过）表达不了
  「点了一张、还等另一张」这个中间态，而找一样的**必须**让用户看见它。
  三值比两值多花一个 `when` 分支，换来的是「第一张点下去有反馈」。
- **`PlayRound` 变动后测试的改动面不小**：本轮 `PlayVoiceTest`、`SchulteGridTest`
  里凡是 `PlayRound(...)` 直接构造或 `copy` 的地方都改写了。
  代价是真的，但只发生在「加游戏」这种低频动作上，且改错会被编译器和测试抓住。
- **仍然不写只有一个实现的接口**（`docs/02` 第 2.2 节、`docs/01` NFR-14）：
  `PlayRound` 有**两个**实现才写成接口，`PlayGame` 到现在仍是 data class。
  这条纪律没有因为「反正以后会加游戏」而放松。

**关联**

- `docs/01` FR-11（脑力互动的验收标准 AC-11.1~11.4）、FR-12、DR-09；
- `docs/03` 第 3 节（形状）、`records/02` RC-011（这次变更的由来与全部改动）、
  `records/03` ADR-015（被本条部分取代的那一条）；
- 代码：`domain/play/PlayGame.kt`（`PlayRound`/`PlayHint`/`CellMark`）、
  `domain/play/FindPair.kt`、`domain/play/SchulteGrid.kt`、
  `ui/play/PlayScreen.kt`（第 165~198 行）、`ui/play/PlayVoice.kt`、`ui/play/PlayViewModel.kt`。

**状态**：已采纳（第 12 轮）。


## ADR-017：用户可见文案进同包的 `*Voice.kt`，不进 `res/values/strings.xml`（第 16 轮）

**背景**

`docs/01` NFR-17 原文是：「**当前仅中文；所有用户可见文案必须进资源文件或集中常量，不散落硬编码**」（`docs/01:399`）。它一直挂在 `docs/01` 的 GAP-04 行上（计划第 16 轮），本轮去落实。

落实之前先量了一遍现状。写了一条机械守卫（形状见「决策二」），在**还没改任何代码**的仓库上跑，它当场报出**界面代码里有 138 处中文文案就地写着**：

| 文件 | 处数 |
| --- | --- |
| `ui/settings/SettingsScreen.kt` | 49 |
| `ui/onboard/OnboardingScreen.kt` | 39 |
| `ui/talk/TalkScreen.kt` | 34 |
| `ui/home/HomeScreen.kt` | 9 |
| `ui/talk/TalkViewModel.kt` | 5 |
| `ui/talk/StarterCard.kt` | 1 |
| `ui/common/ElderComponents.kt` | 1 |

全文在 `build/offenders16.txt`（139 行 = 1 行断言文字 + 138 处）。`build/` 由 `.gitignore` 覆盖，不提交；这 138 行是**这条守卫在真能抓到东西**的证据，抄进了 `records/04` 第十四节。

NFR-17 自己留了两条路：「资源文件」**或**「集中常量」。必须选一条，不能两条都沾一半。

**决策**

**一、进同包的 `*Voice.kt`，不进 `res/`。**

`ui/` 下每个界面配一个同包 `object`。本轮新增四个：`ui/common/CommonVoice.kt`（44 行）、`ui/home/HomeVoice.kt`（36）、`ui/onboard/OnboardVoice.kt`（97）、`ui/settings/SettingsVoice.kt`（115）；已有的三个继续用：`ui/home/InterventionVoice.kt`、`ui/play/PlayVoice.kt`、`ui/talk/TalkVoice.kt`（后者由 109 行扩到 171 行，+62）。

移完之后 `app/src/main/res/` 里**一条用户可见文案都没有**。这一点其实有旧账可查：第 12 轮收口 GAP-07 时实测过「15 个宣称词在 `app/src/main/res/` 命中 **0 行**」——文案本来就一直不在资源文件里。

**二、给 NFR-17 一个机械形式，而不是一句纪律。**

新增 `app/src/test/java/com/fortheelder/ui/UiCopyPlacementTest.kt`（85 行，包 `com.fortheelder.ui`），规则只有三条：

1. `ui/` 下名为 `*Voice.kt` 的文件可以自由写中文——那是它们的职责；
2. 其余界面文件里**不允许出现含中文的字符串字面量**（正则 `"([^"\n]*)"` 抓单行字面量，再判 CJK 区间 `[\u4e00-\u9fff]`）；
3. 确有理由就地写在界面代码里的行，必须在该行留下 `copy-ok: 理由`——**理由写在代码里，不是写在记录里**。

外加两条工程细节：注释行（`//`、`*`、`/*` 开头）整行跳过，行尾注释先 `substringBefore("//")` 再扫字面量；源码目录由 `app/build.gradle.kts:96-98` 的 `tasks.withType<Test>().configureEach { systemProperty("forthelder.mainSrc", …) }` 交进测试 JVM，**属性缺失时 `error(...)` 直接让用例失败，不跳过**。

**三、守卫只管 `ui/` 层，`domain/` 层是评审项，不是守卫项。**

这条是刻意的。`domain/` 是**产文案的地方**，写一条「domain 里不许有中文」的守卫是错的——它会逼人把文案挪到 `ui/` 去假装领域层干净，而产文案的逻辑本来就是领域逻辑（`Encouragement.forAction(action)` 的输入是那一步的原文）。逐文件盘点过一遍：`domain/` 的文案都落在具名常量（枚举构造器实参、`object` 的属性、`private val sentenceEnds` 这类清单）或唯一的格式化函数里，符合 NFR-17 的「集中常量」。**但没有机械形式可判**，所以它作为**评审项**记账（`docs/01` GAP-04 行如实写），不冒充「有守卫」。

**四、三条防假绿断言。**

守卫自己的失效方式比违规更难发现：路径写错、目录空了、正则坏了，它都会**绿**。所以用例里有三句断言不是判违规的，是判自己还活着的：扫到的界面文件 ≥ 10 个、至少扫到一个 `*Voice.kt`、扫过的代码行 > 500。本轮实测这三个数分别是 24 / 7 / 3447 行中的 2784 行（非 Voice 部分）。

**理由**

1. **禁用词的机器扫描建立在「文案是 Kotlin 常量」这个前提上。** AC-11.1 是**全 App** 规则，它的机械形式是「逐词扫描 `app/src/main/java/`」，扫描的实现（`ClaimWords.violations`）与守着文案的四组用例（`CompanionVoiceTest` 12 例、`InterventionVoiceTest` 16、`PlayVoiceTest` 15、`TalkVoiceTest` 16）都在 Kotlin 里。文案一旦搬进 `res/values/strings.xml`，这套扫描就**扫不到它**，等于把 AC-11.1 的覆盖面悄悄缩小一圈；要补回来得另写一套 XML 解析扫描。用 `*Voice.kt` 则一步都不用改：搬的是位置，不是语言。
2. **`*Voice.kt` 能接收参数，`strings.xml` 不能。** 现有文案大量是函数而不是常量：`PlayVoice.doneLine(round)` 按局面分支、`TalkVoice.kindLabel(kind)` 把枚举变成人话、`Encouragement.forAction(action)` 把用户那一步的原话嵌进回话。`strings.xml` 的 `%s` 占位符与 `plurals` 表达力弱得多，且**编译期不检查参数个数与类型**——写错一个占位符是运行时崩或串位，不是编译错。
3. **拼写错误可以在纯 JVM 上断言，不需要 Robolectric。** `app/src/test` 现在是 26 个文件 / 4540 行，全部跑在 JVM 上（NFR-12 实测无 Robolectric、无真机依赖）。`TalkVoiceTest` 之类直接断言字符串常量，秒级完成。文案进 XML 后这些断言要么全部改造成 Robolectric（引入一套新依赖，与 C-06「依赖尽量少」冲突），要么消失。
4. **本版本只承认一种语言。** NFR-17 开头就写着「当前仅中文」。为一句还没成立的需求先把文案搬到 XML，是**提前抽象**——与 NFR-14「不写只有一个实现的接口」同一条纪律。

**代价**

- **以后真要多语言，成本比现在高。** 那时要动的是 Kotlin 源文件而不是替换一份 XML；Android Studio 的翻译编辑器、未翻译项检查也帮不上忙。真要多语言时，这次决定要重开一次 ADR（把文案从 `*Voice.kt` 迁到 XML，并把守卫的方向反过来：`ui/` 里**不许**有中文，包括 `*Voice.kt`）。
- **放弃了「资源文件」那一半，只兑现「集中常量」那一半。** 记账时必须这么说，不能宣称「文案已进资源文件」——那是假的。
- **`domain/` 层没有机械守卫，只有评审。** 这是本轮唯一一处「靠人看」的地方，它随时可能腐化：下一次往 `domain/` 里插中文时，没有任何东西会红。`docs/01` GAP-04 行如实写着这一点。
- **集中文案不会让代码变短。** 实测：界面文件（`HomeScreen` / `OnboardingScreen` / `SettingsScreen` / `TalkScreen` / `StarterCard` / `ElderComponents`）净减 **25** 行，`*Voice.kt` 净增 **354** 行（新增 4 个文件 292 行 + `TalkVoice.kt` +62），`ui/` 层净 **+329** 行。`app/src/main/java` 由 64 个 `.kt` / 7066 行变成 **68 个 / 7413 行**。**这是集中化的真实票价**：多一个间接层，换来「文案在哪里」有唯一答案。
- **一处重复被保留下来。** `TalkVoice.kt:98` 那句「「${wish.term}」在下面「常伴记住的事」里，随时能删。」与 `rememberedSection` 里的话重复出现。本轮是**搬家**轮，一个词都没改；重复是搬家前就有的，留到需要改那句话的时候一起处理。

**与 NFR-14 的关系**

「不写只有一个实现的接口」管的是**接口**，本条管的是**常量容器**。`*Voice.kt` 全是 `object` + `val`/`fun`，没有任何多态——不为将来可能的第二种措辞风格预留 `interface Voice`。

**关联**

- `docs/01` NFR-17（`:399`）、GAP-04；`docs/02` 第 9 节 D-09、第 5 节规则一/规则二（文案与判断同处、禁用词用纯函数守）；
- `records/02` RC-012（排期顺延）、RC-013（GAP-04 的拆分口径）、`records/04` 第十四节（守卫先红后绿的完整证据）；

**顺延**：第 15 轮原计划写「第三个游戏」的 ADR-017，因本轮先把文案与标点两件事收口，**第三个游戏的 ADR 顺延为 ADR-018**（决定与理由见 `records/01` 第 16 轮与 `records/02` RC-012）。

## ADR-018：第三个游戏的筛选规则——「说得成一个点格子的动作」且「不让领域层认识时钟」（第 17 轮）

**背景**

脑力互动这一块从第 11 轮起就是这么搭的：`PlayGame` 是**数据类**（`domain/play/PlayGame.kt:221`），描述一个游戏是谁、格子怎么摆、怎么出一局；`PlayRound` 是 **sealed interface**（`PlayGame.kt:68`），描述「一局走到某一步是什么样」。界面只认 `PlayRound` 的这七个成员：`gameId` / `cells` / `hint` / `finished` / `stepsToFinish` / `tap(index)` / `markOf(index)`——它不认识任何一条具体规则（`PlayGame.kt:50-67`）。

这套结构的**交互面只有一个动词**：`PlayRound.tap(index)`（`PlayGame.kt:91`）。用户在一局里能做的全部事情就是「点某一格」——界面上没有输入框、没有拖拽、没有计时器（`ui/play/PlayScreen.kt:181` 只做一件事：把 `round.cells` 按 `game.columns` 切行铺成网格）。

第 12 轮加进第二个游戏（找出一样的）之后，`records/02` RC-012 写下一条预判：

> 三个候选游戏（记一记/翻牌、反应速度、连续减七）**每一个都会让领域层认识时钟**，直接破坏 DR-09「领域层不认识时钟」。

本轮就是来处理这句话的。处理的结果是：**这句话一半是错的**，而错的那一半正是第三个游戏的落地路径。下面说的都是这一轮的实测，不是设想。

**决策**

**一、把「一个游戏能不能进这个框架」写成一条可判定的筛选规则，而不是逐个候选凭感觉定。**

> 一个游戏能进 `PlayCatalog.games`，当且仅当它同时满足两条：
>
> 1. **它在一局里的全部交互，说得成一个「点某一格」。** 也就是 `PlayRound.tap(index)` 一个动词就够——不需要输入框、不需要拖拽、不需要第二个动词（比如「翻过去」「盖起来」）。
> 2. **判断对错、判断结束，都不需要读时钟。** 也就是 `domain/play/` 里不出现 `AppClock`、不出现 `System.currentTimeMillis()`；用时（如果哪个游戏要报）只能在界面层由 `PlayViewModel` 现算，算完只活在一屏之内。

这两条**不是新发明的约束**，是把已经存在的事实明写成筛选条件：`tap` 本来就是唯一的动词，用时本来就由 `AppClock` 在界面层现算而不是进 `domain/`（`PlayGame.kt:61-64` 写明了这一点）。区别在方向：第 11、12 轮是「先挑一个游戏、再看结构撑不撑得住」，本轮是「先用结构筛一遍候选」。

**二、在筛选规则下，三个候选的判定结果**不**一样。**

| 候选 | 全部交互说得成一个「点格子」吗 | 判对错、判结束要读时钟吗 | 判定 |
| --- | --- | --- | --- |
| 反应速度 | 说得成 | **要——它比的就是「多快」** | **判退**（不是顺延） |
| 记一记（翻牌） | **说不成**——「盖着的格子」得有个说法 | 要（「翻开后停多久盖回去」） | **顺延** |
| 算一算（从 100 开始每次减 7，三选一） | 说得成 | 不要 | **本轮落地** |

**三、反应速度是判退，理由写清。**

它全部的内容就是时间。屏幕上必然要报秒数——不报，用户就不知道自己反应了多久，游戏也就不成其为游戏。而要在 `PlayRound` 里报一个用时，得先有「用时」这个量，它只能来自时钟。这一条与两条已采纳的验收口径正面冲突：

- **AC-11.3**（`docs/01:328`）：「单局时长 ≤ 3 分钟；结束时不得以『再来一局』诱导续玩」，其字段 KDoc 里还额外写死「**不做倒计时**」（`PlayGame.kt:235-239`）。一个以「多快」为规则的游戏，屏幕上出现秒数是**规则的必然，不是可以删掉的装饰**——删了它游戏就没了。
- **AC-11.2**（`docs/01:327`）：「不得给出分数评级、不得与『同龄人』比较、不得给出能力结论」。反应速度是**天然的排行素材**：快和慢自己就能排序。本项目不落库、不排行（DR-09），那这个游戏剩下的唯一读法就是「今天比昨天慢」——恰恰是这个应用最不该制造的那种读法。

**判退不等于说它没价值**，而是说它与本应用的立场不相容。这条如实进 `records/02`（RC-015 的前半）；`docs/01` **不为它新增 FR 条目**——留一个永远不会实现的 FR 编号，比不留更容易变成假账。

**四、记一记是顺延，而且它欠的账金额已知。**

它卡住的地方不在时钟，在**界面契约**。现在的界面直接读 `round.cells` 渲染（`ui/play/PlayScreen.kt:181`），而「这一格现在是盖着的」这件事在数据上**无处表达**：`cells` 的含义是「摆在格子上的字」，没有第二个层次可以说「但你现在看不见它」。要落地，下面两条至少要付一条：

- 给 `PlayRound` 加一个「这一格现在该显示什么」的查询（`cells` 退回成「这一格的底牌是什么」），并加一个**非 `tap` 的阶段转换动词**——用户得有个动作能把牌盖回去；或
- 让时间决定什么时候盖回去——那就直接踩 DR-09。

两条都不是小改：前一条要动 `PlayRound` 的公共面（第 12 轮加 `markOf` 时付过一次这种账），后一条要推翻一条已采纳的架构约束。所以**值一个专门的 ADR**，本轮不做，也不留半个「翻牌」的半成品在目录里（AC-11.4：目录里有一条点进去玩不了的东西，比目录里只有两条糟得多）。

**五、算一算把心算题做成三选一，于是它过了筛选。**

「从 100 开始每次减 7」这件事本身既不需要打字、也不需要计时：

- **三个选项而不是输入框** ⇒ 「答」仍然只是 `tap(index)`，**`PlayRound` 的公共契约零改动**；
- 判对错只比较两个整数（`current - deduction` 是不是选中那个） ⇒ 不需要时钟；
- 5 道题的**全部题面在出局时就算好**（`deal(Random)` 是纯函数）——因为 `tap` 没有 `Random` 可传，下一题的选项必须预先算好；同一个种子出同一局，测试因此能造出确定的局面。

顺带它还避开了一个已经挂着的老缺口：**GAP-02**（`docs/01:462`，中文输入在 `adb shell input text` 下只能送 ASCII，「用户用中文输入法打字」这条路径从未被任何人验证过）——这个游戏压根不需要打字。

**六、`markOf` 在这个游戏里恒为 `PLAIN`，这是刻意的，不是漏写。**

`CellMark` 的三态（`PlayGame.kt:39-48`）是第 12 轮为「按顺序点」和「找一样」两个游戏造的：`PICKED` 在找一样里意思是「这张选中了、还没配上」。算一算**没有这个中间态**——答对立刻换下一题，答错状态一格不变。把 `PICKED` 用在这里语义是错的；而给答过一次的选项留一个陈旧高亮更糟（用户会以为那一格还得再点它）。所以这个游戏只用到三态里的**一态**。

这一点本轮**如实记下**：`CellMark` 这个抽象目前只服务前两个游戏，它没有在本轮被证明是通用的。

**理由**

1. **把筛选规则明写出来之后，「顺延」和「判退」都变成可复核的。** RC-012 的预判有一半被本轮证伪——连续减七的**缩减形式**（三选一，而不是输入框）不需要时钟。如果本轮只留一句「感觉这个行那个不行」，下次没人判断得出该不该重开；留一条写死的规则，下一个候选可以对着它逐条判。
2. **扩 `tap` 比加一个游戏贵得多。** 加一个动词意味着 `PlayRound` 的每个实现都要应答它（第 12 轮加 `markOf` 时已经付过一次），`PlayViewModel` 的三态状态机要重新过一遍，设备用例要全量重跑。用「三选一」把新规则塞进既有的那个动词，界面上**一行都不用改**——本轮实测证实了这一点。
3. **不报用时是这个应用的一贯取舍，不是这一轮的惰性。** 现在三个游戏里只有舒尔特报用时（`PlayVoice.kt:80-83`）。找一样不报的理由 ADR-016 已经论证过（用时长主要反映「看不看得清」，报出来更接近一次视力测评）；算一算同理，而且更明显：报「算 5 道用了 40 秒」几乎就是一次心算测评——而 AC-11.1（`docs/01:326`）明禁把这类话讲出口。
4. **编译器替我们盯着新规则的措辞。** `PlayVoice` 里三处按规则分支的地方用的都是 `when` 而不是 `if`（`PlayVoice.kt:60` / `:80` / `:92`），加一种 `PlayRound` 实现时编译器会**当场报出漏掉的分支**。这是 ADR-016 把 `PlayRound` 改成 sealed interface 时想要的连带效果，**本轮第一次真的兑现**：三个 `when` 各报一次，补完才编得过。散落的 `if (round is X)` 不会有这个效果。

**代价**

- **这是「用约束选游戏」，不是「用游戏找约束」。** 三个候选里两个没进来，进来的那个还是**改小了**才进来的（心算题从「输入答案」缩成「三选一」）。诚实的说法是：本轮**没有**证明这套结构能装下更多种类的游戏，只证明了它能装下第三个**同形**的游戏。结构真正的承载力上限仍然没有测出来。
- **`CellMark` 三态在本游戏只用到一态。** 三态的价值没有被第三个游戏加强，反而被指出「它可能只是前两个游戏的并集」。若第四个游戏也只用到其中一两态，应当重开一次 ADR 讨论这个枚举要不要拆。
- **记一记的账继续欠着，而且是一笔金额已知的账。** 代价写在决策四里：将来落地要么扩 `PlayRound`（加一个「这一格现在显示什么」的查询 + 一个非 `tap` 的阶段转换），要么推翻 DR-09。这不是「早晚能做」的模糊欠账。
- **反应速度被排除在这条产品线之外**（除非推翻 AC-11.2 / AC-11.3）。它记在 `records/02` 里，`docs/01` 不为它留 FR 编号。
- **`longestSeconds = 180` 直接取到了 AC-11.3 的上限。** 于是规则页会说「一局最多 3 分钟」。这个数字是**上限不是目标、不是及格线**（`PlayGame.kt:218-219` 已经写死这条口径），但它确实比另两个游戏更贴近上限：若某天要收紧 AC-11.3，这个游戏是第一个受影响的。

**与既有条款的关系**

- **不修改** AC-11.1~11.4、AC-12.1~12.4：算一算不落库（DR-09）、不报用时、不排名、不计数，全部照旧。
- **补充** `docs/01` FR-16（算一算）+ AC-16.1~16.4，并接进 US-08 的功能列与追溯矩阵第 17 行。
- **部分更正** `records/02` RC-012 那句「三个候选每一个都会让领域层认识时钟」，以 RC-014 记下更正。
- **AC-11.4 的条目数 2 → 3**（`docs/01:329` 里那句「注册表现在有 2 条」本轮改写）。

## ADR-019：无障碍语义只挂「位置固定的节点」；标题与页码合成一个块；「新节点会不会被朗读」本项目不碰（第 18 轮）

**背景**

无障碍这件事在本项目里的来历，本身就是一条证据。`docs/01` 从第 1 轮到第 17 轮，跟「读屏 / TalkBack / 语义标签」有关的**从头到尾只有 GAP-05 这一行缺口**：可访问性真正有编号的需求只有两条——NFR-05（对比度 ≥ 4.5:1）与 NFR-06（不依赖颜色单独传达信息），两条都只管**看得见**的那一面。语义这件事**没有任何 FR / AC / NFR 承诺过它**。它排了八轮才排上，原因就在这里：它不是一条被承诺的需求，只是一个被记下来的缺口，而排期总是被有编号的需求挤走。

第 18 轮第一次给它落地：新建 `ui/common/A11y.kt`（58 行 / 5 个 `Modifier` 扩展），挂到 9 个点，配 8 个测试（3 个 JVM 源码级守卫 + 5 个设备上的语义树用例）。这些工作**全部落在实现层与验证层**，没有改动任何已基线需求（这一点单独记在 `records/02` RC-017）。

本条记的是**边界**——哪些节点加了标签、哪些节点**刻意不加**、为什么合成一个块而不是两个，以及写测试时踩到的一条库层事实。之所以要单独成条：`A11y.kt:22-23`、`A11y.kt:42` 与 `docs/03` §4.7（含 `:652` 那条）**都引用本条**，它不落地就会留下悬空引用。

**决策**

**一、语义标签只加在两类节点上：位置固定的区域，与可数的结构。新出现的节点一律不加播报区。**

加了的（本轮实测的位置）：

| 修饰符 | 加在 | 位置 |
| --- | --- | --- |
| `heading()`（表头标题） | `ElderHeader` 的表头 `Text` | `ui/common/ElderComponents.kt:110`。四屏各一：首页 / 对话页 / 游戏页 / 设置页 |
| `heading()`（卡片标题） | `SectionCard` 的标题 `Text` | `ui/common/ElderComponents.kt:142` |
| `heading()`（小节标题） | `SectionTitle` 的 `Text` | `ui/common/ElderComponents.kt:157` |
| `liveRegion = Polite` | 题面 / 提示行 / 结束语 | `ui/play/PlayScreen.kt:142` / `:153` / `:167`。全仓**恰好这 3 处** |
| `collectionInfo` | 棋盘 `Column` | `ui/play/PlayScreen.kt:191` |
| `collectionItemInfo` | 单个格子 | `ui/play/PlayScreen.kt:250` |

三处 `liveRegion` 的共同点只有一个：**节点一直在、变的只是字**。题面在同一位置从「现在点 1」换成「现在点 2」，提示行始终占着位置（点错时才有字），结束语是同一块区域的文字替换。这类「原地换字」有明确的触发时刻，播报才不会变成噪音。

**刻意不加的两处，要写清楚是「不知道」而不是「知道不会」：**

- **首页问候语**与 **`TalkScreen` 的结果卡**都**不加** `liveRegion`。它们与上面三处刚好相反：是**新出现的节点**（整块在第一次合成时才出现）。而「新出现的节点是否会请求朗读」这件事——比如 Android 对「新节点带 liveRegion 自动进焦点范围」的处理——本项目**没有实测过**：没有做过 A/B 对照，也没有真机戴着读屏软件观察过。**没实测就不加**：这里的选择是「不去碰这个不确定的行为」，**不是**「已知它不会被读」。
- **全仓没有一处 `onClickLabel`。** 本项目的可点元素自带说明文字（例如返回按钮的 `contentDescription = CommonVoice.back`、「返回上一页」），再加一层 `onClickLabel` 会是多出来的维护点，而且说不出它比按钮文字多给了什么。这条留待将来真的发现了缺口时再改，现在不提前加。

**二、`heading()` 与 `stateDescription` 合成同一个 `semantics {}` 块。**

`asScreenTitle(state: String? = null)` 因此**只有一个** `semantics {}`（`A11y.kt:32-35`）：块里先 `heading()`，`state` 非空时再给一个不显示的 `stateDescription`（引导页三页会传「第 2 页，共 3 页」这类补充状态）。页码是**参数**传进来的，不是叠第二个块。

- **说得清的理由只有一条**：标题与页码从此**只有一处入口**，不会各自漂移。
- **「同一节点上叠两个 `semantics` 块会让语义节点分裂成两个」这句话，本项目没有实测过。** 没有 A/B 对照过两种写法在 Compose 语义树与平台层 `AccessibilityNodeInfo` 里各是什么样。所以本轮的选择是**根本不去碰这个不确定的行为**，而不是「已知会分裂」。
- 这一句在第 18 轮末被**收窄过一次**：原先 `A11y.kt` 的 KDoc 与 `docs/03` §4.7 两处都把它当**已知事实**写（「会让语义节点分裂成两个」），收窄后两处都改成「本项目未实测、选择不碰」。`A11y.kt:22-23` 与 `docs/03` §4.7（含 `:652`）现在**都引用本条**的第 2 条。

**三、装饰性图标显式写 `contentDescription = null`，并在附近留 `a11y-decorative: 理由` 豁免标记。**

全仓**恰好 1 处**：`ui/home/HomeScreen.kt:158`（注释 `// a11y-decorative: 这枚箭头只是「这一行可以点」的视觉提示，文字本身已经把意思说完了`）→ `:162`（`contentDescription = null`）。理由是那枚箭头只是视觉提示，文字已经把意思说完了。

- 这一条不是口头约定，由源码级守卫 `A11yPlacementTest` 的**第二条规则**盯着：每个 `Icon(` 必须显式写 `contentDescription =`；写 `null` 要在**前 4 行 / 后 8 行内**留 `a11y-decorative: 理由`。守卫扫到 ≥3 个 `Icon(` 才不判假绿。
- 另外两处 `contentDescription` 是**带信息**的，不是装饰：`ui/common/ElderComponents.kt:98`（返回按钮 = `CommonVoice.back`）、`ui/talk/StarterCard.kt:102`（展开/收起 = `TalkVoice.expandStep` / `collapseStep`）。全仓 `Icon(` 共 3 处，`contentDescription` 也共 3 处，一一对上。

**四、`CollectionInfo` / `CollectionItemInfo` 没有重写 `equals`——写测试时不许拿 `expectValue` 去比它们。**

- **事实**（`javap` 查实 Compose UI 1.7.5 的字节码）：这两个类**都没有** `equals`，比较退化成引用相等。
- **后果**：用 `expectValue(CollectionInfo(r, c))` 写断言，**永远是红的**——每次构造出来的新实例都不可能等于节点上那个实例。这是「**永远红**」，不是假绿；但一个永远红的断言仍然会让守卫失去意义（写的人只会把它注释掉）。改法是**自造 `SemanticsMatcher` 按字段读值**（`A11ySemanticsTest` `:232-241`）。
- 顺带核对出另一个数：算一算棋盘的 `rows` 由 `(round.cells.size + game.columns - 1) / game.columns` **现算**（`ui/play/PlayScreen.kt:189`），结果是**1 行 3 列**，不是 3 行（测试原先误写成 3，已改 `A11ySemanticsTest:208-211`）。
- 这条记在这里的原因：它是一个**库层事实**，与「语义标签加在哪」无关；将来任何人写第二个涉及 `CollectionInfo` 的用例都会再撞一次，写在 ADR 里比埋在测试注释里更找得到。

**代价与诚实边界**

- **语义树里有标签 ≠ 有人用耳朵听过。** 本轮验的是 Compose 语义树与平台层 `AccessibilityNodeInfo`（仪器化测试里读的），**没有**任何一位真实用户戴耳机走一遍核心链路。所以本轮**没有**给读屏补一个需求编号（理由见 `records/02` RC-017）。
- **`announcesWhenItChanges()` 的三处里，提示行在「无提示」时仍是带 `LiveRegion` 的节点。** 本轮实测：空字符串的提示行**确实仍生成带 LiveRegion 的语义节点**。这是有意保留的（节点始终占位，才有「原地换字」这个触发时刻），但它也意味着「没有提示的时候」同样挂着一个播报区属性——这一点没有被单独验过它会不会引起多读。
- **装机走查看不见本轮的任何语义。** `uiautomator dump` 吐出的节点属性只有 17 个（`bounds/checkable/checked/class/clickable/content-desc/enabled/focusable/focused/index/long-clickable/package/password/resource-id/scrollable/selected/text`），标题、页码、行列、播报区**一个都不在里面**。结论：**语义只能靠仪器化测试里的语义树断言来验，不能靠装机走查**。走查脚本里因此**没有**为语义加任何断言。
- **装饰图标的豁免只覆盖了 1 处**，覆盖靠的还是那条机械守卫，不是人工巡检；守卫本身也有盲区（只在 `ui/` 一层，且阈值是「≥3 个 `Icon(`」才检查）。
- **九轮的账没有一次被补上**：本条只讨论「加在哪」，「覆盖到什么程度算够」仍然没有判据。

**与既有条款的关系**

- **不修改** FR-01 ~ FR-16、AC-1.x ~ AC-16.x、NFR-01 ~ NFR-17、DR-01 ~ DR-10 的任何编号与正文。第 18 轮对 `docs/01` 的全部改动只有两处：GAP-03 那一格补上「第 18 轮的预算去向」，GAP-05 那一行从「尚未添加」改成「已关闭」。

- 第 15 轮留下的「三条旧实测」口径**本轮作废**，原委见 `records/01` 第 18 轮条目。

## ADR-020：屏幕上不写无法兑现的硬上限——「一局最多 N 分钟」改成「一局大概 N 分钟」（第 22 轮）

**背景**

`docs/01` 里三个脑力小游戏各有一行「单局时长 ≤ 3 分钟」的需求（AC-11.3 / AC-15.3 / AC-16.3），界面把游戏定义里的 `longestSeconds` 渲染成规则页上的一句承诺。这句话从第 17 轮起一直写作「一局**最多** N 分钟就完了。」（`PlayVoice.promise`）。

第 22 轮做的是「把屏幕上每句承诺回去找它的执行者」——找到这句时发现它没有执行者。

**事实核实（三条，都有出处）**

1. **`longestSeconds` 全仓只有两类读者**：`PlayVoice.promise`（拼那句承诺）、`PlayVoice.minutes`（取整成分钟数），以及测试。`ui/play/` 与 `domain/play/` 里 **`delay(`、`LaunchedEffect`、倒计时、超时结束一处都没有**（第 22 轮逐字 grep，结果为空）。
2. **没有任何代码路径会在超时后把这一局停下**。这一局只因为两件事结束：做完了（`PlayScreen` 的完成分支），或者用户自己退出（`leaveLabel`）。
3. **对照组「最多一天一次」是有执行者的**：`InterventionWindow.kt:26` 的 `maxGapMinutes = 1440` 与 `:47` 的 `coerceAtMost` 真的把两次干预卡在 24 小时以上，并且 `InterventionWindowTest` 守着它。

**结论**：「一局最多 3 分钟」在屏幕上是一句**无法兑现的硬话**——真玩到 8 分钟，App 既不会拦也不会停。它不是「保守的说法」，而是**写了一个不存在的机制**。

**决策**

**一、改文案，不加倒计时、不加超时中断。**

三条理由，按分量排：

- **撞自己发过的需求**：`docs/01:328` AC-11.3 明写「不做倒计时」。为了兜住一句文案而违反一条已基线的需求，是拿一个错误补偿另一个错误。
- **倒计时对大龄用户就是催促**：屏幕上跳动的秒数本身就是压力源。这个游戏的全部意义只是「手上有件事做」，把它变成计时挑战走反了方向。
- **机制比文案贵得多**：加倒计时要说清「到点之后是停还是等」、「做到一半被停掉算不算失败」、「读屏怎么播报剩余时间」——每一条都得新写需求与测试，而这些需求没有一条被人要过。

所以本轮**只改文案**：`PlayVoice.promise` 从「一局最多 N 分钟就完了。」改成「一局大概 N 分钟就完了。不用计时，也没有分数跟谁比；慢一点也不要紧。」——后半句顺带把「不用计时」「没有分数跟谁比」两件事写在屏幕上，它们本来就是这一版的设计边界（ADR-011）。

**二、`longestSeconds` 保留，不改名、不改值。**

它是**那句话里数字的唯一出处**。删掉它或改小它，屏幕上就会凭空多出一个没人量的数字——比留着一个名字不好听、但含义已被写清的字段差得多。第 22 轮做的是把它的语义在 KDoc 里写死（`PlayGame.kt:232-240`：首行从「这一局**最多**花多久」改成「这一局**大概**花多久」，并写明「它不做倒计时……是个估时、不是硬上限，界面上也不能被说成硬上限」）。

**本轮没有改名。**「longestSeconds 读起来像上限」这件事是真的，但改名会牵动三个游戏定义（`SchulteGrid` / `FindPair` / `SubtractSeven`）加四个测试文件，为一句命名付出的改动面大于收益。这笔账记在这里。

**三、「最多一天一次」不受影响。**

这条决策**只管没有执行者的硬话**。`InterventionWindow` 那条有 `maxGapMinutes = 1440` 与 `coerceAtMost` 真在跑，所以它继续写作「最多一天一次」。判据是**有没有东西执行它**，不是话软话硬。

**四、守卫落点。**

- JVM 源码级守卫：`PlayVoiceTest.thePromiseMakesNoHardLimitItCannotKeep`——硬话词表（`最多` / `上限` / `不超过` / `不会超过` / `保证` / `必须`）一个都不许出现，且必须同时含「不用计时」与「没有分数跟谁比」。
- 同文件另两条盯**数字出处**与**整句一致性**：`theNumberInThePromiseIsComputedFromTheGame`、`thePromiseSaysItHonestly`（取代原来的 `thePromiseTakesTheCeilingFromTheGameItself`）。
- 设备端：装机走查把规则页那句整串 dump 出来逐字比对（第 22 轮实测 `build/screens22.log`，该串在 y750-876）。

**代价与诚实边界**

- **「大概 3 分钟」仍是估时，不是测量值。** 180 / 120 / 180 这三个数是设计时定的余量，**全项目没有采过任何一局真实用时的样本**。本轮只验了「屏幕上的字与 `longestSeconds` 一致、且不含无法兑现的硬话」，**没有验这句估时对真实用户准不准**。
- **本轮没有对三个游戏做「玩满 N 分钟会发生什么」的实测**；「什么也不会发生」是从「没有定时机制」这条源码事实推出来的（证据是第 1 条 grep 为空），不是玩出来的。
- **`longestSeconds` 的名字仍会误导下一个读代码的人。** KDoc 已经写清是估时，名字没改。
- **词表守卫是黑名单，不是证明**：它只能拦住那几个词。以后换个说法（比如「不超过一刻钟」之外的句式）它拦不住——这类守卫的作用是钉住此刻的结论，不是证明文案永远正确。

**与既有条款的关系**

- **不修改** FR-01 ~ FR-16、AC-1.x ~ AC-16.x、NFR-01 ~ NFR-17、DR-01 ~ DR-10 的任何编号；AC-11.3 / AC-15.3 / AC-16.3 的「≤ 3 分钟」写法保持原样，只各加一句括注说明是估时口径（详见 `records/02` RC-019）。
- **不关闭任何 GAP**；**不改 GAP-03（性能基线）的状态**。
- 与 ADR-011（「不报用时、不设排名」）同向：那条说的是**不拿成绩评价用户**，本条说的是**不拿时限催促用户**，两者都是「不用数字制造压力」。

## ADR-021：规则页上的退路只开在规则页——用纯函数 `playStartState` 把「什么时候才摆这条路」钉住（第 23 轮）

**背景**

第 23 轮发现一条**没得走的回头路**：挑选页上不想玩可以回首页，但一旦进了某个游戏的规则页，发现不是想要的那个，除「开始」之外没有第二条路——只能退回首页、重进「玩一会儿」、重新挑。多花三步，且这多出的三步**没有任何理由**（这一局还压根没开始，什么都不会丢）。

给规则页补一条退路是显然的；难的是**它该在什么时候出现**。三种情形要分开处理：

| 处在 | 该不该有这条退路 |
| --- | --- |
| 规则页（`Ready`），且**有别的游戏可换** | **该有** |
| 规则页（`Ready`），但**应用里只有一个游戏** | **不该有**——没有第二个可换，摆出来只会让人点了没反应 |
| 玩到一半（`Playing`） | **不该有**——那一屏每格都在等人点，走掉就是半途而废 |
| 结束了（`Finished`） | **不该有**——那一屏只允许一个按钮（第 11 轮就钉下的断言 + AC-11.3） |

**决策**

**一、把「进这一页之后第一批状态」抽成纯函数 `playStartState(games)`。**

第 23 轮把它抽到 `PlayViewModel.kt` **类外**（`:154-159`，KDoc `:148-153`）：

- `games.size == 1` → `PlayUiState.Ready(first, canChooseAgain = false)`；
- 否则 → `PlayUiState.Choose(games)`。

**为什么抽出来**：这是整个决策里**唯一有分支的部分**，也是唯一「摆不摆这条路」的判据落点。把它做成**没有副作用、没有时钟、没有 `Random` 的类外纯函数**，就能被单测直接钉住（`PlayViewModelTest` 有三条专门盯它的分支），也不至于让 `Ready` 的构造被摊在状态机里、每换一次布局就得跟着改。

**二、`canChooseAgain` 是 `Ready` 状态自己的字段，不是界面的猜测。**

`PlayUiState.Ready` 加 `canChooseAgain: Boolean`（`:34`）。**界面层不自己判断**：`PlayScreen.ReadyPanel` 只按 `if (canChooseAgain)` 决定摆不摆（`:155-157`），摆或不摆**由状态决定**。理由：如果让界面去看 `PlayCatalog.games.size`，判据就散在两个地方了；以后若出现「某些游戏之间不能互相换」的规则，界面那一版会静默错掉。

**三、`chooseAgain()` 只在 `Ready` 态生效，另外两态一律不动。**

`:102` 的实现是「不是 `Ready` 就原样返回」。被调用时若不是 `Ready` 态，状态一动不动——**不抛错、不静默跳转**。这与 `choose(game)`（`:86`，只从 `Choose` 进）是同一种写法：**每条状态转换自己挡一道**，不依赖调用方守规矩。装机走查实测：点 `开始` 之后那一屏上 `换一个游戏` 计数为 0；单测实测：`Playing` / `Finished` 上调 `chooseAgain` 状态不动。

**四、`Playing` / `Finished` 都不加。**

- `Playing`：三款游戏那一屏每格都在等用户点，多一个按钮就多一处误触，且玩到一半走掉就是半途而废。
- `Finished`：`PlayScreenTest.kt` 有一条**第 11 轮就钉下的断言**「结束卡只有一个按钮」，`docs/01:328` AC-11.3 也这么要求。这条断言与设计意图**本轮一行未动**。

**五、两个标签分开写、各自写清方向。**

`PlayVoice.switchLabel = "换一个游戏"`（`:50`）与 `leaveLabel = "回去歇会儿"`（`:53`）放在同一个文件里，KDoc（`:43-53`）写明方向：`switchLabel` 是「这一个不想玩，换一个」→ 回**挑选页**；`leaveLabel` 是「这一局完了，回去歇会儿」→ 回**首页**。分开写、各写清，是为了不让后来人把两个方向混掉。

**守卫落点**

- JVM（本轮**新增**文件）：`app/src/test/java/com/fortheelder/ui/play/PlayViewModelTest.kt`（**311 行 / 16 例**）——`playStartState` 三条分支、`chooseAgain` 只在 `Ready` 生效（`Playing` / `Finished` 上调用不动状态）、`choose` 只在 `Choose` 生效、`start` / `tap` / `secondsSince` 既有行为。这是这个 ViewModel 的**第一份单测**。
- JVM（既有文件扩充）：`PlayVoiceTest`（15 → **18 例**）——两条词表扫描加上 `switchLabel`；新增 `theSwitchLabelBacksOutInsteadOfPushingForward`（这一句必须是**往后退**，不含「再来 / 继续 / 下一局 / 再玩」这类往前推的词）。
- 设备端：`PlayScreenTest`（5 → **6 例**）——「规则页上可以换一个游戏而开始之后就没有这条路了」。**既有断言一行未动**。
- 装机走查：`build/probe23.py`（从 `pm clear` 起步），实测 `开始` 与 `换一个游戏` 中心 y 差 **210 px**、点后者回挑选页且此屏 `开始` 计数 0、点 `开始` 后此屏 `换一个游戏` 计数 0。

**代价与诚实边界**

- **`canChooseAgain` 只在「有第二个游戏可换」时为真**；这一版 `PlayCatalog.games` 有 3 条，所以规则页上这条路**总会摆出来**。只有游戏被砍到 1 个时它才会消失——**这条分支有单测，但没有装机实测过**（本轮装机是 3 个游戏）。
- **`Playing` 上「没有这条路」是走查与单测一起证的**（走查点 `开始` 之后计数 0；单测在 `Playing` 上调 `chooseAgain` 不动状态），**没有试过在 `Playing` 上强行点那个坐标**（那一屏上那个坐标是格子，不是按钮）。
- **本条不改任何需求编号、不新增需求、不关闭任何 GAP**；`MainNav.kt` 一行未改（回挑选页就是 `Ready → Choose`，不涉及导航层）。
- **它与 AC-11.3 不冲突**：那条禁的是**同一局**的续玩邀请（「再来一局」），而这条路退回的是「还没开始」这一步。射程澄清记在 `records/02` RC-020。

**关联**

- `docs/01:328`（AC-11.3 第 23 轮澄清）、`:389`（AC-16.3）、`:390`（AC-16.4 复核）；`docs/03` §4.1 / §4.2 / §4.3（状态图与转换表）/ §4.4（结构树与布局决策）/ §4.5（导航接线）/ §7（追溯矩阵）；
- `docs/09:507`（结束卡那句改正）/ `:510`（新退路）/ `:760`（§8.9）；

  `app/src/main/java/com/fortheelder/ui/play/PlayViewModel.kt`（**159 行**：`Ready` `:34`、`choose` `:86`、`chooseAgain` `:102`、`playStartState` `:154-159`）、

## ADR-022：把会漂移的宣称做成表、用守卫钉住，而不是靠人工比对（第 24 轮）

**背景**

`docs/07` R-10「文案与代码事实漂移」在此之前记过三次案例，三次都是人肉比对撞上的：

| 案例 | 撞上 | 处置 |
| --- | --- | --- |
| 「有两个小游戏」（实际 3 个） | 12 → 16 轮 | RC-016 改成「三个」 |
| 引导页里「四档」（实际 3 档） | 17 → 19 轮 | 第 19 轮改成「三档」 |
| KDoc「四档排版表」（实际 3 档） | 24 轮 | 本轮改成「三档」（就是本 ADR 的守卫抓到的） |

问题不在「看漏一次」，在**人肉比对只在两处正好被摆在一起时才生效**。R-10 原文当时写的就是这类漂移「**没有机器守卫**」。

**一、把「会漂移的宣称」从散在各处的句子收成一张表。**

`CopyCountGuardTest` 里一个 `private data class DeclaredCount(what, pattern: Regex, fact: String, minHits: Int, truth: () -> Int)`，`declared` 共 8 条：小游戏款数、字号档数（`N档排版表` / `N档之间` 两种写法）、同一件事下的起点条数、引导页数（`引导N页` / `N页上的字` 两种写法）、「会做的」条数、「不会做的」条数。

**为什么不把这些要求散着放**：散着放就没法枚举，没法枚举就没法知道「到底管住了几条」。做成表以后，`docs/07` R-10 里可以照抄同一张表——**文档里写的守卫范围，就是代码里那个 `declared` 列表**，两边不必再对口径。

**二、事实出处一律指到代码里的那个数，而不是「文案之间互相对齐」。**

每条的 `truth` 都从事实出处现算：`PlayCatalog.games.size`、`FontSize.entries.size`、`StarterCatalog.all` 的分组条数、`OnboardingScreen.PAGE_COUNT`、`doesBullets.size` / `wontBullets.size`。

**为什么不用「几处文案互相对齐」**：两处错成同一个数时，互相对齐会**一起绿**——这正是案例②③的形态（页数、字号都是「错得一致」）。唯一能当事实的是代码里那个数本身。所以 `StarterCatalog` 那条还得**先 `check` 分组内条数一致**，否则「每组条数」这个事实本身就没定义。

**三、扫描范围连注释与 KDoc 一起扫，且认不出的写法判失败。**

扫 `System.getProperty("fortheelder.mainSrc")` 下全部 `**/*.kt`，`readLines(Charsets.UTF_8)`；中文数字支持 一~十 / 两 / 十X / X十 / X十Y / 阿拉伯数字，**认不出来的写法直接判失败，不静默跳过**。

**为什么连 KDoc 一起扫**：案例③就发生在 KDoc 里。KDoc 不在 dex 里（装机看不出），但它是后来人唯一的线索——**看不见的错误比看得见的更危险**。

**为什么认不出要判失败**：静默跳过等于「写得不规范就自动免疫」，守卫会退化成装饰。失败时打印 `相对路径:行号 「命中原句」 ——宣称名：文案说 X，事实出处 是 Y`，直接可定位。

**四、加三条防假绿断言，挡住「扫描范围被缩掉」这种无声失效。**

`files.size >= 50`、必须扫到至少一个 `*Voice.kt`、`scannedLines > 6000`（本轮实测 **70 个文件 / 7786 行**）。

**为什么需要**：源码级守卫最危险的失效不是「漏报一条」，是「某次重构把目录挪了」之后它扫到 0 个文件、然后**全绿通过**。三条断言把「扫描范围」也变成被钉住的东西。

**五、把 R-10 的措辞从「没有自动校验」改成「有，但只在册」。**

`docs/07` R-10 残余风险首行随之改写，并新增一条「只在册的宣称看得见」。**这不是措辞洁癖**：写「有自动校验」会让后来人以为文档正文里的个数也受管；写「只在册」才准确。

**守卫落点**

- JVM（本轮**新建**）：`app/src/test/java/com/fortheelder/ui/CopyCountGuardTest.kt`（**11,834 字节 / 1 例**）。反向验证过：把 `OnboardVoice.kt:36` 改回「四档」即报红（原文见 `records/04` 第二十二节），随后还原。
- 行为侧（既有走查）：`build/probe24.py` → `build/screens24.log`（**263 行 / 68 条 `OK` / 0 条 `!!`**）。8 条宣称里有 6 条在屏上有对应断言：小游戏「各 1 次」、字号档位「正好 3 个」、起点行「正好 3 条」、第 1 页短句「正好 8 条」（= 5 + 3）、引导「连翻两次到底」。
- 装机实测旁证：`adb logcat -b crash -d` **0 行**。

**代价与诚实边界**

- **只覆盖已登记的宣称。** 没进表的（文档正文里的个数、速查卡、列举式文案）**一条都看不见**；「第二个游戏」「不止一个」「几个」这类**不定数**的历史叙述也**不在射程**——它们本来就不是「写死的个数」。所以本 ADR 只把 R-10 抬到「**有，但只在册**」。
- **`minHits` 达标不等于「该说的地方都说了」。** 它只保证「至少这些地方说得对」；宣称 1 / 4 要求 ≥ 2 处（同一句在多个地方出现），其余 1 处。**多写少写没被管住**，管的只是「写了的地方数对不对」。
- **它是源码级守卫，不是运行时保证。** 它**不保证**用户屏幕上不会出现错数字——那种错（比如字符串拼接出的数）它扫不到，仍要靠走查；本轮走查确实另做了 6 条屏上断言。

## ADR-023：给 ViewModel 写设备层测试（真仓库、真 Room、不加接口），并用「注入错误」做反向验证（第 25 轮）

**背景**

到第 24 轮为止，「对话页」这条链路的机械覆盖只到两头：

- **一头是 L1 的纯函数**：`IntentScan` / `TalkUiState` / `WishGate` / `AnchorRules` / `StarterCatalog` / `CompanionVoice` 各自在 JVM 上被断言得很细（合计 100+ 例）。
- **另一头是 L3 的仓库与 DAO**：`WishDaoTest` / `WishRepositoryTest` / `AnchorDaoTest` / `AnchorRepositoryTest` / `TalkInputTest` / `TalkStarterTest` 验的是「存进去能不能取出来」「闸门函数在真库上还对不对」。

**中间那一层没有一个例**：`TalkViewModel` 把这些纯函数和仓库**串起来**之后，还是不是那个意思——「听出来的意愿先是不表态的」「又提一遍同一件事不算表态也不重置状态」「确认过之后点时段才建日常，而且只问一次」「删掉就是删掉，不留痕也不追问」。这些句子在 `docs/01` 里是验收判据（AC-06.2 / AC-07.1~07.4 / AC-08.1~08.3 / AC-09.1 / AC-09.3 / AC-10.1~10.3），**但它们在 ViewModel 这一层的形态此前从未被机械看过**。

**一、测试放在设备层（`androidTest`），不放 JVM。**

`TalkViewModel` 的构造参数是 `WishRepository` / `AnchorRepository` / `InterventionStore` 这类 **final 类**（`SettingsStore.kt` 一带的决策是数据层不开接口），在纯 JVM 上没法替身；换掉它们就得先加接口或引入 Robolectric。

**为什么不加接口**：数据层不开接口是本项目**已经立过的决策**（第 11 轮一带），只为「让测试能造替身」去改生产代码的形状，是**让被测物迁就测试**。也不引 Robolectric——那是给整个测试栈再加一层影子实现，为了一个 ViewModel 不值得。

**所以选：在设备上跑，用真 `ElderDatabase.open` + 真仓库 + 真 DataStore。** 代价是慢（13 例要真起库、真写文件），换回来的是**测的就是要发货的那套东西**：真 SQLite、真唯一索引、真迁移路径、真 DataStore 落盘。

**二、真 DataStore 与真 ViewModelStore 的回收，一律写在 `tearDown` 里。**

每次运行用 `talk-vm-${System.nanoTime()}.preferences_pb` 写在 `cacheDir` 下（**不固定文件名**，避免上一次运行的残留冒充这一次的初值）；`tearDown` 依次 `viewModelStore.clear()` → 取消 `storeScope` → `database.close()` → `deleteDatabase` → 删 DataStore 文件。**顺序不能换**：先关库再删库、先清 ViewModelStore 再取消 scope。

**为什么这么较真**：设备层测试一旦留下残留状态，会**变成「上一次跑过一次就绿」的样子**——那是本 ADR 里最想避免的失效形态。

**三、固定时区与固定时刻，让「时段」这件事可断言。**

`TimeZone.setDefault(Asia/Shanghai)` + `now = 2026-03-10 09:00`。**锚点的时段判定（上午 / 下午 / 晚上 / 想起来就做）本质上依赖时钟**，不钉住就没法写「点了上午，日常上写上午」这种断言。

**为什么不用相对时间**：相对时间会随「跑测试的那一刻」漂，同一个用例在不同小时跑出不同结果——那比不测更糟。

**四、「不该变」的地方用轮询，不用 sleep。**

`awaitUntil(5000){…}` 轮询真状态；只有在断言**恰恰是「什么也不该发生」**时（`settleQuietly()`）才用一个 300ms 的空排队 + 短暂等待。

**为什么**：能等的信号一律等信号；**等不到信号的才是「不该变」**。这一点是本文件唯一一处靠时间的窗口，**它只能证明「窗口内没观察到变化」，不能证明「真的什么都没发生」**——所以它只用在「断言变少/不出现」这几条上。

**五、反向验证：把守卫故意改错，看它红不红。**

本轮只加一类测试、不碰生产行为，所以「新测试真的在测东西吗」成了**唯一需要自证的问题**。做法：把 `Anchor.kt:73` 的 `mayPropose` 从
`status == WishStatus.CONFIRMED && StarterCatalog.byId(optionId) != null`
**临时注入**成 `||`，重跑这一类：

```
TalkViewModelTest > 没确认过的时候点了时段也不建锚点 … FAILED  expected:<0> but was:<1>
TalkViewModelTest > 说了不用的意愿也推不出锚点     … FAILED  expected:<0> but was:<1>
```

**2 例当场变红**，随后还原、`git diff` 复核为 0 行。

**为什么非要注入一遍**：绿得很快的测试最常见的失效是**它其实什么都没断言**（节点找不到就跳过、状态取到了默认值所以恒等）。注入错误是把「它到底会不会红」从**推断**变成**实测**。

**代价**：本轮只打了这一条守卫（`mayPropose`）。**其余守卫「会红」的性质是推断，不是实测**，标未验——这条边界写进 `records/04` 二十三节与 `docs/06` §3.4。

## ADR-024：给首页 ViewModel 写设备层测试（真 Room、真 DataStore、常驻收集器绕开 `stateIn` 的 `WhileSubscribed`），并用两处注入做反向验证（第 26 轮）

**背景**

第 25 轮给对话页补了 `TalkViewModelTest`（ADR-023），留下一个明确的缺口：**`HomeViewModel` 的同类测试「留给第 26 轮」**。这一轮就是来还这笔账的。

首页这条链路此前被机械看过的只有两头：

- **一头是 L1 的纯函数**：`GreetingEngine` 的问候语分段与「第一次见面」措辞、`InterventionRules` 的「此刻该不该开口」、`AnchorRules.draftOf` 的时段草稿，各自在 JVM 上被断言得很细。
- **另一头是 L3 的仓库与 DAO**：`AnchorDaoTest` / `AnchorRepositoryTest` 验的是「起点卡存进去能不能取出来」「唯一索引真的拦得住重复」。

**中间那一层没有一个例**：`HomeViewModel` 把设置、问候语、此刻该不该开口、起点卡这四样串起来之后，还对不对——而它比 `TalkViewModel` 多一层难处：**它的状态是 `combine(...).stateIn(viewModelScope, WhileSubscribed(5_000L), Loading)`**。

**一、测试放在设备层（`androidTest`），不放 JVM。**

理由与 ADR-023 第一条相同：`SettingsStore` / `AnchorRepository` / `RhythmProfileService` 都是 **final 类**（数据层不开接口是本项目已立的决策），纯 JVM 上没法替身；换掉它们就得加接口或引入 Robolectric，那都是**让被测物迁就测试**。所以照旧：真 `ElderDatabase.open`、真仓库、真 DataStore（文件写在 `cacheDir` 下、每次运行换名 `home-vm-${System.nanoTime()}.preferences_pb`）。

**二、`WhileSubscribed(5_000L)` 这个坑必须显式绕开——这是本轮最值当留下的一条技术决策。**

`stateIn(..., WhileSubscribed(5_000L), ...)` 的语义是：**没有订阅者时，上游在 5 秒后停掉，状态回到初值；新一轮订阅再重放 `Loading` 并让上游重新起跑。** 在应用里这是好事（息屏省电）；在测试里它是**假绿温床**：如果每个断言都临时 `state.first()` 取一次就走，那么

- 每次取数之间都没有订阅者，上游被反复重启；
- 采集到的值可能来自**上一轮订阅的残留 / 初值 `Loading`**，而不是「ViewModel 现在真的算出来的那个」；
- 「不该变」的断言会**恒真**（读到的永远是初始态），「该变」的断言会**偶发假红**。

**决策：测试里挂一个常驻收集器**，`observerScope` + `observerJob` 从 `@Before` 起一直收 `HomeUiState`，写进 `mirror: MutableStateFlow<HomeUiState>`；**所有断言一律读 `mirror`**。这样订阅从不间断，`WhileSubscribed` 的 5 秒窗口**永远进不去**，被测的就成了 `HomeViewModel` 真实的输出流。

**为什么不用 `runTest` 的虚拟时间把它「推快」**：androidTest 侧没有 `kotlinx-coroutines-test`（ADR-023 已定不加这个依赖），虚拟时间为 0 也**绕不过「订阅者判空」这个语义**——它不是时间问题，是「有没有人在收」的问题。

**三、「不该变」用 `settleQuietly()`，其余一律等信号。**

`awaitReady()` / `awaitOpening()` / `awaitUntil(5000){…}` 轮询真状态；只有断言**恰恰是「什么也不该发生」**时才用 `settleQuietly()`（`withContext(Dispatchers.Main){}` + `delay(300)`，**不调 `waitForIdleSync`**）。

**它只能证明「这 300ms 窗口内没观察到变化」，不能证明「真的什么都没发生」**——所以它只用在「不该多记一笔」「不该改口」这类断言上。与 ADR-023 第四条一脉相承，但**本轮多了一层教训**：`settleQuietly()` 放在断言**之前**还是**之后**，决定了观察窗口够不够长。M1 第一版只红 1 例就是窗口偏早（详见第五节）。

**四、反向验证：两处注入，而且**第一次的结果要照实看**。**

本轮与第 25 轮不同的地方在于，注入了**两处**，而不是只打一条守卫：

| 注入 | 位置 | 期望 | 实测 |
| --- | --- | --- | --- |
| M1 | `refresh()` 里加一次 `open()` | 「同一露面内再刷新也不改口」+「跨时段边界靠刷新重读，但不动账本」 | 第一版**只红 1 例**；补 `settleQuietly()` 后**恰好红 2 例**，`BUILD FAILED in 21s` |
| M2 | 去掉 `onStart()` 的 `if (!leftSinceLastOpening) return` | 「没真的离开过就不算新露面」 | **恰好红 1 例**，`BUILD FAILED in 24s` |

**M1 第一版为什么只红 1 例**：那个用例的等待条件是 `awaitUntil { headline == "中午好" }`，而**问候语是由 `state` 的 `combine` 重算出来的、不依赖 `open()`**——它比 `open()` 落笔记账**更早**满足，于是断言在记账发生之前就跑完了。

**这条教训比「注入一下看看红不红」更有价值**：把守卫改错是**制造错误**，但**用例自己的观察窗口**同样能决定它看不看得见这个错误。**「注入后红了」不等于「负例有效」**——只红一例也是一种红，看到红就收工，这条守卫就永远缺半边。所以本 ADR 把「反向验证要问『该红的都红了没有』，而不是只问『红了没有』」写成纪律。

## ADR-025：用 `RuleChain.outerRule` 把「关库」排在「组合」之后，并把这条顺序做成一条会红的规则（第 27 轮）

**背景**

第 26 轮审其余设备用例类的收尾顺序时，账目是这样的：`TalkViewModelTest:126` 与 `RhythmCollectorTest:87` 两处**顺序正确**（先取消收集器 / 先等 job 收干净，再关库）；纯 DAO 与仓库类**根本没有可疑点**（没有 Activity、没有组合）；**唯一一处没底的是** `app/src/androidTest/java/com/fortheelder/ui/play/PlayScreenTest.kt:72` 那条「注销」路径——它走的是 `AppContainer`，而收尾是 `@After 关掉并删掉测试库()`。

**问题不在于「有没有 bug」，在于「有没有东西会红」。** 关库如果发生在界面组合还在场的时候，可能出现的是**偶发**的数据级失败——写库撞上关库，谁先谁后取决于调度。偶发失败的坏处不是它难修，是它**平时是绿的**：写反了也照样全绿，直到某天 CI 上随机红一次，而那时没人记得这个顺序。

**一、三种做法**

| 做法 | 为什么不选 |
| --- | --- |
| 保持 `@After`，只在注释里写「必须先等组合退场」 | 这正是第 26 轮之前的状态：注释不是守卫，写反了不会红。**没有红过的守卫就是假绿守卫**（承接 `records/03` ADR-024 的教训） |
| 在 `@After` 里先断言「前台宿主数为 0」，再关库 | 断言顺序对了，但**它自己就是那段顺序**——断言写在 `@After` 里，`@After` 与 Compose 规则的退场次序由 JUnit 的规则机制决定，写错一次照样是绿的。约束必须由**框架的次序**保证，不能靠同一个人肉顺序里的断言 |
| **用 `RuleChain.outerRule(...).around(compose)` 把顺序交给框架** | **采纳**：`outerRule` 里的清理在 `around` 的组合规则**之外**，也就是组合先退场、外层再动手，次序是框架给的，不是人给的 |

**二、做了什么**

新建 `app/src/androidTest/java/com/fortheelder/ui/TestTeardown.kt`（**顶层函数，不是测试类**）：

```kotlin
fun 关库排在组合之后(databaseName: String, container: () -> AppContainer): TestRule
```

它的 `finally` 顺序固定为：

1. **断言前台上没有本应用的 Activity**（`ActivityLifecycleMonitorRegistry` 的 `getActivitiesInStage(Stage.RESUMED)` 数为 0）——这一步是**把顺序本身变成断言**：如果组合还没退场就轮到了关库，这句直接红，而不是等一个偶发写库失败；
2. `container().database.close()`；
3. `deleteDatabase(databaseName)`。

四个屏幕级用例类改成：

```kotlin
RuleChain.outerRule(关库排在组合之后(TEST_DB) { container }).around(compose)
```

并删掉原来的 `@After 关掉并删掉测试库()`。

**三、为什么屏幕级用例够不着 `ViewModelStore`（照实写）**

`ui.home.HomeViewModelTest` 那种写法用的是 `ViewModelStore`（`viewModelStore.clear()` + 独立的 `storeScope.cancel()`），**它能自己指定顺序**，所以第 26 轮它就写对了。屏幕级用例完全不同的地方在于：

- 它跑的是**真实 Activity** 上的真实组合，界面靠 `ComposeTestRule` 驱动；
- **`ComposeTestRule` 的退场（销毁宿主 Activity）不由用例代码控制**——它在规则自己的收尾里发生；
- 因此用例**没有任何办法**在 `@After` 里「自己先等组合退场」：`@After` 与规则退场谁先谁后是 JUnit 的内部次序。

⇒ 结论：**屏幕级用例只能靠把「关库」挂到比组合规则更外层的位置来保证顺序**，也就是本 ADR 的做法。这也是为什么这件事不能像 `HomeViewModelTest` 那样「在用例里写对顺序」了事。

**四、代价与边界**

- **代价一**：四个用例类各多一层规则链；`createComposeRule()` 不能再挂 `@get:Rule`，改为存进 `private val compose` 由 `RuleChain` 持有。读起来比原来长一点。
- **代价二**：`TestTeardown.kt` 是 `androidTest` 里**第一个不是测试类的 Kotlin 文件**（顶层函数会编成 `TestTeardownKt`）。理论上不带 `@Test` / `@RunWith` 就不会被 runner 计成第 19 个测试类，**这一条已由本轮 L3 全量的类数实证**（见 `records/04` 第二十六节）。
- **边界一**：这条规则只保证「关库在组合之后」，**不保证**「用例里所有在飞的写库都已结束」——那是 ADR-023 那条 `join` 纪律管的事，两者互补，不互相替代。
- **边界二**：`androidx.test:runner` 的 `getActivitiesInStage` 要求在主线程调用的说法，是照文档推断的；实现里用 `runOnMainSync` 兜住，**没有另外用一个反例去证「不在主线程调会怎样」**。

**五、负例（照实写）**

- **有负例的**：把 `TalkStarterTest.kt` 的规则链临时反过来写成 `RuleChain.outerRule(compose).around(关库排在组合之后(...))`，单跑该类 → `EXIT=1`、`AssertionError: 关库时前台上还有 1 个 Activity：收尾顺序反了（见 TestTeardown.kt）`、`There was 1 failure(s).` / `BUILD FAILED`。用完即还原（备份与还原后的 md5 一致）。⇒ **这条规则真的会红。**
- **没有负例的**：`records/02` RC-024 第四节那条——**「旧 `@After` 写法会产生可观察的数据级失败」仍未构造出来**。本轮证的是「规则能识别反序」，不是「旧写法必然出错」。

**状态**：已采纳（第 27 轮）。

## ADR-026：屏幕级用例固定不了时钟时，不开时钟口子，而是把这条限制本身做成一条被测行为——顺带接受「共用 settings DataStore」的隔离代价（第 28 轮）

**背景**

第 28 轮要给「设置」补仓库里第一条屏幕级用例，把 `AppRoot` 整棵渲出来。目标是 `docs/01` §4.13 的四条 AC——其中 AC-13.1 说「改完称呼回到首页，首页立刻用新称呼打招呼」，AC-13.2 说「深夜/安静时段首页换安静语」。

卡住的地方是：**首页说什么，同时取决于钟点。** `AppContainer.clock` 写死是系统钟（`Clock.systemDefaultZone()` 一类），屏幕级用例完全没有办法把它换掉——它拿不到 `AppContainer` 的构造参数以外的东西。于是「首页那句话里出现新称呼」这条断言，会因为运行时刻不同而忽红忽绿：深夜跑就走进安静分支，称呼不出现。

另一处卡点：`AppContainer` 只有 `databaseName` 一个测试口子。`settings` 取的是**应用也在用的那个进程单例** `DataStore`。所以屏幕级用例往设置里写的每一次改动，都是真写在这台设备的应用存储上的。

**一、三种做法**

| 做法 | 为什么不选 |
| --- | --- |
| 不给屏幕层开时钟口子，干脆不写「带名字」那条断言 | 那就是把 AC-13.1 整条放弃掉。可它恰恰是本轮唯一能验「首页重新读了设置」的地方，放弃等于白来 |
| 给 `AppContainer` 开一个可注入时钟的口子，屏幕用例注入假钟 | **能解，但为了测试去改产品构造参数**。本轮 `app/src/main` 一行未改是既定的纪律（RC-025），而且 `AppContainer` 的口子会立刻被下一个用例类要求更多口子，越开越宽 |
| **不开口子，改往库里摆一个「把此刻裹在中间」的安静时段** | **采纳**：`wakeAt = now.plusMinutes(10)`、`sleepAt = now.minusMinutes(10)`。落库会截掉秒，实际跨度是 `[整分-10min, 整分+10min)`，等号两端都落在里面；跨子夜时 `TimeSpan.contains` 走的是另一支，照样为真。于是**不管几点跑，首页都该判 `SLEEP_HOURS`** |

**二、做了什么**

新建 `app/src/androidTest/java/com/fortheelder/ui/settings/SettingsScreenTest.kt`（299 行、7 例）：

```kotlin
private val compose = createComposeRule()

@get:Rule
val rules: RuleChain = RuleChain.outerRule(关库排在组合之后(TEST_DB) { container }).around(compose)

private fun show() { compose.setContent { AppRoot(container = container) } }
```

七例覆盖 `docs/01` §4.13 的四条 AC：改称呼回首页不再问称呼（AC-13.1 的一半）、安静时段首页换安静语而称呼不冒出来（AC-13.2 兼时钟限制本身）、点「更大」字号立刻落库（AC-13.3）、设置页显示构建配置的版本号、清空设置先问一次点「不清」什么都没发生、确认清空之后**回到引导页**（AC-13.4）、清掉作息数据那一行立刻变成零。

`@After 把共用的设置清回出厂状态()` 用 `resetToDefaults()` 收尾。`@Before` 用 `resetToDefaults()` + `completeOnboarding()` + `setFontSize(STANDARD)` 摆一个「引导已走过」的起点。

**三、代价与边界**

- **代价一（隔离性）**：本类动的是与应用**共用**的 `settings` `DataStore`。`resetToDefaults()` 能把它清回出厂，但**这台机器上真实的设置会被清掉**（下次打开应用会重新看到引导页）。而且 `onboardingDone` / `firstLaunchEpochDay` 这类字段**公开 API 恢复不回去**，所以「先存一份、事后还原」这条路不通。库那条口子（`elder-test-settings-screen.db`）只解决了数据库，没解决 `DataStore`。
- **代价二（覆盖减半）**：AC-13.1 的「那句话带名字」那一半仍只能在 `ui.home.HomeViewModelTest` 验——那个类走 `ViewModelStore` 能注入时钟。屏幕层能验的只是「首页重新读了设置」。
- **边界一**：`InterventionStore` 是**进程单例**，且**没有清空口**。节流状态会跨用例残留，所以这里不硬断言「那句话里有名字」——那会变成一条随运行时刻忽红忽绿的用例。
- **边界二**：`performTextInput` **不是真 IME**，它绕过输入法直接塞文本。所以这条用例证明不了「真实中文输入法下也能改地址」。
- **边界三**：较真说，「安静时段的文案是库驱动的」这件事没有被证明（见第五节）。

**四、为什么这条限制值得变成被测行为，而不是被绕过**

把「不管几点跑都该判安静」写进库，等于让**时钟这条限制本身**成为一条被测行为：它红了，说明要么 `TimeSpan.contains` 的跨子夜分支坏了，要么首页读作息画像的路径坏了。**这比「绕过限制、少验一条」多拿到一点东西**，代价只是用例里多一个辅助函数。

**五、负例（照实写）**

- **有负例的**：备份 `SettingsScreen.kt`（md5 `5384c0bdfe42338d50cba8c693887713`），把第 175 行的 `container.settings.resetToDefaults()` 换成一行 `// MUTATION-28:` 注释 → 定向单跑该类 → `MUT_EXIT=1`、`Starting 7 tests` / `Finished 7 tests` / `BUILD FAILED in 54s`，XML 里 `tests="7" failures="1"`，**恰好**「确认清空设置之后就回到引导页」这一例红，另外 6 例全绿（含走「不清」分支那条）。`cp` 还原后 md5 回到 `5384c0bd…`、无 `MUTATION-28` 残留、`git diff --stat -- app/src/main` 空。⇒ **反例真的会只打中该打中的那一例。**
- **没有负例的**：反例**只打了一处**，7 例里另外 6 例没做过「打坏必红」的检验。
- **没有负例的**：**AC-13.3 的「源码没有写死同一字面量」这件事，本类证明不了**。用例比的是「界面上的字」和「库里的字」相等；如果源码就是把 `"这会儿是您休息的时间。"` 写死的，这个用例照样绿。（`InterventionVoice.kt:78` 处确实没有可引用的常量。）

**状态**：已采纳（第 28 轮）。
