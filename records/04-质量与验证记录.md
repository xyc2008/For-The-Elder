## 一、字号缩放的真实行为(原始数据)

### 1.1 探针：`Density(density, fontScale)` 的 `sp→px` 不是线性的

方法：临时仪器化测试 `FontScaleDensityProbeTest`(故意 `fail()`，用失败信息带回测量值；
**已删除**，见 `records/01` 第 3 轮)。固定 `density = 2.625`，只改 `fontScale`。

```
case          | density | fontScale | 20sp.toPx | 30sp.toPx | 6字正文px | 6字标题px
fontScale-1.0 | 2.625   | 1.0       | 52.5      | 78.75     | 312       | 468
fontScale-1.5 | 2.625   | 1.5       | 68.25     | 78.75     | 408       | 468
```

**读法**

- `fontScale=1.0` 时 `sp→px` 就是乘 density：20 × 2.625 = 52.5，30 × 2.625 = 78.75。线性。
- `fontScale=1.5` 时：20sp 放大到 68.25(= 52.5 × 1.30，只到 1.30 倍而非 1.5 倍)，
  而 30sp **仍然是 78.75**，即放大倍率 **1.00**。
- 决定性对照：`fontScale=1.0` 的 30sp = 468px，`fontScale=1.5` 的 20sp = 408px。
  后者物理上应当不小于前者，实测小 60px。

**结论**：`fontScale` 越大、字号越大，放大被压制得越狠。30sp 在 1.5 倍系统字号下完全不放大。
这个非线性来自 **Compose 1.7 的 `Density(density, fontScale)` 工厂**
(被测对象是手搓的 `Density` 实例，与平台 `DisplayMetrics` 无关)。

这解释了历史上所有「怪数字」：20sp 只放大 9.6%、≥30sp 完全不放大。

### 1.2 修复后的实测倍率

方法：`ThemeFontScaleTest.系统字号会被保留且应用内档位仍然有效`，
在主题外下发一个合成的 `fontScale = 1.5`，并打印测量值。

`logcat` 原始行：

```
11-20 19:39:31.117  7096  7111 I System.out: FONTSCALE-PROBE plain=320 syntheticStandard=419 syntheticExtra=461 systemOnlyRatio=1.309375 appTierRatio=1.1002387
```

| 项 | 像素宽度(6 字 `bodyLarge`) | 倍率 |
|---|---|---|
| `plain`(应用标准档，系统 1.0) | 320 | 基准 |
| `syntheticStandard`(应用标准档，系统 1.5) | 419 | **1.309375** |
| `syntheticExtra`(应用更大档，系统 1.5) | 461 | 相对上一行 **1.1002387**(标称 1.30) |

**读法**

- 系统字号 1.5 被**保留**(419 > 320)，应用没有抹平它。
- 应用内「更大」档在该环境下**仍然放大**(461 > 419)，不是摆设。
- 但两者都被平台的非线性换算压缩：系统 1.5 只兑现 1.309×，应用 1.30 只兑现 1.100×。
  **这是平台行为，不是应用缺陷**；不干预的理由见 `records/03` ADR-004。

### 1.3 踩过的坑

**坑 1：用 dp 当量尺，量出来的倍率偏低。**
第一版渲染测试用 `getUnclippedBoundsInRoot()` 取 dp 宽度做比值：
「大一点」档量出 **1.097**(标称 1.15)，`headlineMedium` 的倍率**恒等于 1.0**。
看起来像主题坏了，实际是那个接口换算成 dp 时用的 density **本身带 `fontScale`**，
分母跟着一起放大，把比值抵消掉了。**被试和量尺是同一个东西。** 改用原始像素后正常。
→ 固化为 ADR-005。

**坑 2：对平台做它不承诺的线性假设。**
第一版断言「系统 1.5 × 应用内 1.3 线性相乘」，实测算出 1.309375 而不是 1.5，测试红。
**这个断言本身写错了**，不是代码错了。已改写为断言两条真正要保证的性质
(不抹平系统设置 / 应用档位仍显著放大)，并把实测倍率打印出来归档。

**坑 3：`DensityImpl` 没有实现 `equals`。**
在 `setContent` 里每次重组新建 `Density` 实例会让下游读取者反复失效。
合成 density 必须 `remember` 住。

**坑 4：诊断测试故意 `fail()`。**
`FontScaleDensityProbeTest` 用失败信息带回测量值，留着会让整个
`connectedDebugAndroidTest` 变红。用完已删除。

### 5.2 本轮两次真实的红，以及它们各自证明了什么

| 位置 | 报错原文 | 真因 | 处理 |
|---|---|---|---|
| `RhythmDaoTest.kt:92` | `expected:<[-1,2,3]> but was:<[-1,3,4]>` | `INTEGER PRIMARY KEY AUTOINCREMENT` 的序号表不回滚：一行即使被 `INSERT OR IGNORE` 拦下，AUTOINCREMENT 序号也已消耗 | **改断言**(并改成断言真正关心的性质)，表结构不动 |
| `RhythmRepositoryTest.kt:94` | `expected:<3> but was:<0>` | 同一批里重复的同一条信号全部被 `IGNORE`，一条也写不进 | **改断言为 0** |

两条都不是代码错，是期望值错了。写在这里的原因是：**它们证明唯一索引去重真的在起作用**——
如果去重没生效，这两条反而会「通过」。

另一件小事：Kotlin 会给测试方法内的 lambda 生成匿名类，类名取外层方法名。
方法名里带空格时文件名非法，产物形如
`RhythmRepositoryTest$入睡锚点看不出规律时读回来仍是 null$1.class`。
全仓改了 **4 处**(把方法名里的空格去掉)。

### 6.2 本轮一次真实的打包红：`androidTest` 的反引号测试名不能带空格

```

```

- 出错任务：`:app:dexBuilderDebugAndroidTest`。
- 根因：Kotlin 对含 lambda 的测试方法会生成匿名类，SimpleName 取自外层方法名，

- 教训：Gradle 控制台乱码时**不要靠读错误文本判断**，加 `--stacktrace` 或直接读

### 6.3 「广播测试绿得太快」的证伪过程

`RhythmCollectorTest.屏幕开关广播真的能从系统收到` 的 `time=0.211s`，
对一个要等系统异步投递的用例来说快得不正常。怀疑方向：
**会不会是采集器自己凭空造了一行，而不是真收到了广播**。

处理办法不是「看着还行就算了」，而是把它改成能证伪的形状：

```kotlin
assertEquals(0, repository.signalCountOnce())                        // 前提：库是干净的
// … 触发系统广播(真实 input keyevent 26) …
assertEquals(listOf(now), repository.stored.map { it.at }.distinct()) // 结论：行是采集器写的
```

第二条断言里的 `now` 是**注入采集器的固定时钟**的值。只有采集器读到广播、
再用自己的 clock 落库，才会得到这个时间戳——实现对不上就红。
收紧后仍然 **6/6 绿**，投递为真。

**一般化的经验**：测试跑得快不等于假，但一个用例必须**能够失败**才算证据。
本轮的形状里，「库里干净」和「时间戳来自注入的时钟」这两条都是可以被破坏的。

### 7.2 本轮一次真实的红，以及它证明了什么

第一次跑设备端用例时 **1 例失败**：

```
com.fortheelder.data.rhythm.RhythmCollectorTest > 屏幕开关广播真的能从系统收到  FAILED
java.lang.AssertionError: expected:<[2026-03-10T09:00:12.345]>
but was:<[2026-03-10T09:00:12.345, 2026-11-21T00:12:34.765, 2026-11-21T00:12:34.833]>
```

**根因**：仪器化用例与应用跑在同一个进程里，`ElderApp.onCreate` 已经按用户设置把
**进程级采集器**挂上了；用例里那两次 `input keyevent 26` 是发给**系统**的，
于是两个采集器同时收到同一个亮灭屏广播，一个用注入的固定时钟写、一个用真实时钟写。
后两条 `2026-11-21T00:12:34.xxx` 就是真实时钟那两行。

**修法**：`RhythmCollectorTest.setUp()` 里先
`(context.applicationContext as ElderApp).container.rhythmCollector.stop()`，
把写库的人收敛成一个。修完重跑 42/42 绿。

**它证明了什么**：这不是产品缺陷(真机上只有一个采集器)，而是**测试隔离**问题。
但更重要的是它反过来确认了第 6 轮那条收紧过的断言**是有效的**——
第 6 轮加它的理由正是「万一是别的东西写了库，这条用例就成了假绿」，
这一次真的抓到了「别的东西」，只是那个「别的东西」在真机上不存在而已。
**唯一的遗憾**：这条断言只在被污染时才会红，而污染只在「用户开着采集开关
且应用进程存活」时发生——也就是说它是**条件性**的，不总能触发。

### 7.3 边界用例清单(`IntentScanTest` 29 例守的是什么)

逐条列出「为什么这条例存在」，因为词表匹配最容易在边界上悄悄错：

| 用例守的东西 | 为什么它会错 |
|---|---|
| 逗号不是句断 | 「我想学书法，也想学画画」必须出**两件**事。若按逗号切句，后半句会单独成句，「想学」和「画画」还算同行；但「我不喜欢下棋，想学书法」这种就会因为前半句的「不」把后半句一起杀掉 |
| 「一直想」盖住「想学」与「想」 | 长词优先 + `taken` 数组。不然「我一直想学书法」会同时报三条(甚至不同 term)，用户看到重复 |
| 证据是「一直想学书法」 | cue 与 topic 的**最短包住片段**。取「一直想」会让人以为我们只听到一半，取「书法」会丢掉「想」 |
| 否定只在兴趣上生效 | 「最近老是睡不着」里没有否定词，但「我睡不着，不想下棋」里前半句的状态**必须保留**——状态不是用户能「不想」的东西 |
| 「特别想学书法」不能被裸「别」误杀 | `negationMarkers` 故意不收裸「别」；这条用例就是那次取舍的守卫 |
| 只说主题词不算兴趣 | 「书法」单独出现 → `NotRecognized`。对应 AC-06.2，是 RC-006 收窄的那条边界 |
| 同一件事说两遍只报一次 | `distinctBy { kind to term }`。不然「我想学书法，想学书法」会出两条卡片 |
| 偏移是原文绝对值 | `forEachSentence` 里剃过空白，若偏移按句内计就会整体前移 |

29 例**首次运行即全绿，零返工**。

### 7.6 本轮**未**验证的

- **裸「想」的误判率没有量化**：「下棋这件事我想想」会被算成兴趣。
  没有真实语料，也没有做误判率测量——这一条是**已知的、写下来的**限制
  (见 ADR-010 与 `docs/01` FR-06)，不是隐藏缺陷。
- **裸「不」的杀伤面没有量化**：「不错」「不着急」会让整句的兴趣命中作废。
  同上。
- **词表覆盖率没有测**：口琴、太极剑、抖空竹这类词表外主题一律不识别，
  但「有多少种主题会说漏」这件事没有数据。
- **用户不能自己打字**：设备侧 `adb shell input text` 送不进中文(GAP-02)，
  所以「自由说一句」这条路径**一次都没被人走过**，包括开发时。
- 说两句页在**大字号下的证据行是否仍完整可见**：只验了默认字号。
- 新增入口与结果卡的 **TalkBack 可达性**未验证。
- 前面各轮遗留(真机、系统字号真实 1.5、性能基线 GAP-03、进程被杀后的丢事件量、
  `pruneIfDue()` 跨天、`SAVED_HINT_MILLIS`、`RhythmConfig` 阈值)**一条都没关闭**。
