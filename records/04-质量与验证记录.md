## 一、字号缩放的真实行为(原始数据)

### 1.1 探针：`Density(density, fontScale)` 的 `sp→px` 不是线性的

方法：临时仪器化测试 `FontScaleDensityProbeTest`(故意 `fail()`，用失败信息带回测量值；
**已删除**，见 `records/01` 第 3 轮)。固定 `density = 2.625`，只改 `fontScale`。

```
case          | density | fontScale | 20sp.toPx | 30sp.toPx | 6字正文px | 6字标题px
fontScale-1.0 | 2.625   | 1.0       | 52.5      | 78.75     | 312       | 468
fontScale-1.5 | 2.625   | 1.5       | 68.25     | 78.75     | 408       | 468
```

**读法**

- `fontScale=1.0` 时 `sp→px` 就是乘 density：20 × 2.625 = 52.5，30 × 2.625 = 78.75。线性。
- `fontScale=1.5` 时：20sp 放大到 68.25(= 52.5 × 1.30，只到 1.30 倍而非 1.5 倍)，
  而 30sp **仍然是 78.75**，即放大倍率 **1.00**。
- 决定性对照：`fontScale=1.0` 的 30sp = 468px，`fontScale=1.5` 的 20sp = 408px。
  后者物理上应当不小于前者，实测小 60px。

**结论**：`fontScale` 越大、字号越大，放大被压制得越狠。30sp 在 1.5 倍系统字号下完全不放大。
这个非线性来自 **Compose 1.7 的 `Density(density, fontScale)` 工厂**
(被测对象是手搓的 `Density` 实例，与平台 `DisplayMetrics` 无关)。

这解释了历史上所有「怪数字」：20sp 只放大 9.6%、≥30sp 完全不放大。

### 1.2 修复后的实测倍率

方法：`ThemeFontScaleTest.系统字号会被保留且应用内档位仍然有效`，
在主题外下发一个合成的 `fontScale = 1.5`，并打印测量值。

`logcat` 原始行：

```
11-20 19:39:31.117  7096  7111 I System.out: FONTSCALE-PROBE plain=320 syntheticStandard=419 syntheticExtra=461 systemOnlyRatio=1.309375 appTierRatio=1.1002387
```

| 项 | 像素宽度(6 字 `bodyLarge`) | 倍率 |
|---|---|---|
| `plain`(应用标准档，系统 1.0) | 320 | 基准 |
| `syntheticStandard`(应用标准档，系统 1.5) | 419 | **1.309375** |
| `syntheticExtra`(应用更大档，系统 1.5) | 461 | 相对上一行 **1.1002387**(标称 1.30) |

**读法**

- 系统字号 1.5 被**保留**(419 > 320)，应用没有抹平它。
- 应用内「更大」档在该环境下**仍然放大**(461 > 419)，不是摆设。
- 但两者都被平台的非线性换算压缩：系统 1.5 只兑现 1.309×，应用 1.30 只兑现 1.100×。
  **这是平台行为，不是应用缺陷**；不干预的理由见 `records/03` ADR-004。

### 1.3 踩过的坑

**坑 1：用 dp 当量尺，量出来的倍率偏低。**
第一版渲染测试用 `getUnclippedBoundsInRoot()` 取 dp 宽度做比值：
「大一点」档量出 **1.097**(标称 1.15)，`headlineMedium` 的倍率**恒等于 1.0**。
看起来像主题坏了，实际是那个接口换算成 dp 时用的 density **本身带 `fontScale`**，
分母跟着一起放大，把比值抵消掉了。**被试和量尺是同一个东西。** 改用原始像素后正常。
→ 固化为 ADR-005。

**坑 2：对平台做它不承诺的线性假设。**
第一版断言「系统 1.5 × 应用内 1.3 线性相乘」，实测算出 1.309375 而不是 1.5，测试红。
**这个断言本身写错了**，不是代码错了。已改写为断言两条真正要保证的性质
(不抹平系统设置 / 应用档位仍显著放大)，并把实测倍率打印出来归档。

**坑 3：`DensityImpl` 没有实现 `equals`。**
在 `setContent` 里每次重组新建 `Density` 实例会让下游读取者反复失效。
合成 density 必须 `remember` 住。

**坑 4：诊断测试故意 `fail()`。**
`FontScaleDensityProbeTest` 用失败信息带回测量值，留着会让整个
`connectedDebugAndroidTest` 变红。用完已删除。

### 5.2 本轮两次真实的红，以及它们各自证明了什么

| 位置 | 报错原文 | 真因 | 处理 |
|---|---|---|---|
| `RhythmDaoTest.kt:92` | `expected:<[-1,2,3]> but was:<[-1,3,4]>` | `INTEGER PRIMARY KEY AUTOINCREMENT` 的序号表不回滚：一行即使被 `INSERT OR IGNORE` 拦下，AUTOINCREMENT 序号也已消耗 | **改断言**(并改成断言真正关心的性质)，表结构不动 |

两条都不是代码错，是期望值错了。写在这里的原因是：**它们证明唯一索引去重真的在起作用**——
如果去重没生效，这两条反而会「通过」。

另一件小事：Kotlin 会给测试方法内的 lambda 生成匿名类，类名取外层方法名。
方法名里带空格时文件名非法，产物形如
`RhythmRepositoryTest$入睡锚点看不出规律时读回来仍是 null$1.class`。
全仓改了 **4 处**(把方法名里的空格去掉)。

### 6.2 本轮一次真实的打包红：`androidTest` 的反引号测试名不能带空格

```

```

- 出错任务：`:app:dexBuilderDebugAndroidTest`。

### 6.3 「广播测试绿得太快」的证伪过程

`RhythmCollectorTest.屏幕开关广播真的能从系统收到` 的 `time=0.211s`，
对一个要等系统异步投递的用例来说快得不正常。怀疑方向：
**会不会是采集器自己凭空造了一行，而不是真收到了广播**。

处理办法不是「看着还行就算了」，而是把它改成能证伪的形状：

```kotlin
assertEquals(0, repository.signalCountOnce())                        // 前提：库是干净的
// … 触发系统广播(真实 input keyevent 26) …
assertEquals(listOf(now), repository.stored.map { it.at }.distinct()) // 结论：行是采集器写的
```

第二条断言里的 `now` 是**注入采集器的固定时钟**的值。只有采集器读到广播、
再用自己的 clock 落库，才会得到这个时间戳——实现对不上就红。
收紧后仍然 **6/6 绿**，投递为真。

**一般化的经验**：测试跑得快不等于假，但一个用例必须**能够失败**才算证据。
本轮的形状里，「库里干净」和「时间戳来自注入的时钟」这两条都是可以被破坏的。

### 7.2 本轮一次真实的红，以及它证明了什么

第一次跑设备端用例时 **1 例失败**：

```
com.fortheelder.data.rhythm.RhythmCollectorTest > 屏幕开关广播真的能从系统收到  FAILED
java.lang.AssertionError: expected:<[2026-03-10T09:00:12.345]>
but was:<[2026-03-10T09:00:12.345, 2026-11-21T00:12:34.765, 2026-11-21T00:12:34.833]>
```

**根因**：仪器化用例与应用跑在同一个进程里，`ElderApp.onCreate` 已经按用户设置把
**进程级采集器**挂上了；用例里那两次 `input keyevent 26` 是发给**系统**的，
于是两个采集器同时收到同一个亮灭屏广播，一个用注入的固定时钟写、一个用真实时钟写。
后两条 `2026-11-21T00:12:34.xxx` 就是真实时钟那两行。

**修法**：`RhythmCollectorTest.setUp()` 里先
`(context.applicationContext as ElderApp).container.rhythmCollector.stop()`，
把写库的人收敛成一个。修完重跑 42/42 绿。

**它证明了什么**：这不是产品缺陷(真机上只有一个采集器)，而是**测试隔离**问题。
但更重要的是它反过来确认了第 6 轮那条收紧过的断言**是有效的**——
第 6 轮加它的理由正是「万一是别的东西写了库，这条用例就成了假绿」，
这一次真的抓到了「别的东西」，只是那个「别的东西」在真机上不存在而已。
**唯一的遗憾**：这条断言只在被污染时才会红，而污染只在「用户开着采集开关
且应用进程存活」时发生——也就是说它是**条件性**的，不总能触发。

### 7.3 边界用例清单(`IntentScanTest` 29 例守的是什么)

逐条列出「为什么这条例存在」，因为词表匹配最容易在边界上悄悄错：

| 用例守的东西 | 为什么它会错 |
|---|---|
| 逗号不是句断 | 「我想学书法，也想学画画」必须出**两件**事。若按逗号切句，后半句会单独成句，「想学」和「画画」还算同行；但「我不喜欢下棋，想学书法」这种就会因为前半句的「不」把后半句一起杀掉 |
| 「一直想」盖住「想学」与「想」 | 长词优先 + `taken` 数组。不然「我一直想学书法」会同时报三条(甚至不同 term)，用户看到重复 |
| 证据是「一直想学书法」 | cue 与 topic 的**最短包住片段**。取「一直想」会让人以为我们只听到一半，取「书法」会丢掉「想」 |
| 否定只在兴趣上生效 | 「最近老是睡不着」里没有否定词，但「我睡不着，不想下棋」里前半句的状态**必须保留**——状态不是用户能「不想」的东西 |
| 「特别想学书法」不能被裸「别」误杀 | `negationMarkers` 故意不收裸「别」；这条用例就是那次取舍的守卫 |
| 只说主题词不算兴趣 | 「书法」单独出现 → `NotRecognized`。对应 AC-06.2，是 RC-006 收窄的那条边界 |
| 同一件事说两遍只报一次 | `distinctBy { kind to term }`。不然「我想学书法，想学书法」会出两条卡片 |

### 8.2 本轮三处真实的红，以及它们各自证明了什么

**红 1：`WishDaoTest > 同一件事记两次只留一条` —— 测试笔误**

```
java.lang.AssertionError: expected:<true> but was:<false>
com.fortheelder.data.db.WishDaoTest > 同一件事记两次只留一条  FAILED
```

用例断言第二次 `insert` 的返回 `rowId > 0`。但 `INSERT OR IGNORE` 撞上 `(kind, term)`
唯一索引时**本来就应该**返回 `-1`——这正是「重复提不重置状态」那条设计的落地点。
**这是断言写错了，不是产品错了**：把「忽略」误当成了「更新」。
改成「第一次 `rowId > 0`、第二次 `assertEquals(listOf(-1L), …)`、`count() == 1`」后绿。
它证明了那条唯一索引**真的在生效**：如果索引没建上，第二次插入会成功，
用例同样会红，只是红在别的地方。

### 8.3 边界用例清单(`WishGateTest` 18 例守的是什么)

状态机最容易在「没变的那些输入」上悄悄错，所以逐条列出「为什么这条例存在」：

| 用例守的东西 | 为什么它会错 |
|---|---|
| `PENDING + CONFIRM → CONFIRMED` | 唯一被允许的「第一次表态」 |
| `PENDING + DECLINE → DECLINED` | 同上，反方向 |
| `CONFIRMED + DECLINE → DECLINED` | 用户改主意要生效(不能锁死在同意) |
| `DECLINED + CONFIRM → CONFIRMED` | **刻意的**：AC-07.3 挡的是**常伴主动提起**，不是用户自己改主意 |
| `CONFIRMED + CONFIRM → null` | 状态不变必须返回 `null`，否则第一次表态时刻被覆盖 |
| `DECLINED + DECLINE → null` | 同上 |
| `PENDING + CONFIRM` 之后**不**再被 `mayBringUp` 放行 | 问过一次就不许再问 |
| `DECLINED` 不被 `mayBringUp` 放行 | 拒绝过的事一次都不许主动提 |
| `mayOffer` 对 `PENDING`/`DECLINED` 均为假 | AC-07.4：未确认 → 产出必须是空 |
| `bringUpable()` 只筛 `PENDING` | 列表分组的分界线 |
| `decide_neverProducesPending` | 表态的出口只有「记住」和「先不用」，跑出一堆「还没问过」就等于把问题又问一遍 |

(「库里的未知状态字符串如何兜底」**不在**这 18 例里，它在仓库层——`WishRepository` 读库时
把认不出的状态当 `DECLINED` 处理，方向是「少打扰」。`WishGateTest` 只吃类型化的枚举，
构造不出非法状态，所以这条边界由 `WishRepositoryTest` 12 例覆盖。)

`TalkVoiceTest` 16 例守的是**措辞**，逐条对应到它扫的两个**具体禁用词表**：

| 用例 | 它扫的禁用词表 |
|---|---|
| `noStringUsesNotificationOrContentDeliveryWords` | 提醒 / 通知 / 推送 / 安排 / 课程 / 报名 / 链接 / 优惠 / 活动通知 / 已为您 / 我帮您 / 帮您找 |
| `noStringJudgesTheUserOrPressuresThem` | 加油 / 坚持 / 优秀 / 真棒 / 应该 / 必须 / 要努力 / 别偷懒 / 上次 / 昨天 / 多久没 / 好几天 |

其余 14 例守的是结构与差异：三类意愿(`kind`)的问句/同意/拒绝/改主意/结果语**两两不同**
(否则用户会觉得它其实没听懂)、期望的按钮文案(如 `愿意了解一下`)逐字存在、
`offerLines` 在未确认时是**空列表**(5 例)、`statusLabel` 三种状态各有专名、
`everyStringIsNonBlank`(没有空字符串漏出来)。

**这组用例的弱点要写清楚**：它扫的是**禁用词**，不是人工评审——也就是说，
它能挡住「加油」「坚持」「还有 3 天」这类已列举的词，**挡不住一句新造出来的、
同样空洞但没进禁用词表的承诺**。这是本项目里约束最弱的一处(ADR-011 已记)。

### 10.2 本轮两处真实的红，以及它们各自证明了什么

**红 1 —— `com.fortheelder.data.anchor.AnchorRepositoryTest > dueNow只给出时段命中的那些`，
`java.lang.NullPointerException at AnchorRepositoryTest.kt:107`。**

第一次跑设备测试的输出原文是：

```
Starting 92 tests on Elder_API35(AVD) - 15
Finished 92 tests
There was 2 failure(s)
BUILD FAILED in 38s
```

第 107 行是 `repository.add(AnchorRules.draftOf("chess-square", AnchorSlot.ANYTIME)!!)`。
`draftOf` 返回了 null —— 因为**目录里没有 `chess-square` 这个 id**；棋类那颗的 id
实际是 `chess-solo`(`StarterOptions.kt:68`)。

- **这条证明的是测试写错了，不是产品缺陷。** 产品代码一行没动。已用
  `Edit replace_all` 把该文件里 3 处 `chess-square` 全部改成 `chess-solo`。
- 为什么是 NPE 而不是断言失败：`!!` 把「目录里没有」翻译成了一次非空断言失败。
  用例本身是对的——同类的 `目录里没有的起点造不出草稿` 正是在证明目录外的 id 造不出草稿；
  错的是这个数据挑错了 id。
- 记这一条是为了免得以后有人看到 `chess-square` 这个词，以为目录里少了一项。

**红 2 —— `com.fortheelder.data.db.MigrationTest > 升级之后新表能真的写进去`，
`java.lang.IllegalStateException: A migration from 1 to 3 was required but not found.`
从 `RhythmSignalDao_Impl` 抛出。**

**这是第 9 轮写下的旧用例，不是本轮新写的三条。它在第 9 轮是绿的。**
红的原因是本轮把 `ElderDatabase` 的版本从 2 升到了 3。

- **根因**：那条用例用 `helper.createDatabase(TEST_DB, 1)` 建第 1 版的库，然后自己拼了一个
  `Room.databaseBuilder(context, ElderDatabase::class.java, TEST_DB).addMigrations(MIGRATION_1_2).build()`
  来打开它。**手拼的 builder 自带一份迁移清单**，所以生产代码里漏接一条 Migration，
  它照样绿——它最该发现的事情，恰恰是它发现不了的。第 9 轮只有一个迁移，这个缺陷藏着；
  第 10 轮多了一个迁移，它当场暴露。
- **修法**：改成调用 `ElderDatabase.open(context, TEST_DB)`，让测试与生产**共用同一个入口**
  （迁移清单只有一份，写在 `ElderDatabase` 里）。同一个文件里新加的那条
  `升到第三版之后锚点能真的写进去` 也直接用了 `ElderDatabase.open`，不走手拼。
- **复跑结果**：**92 例 / 14 类 / 0 fail / 0 err，`BUILD SUCCESSFUL in 36s`**，
  `adb logcat -b crash -d` 空。
- 这条是本轮最值得记住的一处测试缺陷，已写进 `docs/02` 第 8.3 节、
  `records/01` 第 10 轮「问题与解决」第 1 条；`MigrationTest` 的类注释里也留了这段经过。

**关于两个反向断言的诚实说明。** 上面四条 `NOT contains` 里，`talk-heard NOT contains '可以这样开始'` 与 `fp-after-first NOT contains '不是它'` 是**有效**的反向断言——这两个串确实会被渲染，只是那一刻不该出现。而两处 `NOT contains '再来一局'` / `NOT contains '排名'` 是**恒真的**：核对过 `app/src/main/java`，`再来一局` 只出现在注释里（`PlayScreen.kt:42`、`PlayVoice.kt:18,39`），`排名` 只出现在 `OnboardingScreen.kt:82` 的「不算分也不排名次」——两处都不是结算屏上的渲染文本。所以这两条断言在当轮**不可能失败**，它们的作用只是防止将来有人往结算屏里加回归词，写成「本轮验证了不出现 `再来一局`」是不诚实的；准确的说法是「本轮把这两条反向断言挂上去当护栏，它们在当轮恒真」。

stdout 只有一行 `OK` 是脚本的约定：`walk12e.py` 把断言明细写进 `build/walk12e.log`（用 `_ProgressLog` 每行落盘，便于走查中途就能看进度），stdout 只吐最终结论。所以复现时看的是两个文件：尾行为 `OK` 即通过，要看细节翻日志。

#### 12.2.5 走查脚本自身的七处坑（都不是产品缺陷）

`walk12e.py` 前 12 次都失败（第 13 次才通过），根因**七处都在脚本这一侧**，必须在记录里说清，否则会被误读成「App 有问题」：

1. **走查之间不留状态。** 第一次跑到谈话页时，库里「书法」这条意愿已经是 `WishStatus.CONFIRMED`（上一轮走查留下的），于是 `TalkScreen` 的意愿块直接进「已确认」分支，待定分支的三句文案（`TalkScreen.kt:181-197`）根本不会被渲染——断言自然找不到「愿意了解一下」。修法是脚本开头 `pm clear` 把 App 数据清掉，每轮从干净状态起步。这条也说明**走查脚本必须在开头清数据**，否则上一轮的状态会让断言假失败。
2. **`input swipe` 带惯性，单向扫会漏行。** 第 5 次走到了谈话页的「我听见的」卡片，屏幕上**确实有**「愿意了解一下」（探针在同一处抓到 `TextView [383,1353][698,1428] text='愿意了解一下'`），但脚本的收集函数只做单向 `swipe_up`，一次滑动带惯性滑过一屏多，把中间几行整段跳过了，之后再越滚越远、回不来。修法是把收集函数改成**双向扫**（先向上扫一遍、回顶、再向下扫一遍，累积「见过」的项），并把「见过最多项的那份 dump」还回去供断言用。

3. **断言取错了那一份 dump。** 第 6 次走到了「记在上午」之后，锚点卡上「上午 / 「找一张白纸，用自己顺手的笔，从上往下写满它，写什么字都行。」/ 不用记了」三行**都真实出现**，但脚本还顺带在**同一份 dump** 里找「这一步已经记成日常了」——而这句话在**上面**的起点卡上（`StarterCard.kt:126` 的 `QuietNote`，作用是把已记过那一步的「把这一步记成日常」按钮换掉）。`reach()` 为了找到页面最下面的锚点卡已经向下滚过，这句话早就不在屏幕里了，同一个 dump 里必然找不到。修法是把这一句拆成**两次取屏**：先在锚点卡那份 dump 里验「不用记了 / 上午 / 「找一张白纸…」」，再 `from_top=True` 回顶**另取一份** dump 验「这一步已经记成日常了」+「记在上午」。

4. **同一时刻的两份 dump 不一致。** 第 7 次走到了锚点卡，三行断言（不用记了 / 上午 / 「找一张白纸…」）都过了，但紧接着回顶去找「这一步已经记成日常了，记在上午。」时报「屏幕上没有」。这句话在起点卡的展开区里（`StarterCard.kt:126` 的 `QuietNote`，把已记过那一步的「记成日常」按钮换掉；`StarterCard.kt:109` 的 `if (open)` 决定它只在卡片展开时才渲染），回顶去找方向是对的。可疑的是两份 dump 的差：两次取屏之间只夹了回顶的十次滑动（约 8 秒），**其间没有任何点击、页面状态没变**，而两份 dump 的其余文字逐字相同——差别只是这一句和另外两行「挑一支顺手的笔／照着喜欢的字描一遍」，一份有、一份没有。同一屏、同一状态，两次取屏给出不同的节点集，说明这是 `uiautomator dump` 在滚动之后对 Compose 无障碍树给出了一份**残缺的节点集**，不是页面真的少了东西。修法是不再赌单份 dump：回顶后**多取几份、把文字并起来**再判断（`texts_union_until()`；起初是「固定取四份」，第 12 次又被同一个症状绊倒，见第 7 条），判据也从「含『记在上午』」收紧成「含整句『这一步已经记成日常了，记在上午。』」——时段名写在整句里，读断言的人不必再去猜「上午」是哪个界面的「上午」。

5. **单步滑动超过一屏，相邻两次取屏之间会留下空隙。** 第 8~10 次都卡在同一个地方：`reach()` 找得到锚点，但**紧挨着的下一行**断言目标不在同一份 dump 里——第 8 次是「要准备：什么都不用准备」被切在视口**上沿**之外，第 9 次是卡片最下面那个「这一步做完了」按钮被切在视口**下沿**之外（同一份 dump 里「找一张白纸…」和「要准备：…」两行都在），第 10 次最彻底：`collect()` 双向扫了十八屏，硬是没见到「愿意了解一下」。根因在滑动基元 `input swipe 540 1900 540 850 250`：250ms 滑 1050px 会触发 fling，实测单步位移超过一屏（2400px）。窗口 i 覆盖 `[i*d, i*d+H]`，某个位置一旦落进 `(i*d+H, (i+1)*d)` 就一次都不会进屏，而 `uiautomator dump` **只含屏幕内的节点**，这一行便从十八份 dump 里一起消失。这和第 4 条是两回事：第 4 条是「同一时刻的两份 dump 不一致」（节点集残缺），这一条是「同一份 dump 永远不含某一行」（那行压根没进过屏）。修法是把滑动基元改成 600px/500ms 的慢滑（脚本里的 `SWIPE_DY`），单步位移约 600~1000px，相邻窗口重叠 1400px 以上，任何一行都会出现在好几份连续 dump 里；断言方式也随之收敛成两种写法——**相邻的几句用同一份 dump 里的共现**，**相隔较远的项各自 `reach` 一次**。

6. **断言摆在视口之外，而且目标只是无障碍描述。** 第 11 次把滑动基元改小之后，设置页与谈话页一次走完（`collect talk-heard-bottom` 收到「不会拿这件事给您推任何东西 / 先不用 / 愿意了解一下」三句，全绿），却死在 `assert failed: talk-confirmed should contain '展开这一步'`。两个原因叠在一起：一是「展开这一步」根本不是可见文本，它是 `StarterCard.kt:102` 上那颗按钮的 `contentDescription`（给读屏用的）；二是脚本在进入谈话页后**立刻**取了一份 dump 就往下走，而这句话在起点卡上、当时还没滚进屏。修法是把这条断言单独拆出来，用 `reach("展开这一步", "talk-confirmed-expand")` **滚到它那一屏**再断言——`reach`/`expect` 本来就会同时查 `text` 与 `content-desc`，取屏对了就必然命中。这条和第 4、5 条合起来说明一件事：**断言目标必须自己 `reach` 一次，不能借别人那份 dump**。

7. **固定取四屏的并集还是不够长。** 第 12 次把第 6 条修好之后一路绿到锚点段（`talk-anchor-title / row / slot / action / forget` 全部 ok），却又死在同一句话上：`cannot find '这一步已经记成日常了，记在上午。' near top at talk-anchor-already`。这一回的根因**既不是第 4 条的节点集残缺，也不是页面缺东西**——紧接着它上面那份 `ANCHOR texts`（`reach` 到 `talk-anchor-row` 的那份 dump）里这句话**明明白白在**：「… | 这一步做完了 | 这一步已经记成日常了，记在上午。 | 挑一支顺手的笔　大概 5 分钟 | …」。而 `texts_around_top()` 取回来的四屏并集，末尾正好停在「这一步做完了」——并集确实是从页顶开始的（「说两句」「您可以把想说的写下来」都在里面），只是**四屏 × 600px 还够不到这一句**，目标行落在第 4 屏下沿之外。修法：把「固定取几屏的并集」换成**边滚边并集、找到就停**（`texts_union_until(sub, tag, screens=8)`），上限 8 屏 × 600px = 4800px，比谈话页从开口说话到记成日常还长一截。这条的教训是：并集能治「同一时刻取屏不稳」（第 4 条），但治不了「取的范围不够长」，两者要用同一把尺子兜住——边走边并、以找到为停。

七处修完后的结果见上面的 12.2.4。七处也逐条对应 12.6 第 10 条。

### 12.3 三档字号实测

脚本 `build/walk12c.py`，表在 `build/walk12c-rerun.log`（这个脚本把表直接 print 到 stdout，所以重定向文件里就是表本身；`build/walk12c.log` 是同一份内容）。模拟器 `Physical size: 1080x2400` / `Physical density: 420`，即 2.625x。逐字如下：

```

SCHULTE FONT=标准: cells=25 rows=5 rowPitch=[158, 158, 158, 158] cellH=[90] grid=[727,1449] screenH=2400
FINDPAIR FONT=标准: cells=16 rows=4 rowPitch=[158, 158, 158] cellH=[91] grid=[726,1291] screenH=2400
SCHULTE FONT=大一点: cells=25 rows=5 rowPitch=[158, 158, 158, 158] cellH=[103] grid=[751,1486] screenH=2400

FINDPAIR FONT=更大: cells=16 rows=4 rowPitch=[170, 170, 170] cellH=[117] grid=[779,1406] screenH=2400
restored to 标准
```

`cells` 是格数，`rows` 是行数，`rowPitch` 是相邻两行格子上沿的间距，`cellH` 是单格高，`grid` 是棋盘区域的宽×高，`screenH` 是屏幕高；单位都是像素。

这张表要证的是**「娱乐页在最大字号下仍然装得下、仍然按得着」**，不是「好看」：

- `cells` / `rows` 三档完全相同（25 / 16，5 / 4）。格数与行数由规则决定，和字号无关——字号只影响每格多高、棋盘多高。
- `cellH` 随字号单调增大：舒尔特 90 → 103 → 117，找一样 91 → 105 → 117。
- `rowPitch` 前两档同为 158，最大档 170。
- 最大档棋盘高 1576（舒尔特）/ 1406（找一样），都远小于屏高 2400，没有溢出屏幕。
- 可点区域下限：最大档 `rowPitch` 170px ÷ 2.625 = **64.8dp**，大于 DR-04 写死的 56dp。三档都满足。
- 末行 `restored to 标准` 是脚本把字号改回去的确认，三档跑完不留副作用。

这一节只测了「装得下」和「按得着」，**没测「好不好看」**，见 12.6 第 4 条。

注意两个容易误读的点：**① 这个 7,550,437 字节是「首次 release 构建」的数**，和 debug 的 10,971,528 不是同一件事，也不能互相比（debug 是 §12.1 里全量 `--rerun-tasks` 两次一致的数；release 只在这一次构建里量过，没有复现第二次，所以 `docs/08` §3.3 那句「字节数别当回归判据」对它同样适用）。**② `install` 失败是预期结果，不是缺陷**——没有 `keystore.properties`，`build.gradle.kts` 的签名配置本来就不挂上；交付物是 debug APK + 模拟器走查（`docs/08` §6.1 末段已写明）。

### 12.6 本轮未验证的

1. **NFR-07 / NFR-08 的性能基线仍未测**（GAP-03）。启动耗时、页面切换耗时只有体感（模拟器上点下去就出），没有冷启动/热启动的毫秒数。排在第 13 轮之后补。
2. **`medicalWords` / `PlayWords` 只有两行残留，且是故意保留的 KDoc**（`ClaimWords.kt:7`、`:10`）。这不是漏改，见 12.4 ⑦。
3. **APK 字节数受「构建模式」影响，不能当成源码等价的判据。** 第 11 轮记录过「字节数与第 10 轮一模一样，存疑」。本轮先按旧法 `rm -rf app/build/outputs/apk/debug && ./gradlew :app:assembleDebug --rerun-tasks` 强制重跑，两次（13:12、13:13）都得到 **10,971,528** 字节，逐字节相同——这是**全量构建在同一份源码上可复现**的证据。但后来一次**增量**构建（`./gradlew :app:assembleDebug`，不带 `--rerun-tasks`）给出 **11,001,618** 字节，比全量多 30,090。为排除「是源码变了」这一解释，做了一次对照：把 `data/db/ElderDatabase.kt` 用 `git show HEAD:…` 回退到上一版再做增量构建，得 **11,001,614**，即那处 KDoc 改动恰好值 4 字节；随后已把该文件恢复成本轮版本（`git diff --stat` 复核 3 insertions / 2 deletions）。再各跑一次全量构建（14:07、14:08，源码为本轮版本），**仍是 10,971,528**，两次逐字节相同。结论：**同一份源码，全量构建逐字节可复现 = 10,971,528；增量构建 = 11,001,618。差异来自构建模式（增量路径下打包顺序/对齐/时间戳写入不同），不能归因于源码。** 因此 10,971,528 仍是有效的交付产物字节数，**不需要重装 APK、也不需要重跑设备测试**——设备测试装的正是这个字节数的产物。日志：`build/round12-apk3.log`（增量）、`round12-apk4.log`、`round12-apk5.log`（全量）。
4. **三档字号只测了「装得下、按得着」，没测「好不好看」。** 12.3 那七行全是像素测量，没有主观观感，也没有与人眼舒适度的关系结论。
5. **`domain/play` 在 API 26 上未验证。** 本轮所有设备测试与走查都跑在 API 35 的 AVD 上。代码里没有用到新 API（静态检查 ⑤ 显示这一层只依赖 `kotlin.random.Random`），但「没用到」是推断，不是实测。
6. **TalkBack 读屏下这一页未走查**（GAP-05，排在第 17 轮）。本轮只确认了统一的「返回上一页」有 `contentDescription`（走查脚本把它当唯一可靠的返回入口），娱乐页每个格子的读屏标签没有逐格核对。
7. **宣称词扫描是朴素子串，且没有人工评审。** `ClaimWordsTest` 的 7 例证的是「扫描器抓得到、每个禁用词都能命中」，不是「该禁的都禁了」。词表本身合不合规、有没有漏词，靠的还是 12.4 ① 那条 grep，不是评审结论。
8. **本轮自查发现并修正了一处失实说法。** 原稿写「加找一样时 `PlayScreen.kt` 摆格子那一段一行都没动」，`git diff --numstat` 实测是 **81 insertions / 19 deletions**，这话不成立。准确说法是：**布局**一行没动（`columns` / `chunked` / `weight` 三件事都不用改），改的只有一处**判据**——`PlayCell` 的入参从 `passed: Boolean` 换成 `mark: CellMark`，`PlayGrid` 里把 `rowIndex * game.columns + columnIndex` 提成 `val index`（`PlayScreen.kt:187`）。已同步修正 5 处：`PlayScreen.kt` 的 KDoc 两处（行数刻意保持 249）、`docs/03:507`、`records/01` 的对应两条、`records/02:584-592`。
9. **宽口径否定的 8 行全是否定式文案、窄口径网络扫描 0 行**——两个数字口径不同，写进结论时不能互相替代：窄口径只说明「没有 HTTP 客户端/URL/Socket 这些具体类型」，宽口径只说明「否定式声明都在明面上」。真正要证的「没有联网能力」还需 `AndroidManifest.xml` 无权限（12.4 ③）一起看。
10. **`walk12e` 的失败全部出在脚本这一侧，前 12 次运行都没到终点**（第 13 次通过；详见 12.2.5，七处坑逐一对应）。按时间顺序：① **起点状态**——前 4 次运行时库里「书法」已被上一轮走查定成 CONFIRMED，于是「我听见的」直接进 CONFIRMED 分支，PENDING 那三个字符串根本没渲染；第 5 次起脚本开头加 `adb shell pm clear <包名>` 从干净数据起步。② **单次滑动跳过整行**——第 5 次单向 `swipe_up` 一次滑过一屏多，把「愿意了解一下」整行跳过。③ **断言取错那一份 dump**——第 6 次 `REACH` 落到页面最下面的锚点卡，而「这一步已经记成日常了」在**上面**的起点卡里（`StarterCard.kt:126`），同一个 dump 里必然找不到。④ **同一时刻两份 dump 节点集不一致**——第 7 次同一屏、同一状态（其间只有回顶的滑动，没有任何点击），两份 dump 一份含那句、一份不含。⑤ **单步位移超过一屏留下空隙**——第 8~10 次，`reach()` 找得到锚点但紧邻的下一行不在同一份 dump 里（第 9 次实测：做法行、准备行都在屏内，最下面那个按钮不在）；第 10 次更彻底，双向扫了十八屏也没见到「愿意了解一下」。⑥ **断言摆在视口之外，而且目标只是无障碍描述**——第 11 次把滑动基元改小之后设置页与谈话页一次走完（`collect talk-heard-bottom` 三句全绿），却死在 `assert failed: talk-confirmed should contain '展开这一步'`：「展开这一步」不是可见文本，而是 `StarterCard.kt:102` 那颗按钮的 `contentDescription`，同时脚本借用的那份 dump 取在起点卡滚进屏**之前**，两件事叠在一起才找不到。⑦ **固定取四屏的并集不够长**——第 12 次把 ⑥ 修好、一路绿到锚点段（`talk-anchor-title / row / slot / action / forget` 全部 ok），又死在同一句话上；这一回它**确实在** `reach` 到的那份 dump 里（紧跟在「这一步做完了」之后），只是四屏 × 600px 的并集够不到它。第 ⑤~⑦ 条都是修完前一条之后才暴露出来的，也正是「前 4 条都修好了为什么还失败」的答案：前三条是「找错了地方」，④ 是「同一时刻取屏不稳」，⑤ 是「那行压根没进过屏」，⑥ 是「借了别人那份 dump、而且目标只是无障碍描述」，⑦ 是「并集取的范围不够长」。七处都是脚本文具的问题，**不是产品缺陷**——但也说明以前没人管「走查之间不留状态」「滚动后必须重新取整屏」「单步滑动不能超过一屏」「断言目标必须自己 reach 一次」这四件事。
