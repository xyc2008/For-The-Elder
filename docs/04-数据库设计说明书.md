## 1. 存储全景

常伴在手机上只有两种持久化位置，一共 **6 个文件**。

| # | 位置 | 物理文件（`/data/data/<包名>/`） | 内容 | 管理者 |
| --- | --- | --- | --- | --- |
| 1 | Room 库 `elder.db` | `databases/elder.db`（含 `-wal`、`-shm`） | 4 张表：作息信号、作息画像、被记住的意愿、生活锚点 | `data/db/ElderDatabase.kt` |
| 2 | 设置 DataStore | `files/datastore/settings.preferences_pb` | 称呼、字号档、首次启动日、引导是否走完、是否同意采集、上次清理日 | `data/prefs/SettingsStore.kt` |
| 3 | 节流 DataStore | `files/datastore/intervention.preferences_pb` | 「上次开口 / 上次被接话 / 连续被忽略次数」 | `data/intervention/InterventionStore.kt` |

**没有第 4 个位置**：没有缓存目录使用、没有 `SharedPreferences`、没有外部存储读写、没有网络。`AndroidManifest.xml` 里权限声明 **0 条**、`<receiver>` **0 个**——后者是因为采集用的广播接收者在运行时按用户意愿动态注册（见 §10.3）。

两种存储的分工是一条硬边界：

> **凡是「用户攒出来的东西」进 Room；凡是「这台设备的一个开关值」进 DataStore。**

这条边界不是风格问题。作息记录、被记住的意愿、用户自己定的日常小事这三样，坏掉之后用户会觉得「我的东西没了」；而字号档位坏掉，重新点一下就好。前者需要事务、需要迁移、需要 schema 版本；后者不需要，也不需要为它建一张表。

## 2. 选型与三条红线

### 2.1 为什么是 Room

`docs/02-概要设计说明书.md` 已经把「数据层」划成一个独立分层，这里只补选型理由：

- **唯一索引是需求的一部分，不是性能优化。** 「同一件事只记一条」（`wish`）、「一个起点只记一条日常」（`anchor`）、「同一次亮屏不记两遍」（`rhythm_signal`）三句话在代码里都是 `unique = true`。把去重放在上层「先查后插」也能写出来，但那是**约定**；写成唯一索引是**结构**，并发下也成立（`records/03-架构决策记录.md` 的 ADR-014）。
- **迁移要能被检查。** `exportSchema = true`，schema 落盘并随代码提交，`MigrationTest` 拿上一版 schema 建旧库、跑迁移、再让 Room 校验表结构。SQLite 手写也能做，但没人替你校验「你写的表和你以为的表是不是同一张」。
- **查询要能被断言。** 库层的用例直接读表验证「真正写进去几条」，而不是靠仓库返回值。

### 2.2 为什么有两份 DataStore

`settings` 与 `intervention` 分开，是因为设置页有一个「恢复到出厂设置」按钮，它执行 `prefs.clear()`。节流状态如果混在同一个文件里，用户点一次重置就会顺带丢掉「上次说到哪儿了」——而确认对话框里并没有承诺这件事。分开之后，各自的清理范围就是各自的范围（`data/intervention/InterventionStore.kt:20-26` 的注释）。

### 2.3 三条红线

1. **禁止 `fallbackToDestructiveMigration()`。** 版本号变更必须配一条 `Migration`。理由是库里是用户攒的数据，重建库会让界面显示「还没有记录」，错得像用户手机自己出了问题。
2. **不上传、不联网。** 库里没有任何一列是为了和远端对齐而存在的：没有 `remoteId`、没有 `syncedAt`、没有 `deleted`（软删）。真删就是 `DELETE`。
3. **库里不存能算出「评价」的东西。** 没有连续天数、没有完成次数、没有「最近一次做到」。AC-09.2 要求用户中断之后不显示「已中断 N 天」、不归零、不催人恢复——常伴的做法是让库里**没有地方能算出 N**（见 §4.4 与 §11.2）。

## 3. 逻辑模型

四张表，**没有外键**（`"foreignKeys": []` 出现在每一张实体的 schema 里）。关系靠值表达，不靠约束：

```
        ┌──────────────────┐
        │  rhythm_signal   │  一条 = 一次屏幕/充电事件
        │  (原始事实)       │  保留 30 天
        └────────┬─────────┘
                 │ 推断（domain/engine/rhythm，纯函数）
                 ▼
        ┌──────────────────┐
        │  daily_rhythm    │  一行 = 一个作息日的画像
        │  (派生态)         │  保留 30 天；可随时重算
        └──────────────────┘

        ┌──────────────────┐         ┌──────────────────┐
        │      wish        │         │      anchor      │
        │  被记住的意愿      │         │  用户自己定的日常  │
        │  唯一 (kind,term) │         │  唯一 (optionId)  │
        └──────────────────┘         └──────────────────┘
              ▲  无保留期，删不删由用户决定  ▲
              └────────── 与左半部分无任何关联 ──────────┘
```

三处值得留意：

- **左半部分是「推断链」，右半部分是「记忆」**，两者之间**一条外键、一个共享 id 都没有**。这是刻意的：作息画像坏掉不应该影响意愿，意愿的存在也完全不依赖作息。测试里可以单独建其中一头的库。
- **`anchor` 与 `wish` 之间也没有关系。** 锚点是从「兴趣陪伴」里挑一件事记成日常，`anchor.term` 会等于某个 `wish.term`，但这是一个**字符串巧合**，不是约束。用户可以把意愿删掉而留下日常——常伴不该因为「你说过想学书法」被删掉，就把「照着喜欢的字描一遍」也一起删掉。
- **没有用户表、没有账号表、没有内容表。** 单用户、无登录、内容全部编译进 APK（`domain/play/`、`domain/voice/` 是纯 Kotlin 常量）。库里也就没有需要和服务端对齐的表。

## 4. 表设计

约定：所有 `Long` → `INTEGER`，`Int` → `INTEGER`，`String` → `TEXT`，`Float` → `REAL`；可空类型在 DDL 里是同一 affinity 但 `NOT NULL` 缺席。

### 4.1 `rhythm_signal` —— 作息信号

实体：`data/db/RhythmSignalEntity.kt`（34 行）。DAO：`data/db/RhythmSignalDao.kt`（47 行）。

建表语句（照 `3.json` 的 `createSql` 逐字抄，`${TABLE_NAME}` 即 `rhythm_signal`）：

```sql
CREATE TABLE IF NOT EXISTS `rhythm_signal` (
  `id` INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  `kind` TEXT NOT NULL,
  `atEpochMilli` INTEGER NOT NULL,
  `offsetSeconds` INTEGER NOT NULL
)
```

| 列 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| `id` | INTEGER | PK, AUTOINCREMENT, NOT NULL | 自增主键。**没有任何业务含义**，也不当计数器用（见下） |
| `kind` | TEXT | NOT NULL | 信号种类，存枚举名（`SCREEN_ON` / `SCREEN_OFF` / `USER_PRESENT` / `CHARGING_START` / `CHARGING_END`） |
| `atEpochMilli` | INTEGER | NOT NULL | 事件发生的**绝对时刻**（毫秒） |
| `offsetSeconds` | INTEGER | NOT NULL | 事件发生时设备的**时区偏移**（秒） |

三处设计取舍：

**① 存绝对时刻，另外单存时区偏移。** 不存「本地时间字符串」：字符串的排序、去重、30 天清理都要先解析，而且在用户改时区之后会指向另一个瞬间。偏移单独一列，是为了让本地时刻能被**原样还原**——推算出的作息画像必须和用户看到的手机时间一致，不能因为后来换了个时区就把历史作息整体平移几小时。

**② `kind` 存字符串而非枚举序号。** 以后往 `RhythmKind` 里插一种新信号时，老数据不会被错读成别的种类。同一条规矩在 `wish.status`、`anchor.slot` 上重复了三次。

**③ `id` 不当计数器。** `insertAll` 返回每个位置的 rowId，被 `INSERT OR IGNORE` 挡掉的返回 `-1`。行号**不保证连续**——AUTOINCREMENT 会把被 IGNORE 掉的那次序号也用掉。设备上实测插「[重复, 新, 新]」返回 `[-1, 3, 4]`，而不是想当然的 `[-1, 2, 3]`。所以「写进去几条」只能数正数：

```kotlin
return signalDao.insertAll(rows).count { it != -1L }   // RhythmRepository.kt:64
```

这个数字要显示给用户（设置页的「已记录 N 条」），算错就是骗人。

**写入路径**：`RhythmCollector` → `CapturedSignal` → `RhythmMapping.toEntity`（补上 `zone` 算出的 `offsetSeconds`）→ `RhythmRepository.record`。采集器**不需要自己去重**，重复由唯一索引挡掉。

### 4.2 `daily_rhythm` —— 作息画像

实体：`data/db/DailyRhythmEntity.kt`（32 行）。DAO：`data/db/DailyRhythmDao.kt`（36 行）。

```sql
CREATE TABLE IF NOT EXISTS `daily_rhythm` (
  `dayEpochDay` INTEGER NOT NULL,
  `wakeOffsetMinutes` INTEGER NOT NULL,
  `sleepOffsetMinutes` INTEGER NOT NULL,
  `activeSpans` TEXT NOT NULL,
  `idleSpans` TEXT NOT NULL,
  `nightChargingOffsetMinutes` INTEGER,
  `sampleDays` INTEGER NOT NULL,
  `confidence` REAL NOT NULL,
  `computedAtEpochMilli` INTEGER NOT NULL,
  PRIMARY KEY(`dayEpochDay`)
)
```

| 列 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| `dayEpochDay` | INTEGER | PK, NOT NULL | **作息日**的日期（epoch day），以凌晨分界点 `RhythmConfig.DEFAULT_CUTOVER_HOUR` 为界 |
| `wakeOffsetMinutes` | INTEGER | NOT NULL | 起床时刻相对作息日起点的分钟数（0..1439） |
| `sleepOffsetMinutes` | INTEGER | NOT NULL | 入睡时刻，同上 |
| `activeSpans` | TEXT | NOT NULL | 活动时段，`HH:mm-HH:mm,HH:mm-HH:mm` |
| `idleSpans` | TEXT | NOT NULL | 闲置时段，同上编码 |
| `nightChargingOffsetMinutes` | INTEGER | **可空** | 夜间充电开始的分钟数。**没有这个习惯就是 NULL**，不是 0 |
| `sampleDays` | INTEGER | NOT NULL | 这次推断用到的有效天数 |
| `confidence` | REAL | NOT NULL | 置信度 0.0~1.0 |
| `computedAtEpochMilli` | INTEGER | NOT NULL | 这次推断算出来的绝对时刻（观测用） |

四处取舍：

**① 这是派生态。** 随时可以拿 `rhythm_signal` 重算出来，所以它坏掉了不算数据丢失，清掉重算即可。存它只是为了避免每次开界面都跑一遍推断——`DailyRhythmEntity.kt:6-10` 把这句话写在了 KDoc 里，它是这一层「可以随便删」的许可证。

**② 时刻存偏移分钟数，不存 `LocalTime` 也不存时间戳。** 作息日以凌晨分界点为界，偏移量与分界点必须写死在同一套换算里（`RhythmMapping` 的 `toRhythmOffset`）。存成 `LocalTime` 会让「这一行属于哪个作息日」变成可以含糊的事情。

**③ 时段存文本，不存二进制或序列化对象。** 出事时能用 `sqlite3` 直接看出来里面是什么，这一点比省几十个字节重要。编解码在 `data/db/SpansCodec.kt`（50 行），**`decode` 用返回 `null` 表达失败而不是抛异常**：一行坏数据不该让设置页崩掉，上层看到 `null` 就当这天的画像不存在，等下一次推断重算。判为损坏的三种情况：一段里没有 `-`、时刻不是两位的 `HH:mm`、空段（`07:00-07:00`）。空列表编成空串——空串与「字段是空的」在库里本就该是同一种东西。

**④ 一天一行，重复推断整行覆盖（`OnConflictStrategy.REPLACE`），刻意不保留历史版本。** 留着「上个月的作息」既没用，又会诱使后面的功能去比较「最近作息变了没有」——那种比较一旦做出来，就会变成对用户的评价（`DailyRhythmDao.kt:11-14`）。

**写入路径**：`RhythmProfileService` → `RhythmRepository.saveProfile(dayEpochDay, rhythm)`；读取 `profile(dayEpochDay)` / `latestProfile()`。

### 4.3 `wish` —— 被记住的意愿

实体：`data/db/WishEntity.kt`（34 行）。DAO：`data/db/WishDao.kt`（59 行）。

```sql
CREATE TABLE IF NOT EXISTS `wish` (
  `id` INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  `kind` TEXT NOT NULL,
  `term` TEXT NOT NULL,
  `evidence` TEXT NOT NULL,
  `sentence` TEXT NOT NULL,
  `status` TEXT NOT NULL,
  `heardAtEpochMilli` INTEGER NOT NULL,
  `decidedAtEpochMilli` INTEGER
)
```

| 列 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| `id` | INTEGER | PK, AUTOINCREMENT, NOT NULL | 自增主键；界面按 `id ASC` 排，得到「首次听到的先后」这个稳定顺序 |
| `kind` | TEXT | NOT NULL | 意愿种类，存 `IntentKind` 枚举名：`INTEREST` / `STATE` / `REQUEST` |
| `term` | TEXT | NOT NULL | **规范名**，例如 `书法`（不是原话） |
| `evidence` | TEXT | NOT NULL | 判定的**逐字片段**，例如 `一直想学书法` |
| `sentence` | TEXT | NOT NULL | 当时说的**整句原话** |
| `status` | TEXT | NOT NULL | 状态，存 `WishStatus` 枚举名：`PENDING` / `CONFIRMED` / `DECLINED` |
| `heardAtEpochMilli` | INTEGER | NOT NULL | 首次听到的绝对时刻 |
| `decidedAtEpochMilli` | INTEGER | **可空** | 用户表态的绝对时刻；**没表过态就是 NULL** |

四处取舍：

**① 唯一索引 `(kind, term)` 是「同一件事只记一条」的结构性保证。** 用户今天说「想学书法」，三个月后又说一遍，还是同一条，而且**状态不会被这次重复提到冲掉**——这靠 `INSERT OR IGNORE` 加唯一索引从结构上成立，不靠上层先查后插。并发下也不会出现两条。

**② `evidence` 与 `sentence` 存用户原话，不改写。** 存下来是为了在「常伴记住的事」里能回答「它是从哪儿听出这件事的」。答不出这个问题，用户就没法判断它记得对不对。对应的不变式（`text.substring(start, endExclusive) == evidence`）由单测守着，见 `domain/engine/intent/IntentScan.kt:21-22`。

**③ 时间只存绝对毫秒，不带时区偏移。** 与 `rhythm_signal` 不同——这张表上**没有任何一处需要把时间还原成本地时刻显示**，界面不显示任何时间。存了偏移就是给以后「显示时间」留后门。

**④ 刻意不存「最近一次提到是什么时候」。** 一旦能显示「上次说的时候是三个月前」，这个 App 就从陪伴变成了评价（`domain/wish/Wish.kt` 的 KDoc）。这也解释了为什么重复提到不会更新 `heardAtEpochMilli`。

**唯一的写改语句**（这张表上只有这一条 `UPDATE`）：

```sql
UPDATE wish SET status = :to, decidedAtEpochMilli = :at
WHERE kind = :kind AND term = :term AND status = :from
```

带 `AND status = :from` 是**乐观并发**：只有当前状态正好等于调用方以为的那个时才生效。用户连点两下、或者补录的写入还在路上时，第二次不会把一个已经落定的状态再盖一遍，而是返回 0 行。返回 0 有两种情况——这条意愿根本不在（点得比落库快），或者它已经不是 `from` 了（重复点）——两种都应当被调用方当成「这次点击没有生效」，而不是硬写一遍。改动只有一处且是乐观并发，这张表就不需要额外加锁。

**读取**：`allFlow()` 按 `id ASC` 发出，供「常伴记住的事」列表用；界面不显示时间也能有稳定顺序。

### 4.4 `anchor` —— 用户自己定的日常小事

实体：`data/db/AnchorEntity.kt`（31 行）。DAO：`data/db/AnchorDao.kt`（36 行）。

```sql
CREATE TABLE IF NOT EXISTS `anchor` (
  `id` INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  `term` TEXT NOT NULL,
  `optionId` TEXT NOT NULL,
  `action` TEXT NOT NULL,
  `slot` TEXT NOT NULL,
  `createdAtEpochMilli` INTEGER NOT NULL
)
```

| 列 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| `id` | INTEGER | PK, AUTOINCREMENT, NOT NULL | 自增主键；列表按 `id ASC` 排 |
| `term` | TEXT | NOT NULL | 这件事的名字，例如 `书法`（与 `wish.term` 同值，但无外键） |
| `optionId` | TEXT | NOT NULL | 起点选项的稳定 id（来自 `domain/companion/StarterOptions.kt`） |
| `action` | TEXT | NOT NULL | 具体做法，例如 `照着喜欢的字描一遍` |
| `slot` | TEXT | NOT NULL | 时段，存 `AnchorSlot` 枚举名：`MORNING` / `AFTERNOON` / `EVENING` / `ANYTIME` |
| `createdAtEpochMilli` | INTEGER | NOT NULL | 记下这件事的绝对时刻 |

**这张表的全部价值在于它没有的东西。** 它只有六列，**没有一列是计数**：

> 没有连续天数、没有完成次数、没有「最近一次做到」、没有 `lastDoneAt`、没有 `streak`。

AC-09.2 要求用户中断之后不显示「已中断 N 天」、不归零、不催人恢复。常伴把这句话做成了结构性的：**库里没有地方能算出 N，界面就不可能显示它。** 这是这条需求最省事的守法——不需要在界面层记得「别写那句话」，也不需要写测试守着「没有那句话」。

配套的第二条结构性事实：**DAO 里没有 `UPDATE`。**（`AnchorDao.kt:12-14`）

```
这张表上只有三种语句：INSERT OR IGNORE、SELECT、DELETE。
```

锚点只有两种命运——被用户记下来，或者被用户删掉。没有「完成」也没有「跳过」要记录，所以不需要改任何一行。少了这条语句，「已中断 N 天」这类显示在数据层就无处生根。

第三处：**唯一索引落在 `optionId` 上**，不是 `(term, optionId)`。一个起点只记一条日常。用户想改时段，删掉再记一次即可——比在同一件事上维护两个时段更简单，也不会出现「同一件事上午一条、晚上一条」的重复。

## 5. 索引设计

库里的索引共 **4 个**，全部由实体注解生成，没有手写索引。

| 表 | 索引名 | 列 | 唯一 | 为什么存在 |
| --- | --- | --- | --- | --- |
| `rhythm_signal` | `index_rhythm_signal_kind_atEpochMilli` | `(kind, atEpochMilli)` | **是** | 给「同一个广播被重复投递」准备。系统在某些情况下会把一次亮屏报两遍，重复事件会让「这天信号数」虚高，直接影响有效天的判定 |
| `rhythm_signal` | `index_rhythm_signal_atEpochMilli` | `(atEpochMilli)` | 否 | 撑 `since(cutoff)` 与 `deleteBefore(cutoff)` 两个按时刻的区间操作 |
| `wish` | `index_wish_kind_term` | `(kind, term)` | **是** | 「同一件事只记一条」的结构性保证 |
| `anchor` | `index_anchor_optionId` | `(optionId)` | **是** | 「一个起点只记一条日常」的结构性保证 |

**没有任何索引是为了「排序快」而建的。** 两张记忆表都是按 `id ASC` 全表读（常伴的用户最多记几十条），刻意不为列表页建 `ORDER BY` 用不上的复合索引。

**唯一索引承担了去重，所以代码里没有「先查后插」的地方。** 这一点在数据层是可见的：`RhythmSignalDao.insertAll`、`WishDao.insertAll`、`AnchorDao.insert` 全部是 `OnConflictStrategy.IGNORE`，且都返回 `List<Long>` 或 `Long`，把「有没有真的插进去」交给调用方判断（`-1` = 被挡掉）。

## 6. 编码与时间约定

四条规矩，全库一致：

| 规矩 | 落地 | 例外 |
| --- | --- | --- |
| 枚举存**名字符串** | `rhythm_signal.kind`、`wish.kind`、`wish.status`、`anchor.slot` | 无 |
| 时刻存**绝对毫秒**（`*EpochMilli`） | `rhythm_signal.atEpochMilli`、`wish.heardAtEpochMilli`、`wish.decidedAtEpochMilli`、`anchor.createdAtEpochMilli`、`daily_rhythm.computedAtEpochMilli` | 无 |
| 需要还原本地时刻的，**另存偏移** | 只有 `rhythm_signal.offsetSeconds` | `daily_rhythm` 存的是相对作息日起点的分钟数，不是绝对时刻，所以不需要偏移 |
| 日期用 **epoch day**（`*EpochDay`） | `daily_rhythm.dayEpochDay` | DataStore 里的 `first_launch_day` / `last_prune_day` 同约定 |

**列名后缀是约定的一部分**：看到 `…EpochMilli` 就知道是绝对毫秒，看到 `…OffsetMinutes` / `…OffsetSeconds` 就知道是相对量，看到 `…EpochDay` 就知道是日期。没有一列叫 `time`、`date`、`created`。

**枚举名解析失败时的兜底各表不同，是刻意的：**

| 位置 | 解不出来时 | 理由 |
| --- | --- | --- |
| `WishEntity.toStatus()` | `WishStatus.DECLINED` | **宁可当「人家说了不用」**。错当成 `CONFIRMED` 就会拿一件用户没答应的事去推内容（AC-07.1），错当成 `PENDING` 就会再问一遍（AC-07.3）。只有 `DECLINED` 的错法两头都安全：不给内容，也不再提 |
| `AnchorSlot.parse()` | `AnchorSlot.ANYTIME` | **宁可时段不准，也不能把用户记下的事静默丢掉**（`Anchor.kt:26-27`） |
| `SpansCodec.decode()` | 返回 `null` → 当这天的画像不存在 | 画像是派生态，丢了不心疼 |

三处兜底方向不同，但同一条原则：**错的时候往「更不打扰用户」和「不丢用户东西」那一侧倒。**

## 7. 迁移与版本演进

### 7.1 现状

| 项 | 值 |
| --- | --- |
| 当前版本 | **3**（`ElderDatabase.kt:33`） |
| 库文件名 | `elder.db`（`ElderDatabase.FILE_NAME`） |
| 已注册迁移 | `MIGRATION_1_2`、`MIGRATION_2_3`（`data/db/Migrations.kt`，64 行） |
| `fallbackToDestructiveMigration()` | **未使用，且不允许使用** |
| schema 落盘 | `app/schemas/com.fortheelder.data.db.ElderDatabase/{1,2,3}.json` |
| 落盘目录的来源 | `app/build.gradle.kts:90` 的 `ksp { arg("room.schemaLocation", "$projectDir/schemas") }` |
| 版本 3 的 identityHash | `15d43e0672939af50eca26dc5cd99df2` |

### 7.2 两条迁移做了什么

两条迁移的形状相同：**只建新表，不动已有的表。**

| 迁移 | 从 → 到 | 语句 | 保住的数据 |
| --- | --- | --- | --- |
| `MIGRATION_1_2` | 1 → 2 | `CREATE TABLE IF NOT EXISTS wish (...)` + `CREATE UNIQUE INDEX IF NOT EXISTS index_wish_kind_term ON wish (kind, term)` | 两张作息表一条不丢（这一版没有任何列改名或改类型） |
| `MIGRATION_2_3` | 2 → 3 | `CREATE TABLE IF NOT EXISTS anchor (...)` + `CREATE UNIQUE INDEX IF NOT EXISTS index_anchor_optionId ON anchor (optionId)` | 三张已有表一条不丢 |

**迁移语句是照 schema JSON 抄的，不是凭记忆写的。** `Migrations.kt:14-16` 把这条写成了规矩：语句必须与 `app/schemas/.../N.json` 里 Room 生成的 `createSql` **逐字一致**，否则 `MigrationTestHelper` 的校验会失败。

### 7.3 谁在守着这条规矩

`app/src/androidTest/` 下的 `MigrationTest`：拿上一版的 schema 建旧库 → 跑迁移 → 让 Room 校验表结构。表结构对不上就直接红。这一条用例的存在，使「忘记写迁移」和「迁移写错一个字」都在 CI 级别就被拦下，而不是等用户升级后发现数据没了。

配套的一条：**仪器化测试不共用 `elder.db`。** `ElderDatabase.open(context, name = FILE_NAME)` 的 `name` 是参数，测试传自己的名字。理由记在 `ElderDatabase.kt:25-29`：几个 androidTest 会在同一个进程里 `deleteDatabase` 再重开同一个文件，而应用容器的 Room 实例一旦建好就一直在；两者共用 `elder.db` 时，真机上出现过 `no such table: wish` 的崩溃，事后留下的库是个 `user_version=0`、只剩 `android_metadata` 的空壳。

### 7.4 下一版迁移的写法（给下一位改库的人）

1. 改实体 → 升 `version` → 写 `MIGRATION_n_(n+1)` → **从新生成的 `(n+1).json` 里把 `createSql` 抄进迁移**。
2. 在 `ElderDatabase.open` 的 `addMigrations(...)` 里注册。
3. `MigrationTest` 加一条 `n → n+1` 的用例。
4. 只建新表就别动老表；确实要改列，迁移里得写 `CREATE TABLE 新 + INSERT SELECT + DROP 旧 + ALTER RENAME`，并且**必须先想清楚老数据怎么落到新列上**。
5. 四条都做完才算改完；`exportSchema` 已经保证了第 1 步有东西可抄。

## 8. 数据生命周期

### 8.1 保留期

| 表 | 保留期 | 常量 | 依据 |
| --- | --- | --- | --- |
| `rhythm_signal` | **30 天** | `SIGNAL_RETENTION_DAYS`（`RhythmRepository.kt:22`） | 30 天是「够推断出作息」和「不无限攒数据」之间的取舍：推断最少只要 3 天，30 天足够看出这个月和下个月有没有变化，同时让 App 手里始终只有最近一个月的屏幕开关记录 |
| `daily_rhythm` | **30 天** | `RHYTHM_RETENTION_DAYS`（`RhythmRepository.kt:28`） | 与信号同一个窗口。画像由信号推出来，留下比信号更老的画像只会出现「画像里的日子已经没有信号了」这种对不上的状态 |
| `wish` | **无保留期** | 无 | 用户说过的事不该因为时间到了而被忘掉 |
| `anchor` | **无保留期** | 无 | 同上 |

**删除只由用户决定**（两张记忆表）：`wish` 有「不用记了」（删一条）和「全部清空」；`anchor` 有「不用记了」。设置页另有「清空作息数据」，它删的是左半部分两张表，与用户的记忆无关。

### 8.2 窗口按「作息日」切，不按自然日切

`RhythmRepository.windowStartEpochMilli(days)` 的算法：

```
今天(作息日) 减去 (days - 1) 天，取该日的 cutoverHour 点，换成绝对毫秒
```

不写成「此刻往前推 30×24 小时」，是为了让「最近 30 天」在界面上和在库里是同一件事——不然下午三点打开时，窗口起点会落在某个凌晨三点半，切在半夜里。

同一条约定也用在 `RhythmMaintenance` 的「今天是否已经清过」判断上：它必须和仓库、推断引擎用**同一个** `cutoverHour`，否则会出现一天清两次或一天都不清。

### 8.3 清理的执行节奏

`prune()` 在**一个事务**里删信号 + 删画像：

```kotlin
suspend fun prune(): Int = database.withTransaction { ... }   // RhythmRepository.kt:102
```

只删成功一半会留下「画像还在、信号没了」的状态，下次重算会把画像换成「数据不足」。

**「一天最多一次」记在设置里**（`SettingsStore.lastPruneEpochDay`），由 `RhythmMaintenance.pruneIfDue()` 判断，返回**真正删掉的行数**——测试用它区分「清了但没什么可删」和「今天不打算清」，两者都返回 0 会让用例写不出有效断言。

**不引入 WorkManager。** 清理只是两条 `DELETE`，挂在进程启动时跑一次就够——常伴的进程本来就只在用户打开它的时候才活着。这个日期不是用户设置，所以它**不进 `AppSettings`**，界面看不到它。

### 8.4 「恢复到出厂设置」的边界

| 动作 | 影响范围 | 不影响 |
| --- | --- | --- |
| 设置页「恢复到出厂设置」 | `settings` DataStore 全部键（`prefs.clear()`） | `intervention` DataStore、`elder.db` 全部 4 张表 |
| 设置页「清空作息数据」 | `rhythm_signal` + `daily_rhythm` | `wish`、`anchor`、两个 DataStore |
| 意愿列表「不用记了」 | `wish` 里那一条 | 其他 |
| 意愿列表「全部清空」 | `wish` 全表 | `anchor`、作息 |
| 日常列表「不用记了」 | `anchor` 里那一条 | 其他 |

不存在任何「一键清空所有东西」的按钮。要删用户的记忆，得在记忆自己的列表里逐项决定。

## 9. 并发与一致性

单进程、单用户，但仍然处理了三类真实竞态——它们都来自「用户点得比落库快」。

| 竞态 | 位置 | 处理 | 为什么不能省 |
| --- | --- | --- | --- |
| 同一件事被两次识别写入 | `wish` / `rhythm_signal` | 唯一索引 + `INSERT OR IGNORE` | 去重靠结构，不靠上层先查后插；并发下也不会出现两条 |
| 用户连点两下表态 | `WishDao.decide` 的 `AND status = :from` | 乐观并发，返回 0 行 | 不硬写一遍，第二次点击就当没生效 |
| 用户点了一句示例话，同时补录的写入还在路上 | `WishRepository.writeLock`（`Mutex`） | 写入串行化 | 这是**一个真实的竞态**，不是保险起见（`WishRepository.kt:25`） |
| 同上，锚点的添加与删除 | `AnchorRepository.writeLock`（`Mutex`） | 写入串行化 | 理由与 `WishRepository` 相同（`AnchorRepository.kt:29`） |

`InterventionStore` 的计数则是在 DataStore `edit` 的**读改写**里算的（`ThrottleState.afterSpoken`），这样两次开口的写入撞在一起时，不会各自基于同一份旧状态把计数算成同一个值。

**读路径全部不加锁**：两张记忆表用 `Flow` 发全表，Room 自己保证快照一致；作息表用 `suspend` 单次查询。「已记录 N 条」用 `countFlow()`，改一下立刻能看到。

## 10. DataStore 键设计

### 10.1 `settings`（`data/prefs/SettingsStore.kt`）

六个键定义在 `SettingsStore.kt` 的私有伴生对象里；DataStore 实例则在 `data/prefs/SettingsDataStore.kt` 用 `Context` 扩展属性声明（`by preferencesDataStore(name = "settings")`），让 `preferencesDataStore` 只创建一次实例——它内部会做同名去重，重复定义会抛异常。两者分开是为了不让「键有哪些」和「实例怎么来」互相牵制。

| 键 | 类型 | 默认 | 含义 | 进 `AppSettings`？ |
| --- | --- | --- | --- | --- |
| `address` | String | 无（= 未填写） | 用户希望被怎么称呼 | 是 |
| `font_size` | String | `standard` | 字号档，存 `FontSize.storageKey`（`standard` / `large` / `extra`） | 是 |
| `first_launch_day` | Long | 无 | 首次启动当天（epoch day）。`ensureFirstLaunchRecorded()` 写成「没有才写」，否则每次启动都会把首次日期冲掉，「认识多少天了」就永远显示第 1 天 | 是 |
| `onboarding_done` | Boolean | `false` | 引导是否走完。`false` 时应用只显示引导页 | 是 |
| `collect_rhythm` | Boolean | **`false`** | 是否同意采集作息信号（AC-04.4） | 是 |
| `last_prune_day` | Long | 无 | 上次清理是哪一天（作息日）| **否**——界面上看不到它，用户也不该能改它 |

**`collect_rhythm` 默认 `false` 是一条需求，不是技术上的稳妥：** 没问过用户之前不采。做成默认开启、再让用户自己去设置里找开关关掉，等于拿用户的没看到当作同意。`false` 时应用功能完整——问候、称呼、字号、设置全部照常，只是没有作息画像可用。

**加一个键时默认值的选择比键本身重要**：任何一个新键，都要先问「用户没表过态时它应该是哪个值」，而不是「Go/Kotlin 给的类型默认值是什么」。

### 10.2 `intervention`（`data/intervention/InterventionStore.kt`）

三个键同样定义在 `InterventionStore.kt` 的私有伴生对象里（DataStore 实例的声明方式与 10.1 同构）。

| 键 | 类型 | 含义 |
| --- | --- | --- |
| `ignored_streak` | Int（`intPreferencesKey`） | 连续被忽略次数 |
| `last_spoken_at` | Long（`longPreferencesKey`） | 上次开口的绝对毫秒 |
| `last_answered_at` | Long（`longPreferencesKey`） | 上次被接话的绝对毫秒 |

这一层**只做存取，不做判断**：要不要说话由 `domain/engine/intervention/InterventionWindow` 现算。这一层要是也插一句判断，同一件事就有两处说法，日后的分歧会很难查。

时刻存 epoch 毫秒、读回来用 `zone` 还原成 `LocalDateTime`。存 `LocalDateTime.toString()` 要避开格式解析——用户改了系统时区之后，存字符串会得到一串「本地时间看起来对、实际含义已经变了」的值。

### 10.3 为什么库里没有「采集开关」这一列

采集开关在 DataStore，不在库里。改动由 `core/AppContainer` 监听到之后**立刻注册或注销广播接收者**，不需要重启应用；撤回同意**不删已经记下的数据**——那是两件事，删数据在设置页有单独的按钮、单独问一次。

`<receiver>` 在 `AndroidManifest.xml` 里是 **0 个**：接收者全部在运行时按用户意愿动态注册。这样「没同意就不采」是清单级别的可核查事实，而不是一句代码注释。

## 11. 刻意不做的结构

把「没做的事」写下来，是为了防止下一位改库的人把它当成遗漏补上。

### 11.1 没有的表

| 没有 | 理由 |
| --- | --- |
| 用户表 / 账号表 | 单用户、无登录。`docs/01` 里没有一条需求需要区分「谁的」数据 |
| 内容表（陪伴话术、游戏词表、起点选项） | 全部编译进 APK 的纯 Kotlin 常量（`domain/play/PlayCatalog.kt`、`domain/voice/`、`domain/companion/StarterOptions.kt`） |
| 同步表 / 变更日志 / 软删标记 | 不上传，就没有需要对齐的远端 |
| 事件日志表 / 埋点表 | 不做行为分析。App 里没有一条需求是「统计用户做了什么」 |

### 11.2 没有的列

| 没有的列 | 本该出现在哪 | 为什么不做 |
| --- | --- | --- |
| `streak` / `doneCount` / `lastDoneAt` | `anchor` | AC-09.2：中断后不显示「已中断 N 天」、不归零、不催人恢复。库里没有地方能算出 N，界面就不可能显示它 |
| `completed` / `skipped` | `anchor` | 锚点没有「完成」这个状态，所以 DAO 里连 `UPDATE` 都没有 |
| `lastMentionedAt` | `wish` | 显示「上次说的时候是三个月前」会让 App 从陪伴变成评价 |
| 任何本地时刻字符串 | 全部表 | 本地时刻只在**需要显示**时才由绝对时刻 + 偏移还原；一旦落库成字符串，用户改时区后含义就变了 |
| `deleted`（软删） | `wish` / `anchor` | 用户点「不用记了」就是真删。留着标记会诱使以后「恢复一下」，而用户并没有要求这个能力 |
| 历史版本的画像 | `daily_rhythm` | 比较「最近作息变了没有」会变成对用户的评价（`DailyRhythmDao.kt:11-14`） |

### 11.3 没有的语句

| 表 | 没有 | 理由 |
| --- | --- | --- |
| `anchor` | 任何 `UPDATE` | 锚点只有「被记下」和「被删掉」两种命运 |
| `wish` | 除 `decide` 之外的 `UPDATE` | 意愿只改状态，不改内容；原话一旦记下就不再改 |
| `rhythm_signal` | `UPDATE` | 信号是事实，事实不改，只过期删除 |
| 全部 | 手写索引 | 索引全由实体注解生成，schema JSON 是唯一的真相 |
