## 1. 文档目的与范围

本文回答三个问题：

1. 常伴依赖的外部世界有哪些面，各自承诺什么、不承诺什么？
2. 模块之间通过什么签名通信，谁负责兜底？
3. 一个输入不成立时（没数据、听不出、时钟被往回调），系统对外承诺什么行为？

**不**重复的三件事：表结构（`docs/04`）、算法内部步骤（`docs/03`）、逐条文案（`docs/09`）。

**一处与 TripWear 的关键差别**：常伴**一个网络接口都没有**。所以本文第 2 节不是「网络 API 清单」，而是「Android 系统服务与平台入口」——这是常伴**唯一**的外部依赖面，到那里就结束了。第 3~5 节才是本文的主体。

分层总览（括号里是本文的接口编号）：

```
┌──────────────────────────────────────────────────────────────┐
│ Compose 界面      AppRoot / MainNav / 四个 Screen / 通用组件    │ IF-20 ~ IF-28
├──────────────────────────────────────────────────────────────┤
│ ViewModel         HomeViewModel / TalkViewModel / PlayViewModel │ IF-15 ~ IF-19
├──────────────────────────────────────────────────────────────┤
│ 领域层（纯函数：不认识 Android、不认识数据库）                    │ IF-06 ~ IF-14
│   GreetingEngine   IntentScanner    InterventionWindow          │
│   RhythmInference  WishGate         AnchorRules                 │
│   StarterCatalog   PlayCatalog      CopyRules / 四个 Voice       │
├──────────────────────────────────────────────────────────────┤
│ 数据层（仓库 + 服务 + 采集器）                                   │ IF-02 ~ IF-05
│   SettingsStore      InterventionStore   RhythmRepository       │
│   RhythmProfileService  RhythmMaintenance  RhythmCollector      │
│   WishRepository     AnchorRepository                           │
├──────────────────────────────────────────────────────────────┤
│ 平台        Room(ElderDatabase) │ DataStore ×2 │ 广播接收者       │ IF-01 ~ IF-02
└──────────────────────────────────────────────────────────────┘
外部面：Android 系统服务（两个 DataStore 文件、一个 SQLite 库、五个系统广播）
        平台入口（Application / 单个 Activity / AndroidManifest）
        没有网络、没有通知、没有 AlarmManager、没有 WorkManager、没有第三方 SDK
```

一条铁律：**界面层不允许自己 `new` 一个引擎或仓库**，全部经 `AppContainer` 取（IF-02）。这不是风格问题——引擎一旦能被界面凭空造出来，测试就换不掉它。

## 2. 外部接口

### 2.1 三个系统服务面

| # | 服务 | 用途 | 实现位置 | 需要权限？ |
| --- | --- | --- | --- | --- |
| IF-01a | `DataStore<Preferences>` ×2 | 两个开关型文件的读写 | `data/prefs/SettingsDataStore.kt`、`data/intervention/InterventionStore.kt` | 否 |
| IF-01b | SQLite（经 Room） | 四张表 | `data/db/ElderDatabase.kt` | 否 |
| IF-01c | 系统广播接收者 | 作息信号采集 | `data/rhythm/RhythmCollector.kt` | 否 |

**IF-01a · DataStore。** 两个独立文件，各由一个 `preferencesDataStore` 属性委托创建一次：

```kotlin
// data/prefs/SettingsDataStore.kt:14
val Context.settingsDataStore: DataStore<Preferences> by preferencesDataStore(name = "settings")

// data/intervention/InterventionStore.kt:26
val Context.interventionDataStore: DataStore<Preferences> by preferencesDataStore(name = "intervention")
```

- 承诺：单进程内是一致的；写入是原子的（`dataStore.edit { }` 要么整个生效要么整个不生效）。
- **不承诺**跨进程。常伴只有一个进程，没有 `MULTI_PROCESS` 需求；项目里也没有任何一处用 `SharedPreferences`。
- 为什么是两个文件而不是一个：见 `docs/04` §2.2——设置页的「恢复到出厂设置」会 `prefs.clear()`，节流状态混进去会被顺带清掉。

**IF-01b · Room。** 入口是一个函数，不是一个单例：

```kotlin
abstract class ElderDatabase : RoomDatabase() {
    abstract fun rhythmSignalDao(): RhythmSignalDao
    abstract fun dailyRhythmDao(): DailyRhythmDao
    abstract fun wishDao(): WishDao
    abstract fun anchorDao(): AnchorDao

    companion object {
        const val FILE_NAME = "elder.db"
        fun open(context: Context, name: String = FILE_NAME): ElderDatabase =
            Room.databaseBuilder(context.applicationContext, ElderDatabase::class.java, name)
                .addMigrations(MIGRATION_1_2, MIGRATION_2_3)
                .build()
    }
}
```

- 承诺：schema 落盘可校验（`exportSchema = true`）；查询返回 `Flow` 时随表变化重发。
- **不承诺**破坏性重建库：这里**没有** `.fallbackToDestructiveMigration()`（`docs/04` §2.3 红线 1）。版本号变了必须配一条 `Migration`。
- `open` 的 `name` 参数是给测试留的口子：正式应用永远走默认的 `elder.db`，仪器化测试各传各的文件名，免得几个用例在同一进程里争删同一个文件。

**IF-01c · 系统广播。** 采集器要的五个 action：

| 广播 action | 映射到 `RhythmKind` | 常量名 |
| --- | --- | --- |
| `android.intent.action.SCREEN_ON` | 屏幕亮 | `RhythmBroadcasts.ACTION_SCREEN_ON` |
| `android.intent.action.SCREEN_OFF` | 屏幕灭 | `RhythmBroadcasts.ACTION_SCREEN_OFF` |
| `android.intent.action.USER_PRESENT` | 解锁 | `RhythmBroadcasts.ACTION_USER_PRESENT` |
| `android.intent.action.ACTION_POWER_CONNECTED` | 插电 | `RhythmBroadcasts.ACTION_POWER_CONNECTED` |
| `android.intent.action.ACTION_POWER_DISCONNECTED` | 拔电 | `RhythmBroadcasts.ACTION_POWER_DISCONNECTED` |

注册方式（`RhythmCollector.kt:80-85`）：

```kotlin
ContextCompat.registerReceiver(
    context, receiver,
    IntentFilter().apply { RhythmBroadcasts.actionableActions.forEach(::addAction) },
    ContextCompat.RECEIVER_NOT_EXPORTED,
)
```

- `RECEIVER_NOT_EXPORTED` 的语义：系统广播照样投得进来，别的应用投不进来。用 `RECEIVER_EXPORTED` 会让任何一个装在这台手机上的应用都能往作息数据里塞假信号。
- 只运行时注册、清单里 `<receiver>` **0 个**：这五个 action 从 Android 8.0 起禁止清单注册。
- 承诺：**进程活着期间**，这五类事件被记成 `rhythm_signal` 一行。
- **不承诺**进程死了之后还记。用户把常伴从最近任务划掉、或系统在内存紧张时回收进程，这期间发生多少次亮屏都不会有人记下来。这一点在设置页与引导页如实写明，不能让人以为「打开过一次就一直在记」（`RhythmCollector.kt:24-26`）。

### 2.2 常伴刻意没有的四个服务面

| 没有 | 因为 |
| --- | --- |
| 网络（HTTP / socket） | 数据不出设备：`docs/04` §2.3 红线 2。库里没有任何一列是为和远端对齐而存在的 |
| 通知（`NotificationManager`） | ADR-009：本版本把「开口」收窄成「用户打开应用时首页那一句话」，不做常驻打扰 |
| `AlarmManager` / `WorkManager` | 进程本来就只在用户打开它时活着，不需要常驻调度：过期清理在启动时查一次就够 |
| 权限（`<uses-permission>`） | 清单 **0 条**。五个广播都是系统直投给已注册接收者的，不需要 `PACKAGE_USAGE_STATS` 或别的授权 |

### 2.3 平台入口

| # | 入口 | 文件 | 承诺 |
| --- | --- | --- | --- |
| IF-02a | `Application` | `ElderApp.kt` | 建容器，然后 `startProcessWork()`；后台工作的寿命 = 进程 |
| IF-02b | `ComponentActivity` | `MainActivity.kt` | 唯一的 Activity；`setContent { AppRoot(container) }` |
| IF-02c | `AndroidManifest.xml` | — | 1 个 Activity（MAIN / LAUNCHER，`exported="true"`）、`allowBackup="false"`、权限 0 条、`<receiver>` 0 个 |

```kotlin
class ElderApp : Application() {
    lateinit var container: AppContainer
        private set
    override fun onCreate() {
        super.onCreate()
        container = AppContainer(this)
        container.startProcessWork()
    }
}
```

顺序是**先建容器、再让它开始跑后台工作**。容器自己不做任何决定，「什么时候开始」由 `Application` 说了算——因此测试里可以只建容器、不调 `startProcessWork()`，不会被后台协程干扰。这是这两行代码分开写的原因，不是啰嗦。

`allowBackup="false"`：库里的作息记录、意愿、锚点不参与系统云备份。

### 2.4 没有第三方 SDK

`app/build.gradle.kts` 的 `dependencies` 里只有四类东西：

- AndroidX（`core-ktx`、`lifecycle-*`、`activity-compose`、`navigation-compose`）
- Compose（BOM、`ui`、`ui-graphics`、`material3`）
- Room（`runtime`、`ktx`、`ksp` 编译器）
- DataStore Preferences、`kotlinx-coroutines-android`

没有广告、统计、崩溃上报、推送 SDK。所以「外部接口」这一节到 2.3 就结束了。这不是遗漏，是需求本身：除了上面那三个界面之外，常伴不认识任何外部系统。

## 3. 内部接口 · 数据层

### IF-03 · 依赖容器 `AppContainer`

```kotlin
class AppContainer(context: Context, databaseName: String = ElderDatabase.FILE_NAME) {
    val clock: AppClock = SystemAppClock
    val settings: SettingsStore = SettingsStore(appContext.settingsDataStore, clock)
    val greetingEngine: GreetingEngine by lazy { GreetingEngine(clock) }
    val database: ElderDatabase by lazy { ElderDatabase.open(appContext, databaseName) }
    val rhythmRepository: RhythmRepository by lazy { RhythmRepository(database, clock) }
    val interventionConfig: InterventionConfig = InterventionConfig()
    val interventionStore: InterventionStore by lazy { InterventionStore(appContext.interventionDataStore, clock) }
    val rhythmProfileService: RhythmProfileService by lazy { RhythmProfileService(rhythmRepository, clock) }
    val wishRepository: WishRepository by lazy { WishRepository(database, clock) }
    val anchorRepository: AnchorRepository by lazy { AnchorRepository(database, clock) }
    val rhythmMaintenance: RhythmMaintenance by lazy { RhythmMaintenance(rhythmRepository, settings, clock) }
    val rhythmCollector: RhythmCollector by lazy { RhythmCollector(appContext, rhythmRepository, clock, processScope) }

    fun startProcessWork()
}
```

| 项 | 内容 |
| --- | --- |
| 谁建它 | `ElderApp.onCreate()`，一个进程一个 |
| 谁调它 | `MainActivity` → `AppRoot(container)` → 各 Screen；`HomeScreen`/`TalkScreen`/`PlayScreen` 用 `container` 里的依赖建自己的 ViewModel |
| 承诺 | 所有依赖都在这里显式声明；同一个字段永远返回同一个实例；`by lazy` 的字段在第一次真正用到时才创建 |
| 不承诺 | 不做生命周期取消。`processScope = CoroutineScope(SupervisorJob() + Dispatchers.Default)` 与进程同生共死，不取消 |
| 不引入 Hilt 的理由 | 只有一个 `app` 模块、对象图很浅，注解处理开销与学习成本大于收益 |

`startProcessWork()` 起两条协程：

1. **跟着设置开关走**：`settings.settings.map { it.collectRhythm }.distinctUntilChanged().collect { if (enabled) rhythmCollector.start() else rhythmCollector.stop() }`。用 `distinctUntilChanged` 是因为 DataStore 每次写入都会把整个快照重发一次，不去重的话改个称呼都会把接收者注销再注册一次。
2. **过期清理**：`rhythmMaintenance.pruneIfDue()`，启动时查一次「今天清过没有」。

`SupervisorJob` 是为了让清理失败不把监听开关那条协程一起带走——两件事互不相干。

### IF-04 · 时钟 `AppClock`

```kotlin
fun interface AppClock { fun now(): LocalDateTime }
object SystemAppClock : AppClock { override fun now(): LocalDateTime = LocalDateTime.now() }
fun LocalDateTime.toEpochDay(): Long = LocalDate.of(year, monthValue, dayOfMonth).toEpochDay()
```

| 项 | 内容 |
| --- | --- |
| 谁调它 | 所有需要「现在几点」的地方：四个仓库、两个服务、采集器、`GreetingEngine`、三个 ViewModel |
| 承诺 | 是**唯一**的时间来源；返回**无时区**的 `LocalDateTime` |
| 不承诺 | 不给时区转换。需要毫秒的地方各自用 `ZoneId.systemDefault()`，时区只在落库那一步出现 |
| 为什么不是 `Instant` | 作息是**地方时间**的概念——「七点起」而不是「UTC 23:00 起」。签名里不掺时区，读代码的人才不用每次心算 |
| 好处 | 计时、问候、节流判定全都能在单元测试里断言，不用真等到第二天 |

`AppClock` 是 `fun interface`，所以测试里一个 lambda 就能顶替：`AppClock { LocalDateTime.of(2026, 3, 1, 8, 0) }`。

### IF-05 · 设置持久化 `SettingsStore`

```kotlin
enum class FontSize(val storageKey: String, val label: String, val scale: Float) {
    LARGE("large", "大", 1.15f), EXTRA_LARGE("extra_large", "特大", 1.3f), STANDARD("standard", "标准", 1.0f);
    companion object { fun fromKey(key: String?): FontSize = entries.firstOrNull { it.storageKey == key } ?: STANDARD }
}

data class AppSettings(
    val address: String? = null,
    val fontSize: FontSize = FontSize.STANDARD,
    val firstLaunchEpochDay: Long? = null,
    val onboardingDone: Boolean = false,
    val collectRhythm: Boolean = false,
)

class SettingsStore(private val dataStore: DataStore<Preferences>, private val clock: AppClock) {
    val settings: Flow<AppSettings>
    suspend fun ensureFirstLaunchRecorded()
    suspend fun setAddress(value: String?)
    suspend fun setFontSize(value: FontSize)
    suspend fun completeOnboarding()
    suspend fun setCollectRhythm(value: Boolean)
    suspend fun lastPruneEpochDay(): Long?
    suspend fun markPruned(epochDay: Long)
    suspend fun resetToDefaults()
}
```

| 方法 | 谁调 | 保证 | 不保证 |
| --- | --- | --- | --- |
| `settings` | `AppRoot`、`HomeViewModel`、`SettingsScreen`、`AppContainer.startProcessWork` | 每次落盘改动都重发整个快照 | 不判断「值有没有变」，去重是调用方的事（`distinctUntilChanged`） |
| `ensureFirstLaunchRecorded()` | `AppRoot` 的 `LaunchedEffect(Unit)` | 只在首次为空时写入当天；已有值则不动 | 不做「今天是第几天」的计算，那是 `GreetingEngine` 的事 |
| `setAddress(value)` | `SettingsScreen`、引导页 | 先 `trim()`，空串存成 `null` | 不校验称呼内容 |
| `setFontSize(value)` | `SettingsScreen`、引导页 | 存 `storageKey` 字符串 | 不通知界面重绘（订阅 `settings` 的那一方自己会收到） |
| `completeOnboarding()` | 引导页最后一步 | 把 `onboardingDone` 置真 | 不改 `firstLaunchEpochDay` |
| `setCollectRhythm(value)` | `SettingsScreen` 的采集开关 | 只写这个键 | 不注册 / 注销接收者——那是 `AppContainer.startProcessWork` 监听它来做的 |
| `lastPruneEpochDay()` / `markPruned(day)` | `RhythmMaintenance` | 读 / 写「上次清理是哪天」 | 不做清理本身 |
| `resetToDefaults()` | 设置页「恢复到出厂设置」 | 清空 `settings` 文件 | **只清这个文件**：节流状态在另一个文件里（见 IF-01a） |

六个键的名字与 `docs/04` §10.1 完全一致：`address` / `font_size` / `first_launch_day` / `onboarding_done` / `collect_rhythm` / `last_prune_day`。

### IF-06 · 节流持久化 `InterventionStore`

```kotlin
class InterventionStore(
    private val dataStore: DataStore<Preferences>,
    private val clock: AppClock,
    private val zone: ZoneId = ZoneId.systemDefault(),
) {
    val state: Flow<ThrottleState>
    suspend fun stateOnce(): ThrottleState
    suspend fun recordSpoken(): ThrottleState
    suspend fun recordAnswered(): ThrottleState
}
```

| 方法 | 谁调 | 保证 | 不保证 |
| --- | --- | --- | --- |
| `state` | 设置页（显示「说话时机」） | 每次写入重发当前状态 | — |
| `stateOnce()` | `HomeViewModel.open()` | 取**此刻**的一次快照 | 不订阅后续变化：判定只要一次快照，订阅反而会让刚写进去的记录把自己说没了 |
| `recordSpoken()` | `HomeViewModel` 判定为「要说话」之后 | `ThrottleState.afterSpoken` 的结果写回去，返回写后的状态 | 不改 `lastAnsweredAt` |
| `recordAnswered()` | `TalkViewModel.hear()` | `afterAnswered` 的结果写回去：忽略计数归零、`lastAnsweredAt` 推到此刻 | 不问用户「说得好不好」 |

三个键：`last_spoken_at`（`Long`，毫秒）、`last_answered_at`（`Long`）、`ignored_streak`（`Int`），与 `docs/04` §10.2 一致。

### IF-07 · 作息仓库 `RhythmRepository`

```kotlin
class RhythmRepository(
    private val database: ElderDatabase,
    private val clock: AppClock,
    private val zone: ZoneId = ZoneId.systemDefault(),
    private val cutoverHour: Int = RhythmConfig.DEFAULT_CUTOVER_HOUR,
) {
    suspend fun record(incoming: List<CapturedSignal>): Int
    suspend fun signals(sinceDays: Int = SIGNAL_RETENTION_DAYS): List<RhythmSignal>
    val signalCount: Flow<Int>
    suspend fun signalCountOnce(): Int
    suspend fun saveProfile(dayEpochDay: Long, rhythm: DailyRhythm)
    suspend fun profile(dayEpochDay: Long): DailyRhythm?
    suspend fun latestProfile(): DailyRhythm?
    suspend fun prune(): Int
    suspend fun clearAll()
}
```

| 方法 | 谁调 | 保证 | 不保证 |
| --- | --- | --- | --- |
| `record(incoming)` | `RhythmCollector.onBroadcast` | 返回**真正新写进去的行数**；重复信号被唯一索引挡掉（返回 `-1`），不计入 | 不告诉你哪几条是新的 |
| `signals(sinceDays)` | `RhythmProfileService` | 按时间升序返回窗口内的信号 | 不排序去重以外的事；不推断 |
| `signalCount` / `signalCountOnce()` | 设置页（显示「记了多少条」）、测试 | 返回表里的总行数 | — |
| `saveProfile(day, rhythm)` | `RhythmProfileService` | 同一天重复调用是覆盖（`REPLACE`） | 不判断这份画像是否可信——那由 `RhythmResult` 决定，只有 `Ready` 才传进来 |
| `profile(day)` / `latestProfile()` | `RhythmProfileService`、设置页 | 取某天 / 最近一天的画像 | 取不到返回 `null`，不抛异常、不造一条空的 |
| `prune()` | `RhythmMaintenance` | **一个事务内**删掉过期的信号与画像，返回真正删掉的行数 | 不动 `wish` / `anchor`（它们没有保留期） |
| `clearAll()` | 设置页「清空作息数据」 | 事务内清空作息相关的表 | 不动意愿和锚点——用户清作息不代表想忘掉自己记的事 |

保留期是常量：`SIGNAL_RETENTION_DAYS = 30`、`RHYTHM_RETENTION_DAYS = 30`（`docs/04` §12）。

### IF-08 · 作息画像服务 `RhythmProfileService`

```kotlin
class RhythmProfileService(
    private val repository: RhythmRepository,
    private val clock: AppClock,
    private val inference: RhythmInference = RhythmInference(),
    private val cutoverHour: Int = RhythmConfig.DEFAULT_CUTOVER_HOUR,
) {
    suspend fun current(): RhythmResult

```

| 项 | 内容 |
| --- | --- |
| 谁调它 | `HomeViewModel.open()`（判定开口前要这份画像）、设置页（显示当前画像） |
| 保证 | 返回 `Ready` 时**同时**把画像落库（`saveProfile`）；同一作息日内已经算过就复用，不重算 |

### IF-09 · 过期清理 `RhythmMaintenance`

```kotlin
class RhythmMaintenance(
    private val repository: RhythmRepository,
    private val settings: SettingsStore,
    private val clock: AppClock,
    private val cutoverHour: Int = RhythmConfig.DEFAULT_CUTOVER_HOUR,
) {
    suspend fun pruneIfDue(): Int
}
```

| 项 | 内容 |
| --- | --- |
| 谁调它 | `AppContainer.startProcessWork()`，启动时一次 |
| 保证 | 今天没清过就清一次并 `markPruned`，返回真正删掉的行数；今天已经清过就返回 0 |
| 不保证 | 不做定时。进程死了不清理，下次启动再补 |

| 项 | 内容 |
| --- | --- |
| 谁建它 | `HomeScreen` 里的 `viewModel { ... }`，依赖全部从 `container` 取 |
| `state` | `settings.settings` × `refreshTick` × `session` 三路 `combine`，`stateIn(started = WhileSubscribed(5s)`，初值 `Loading` |
| `onStart()` | 「用户又来看这一页了」→ 重新判一次；但**必须与 `onStop` 配对**才认：`LifecycleRegistry.addObserver` 会把新观察者同步推进到当前状态，冷启动时补发 ON_START 会让首页连判两次，第二次读到刚写下的「已经招呼过」而翻成安静语 |
| `onStop()` | 只做个记号，不取消任何东西：判定完要落盘，半路掐掉会留下「说过话但没记账」的状态 |
| `refresh()` | 让界面重读一次时钟（跨时段边界时改口）；真的碰一下 `clock.now()`，语义是「刷新时以当前时间为准」 |
| 保证 | 判定为 `Speak` 才 `recordSpoken`：安静的时候不该计入「已经招呼过」，否则用户深夜打开一次，第二天早上就被当成「不理人」 |
| 不保证 | 不做通知、不常驻后台。`Loading` 只出现在最初一瞬间 |

`open()` 的串行化靠一个 `Mutex`：`init` 与界面回报的「又回来了」有可能挨得很近，两次并发判定会各自读到同一份旧状态，把一次招呼记成两次。

`TalkPageState` 里三个维度分开，互不依赖：**「听出了什么」**（`heard`，只活在内存里）、**「要不要记」**（`remembered`，落盘、跨重启还在）、**「确认过之后能接着做什么」**（`anchors` / `openOption` / `anchorAskFor`）。

| 方法 | 保证 | 不保证 |
| --- | --- | --- |
| `editDraft` / `submitDraft` | 提交后输入框清空：那句话已经交给常伴了，留在框里会让人以为没发出去 | — |
| `hear(sentence)` | 识别**同步**算完立刻出结果；落库在后台。同时 `interventions.recordAnswered()`——说一句没被听懂的话也是接话 | 不碰任何状态字段：又说了别的、或把同一件事再说一遍，**都不构成同意**（AC-07.2） |
| `decide` / `forget` / `forgetAll` | 一律后台落库；`forgetAll` 前提是界面已经问过一次 | 落库失败不会让这一页显示错误 |
| `toggleOption` | 一次只摊开一个起点；纯界面动作，不落库、不代表用户答应了什么 | — |
| `markDone` | 只回一句 `Encouragement`，不留记录 | — |
| `proposeAnchor` | 只先问时段，**不直接建**：同一件小事记在早上和记在想起来的时候是两种安排 | 目录里没有的 id 一律不理会 |
| `confirmAnchor` | 用户点了某个时段**才真的建**；这里**再判一次** `AnchorRules.mayPropose`——同一条领域规则同时落在界面与写入路径上 | 意愿还没落库（`statusOf` 为 `null`）时不建 |
| `forgetAnchor` | 不弹对话框、不问任何话、不留「已删除」痕迹（AC-09.3） | — |

`statusOf` 返回 `null` 表示「还没落库」，界面把它当「还没表态」处理：用户刚点完一句示例话就立刻点同意，那时插入可能还在路上，按钮必须照常在、按下去也必须有用。

## 6. 错误与降级约定

常伴没有网络，所以传统意义上的「错误分类」缩小成**四类输入不成立**。每一类都有明确的对外承诺：

| # | 情形 | 系统行为 | 依据 |
| --- | --- | --- | --- |
| 1 | 作息信号不足或自相矛盾 | `RhythmResult.Gathering` / `Inconsistent` → 干预窗口用 `fallbackQuietSpan`（`07:00`–`22:30`）判定；界面据 `RhythmBasis` 说明「按真实作息」还是「按普通作息先来」 | IF-08、IF-14c、IF-14d |
| 2 | 一句话听不出意愿 | 返回 `IntentScan.NotRecognized`，界面显示 `NotUnderstood`，**不猜、不兜底造一条意愿** | IF-14b |
| 3 | 系统时钟被往回调 | 间隔算出负数 → 落到「太近」这一支，静默；用时算成负数 → 按 0 显示 | IF-14c、IF-18 |
| 4 | 落库失败 / 数据还没落下去 | 界面**不显示错误**。意愿这一页承诺的是「听懂了什么会如实告诉你」，不是「一定记住」；`statusOf` 返回 `null` 时按钮照常可用 | IF-17 |

另外两条全局降级：

- **没有画像时不说错话。** `RhythmResult` 不是 `Ready` 时不会假装有画像：安静时段用假定值，开口时机就会保守。
- **用户撤回同意后立刻停止采集。** `stop()` 幂等、立即生效；已经采集的数据不会被偷偷保留到下一次启动才清（清理由用户显式触发 `clearAll` / `prune`）。

## 7. 接口变更与兼容

1. **改一个签名要同时改四处**：接口本身、它的调用方、对应的单测 / 仪器化测试、以及本文与 `docs/03`。`docs/03` 已经立过一条规矩：**新规则的改动要先改文档再动代码**。
2. **`AppContainer` 增删字段**是内部接口变更，不影响持久化：它是每次进程启动时构造的，没有序列化契约。
3. **持久化契约的兼容由 `docs/04` 管**：键名、列名、索引名一旦落盘就不能随手改；要改必须配 `Migration` 或读旧值时兜底（例如 `FontSize.fromKey` 认不出就回 `STANDARD`、`AnchorSlot.parse` 认不出就回 `ANYTIME`）。
4. **文案接口的兼容**：`CompanionVoice` / `TalkVoice` / `PlayVoice` / `InterventionVoice` 的方法签名可以变，但它们产出的字符串要一直能过三张词表。加一个不提字的文案方法不会破坏兼容。
5. **`PlayCatalog.games` 加一项**是受约束的内部接口变更：规则已存在的游戏只需再加一条 `PlayGame(...)`；有新规则的必须先改 `docs/03` §3 的形状（一个 `PlayRound` 实现 + 界面一个分支）再动代码。
6. **不承诺跨版本的运行时兼容**：这是本地应用，没有远端接口，也没有 API 版本协商。
