## 1. 设计目标与约束

概念设计要落成代码，先定几条不能违反的红线。它们不是为了好看，而是为了守住 `docs/00` 第 3.3 节的负面需求（NR-xx）——那部分需求都是**"不能做什么"**，只有靠结构约束才能长期守住，靠自觉守不住。

| 编号 | 约束 | 守住的需求 | 落地方式 |
| --- | --- | --- | --- |
| C-01 | 不联网 | NR-01、DR-05 | 不引入任何网络库；`app/src/main/java` 全量扫描 `okhttp\|retrofit\|java.net\|HttpURLConnection\|Socket\|io.ktor` 仅 1 处命中，且是 `domain/engine/intent/IntentScan.kt:54` 里的 KDoc 文字说明 |
| C-02 | 不申请权限 | NR-05 | `AndroidManifest.xml` 中 `uses-permission` 与 `<receiver>` 计数均为 0 |
| C-03 | 领域层不认识 Android | 可测试性 | `domain/` 下不出现 `import android.*`（实测 0 命中），纯 Kotlin 代码，可在 JVM 上直接跑 |
| C-04 | 用户点头之前不提供帮助 | NR-01 | 「给选项」这件事发生在 `TalkViewModel` 收到用户明确动作之后，没有默认值、没有超时自动给 |
| C-05 | 不做假功能 | G-06 | 任何进导航的入口都必须能走通；没做完的功能不放入口，不放「敬请期待」 |
| C-06 | 依赖尽量少 | 长期可维护 | 无 Hilt、无网络库、图标只用 `material-icons-core` |

关于 C-06 的图标依赖，这里有一条实际踩过的坑，值得写进文档：项目一度引入 `material-icons-extended`，它会带来 **11,404 个图标类**，直接拖长构建并撑大 APK。现在只用 `material-icons-core`，`app/build.gradle.kts` 的依赖注释里保留了这条记录，避免以后有人"顺手"加回来。

## 2. 架构总览

### 2.1 分层

```
app/src/main/java/com/fortheelder/
├── ElderApp.kt        应用入口（Application）
├── MainActivity.kt    唯一 Activity
├── core/              手工依赖装配、时钟抽象
├── data/              持久化与系统信号采集
├── domain/            纯逻辑：规则、推断、文案生成
└── ui/                Compose 界面与 ViewModel
```

依赖方向是单向的：

```
ui  ──►  data  ──►  domain
                 ──►  core/time
```

- `domain` 不依赖任何人，尤其不依赖 Android 与 `data`。
- `data` 依赖 `domain` 的类型（`RhythmSignal`、`Wish`、`Anchor` 等）来完成读写的映射。
- `ui` 只认 `data` 暴露的仓储接口，拿不到 DAO，也拿不到 `Room` 对象。

这么做换来两个具体好处：

1. `domain` 的 JVM 用例全部跑在 `testDebugUnitTest` 上，**不需要模拟器**，一次回归 12 秒左右（第 17 轮实测：`app/src/test/java/com/fortheelder/domain` 下 18 个测试文件、**260** 个 `@Test`；全仓 JVM 共 **28** 类 **367** 例；第 41 轮复测：`app/src/test/java` 共 **37** 个文件、**6982** 行，全仓 JVM 共 **37** 类 **431** 例）。作息推断、意愿识别、文案生成、小游戏规则这些最容易出错的逻辑全在这一层。
2. 想换存储实现时，改动被关在 `data` 里，`domain` 一行不动。

### 2.2 为什么不给每个类都配接口

本项目有一条判断规则：**只有一个实现的接口不写**。`RhythmRepository`、`WishRepository`、`AnchorRepository` 都是 `class`，不是 `interface` + `Impl`。理由是这些接口的第二实现永远不会有——测试用的是"换个数据库文件名"而不是"换个假实现"。接口在这里只增加跳转成本。

需要替换的地方则确实抽象了：时钟是 `core/time/AppClock.kt` 里的接口 `AppClock`，生产实现 `SystemAppClock`，测试注入固定时刻。这是唯一一处真正需要两套实现的地方（`data/intervention/InterventionStore.kt` 的节流判断、`InterventionWindow` 的窗口计算都靠它）。

第 11 轮又添了一个落地例子，这次落在一个「框架」上：`domain/play/PlayGame.kt` 里的小游戏没有写成 `interface PlayGame` + 每个游戏一个 `class`，而是**一条数据 + 一个出局函数**（`data class PlayGame(..., val deal: (Random) -> PlayRound)`），游戏目录是 `PlayCatalog.games`。第 11 轮只有一个游戏，为它单开一个接口正是这条规则要避免的情况。**第 12 轮加进第二个游戏，把这条规则验了一次，结论是"一半对"**：`PlayGame` 的六个字段一个没动、`PlayCatalog.games` 只多写一条 `PlayGame(...)`——这部分成立；但 `PlayRound` 必须从 `data class` 改成 `sealed interface`，因为两个游戏的局面状态字段完全不同（舒尔特是"点到第几个"，找一样是"先点中哪一格、那对找到没有"），硬塞进同一个 data class 会造出"两个字段互相矛盾"的合法态。准确结论与代价见 `records/03` ADR-015 的第 12 轮更正段与 ADR-016。**第 17 轮加进第三个游戏（算一算），把这条规则又验了一遍，第 12 轮那句「一半对」还要再收窄一层**：`PlayGame` 的六个字段依旧一个没动、`PlayCatalog.games` 只多写一条 `PlayGame(...)`，而这次的规则虽然全新（`SubtractRound` 是第三个 `PlayRound` 实现），**界面布局与状态机一行都不用改**（`PlayScreen.kt` 249 行与 `PlayViewModel.kt` 119 行本轮零改动；界面文案层不算——见下）；代价换了个地方付——`ui/play/PlayVoice.kt` 里三处 `when` 会**当场编译不过**，把该补的分支直接报出来。三种代价（① 只加目录一条 ② 加局面 + 界面分支 ③ 加局面但界面靠编译期报错）见 `records/03` ADR-018。**第 41 轮加进第四个游戏（记一记），第四种代价出现了**：规则全新（`MemoryRound` 是第四个 `PlayRound` 实现），而且「每张牌面上显示什么字」这件本来属于界面的事被划回领域层——`PlayRound` 上加了带**默认实现**的 `faceOf` 钩子，前三个游戏一行没改，`ui/play/` 只多读一句、不加分支。四种代价（① 只加目录一条 ② 加局面 + 界面分支 ③ 加局面但界面靠编译期报错 ④ 加局面 + 加带默认实现的口子、界面不加分支）见 `records/03` ADR-038。**第 48 轮加进第五个游戏（找同类），走的还是上面第 ③ 种，但这是它的第二次兑现，代价与第 17 轮同形**：规则全新（`SameKindRound` 是第五个 `PlayRound` 实现），`PlayScreen.kt` 与 `PlayViewModel.kt` 一行未动，`PlayVoice.kt` 里三处 `when` 又当场编译不过、把该补的分支直接报出来（首跑三行 `'when' must be exhaustive`，见 `docs/03` §8.19.3）。它比第 41 轮**便宜**：第 41 轮还在 `PlayRound` 上加了一个口子（`faceOf`），第 48 轮 `PlayRound` 的公共契约一个字没改。理由与边界见 `records/03` ADR-043。

### 2.3 依赖装配：`core/AppContainer.kt`（143 行）

没有用 DI 框架，手写一个容器，在 `ElderApp` 里创建一次，向下传。字段清单：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `appContext` | `Context`（private） | 只用于构造数据库与 DataStore |
| `clock` | `AppClock` | 默认 `SystemAppClock`，测试可替换 |
| `settings` | `SettingsStore` | 称呼、字号档、作息采集开关、引导是否完成 |
| `greetingEngine` | `GreetingEngine` | lazy |
| `database` | `ElderDatabase` | lazy |
| `rhythmRepository` | `RhythmRepository` | lazy |
| `interventionConfig` | `InterventionConfig` | 直接实例化，纯配置常量 |
| `interventionStore` | `InterventionStore` | lazy |
| `rhythmProfileService` | `RhythmProfileService` | lazy |
| `wishRepository` | `WishRepository` | lazy |
| `anchorRepository` | `AnchorRepository` | lazy |
| `rhythmMaintenance` | `RhythmMaintenance` | lazy |
| `rhythmCollector` | `RhythmCollector` | lazy |
| `processScope` | `CoroutineScope`（private） | `SupervisorJob() + Dispatchers.Default` |

构造签名是 `AppContainer(context: Context, databaseName: String = ElderDatabase.FILE_NAME)`。多出来的 `databaseName` 参数不是给生产用的，是留给仪器化测试的：设备测试要能在同一个进程里各用各的库文件（原因见第 9.2 节）。

lazy 不是随手写的。`RhythmCollector` 会注册系统回调、`ElderDatabase` 会建文件，两者都不该在 `Application.onCreate` 里无条件发生——用户可能永远不打开作息采集。

`startProcessWork()` 在 `ElderApp.onCreate` 里调用，起两条协程：

1. 监听 `settings.collectRhythm`，经 `distinctUntilChanged` 后决定注册还是注销采集器。用户关掉开关，采集立刻停，不是"下次启动停"。
2. 调 `rhythmMaintenance.pruneIfDue()`，按到期条件清理过期的作息样本。

`processScope` 用 `SupervisorJob`：一条协程挂掉不影响另一条。

## 4. 数据设计

### 4.1 Room 数据库

`data/db/ElderDatabase.kt`：`version = 3`，`exportSchema = true`，库文件名常量 `FILE_NAME = "elder.db"`。

打开方式是唯一的入口，生产与仪器化测试都走它：

```kotlin
fun open(context: Context, name: String = FILE_NAME): ElderDatabase =
    Room.databaseBuilder(context, ElderDatabase::class.java, name)
        .addMigrations(MIGRATION_1_2, MIGRATION_2_3)
        .build()
```

四个 DAO：`rhythmSignalDao`、`dailyRhythmDao`、`wishDao`、`anchorDao`。

schema JSON 导出到 `app/schemas/com.fortheelder.data.db.ElderDatabase/{1,2,3}.json`（`3.json` 的 identityHash 为 `15d43e067293`）。`app/build.gradle.kts` 里通过 `ksp { arg("room.schemaLocation", ...) }` 指定导出目录，并通过 `sourceSets.androidTest.assets.srcDir("$projectDir/schemas")` 把 schema 打进测试 APK——`MigrationTestHelper` 需要从那里读。

### 4.2 四张表

**`rhythm_signal`（4 列）**——一次原始信号（解锁、充电等）。

| 列 | 类型 |
| --- | --- |
| `id` | INTEGER PK |
| `kind` | TEXT |
| `atEpochMilli` | INTEGER |
| `offsetSeconds` | INTEGER |

索引：唯一索引 `index_rhythm_signal_kind_atEpochMilli`、普通索引 `index_rhythm_signal_atEpochMilli`。

**`daily_rhythm`（9 列）**——按天聚合出的作息画像，主键是 `dayEpochDay`。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `dayEpochDay` | INTEGER PK | 天序号 |
| `wakeOffsetMinutes` | INTEGER | 起床时刻（当天 0 点起算的分钟数） |
| `sleepOffsetMinutes` | INTEGER | 入睡时刻 |
| `activeSpans` | TEXT | 活跃时段，编码见 `SpansCodec.kt` |
| `idleSpans` | TEXT | 空闲时段 |
| `nightChargingOffsetMinutes` | INTEGER | 夜间充电起始时刻 |
| `sampleDays` | INTEGER | 参与推断的天数 |
| `confidence` | INTEGER | 置信度 |

**`wish`（8 列）**——从用户闲谈里识别出的意愿。

| 列 | 类型 |
| --- | --- |
| `id` | INTEGER PK |
| `kind` | TEXT |
| `term` | TEXT |
| `evidence` | TEXT |
| `sentence` | TEXT |
| `status` | TEXT |

| `decidedAtEpochMilli` | INTEGER |

唯一索引 `index_wish_kind_term`：同一个词只留一条意愿，避免同一句话被记两遍。

**`anchor`（6 列）**——用户**自己**记成日常的那一件事。

| 列 | 类型 |
| --- | --- |
| `id` | INTEGER PK |
| `term` | TEXT |

| `action` | TEXT |

| `createdAtEpochMilli` | INTEGER |

唯一索引 `index_anchor_optionId`。

这张表**刻意没有任何计数列**。没有 `streak`、没有 `completedCount`、没有 `lastDoneAt`。原因是 `docs/01` 的术语表把「生活锚点」定义为「不是打卡任务，没有连续天数，不做就消失」。如果表里存了连续天数，界面上迟早会长出一个"已坚持 7 天"，那就变成打卡了。约束放在数据层，比放在文案层可靠。

实测确认（`adb shell run-as com.fortheelder.debug sqlite3 databases/elder.db`）：

```
pragma table_info(anchor) →
  0|id INTEGER PK, 1|term TEXT, 2|optionId TEXT,
  3|action TEXT, 4|slot TEXT, 5|createdAtEpochMilli INTEGER
select name from sqlite_master where type='table' →
  anchor, android_metadata, daily_rhythm, rhythm_signal, room_master_table, sqlite_sequence, wish
pragma user_version → 3
```

### 4.3 迁移

`data/db/Migrations.kt`（64 行）里两个迁移，各自只做一件事，都不触碰已有表：

| 迁移 | 动作 |
| --- | --- |
| `MIGRATION_1_2` | 建 `wish` 表 + 唯一索引 `index_wish_kind_term` |
| `MIGRATION_2_3` | 建 `anchor` 表 + 唯一索引 `index_anchor_optionId` |

只有"新增表"这一种迁移形态，没有列改名、没有数据搬移，因此每个迁移都可以用一句 `CREATE TABLE` + 一句 `CREATE UNIQUE INDEX` 写完，不需要中间表。

KDoc 里写明一条纪律：**迁移语句必须与 schema JSON 逐字一致**。Room 会校验建表结果与 schema 是否匹配，不一致会在升级时抛异常。这条纪律的另一半是"迁移清单要接全"——见第 9.3 节，那里记了一个真实踩到的坑。

### 4.4 DataStore

两个独立文件，各管各的，互不影响：

| 文件 | 声明位置 | 内容 |
| --- | --- | --- |
| `settings` | `data/prefs/SettingsDataStore.kt:14`，`preferencesDataStore(name = "settings")` | 称呼、字号档位、是否采集作息、引导是否完成 |
| `intervention` | `data/intervention/InterventionStore.kt:29`，`preferencesDataStore(name = "intervention")` | 节流状态（上次主动出现时刻等） |

分开的理由很直接：设置是用户改的，节流状态是程序改的。混在一个文件里，程序频繁写节流状态会让设置的读取多绕一圈；更重要的是，用户"清空数据"要清的是设置和数据库，节流状态属于运行态，分开后可以单独决定要不要清。

## 5. 领域层设计

`domain/` 下五个包，各解决一类问题：

| 包 | 解决的问题 | 关键文件 |
| --- | --- | --- |
| `engine/rhythm` | 把零散信号推断成"今天大概几点起、几点睡、哪几个时间段是空窗" | `RhythmInference.kt`(280)、`DailyRhythm.kt`(113)、`RhythmBroadcasts.kt`(56) |
| `engine/intervention` | 判断"此刻该不该开口"，以及该用多大声量开口 | `InterventionWindow.kt`(212) |
| `engine/greeting` | 按称呼、时刻、节流状态生成招呼语 | `GreetingEngine.kt`(100) |
| `engine/intent` | 从用户的话里扫出意愿词（"以前爱听戏"），扫不出就老实说扫不出 | `IntentLexicon.kt`(129)、`IntentScan.kt`(223) |
| `companion` | 陪伴语、鼓励语、低门槛行动卡目录、锚点规则 | `StarterOptions.kt`(448)、`CompanionVoice.kt`(119)、`Anchor.kt`(81)、`Encouragement.kt`(39) |
| `wish` | 意愿的状态机（听到 → 待定 → 已确认 / 已放下） | `Wish.kt`(99) |

两条贯穿领域层的设计规则：

**规则一：文案与判断在同一处，且判断在前。** 例如 `InterventionWindow` 先返回一个"声量"判定（安静 / 轻说 / 可以说），再由 `ui/home/InterventionVoice.kt` 按这个判定挑句子。这里有个已实测确认的行为：在 `StayQuiet(SLEEP_HOURS)` 判定下，首页**不显示**锚点行。这不是漏了，是设计决策——`InterventionVoice.kt:22-24` 与 `:74` 起写明了理由：只有 Speak 时才可能带出锚点，"安静时说一句『您记下的那件事』等于把安静语变成了一半的招呼"。写进这里是为了以后有人看到"首页没显示锚点"时不必重新推一遍。

**规则二：禁用词用纯函数守，不靠人眼，而且词表只有一处。** 生成文案前都要过一遍「累不累的话术」检查：累加与施压的说法、要花钱的说法、要留联系方式的说法、没法照做的空话、放到哪件事上都成立的空话，以及医疗/功效宣称。**第 37 轮起这些词表只住在 `domain/companion/CopyRules.kt` 一处**——原先分散在 `CompanionVoice.absentChannelWords`、`StarterOptions` 的几张词表与 `Encouragement` 的 `gameWords` 里（各自一套、彼此不知情、谁也没扫过谁），现在消费方一律调 `CopyRules.violations(text)`，医疗类复用 `domain/voice/ClaimWords.banned`（单一来源是第 12 轮 GAP-07 定的）。守卫两条：`CopyRulesTest`（行为：六类规则各自命中、两个消费方对同一句话给同一批理由）与 `CopyRulesPlacementTest`（形态：每个规则在 `main` 源码里**只能有一张 ≥2 汉字的 `List<String>` 字面量表**，且必须住在 `CopyRules.kt`）。这比"我们文案里不写这些"可靠得多，而且新加文案时用例会当场红。**守卫的可见边界**（只认 `val … : List<String> = listOf(…)` 形态、只重合 1 词的近似表不报、只管表的张数与词而不管有没有人在用）见 `docs/03` §8.8。

## 6. UI 层设计

### 6.1 导航

`ui/nav/MainNav.kt`（87 行）只有一个 `NavHost`，**五个目的地**：

```kotlin
object Route {
    const val HOME = "home"; const val SETTINGS = "settings"; const val TALK = "talk"; const val PLAY = "play"
    const val ONBOARDING_REVIEW = "onboarding-review"
}
```

`startDestination = HOME`。五个 `composable` 对应 `HomeScreen`、`SettingsScreen`、`OnboardingScreen`（只读重看引导）、`TalkScreen`、`PlayScreen`。文件里明确写了「不预埋空壳页面来占位」——这条与 C-05 是一体的：想加一个目的地，前提是它的界面能走通。

**第 47 轮**加的第五个目的地 `ONBOARDING_REVIEW` 就是按这条标准进的：它渲染的是既有的 `OnboardingScreen`，只是多传一个可空的 `onReviewExit` 进去变成只读，没有新增页面文件。它**不是**把引导那道闸门搬进了导航图——闸门判定仍在 `AppRoot` 里由 `onboardingDone` 说了算（ADR-002，见 6.2），这一条只是 `NavHost` 里的普通目的地：进得来、退得出去、系统返回键天然可用，也永远不会写 `onboardingDone`（`records/03` ADR-042）。

**如实记一笔**：本节此前的版本记的是「55 行 / 三个目的地」，而同一份文档的第 10 节早在更早的轮次就写着 `ui/nav/MainNav.kt` 的 `Route.PLAY`——也就是说这一节在 v1.5 之前就已经与代码脱节（不是本轮改出来的）。本轮按 `wc -l` 与源码实测重出为 87 行 / 五个目的地。

### 6.2 `AppRoot` 是闸门，不是页面

`ui/AppRoot.kt`（65 行）承担两件事：

1. **首次引导在 `NavHost` 之外**。所以引导期间不存在"返回键退出引导"的可能，也不会有导航栈里留一个引导页的历史。第 47 轮加的只读重看那条目的地是**在** `NavHost` 之内的普通目的地，但它**不参与**这道闸门的判定：第一次打开 App 的人只会遇到 `AppRoot` 这道闸门，闸门仍由 `onboardingDone` 说了算（`records/03` ADR-002 未改，第 47 轮只补了 ADR-042）。
2. **设置读盘未完成（`null`）时不画内容**。这样避免字号先在默认档渲染一帧、再跳到用户设定的档位——对老花眼用户来说那一闪很明显。宁可多等十几毫秒。

外层用 `safeDrawingPadding()` 统一处理刘海、状态栏、导航条、手势条四类遮挡，各个页面不需要各自操心。

### 6.3 适老化组件与主题

`ui/common/ElderComponents.kt`（366 行）收拢了重复出现的形态：大触控目标的按钮、可展开的卡片、安静语气的小注（QuietNote）、以及**首页那种大尺寸入口卡 `EntryCard`**（第 49 轮新增）等。页面里只写内容，不重复写尺寸与交互。

字号不走系统设置，走应用内档位（`SettingsStore` 里的档位 → `ui/theme/Type.kt`）。这是 FR-02 的要求：用户调大字是为了看这一款 App，不该连带把微信也变了。

配色是暖底 + 松绿 `#175C46` + 暖白 `#FBF8F3`（**第 49 轮把松绿由 `#1F6E5C` 改深到 `#175C46`**，与暖白底的对比度从 5.76 抬到 **7.46**，越过 AAA 的 7:1）。选色的判断写在 `ui/theme/Color.kt`：不用高饱和蓝（常见的"科技感"，对 55–65 岁人群偏冷），不用纯白底（对比度过高，长时间看不适）。

**第 49 轮另立一条：颜色不承担"区分"的职责，只承担"看得见"的职责。** 三处描边（`SectionCard` / `EntryCard` / `ActionRow`）此前写成 `outline.copy(alpha = 0.35f)`，合成到底色上只剩 1.36~1.76:1，等于没画；本轮换成不透明色 —— 亮色 `OutlineStrong = #7E857F`、暗色 `OutlineStrongDark = #8C938E`，各自对相邻底色 **≥ 3:1**（WCAG 1.4.11 非文本对比度）。按钮、选中态这些"哪个被选中了"的信息仍然由**形状**（`RadioButton` 的圆点）与**文字**承担，颜色只加一层视觉边界（1.4.1 不得只靠颜色传达信息）。台账与实测见 `records/04` 第四十九节，守卫是 `ui/theme/PaletteContrastTest`（13 例）。

### 6.4 各页面的职责边界

| 页面 | 负责 | 不负责 |
| --- | --- | --- |
| `HomeScreen` + `HomeViewModel` + `InterventionVoice` | 决定此刻说什么、要不要说；显示今天这段的锚点 | 不识别意愿，不生成行动卡 |
| `TalkScreen` + `TalkViewModel` + `TalkVoice` + `StarterCard` + `AnchorCard` | 接住用户的话、扫意愿、给选项、把某一步记成日常 | 不判断"此刻该不该开口" |

| `PlayScreen` + `PlayViewModel` + `PlayVoice` | 按目录摆出五种脑力局面、收下这一次的成绩（**第 49 轮更正**：此前写"四种"，是第 48 轮加第五个游戏时漏改的一处） | 不判断"此刻该不该开口"，不诊断记忆或认知 |
| `OnboardingScreen`（第 47 轮新增的**只读重看**那一路） | 把引导三页原样再显示一遍，让用户自己重看 | **一个设置都不写**：四处写盘全挂在首次引导的 `finish` 上；也不参与 `onboardingDone` 的判定 |

标题从「三个页面」改成「各页面」是第 47 轮顺手改的：这张表在 `PlayScreen`（更早的轮次）进导航之后就一直只列着三个页面，与 6.1 的目的地数对不上——不是本轮新欠的账，一并对齐。

`InterventionVoice` 与 `TalkVoice` 分开而不是合成一个"Voice"，是因为两者的输入完全不同：前者输入是时间判定与节流状态，后者输入是用户刚说的一句话。硬合成一个类，里面的分支会互相干扰。

### 8.2 设备测试的库名隔离

设备测试每个用例传入独立库名（如 `elder-test-talk-starter.db`）。这不是洁癖，是修过的问题：同一进程里如果有两方同时争 `elder.db`，真机上会崩 `no such table: wish`。`ElderDatabase.kt:24-28` 保留了这段记录，`AppContainer` 的 `databaseName` 参数就是为它准备的。

### 8.3 迁移测试守什么

`MigrationTest.kt`（5 例）守三件事：

1. 升级不丢老数据；
2. 升级后新表真能写进去；
3. 每一跳都不许漏——1→2、2→3、1→3 都走一遍。

第 2 条曾经是用手拼的 `Room.databaseBuilder` 写的，第 9 轮它还是绿的；等版本升到 3、生产代码接上 `MIGRATION_2_3` 之后当场红（从 `RhythmSignalDao_Impl` 抛 `A migration from 1 to 3 was required but not found`）。原因很清楚：手拼 builder 自带一份迁移清单，**生产代码漏接迁移它照样绿**。现在改成调用 `ElderDatabase.open`，测试与生产共用同一个入口。这是本次迭代最值得记住的一处测试缺陷。
