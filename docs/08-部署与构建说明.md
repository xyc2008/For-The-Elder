## 2. 关键环境配置

### 2.1 为什么必须锁定 JDK 17

`gradle.properties` 里有这样一段：

```properties
# 固定使用 JDK 17 构建。
# 本机 PATH 中排在最前的 java.exe 是 Oracle 的 javapath 影子目录，直接依赖 PATH
# 会拿到不确定的 JVM；这里显式指定 JDK 17，保证命令行与 Android Studio 结果一致。
org.gradle.java.home=C:/Program Files/Java/jdk-17.0.18
```

本机 PATH 上排在最前的 `java.exe` 是 `C:/Program Files/Common Files/Oracle/Java/javapath/java`——这是 Oracle 安装器写的一个**影子目录**，当前恰好指向 17.0.18，但它会随着 Oracle 组件的安装与升级被改写。也就是说：**今天不锁定也对，明天不锁定可能就不对了**。显式指定之后，命令行构建与 IDE 构建拿到的是同一个 JVM。

**不要**为了图省事删掉这一行，也**不要**把它改成相对路径。

### 2.2 SDK 路径：靠 `local.properties`，不设 `ANDROID_HOME`

`local.properties`（不进版本库）：

```properties
# 本文件由构建脚本按机器实际情况生成，不应提交到版本库。
sdk.dir=C:/Users/xyc/Desktop/For-The-Elder/.toolchain/android-sdk
```

SDK 跟着项目放在 `.toolchain/android-sdk`，只用 `local.properties` 指过去，不依赖环境变量。好处是同一台机器上多个项目可以各用各的 SDK 版本，互不干扰；坏处是**这份文件不能提交**，换机器要手工补。

### 2.3 `gradle.properties` 里其余几行的作用

| 配置 | 值 | 为什么 |
| --- | --- | --- |
| `org.gradle.jvmargs` | `-Xmx2560m -Dfile.encoding=UTF-8` | 源码、注释、测试里的中文字符串很多，`file.encoding` 不固定会出现编译期乱码 |
| `org.gradle.parallel` | `true` | 只有一个模块，影响有限，留着无害 |
| `org.gradle.caching` | `true` | 开了构建缓存，重复构建快 |
| `org.gradle.configuration-cache` | **`false`** | 刻意关掉。配置缓存会缓存住任务图的输入输出，本项目大量使用 KSP + Room schema 导出，排查「改了却没生效」这类问题时它的收益小于诊断成本 |
| `android.useAndroidX` | `true` | AndroidX 必需 |
| `android.nonTransitiveRClass` | `true` | 每个模块只生成自己的 `R`，避免依赖里的资源名互相串台 |
| `kotlin.code.style` | `official` | 与 IDE 格式化规则一致 |

### 2.4 版本库不提交什么

`.gitignore` 全文如下（这是实际内容，不是示意）：

```gitignore
*.iml
.gradle/
.toolchain/
build/
local.properties
.idea/
.DS_Store
captures/
.externalNativeBuild/
.cxx/
.kotlin/
*.jks
*.keystore
keystore.properties
```

三条要点：

1. **`build/` 不提交**——而且 `build/` 这个写法会匹配**任意层级**的 `build/`，所以 `app/build/` 也在内。APK 产物、测试报告、本文第 4.3 节说的走查脚本与日志，全部落在 `build/` 里，天然不会被误提交。**不要**用 `git add -f` 去加它们。
2. **`.toolchain/` 不提交**——SDK 有几十 GB，必须靠 `.gitignore` 挡住。
3. **`keystore.properties` / `*.jks` / `*.keystore` 不提交**——签名材料永不进版本库，见第 6 节。

有一样东西**必须**提交，容易被误删：`app/schemas/`。它不在 `.gitignore` 里，是有意保留的——Room 导出的 schema json 是迁移测试的输入（见 2.5）。

### 2.5 `app/build.gradle.kts` 里两处「容易看不懂」的配置

```kotlin
buildFeatures {
    compose = true
    // 设置页要显示版本号。AGP 8 起 BuildConfig 默认关闭，必须显式打开；
    // 否则会出现「明明声明了却找不到 BuildConfig.VERSION_NAME」的编译错误。
    buildConfig = true
}
```

```kotlin
ksp { arg("room.schemaLocation", "$projectDir/schemas") }

sourceSets {
    getByName("androidTest").assets.srcDir("$projectDir/schemas")
}
```

第二处的因果关系是：KSP 把 schema json 导出到 `app/schemas/`，而设备测试里的 `MigrationTestHelper` 是**从测试 APK 的 assets 里**读那些 json 来校验「升级之后的表结构」的。不把 `schemas` 挂进 `androidTest` 的 assets，它不会安静跳过，而是直接报 `Cannot find schema file`——也就是测试红。所以这两行必须成对存在。

## 3. 日常构建

### 3.1 统一的环境前缀

本机是 Windows，日常命令在 Git Bash 里跑。**每条命令前面都带这一段**：

```bash
export MSYS_NO_PATHCONV=1
export JAVA_HOME="C:/Program Files/Java/jdk-17.0.18"
export PATH="$JAVA_HOME/bin:$PATH"
cd /c/Users/xyc/Desktop/For-The-Elder
```

三行的各自作用：

- `MSYS_NO_PATHCONV=1`：挡掉 Git Bash 的路径自动转换。不加的话，传给 `adb`/`emulator` 的 `/sdcard/...` 这类参数会被改写成 `C:/Program Files/...` 形状，报错信息很难懂。
- `JAVA_HOME` + `PATH`：`gradlew` 这个 **wrapper 脚本本身**是由 PATH 上的 `java` 启动的（`org.gradle.java.home` 管的是 Gradle 守护进程用的 JVM，管不了谁把守护进程拉起来）。显式前置 JDK 17 的 `bin`，两层都稳。
- `export PYTHONIOENCODING=utf-8`：**只在跑 Python 走查脚本时加**。不加的话 Git Bash 里 `print` 中文会按 GBK 编码，抛 `UnicodeEncodeError`。

### 3.2 三条命令

| 目的 | 命令 | 产物 |
| --- | --- | --- |
| 编译 + JVM 单测 | `./gradlew :app:testDebugUnitTest` | `app/build/reports/tests/testDebugUnitTest/index.html` |
| 编译 + 设备测试 | `./gradlew :app:connectedDebugAndroidTest` | `app/build/reports/androidTests/connected/` |
| 编译 + 打包 debug APK | `./gradlew :app:assembleDebug` | `app/build/outputs/apk/debug/app-debug.apk` |

只看编译（不跑任何测试）：`./gradlew :app:compileDebugKotlin`。

**第 12 轮实测基线**（第 12 轮的交付物上）：

- `:app:testDebugUnitTest` → **25 个测试类 / 342 个用例 / 0 失败 0 错误 0 跳过**
- `:app:connectedDebugAndroidTest` → **15 个测试类 / 96 个用例 / 0 失败**，`BUILD SUCCESSFUL in 52s`
- `:app:assembleDebug` → `app-debug.apk` **10,971,528 字节**

### 3.3 APK 字节数会随构建方式变，别拿它当回归判据

这一条是本轮踩到的坑，写下来省得下次又怀疑自己。

**同一次提交、同一份源码**，`app-debug.apk` 的字节数可以有两个值：

| 构建方式 | 字节数 |
| --- | --- |
| 先 `rm -rf app/build/outputs/apk/debug`，再 `./gradlew :app:assembleDebug --rerun-tasks` | **10,971,528** |
| 在已有产物上增量 `./gradlew :app:assembleDebug` | 11,001,618 |

全量重跑两次得到的是**逐字节相同**的 10,971,528，所以它是可复现的；差的那 30,090 字节来自增量构建复用了部分中间产物（压缩表、未变的 dex 分片等）。结论只有一句：**APK 字节数只有在「先删产物、再 `--rerun-tasks` 全量重建」的口径下才可比较**。做回归对比时要么固定这个口径，要么干脆别比字节数。

## 4. 安装、启动与走查

### 4.1 模拟器

本项目用的 AVD 名是 `Elder_API35`（基于 `android-35 / google_apis / x86_64`）。无窗口启动：

```bash
export MSYS_NO_PATHCONV=1
cd /c/Users/xyc/Desktop/For-The-Elder
./.toolchain/android-sdk/emulator/emulator.exe -avd Elder_API35 \
  -no-window -no-audio -no-boot-anim -gpu swiftshader_indirect -no-snapshot -port 5554
```

各参数的理由：

| 参数 | 理由 |
| --- | --- |
| `-no-window` | 无人值守跑，不需要界面；走查只看 `uiautomator dump` 的文本 |
| `-gpu swiftshader_indirect` | 软件渲染。本机没有可用的硬件 GPU 加速，用默认 `auto` 会黑屏 |
| `-no-snapshot` | 每次从冷启动开始，避免上一次的快照把 App 状态带进新一轮走查 |
| `-port 5554` | 固定端口号，`adb -s emulator-5554` 才能稳定指定它 |
| `-no-audio` / `-no-boot-anim` | 省资源，缩短启动时间 |

启动后确认：

```bash
./.toolchain/android-sdk/platform-tools/adb.exe devices          # 应看到 emulator-5554  device
./.toolchain/android-sdk/platform-tools/adb.exe shell wm size    # Physical size: 1080x2400
./.toolchain/android-sdk/platform-tools/adb.exe shell wm density # Physical density: 420
```

**1080×2400 / 420dpi** 是本文与 `records/04-质量与验证记录.md` 里所有「第几屏」「视口高 2400px」之类说法的基准。换算关系是 420/160 = **2.625×**：1dp = 2.625px，1sp 的字号在未叠加系统字号时也是 2.625px。

应用内字号只有三档，写在 `data/prefs/SettingsStore.kt` 的 `FontSize` 里，是把倍率**直接乘进每个 `sp`**（而不是替换 `LocalDensity.fontScale`，原因见 `ui/theme/Type.kt` 的类注释与 ADR-004）：

| 档 | 界面文案 | 倍率 | 正文（基准 `bodyLarge = 20sp`） |
| --- | --- | --- | --- |
| `STANDARD` | 标准 | 1.0× | 20sp = 52.5px |
| `LARGE` | 大一点 | 1.15× | 23sp = 60.375px |
| `EXTRA` | 更大 | 1.30× | 26sp = 68.25px |

`build/walk12c.py` 在最大档实测到的可点区域下限是 `rowPitch` 170px ÷ 2.625 = **64.8dp**。这个下限对照的 `ui/theme/Dimens.kt` 里的两个值，**第 49 轮改过**：`minTouchTarget` 与 `buttonHeight` 都已由 56dp 抬到 **64dp**（按 160 dpi 的**名义**换算 ≈ **1.02cm**，对齐 NN/g 引 Parhi/Karlson/Bederson 2006 的 1cm × 1cm 底线；旧 56dp ≈ 8.9mm 不过线）。第 49 轮在 1080×2400 / density 420（1dp = 2.625px）的模拟器上另量到：盘面格高恒 **64.0dp**、格宽 64.0~70.9dp、入口大卡 **124.6dp**、设置行 **71.2dp**。**换密度会让所有像素级结论失效**，要重测（`records/04` §12.3 与第四十九节是实测表）。

### 4.2 安装与启动

```bash
ADB=./.toolchain/android-sdk/platform-tools/adb.exe
$ADB install -r app/build/outputs/apk/debug/app-debug.apk
$ADB shell am start -n com.fortheelder.debug/com.fortheelder.MainActivity
```

启动的组件名必须是 `com.fortheelder.debug/com.fortheelder.MainActivity`：

- 包名（组件名里斜杠**前面**那半）是 **debug 变体**的 `com.fortheelder.debug`——`app/build.gradle.kts` 里 `debug { applicationIdSuffix = ".debug" }`，所以两个变体能同机共存，互不覆盖数据。
- 组件名斜杠**后面**那半**不带** `.debug`，因为 `namespace = "com.fortheelder"`，Kotlin 类名还是 `com.fortheelder.MainActivity`。

这两个「一半带、一半不带」是新手最容易写错的地方，症状是 `Activity class does not exist`。

想从干净状态起步（走查脚本第一步就要做这件事）：

```bash
$ADB shell pm clear com.fortheelder.debug
```

这会清掉 Room 数据库（`wish` / `anchor` / `daily_rhythm` / `rhythm_signal` 四张表）与 DataStore（`settings` / `intervention`）里的一切，等价于重装。**不清的话上一轮走查留下的数据会让断言假失败**——比如「书法」这条意愿已经是 `CONFIRMED`，谈话页就直接进「已确认」分支，待定分支的三句文案根本不会渲染。

### 4.3 走查脚本

装机走查脚本放在 `build/`（因此不进版本库），用 Python 3 直接跑：

```bash
export PYTHONIOENCODING=utf-8
python build/walk12e.py > build/walk12e.stdout.txt 2>&1
```

脚本自己调 `adb`，只做三件事：`uiautomator dump` 取屏、`input tap` / `input swipe` 操作、把断言结果写进 `build/walk12e.log`。**stdout 只有一行 `OK`**（失败时是异常文本），轨迹全在 `.log` 里。所以看结果要 `tail build/walk12e.log`，不要只看 stdout。

三条与「怎么读这些日志」有关的硬事实（都在 `records/04` 第 12 章有完整记录）：

1. `uiautomator dump` **只含屏幕内的节点**。任何「页面上到底有没有这句话」的判断，都必须先把那句话滚进视口。
2. `uiautomator dump` 在滚动之后，对 Compose 的无障碍树可能给出**残缺的节点集**——同一屏、同一状态，前后两份 dump 的文本可以不一样。所以判据要用**多次取屏的并集**，不能赌单份。
3. 单步 `input swipe` 的位移**必须小于视口高（2400px）**。滑太快会触发 fling，一次跨过一屏多，某个位置就永远不会进屏，从而从所有 dump 里消失。本项目走查脚本用 `SWIPE_DY = 600`。

## 6. Release 构建与签名

### 6.1 当前状态：release 变体没有签名

`app/build.gradle.kts` 的写法是**条件式**的：

```kotlin
val keystorePropsFile = rootProject.file("keystore.properties")
...
signingConfigs {
    create("release") {
        if (keystorePropsFile.exists()) { ... }
    }
}
buildTypes {
    release {
        ...
        if (keystorePropsFile.exists()) { signingConfig = signingConfigs.getByName("release") }
    }
}
```

本项目**根目录下没有 `keystore.properties`**（它是 `.gitignore` 里的条目之一，也不会被提交）。所以现在：

- `./gradlew :app:assembleRelease` **可以构建成功**，产物是 `app/build/outputs/apk/release/app-release-unsigned.apk`。第 12 轮实测：构建通过，该文件 **7,550,437 字节**（首次 release 构建的产物；按 §3.3 的理由，字节数同样别当回归判据），同目录的 `output-metadata.json` 记着 `versionCode 1 / versionName 0.1.0`、`minSdkVersionForDexing 26`；
- 这个 APK **没签名，装不上真机**。第 12 轮实测两句：`unzip -l` 的 `META-INF` 下**没有** `.RSA` / `.SF` / `.DSA` 签名块；`adb install -r <该文件>` 报 `INSTALL_PARSE_FAILED_NO_CERTIFICATES: Failed to collect certificates from /data/app/vmdl907715672.tmp/base.apk: Attempt to get length of null array`；
- `isMinifyEnabled = false`——release 也没开混淆。当前阶段刻意如此：混淆会把 Room 实体与反射相关的类名改掉，需要额外的 keep 规则，而本项目还没有对外发布的需求。

**所以「交付物」= debug 变体的 APK + 模拟器上的走查，不是 release 包。** 本文不假装有一个签名好的发布包。

### 6.2 要出签名包时补什么

在根目录建 `keystore.properties`（**不要提交**）：

```properties
storeFile=for-the-elder-release.jks
storePassword=<口令>
keyAlias=<别名>
keyPassword=<口令>
```

`storeFile` 走的是 `rootProject.file(...)`，所以相对路径以**项目根目录**为基准。`.jks` 与 `keystore.properties` 两样都已在 `.gitignore` 里，不会误传。

补上之后 `assembleRelease` 会自动带上签名配置，无需改任何代码——这是当初把它写成条件式的原因。

### 6.3 真机上的注意事项

- `minSdk = 26`（Android 8.0）。低于它的设备装不上，不是 bug，是有意抬高的下限：目标用户（55–65 岁）手里的机器基本都在 8.0 以上，抬高下限省掉了大量兼容分支。
- `targetSdk = 35`。目前 App **不声明任何权限**（`AndroidManifest.xml` 里连一条 `<uses-permission>` 都没有），所以不存在「targetSdk 升高后权限行为变了」这类问题。
- `allowBackup="false"`：不做系统云备份。常伴记录的是很私人的作息与意愿，默认不外流。

## 7. 版本号、包名与数据库版本

### 7.1 版本号分散在三处，改的时候要一起看

| 位置 | 当前值 | 作用 |
| --- | --- | --- |
| `app/build.gradle.kts` → `versionName` | `0.1.0` | 显示给用户看。设置页通过 `BuildConfig.VERSION_NAME` 读取，所以 `buildConfig = true` 是必需的（2.5） |
| `app/build.gradle.kts` → `versionCode` | `1` | 系统用来判断能不能覆盖安装的整数 |
| `docs/00-项目章程与需求计划书.md` 等文档的表头 | 与 `versionName` 对齐 | 文档基线的标记，**不受构建影响**，靠人工保持一致 |

发布前把三处对齐；文档里的版本号写错不会让构建失败，只会让记录失真。

### 7.2 包名规则

| 概念 | 值 | 来源 |
| --- | --- | --- |
| `namespace` | `com.fortheelder` | 决定 `R` 类与 `BuildConfig` 的包名、以及**清单文件里相对类名**（`.ElderApp`、`.MainActivity`）的补全前缀 |
| `applicationId`（release） | `com.fortheelder` | 决定设备上的安装标识 |
| `applicationId`（debug） | `com.fortheelder.debug` | 由 `applicationIdSuffix = ".debug"` 追加 |

`namespace` 与 `applicationId` 当前相同，但**它们是两个概念**：改 `applicationId` 会变成另一个 App（两台机器上能并存），改 `namespace` 只会重排自己代码的包。

### 7.3 数据库 schema 导出

Room 的版本号写在 `app/src/main/java/com/fortheelder/data/db/ElderDatabase.kt` 的 `@Database(version = ...)`。当前是 **3**，对应 `app/schemas/com.fortheelder.data.db.ElderDatabase/` 下的三个 json。

**改库结构的流程**（缺一步就红）：

1. 改实体类 / DAO；
2. 把 `@Database` 的 `version` 加 1；
3. 在 `app/src/main/java/com/fortheelder/data/db/Migrations.kt` 里写这个版本的 `Migration`，并挂进 `ElderDatabase` 的 `addMigrations(...)`；
4. 构建一次，让 KSP **生成新的 schema json**；
5. `git add app/schemas/...` ——**新 json 必须提交**，否则换机器跑迁移测试会报 `Cannot find schema file`；
6. 用 `MigrationTestHelper` 写一条从「上一版」迁到「这一版」的用例。

### 7.4 构建产物清单

| 产物 | 路径 | 进版本库？ |
| --- | --- | --- |
| debug APK | `app/build/outputs/apk/debug/app-debug.apk` | 否（`build/` 被忽略） |
| release APK（未签名） | `app/build/outputs/apk/release/app-release-unsigned.apk` | 否 |
| JVM 单测报告 | `app/build/reports/tests/testDebugUnitTest/index.html` | 否 |
| 设备测试报告 | `app/build/reports/androidTests/connected/index.html` | 否 |
| Room schema | `app/schemas/**/*.json` | **是** |
| 走查脚本与日志 | `build/walk12*.py`、`build/walk12*.log` | 否 |

## 8. 常见故障与排查

以下每一条都是本项目实际撞过的，按「症状 → 原因 → 处置」写。

### 8.1 `Activity class does not exist`

**症状**：`adb shell am start` 报这个。
**原因**：组件名前半段（包名）写成了 `com.fortheelder`，但装上去的是 debug 变体，真实包名是 `com.fortheelder.debug`。
**处置**：`adb shell pm list packages | grep fortheelder` 先看装的是哪个，按 4.2 的写法启动。

### 8.2 `Cannot find schema file`（设备测试红）

**原因**：`app/schemas/` 没有挂进 `androidTest` 的 assets，或者 schema json 没生成/没提交。
**处置**：确认 `app/build.gradle.kts` 里 `sourceSets { getByName("androidTest").assets.srcDir("$projectDir/schemas") }` 存在，并先跑一次 `./gradlew :app:assembleDebug` 让 KSP 导出 json。

### 8.3 中文注释或测试字符串变成乱码

**原因**：`file.encoding` 没固定。
**处置**：确认 `gradle.properties` 的 `org.gradle.jvmargs` 里有 `-Dfile.encoding=UTF-8`；Git Bash 里跑 Python 脚本时另加 `export PYTHONIOENCODING=utf-8`。

### 8.4 走查脚本报「找不到某句话」，但页面看起来明明有

按以下顺序排查，**不要跳步**：

1. 那句话在**这一份 dump 里**吗？`uiautomator dump` 只含屏幕内节点，先确认它已经滚进视口（用 `reach()` 滚到它那一屏再断言）。
2. 是不是**借了别人那份 dump**？锚点卡在页面最下面、起点卡在页面最上面，同一份 dump 不可能同时含两句——各自取一次屏。
3. 是不是**只取了一份 dump**？滚动之后 Compose 的无障碍树可能残缺，用多次取屏的并集。
4. 是不是**取的范围不够长**？并集也不是万能的——固定取四屏就可能够不到目标行，要**边滚边并集、找到即停**。
5. 最后才怀疑产品：把 `build/walk12e.log` 里那次 `REACH` 到的原始 dump 找出来，看那句话到底在不在。

第 12 轮在这五步上连踩七次（`records/04-质量与验证记录.md` §12.2.5 有完整列表）。**七次的根因全在脚本这一侧，没有一次是 App 缺东西**——但也正因为如此，这五步现在是被记录下来的方法，而不是经验。

### 8.5 怀疑 App 联网或要权限

用命令回答，不要靠印象：

```bash
grep -c "uses-permission" app/src/main/AndroidManifest.xml    # 0
grep -c "<receiver" app/src/main/AndroidManifest.xml          # 0
grep -rl "okhttp\|HttpURLConnection\|Retrofit" app/src/main/java | wc -l   # 0
grep -rl "INTERNET" app/src/main                            # 空
```

常伴的这一条是产品承诺级的需求（不联网、不采集、不要额外权限），所以它同时有静态检查和装机走查两层证据，见 `docs/01-需求规格说明书.md` 的 NFR 一节与 `records/04` §12.5。

### 8.6 构建很慢或行为诡异

按顺序试：

1. `./gradlew --stop` 停掉守护进程再重来（守护进程卡住时最常见）；
2. `./gradlew :app:assembleDebug --rerun-tasks` 强制全量（`org.gradle.caching = true` 开着，缓存有时会掩盖真实状态）；
3. `rm -rf app/build` 后重建；
4. 最后才考虑 `rm -rf ~/.gradle/caches`（代价很大，要重新下载依赖）。
