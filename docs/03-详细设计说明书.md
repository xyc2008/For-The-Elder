## 3. 领域层详细设计

### 3.1 `PlayHint` —— 提示只有两种

`domain/play/PlayGame.kt:17-26`

| 枚举值 | 常量 | `text` |
| --- | --- | --- |
| `NONE` | `:19` | `""` |
| `ALREADY_DONE` | `:22` | `这个已经点过了，换一个` |
| `NOT_YET` | `:25` | `这个还在后面，不急` |

设计要点（写在类的 KDoc 里）：

- 只有**两个**非空提示：点过了 / 还没轮到。刻意不做第三、第四种（比如「差得远」「方向错了」）——分得越细，越像在给人打分。
- 类的 KDoc 明写：**这里没有任何一处能记下「错了几次」**。提示是「说一句话」这件事本身，不是一个计数器加一之后的渲染。
- 提示文字**存在枚举里**而不是 UI 层，是为了让 JVM 单测能直接钉住这两句话，不必起模拟器。

### 3.2 `PlayRound` —— 一局的全部状态

`domain/play/PlayGame.kt:46-98`

| 字段 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `gameId` | `String` | 无 | 这一局属于哪个游戏（`SchulteGrid.ID`） |
| `cells` | `List<String>` | 无 | 格子里显示的标签，**已打乱**，下标即格子位置 |
| `order` | `List<String>` | 无 | 应当被点击的顺序，**未打乱** |
| `step` | `Int` | `0` | 已经点对几个 |
| `hint` | `PlayHint` | `NONE` | 最近一次点击留下的提示 |

**派生属性（全部现算，不落字段）**

| 成员 | 位置 | 定义 |
| --- | --- | --- |
| `target` | `:57` | `order.getOrElse(step) { "" }` —— 现在该点哪个；已完成时是空串 |
| `total` | `:59` | `order.size` |
| `finished` | `:61` | `step >= order.size` |
| `passed(label)` | `:68` | `order.indexOf(label) in 0 until step` |

这里有一处刻意的取舍：**「哪些格子点过了」不存成一个集合，而是每次用 `indexOf` 现算。**

理由有两条：

1. **不会有第二个真相。** 如果同时存 `step` 和 `doneSet`，两者一旦不同步（洗牌换了、恢复状态只恢复了一半），界面就会显示一个自相矛盾的棋盘。现算之后，`step` 是唯一真相，格子压暗只是它的一个投影。
2. **`indexOf` 的复杂度无所谓。** 一局最多 25 个格子，`passed()` 被调用 25 次，25×25 = 625 次字符串比较，成本可以忽略。为这么点规模引入集合，换来的是上面那条风险。

### 3.3 `tap(index)` —— 三分支，没有第四种结果

`domain/play/PlayGame.kt:80-97`

```
tap(index):
  1) finished           → return this        // 已经完成，点什么都不动
  2) cells.getOrNull(index) == null
                        → return this        // 越界下标，静默退回
  3) 取 label = cells[index]；rank = order.indexOf(label)
       3a) rank == step   → copy(step = step + 1, hint = NONE)      // 点对
       3b) rank in 0 until step → copy(hint = ALREADY_DONE)         // 点过了
       3c) 否则           → copy(hint = NOT_YET)                    // 还没轮到
```

要点：

- **分支 1 与 2 都是原样返回**，不抛异常、不产生副作用、不改 `hint`。界面永远能安全地调它。
- **3b / 3c 只改 `hint`，不动 `step`。** 点错既不加分也不扣分——`step` 是一个单调不减的量，它在数学上就没有「减小」这条路径（AC-12.3 的结构性保证）。
- 由于 `tap` 是纯函数并返回新对象，`PlayRound` 天然是不可变的：界面手里那个旧 `round` 不会被悄悄改掉。这直接支撑了第 5.5 节的「转屏由 ViewModel 存活」。

### 3.4 `PlayGame` —— 一个游戏是什么

`domain/play/PlayGame.kt:103-125`

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | `String` | 稳定标识（`schulte-5x5`），不随文案改动 |
| `name` | `String` | 显示名（`舒尔特方格`） |
| `howTo` | `String` | 一句话说清怎么玩 |
| `columns` | `Int` | 一行摆几个格子 |
| `longestSeconds` | `Int` | **上限**，不是目标，更不是及格线（KDoc `:101`） |
| `deal` | `(Random) -> PlayRound` | 出局函数：给定随机源，摆出一局 |

**为什么是 `data class` 而不是 `interface`。**

`docs/02` 第 2.2 节定下的规则是「只有一个实现的接口不写」，`records/03` 的 `ADR-015` 把这条规则套到框架上：一个「游戏」需要被提供的东西就是上面这 6 项，用 `data class` 表达即**已经表达了全部契约**，再包一层 `interface PlayGame { … }` 只是把 6 行字段抄成 6 行抽象成员，然后在下面写一个 `object XxxGrid : PlayGame`——两个文件说同一件事。

需要变化的不是「换一个实现类」，而是「在目录里多写一条数据」：`PlayCatalog.kt:11` 的 KDoc 明写，加第二个游戏只需要在那里多写一条 `PlayGame(...)`，出局函数写在同包的一个 `object` 里。

**`longestSeconds` 为什么是上限而不是倒计时。**

界面上没有任何地方把它渲染成「还剩 N 秒」(`ui/play/PlayScreen.kt:37-38`)。它只有两个用途：

1. `PlayVoice.promise(game)` 把它折算成一句「一局最多 N 分钟」；
2. `PlayVoice.minutes` 用它做 `(longestSeconds + 59) / 60` 的向上取整。

一个跳动着的倒计时本身就是催促，而这个模块想给人的只是「手上有件事做」。

### 3.5 `SchulteGrid` —— 第一个实现

`domain/play/SchulteGrid.kt`

| 成员 | 位置 | 值 |
| --- | --- | --- |
| `ID` | `:20` | `"schulte-5x5"` |
| `SIDE` | `:23` | `5` |
| `numbers` | `:26` | `private`，`(1..25).map { it.toString() }` |
| `game` | `:28` | `PlayGame(id = ID, name = "舒尔特方格", howTo = "格子里是打乱的 1 到 25，按从小到大的顺序挨个点一遍。点错了也不要紧，接着点就是。", columns = SIDE, longestSeconds = 180, deal = ::deal)` |
| `deal(random)` | `:43` | `PlayRound(gameId = ID, cells = numbers.shuffled(random), order = numbers)` |

两处值得单独说：

- **`numbers` 是 `private` 的**，且它只被用作「顺序」和「洗牌前的原料」。`shuffled(random)` 返回的是一个**新列表**，`numbers` 本身不变——所以同一进程里连开几局，`order` 永远是 `1..25`，不会因为某一局洗过牌而错位。
- `howTo` 的措辞刻意用「点错了也不要紧，接着点就是」，而不是「尽量别点错」之类。前者描述的是**允许**，后者描述的是**要求**。

### 3.6 `PlayCatalog` —— 注册表

`domain/play/PlayCatalog.kt:14-20`

### 3.7 `PlayWords` —— 禁用词表与扫描

`domain/play/PlayWords.kt`

| 成员 | 位置 | 内容 |
| --- | --- | --- |
| `banned` | `:22-38` | 15 个词：训练 / 改善 / 提升 / 延缓 / 评估 / 认知能力 / 疗效 / 疗程 / 治疗 / 预防 / 诊断 / 康复 / 大脑退化 / 记忆力 / 变聪明 |

**判据是朴素子串**（`text.contains(it)`），不是分词、不是正则。这个选择是**故意**的，KDoc `:14-15` 写明了后果：

### 4.3 状态机的转换

`ui/play/PlayViewModel.kt`

```
        start()                        tap(index) 且 next.finished
Ready ───────────► Playing ─────────────────────────────────────► Finished
  ▲                  │                                                │
  │                  │ tap(index) 且 !finished：留在 Playing，        │
  │                  │ 只把 round 换成 tap() 的返回值                 │
  └──────────────────┴────────────────────────────────────────────────┘
                     离开页面（返回）：ViewModel 销毁，状态一起消失
```

| 转换 | 触发 | 位置 | 动作 |
| --- | --- | --- | --- |
| `Ready → Playing` | `start()` | `:62` | `game.deal(Random.Default)` 摆一局 + `clock.now()` 记 `startedAt` |
| `Playing → Playing` | `tap(i)`，未完成 | `:79` | `round = round.tap(i)` |
| `Playing → Finished` | `tap(i)`，完成 | `:79` | 先算 `secondsSince(startedAt)`，再置 `Finished` |
| 任意 → 消失 | 返回键 / 退出 | — | ViewModel 随页面销毁，不留任何痕迹 |

**取时钟只有两个时点**：`start()` 一次、完成那一次。中间每一次点击都**不读时钟**——所以「用了多久」完全不受点击快慢的影响，也不会因为时钟被拨动而在中途发生变化。

**`secondsSince()` 的实现**（`:90`）：

```kotlin
Duration.between(start, clock.now()).seconds.coerceAtLeast(0L).toInt()
```

`coerceAtLeast(0L)` 处理的是「取整到秒之后出现负数」这种边角：`Duration.between` 本身按纳秒算不会负，但秒级截断之后，若用户在极短的一瞬完成一局，`seconds` 可能是 0；而如果系统时钟在这期间被回拨，结果就是负的。负的用时在界面上是没意义的东西，按 0 处理。

**凭什么不需要 `viewModelScope`。** 这一页**没有**任何挂起调用、没有协程、没有 `Flow` 收集之外的后台工作：

- 没有 repository（不存在读写）；
- 没有 `delay`（没有倒计时）；
- 状态载体就是 `MutableStateFlow`（`:52`），赋值是同步的。

既然没有异步工作，也就没有需要取消的东西——`viewModelScope` 在这里只会是一个没人用的字段。过滤器/持久化一旦接进来（将来真要存什么的时候），它才需要被加上，而不是现在预埋。

三处布局决策，每一处都在源码里写了理由：

1. **提示行始终占着位置**（`:85-86`）。点错时它才有字。若让它「有字才出现」，整张卡片会在用户点错的一瞬间往下跳一下——而用户的眼睛正盯着下面那片格子。
2. **格子用 `heightIn(min = 56dp)`，不用 `aspectRatio(1f)` 也不用固定高度**（`:144-146`）。大字号下数字会比正方形高，正方形会把数字裁掉一截，跟 `ui/common/ElderComponents.kt` 弃用 Material `TopAppBar` 是同一个原因。宁可变成竖长方形，也要让数字完整。三档字号的实测数据见 `records/04` 第十一章。
3. **点过的格子压暗但照样能点**（`:148-149`）。把点击关掉看着更清爽，代价是用户点了一下毫无反应——那比一句温和的提示糟得多，而这一下正是 AC-12.3 要接住的误触。

`cols` 从 `game.columns` 取而不是写死 5（`:113-114`）：将来格子数不一样的小游戏进来时，该改的是那条目录项，不是这一页。用 `chunked` 切行之后，格子数与行宽之间就没有隐含的整除前提了（`:116-118`）。

### 5.4 DR-09「不落库」为什么是结构性保障

需求里写的是「不保存历史成绩」，但**「不保存」不能靠自觉**——真正能守住它的写法，是让写这件事**没有地方发生**：

| 检查 | 结果 |
| --- | --- |
| `ui/play` 是否 import 任何 `data` 层的类 | 否 |
| `PlayViewModel` 的构造参数 | 只有 `clock: AppClock` |
| `PlayViewModel` 里有无 repository 字段 | 无 |
| `PlayRound` / `PlayGame` 里有无 `id` / 时间戳 / 错误计数 / 用时字段 | 无（用时只在 `Finished` 这个 UI 状态里，随页面消失） |
| `domain/play` 里有无线索可寻的存储写入 | 无（四个文件全量读过） |

结论：**这一层没有「上次多少秒」这个数据可以拿出来比较**，因为它从来没有被写下来过。

### 5.5 转屏与重建

`PlayRound` 是 `data class` 且 `tap()` 返回新对象，界面手里那个不会被悄悄改；状态的唯一载体是 `PlayViewModel` 里的 `MutableStateFlow`（`PlayViewModel.kt:52`）。所以设备旋转时 Activity 重建、`ViewModel` 存活，正在玩的这一局原样还在。

对应的设备用例是 `PlayScreenTest` 的「中途退出去再进来是一局全新的」（见 6.1）：它走的是「退出页面 → 重新进入」这条路——重新进入会拿到一个**新的** `ViewModel`，其初值是 `Ready(PlayCatalog.first)`，所以是全新一局，**不会**出现「回来接着上次剩下的一半」。这与 AC-12.4 一致：中途退出不产生任何「未完成」记录。
