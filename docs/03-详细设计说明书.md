## 3. 领域层详细设计

### 3.1 `PlayHint` —— 提示有四种

`domain/play/PlayGame.kt:17-29`

| 枚举值 | 常量 | `text` |
| --- | --- | --- |
| `NONE` | `:19` | `""` |
| `ALREADY_DONE` | `:22` | `这个已经点过了，换一个` |
| `NOT_YET` | `:25` | `这个还在后面，不急` |
| `NOT_THIS_ONE` | `:28` | `不是它，再看看` |

第 11 轮只有前三个。第 12 轮加第四个，理由是**找一样的没有「顺序」**：舒尔特方格点错有两种意思（点过了 / 还没轮到），而找一样的点错只有一种意思——手里这张不是要找的那张。把它的反馈说成「这个还在后面，不急」，是在暗示一个先后关系，而那个关系并不存在。所以新加的第四个取值只陈述事实本身。

设计要点（写在类的 KDoc 里）：

- 四个取值**都只陈述事实**，没有一个是评价（没有「差得远」「方向错了」这类）。分得越细，越像在给人打分。
- 类的 KDoc 明写：**这里没有任何一处能记下「错了几次」**。提示是「说一句话」这件事本身，不是一个计数器加一之后的渲染。
- 提示文字**存在枚举里**而不是 UI 层，是为了让 JVM 单测能直接钉住这几句话，不必起模拟器。`ClaimWordsTest` 除此之外还会把每个取值的 `text` 逐个过一遍宣称词表——这四句话自己也必须干净。

### 3.2 `PlayRound` —— 一局的状态是个 `sealed interface`

`domain/play/PlayGame.kt:68-95`

**公共契约**（任何一局都必须提供这七件事）：

| 成员 | 位置 | 类型 | 含义 |
| --- | --- | --- | --- |
| `gameId` | `:71` | `String` | 这一局属于哪个游戏 |
| `cells` | `:74` | `List<String>` | 格子里显示的标签，**已打乱**，下标即格子位置 |
| `hint` | `:77` | `PlayHint` | 最近一次点击留下的提示 |
| `finished` | `:80` | `Boolean` | 这一局了了没有 |
| `stepsToFinish` | `:83` | `Int` | 走完一局一共对几次（用于完成卡的句式与测试断言） |
| `tap(index)` | `:91` | `(Int) -> PlayRound` | 点一下，返回**新的一局** |
| `markOf(index)` | `:94` | `(Int) -> CellMark` | 这一格现在是什么样子 |

**为什么第 12 轮把它从 `data class` 改成 `sealed interface`。** 两个游戏的局面状态形状不一样：

| 游戏 | 一局的私有状态 |
| --- | --- |
| 舒尔特方格（`OrderRound`） | `order: List<String>`（1..25 的顺序）+ `step: Int`（已经点对几个） |
| 找出一样的（`FindPairRound`） | `pairLabel: String`（要找的那张牌的字）+ `firstPick: Int?`（第一张选中了哪一格）+ `solved: Boolean` |
| 算一算（`SubtractRound`） | `deduction: Int`（每次减几，恒 7）+ `questions: List<SubtractQuestion>`（**这一局的 5 道题在出局时就全算好**）+ `step: Int`（走到第几道） |

这两组字段**互相之间没有意义**。如果把两套字段塞进同一个 `data class`，那么对**任意**一局来说，都会有两个字段永远不被使用；更糟的是，它们能组合出互相矛盾的状态——比如「`step` 已经走完了」同时又「`firstPick` 指着某一格」。一个类型如果能表示它自己都不承认的状态，那它就没把规则说清楚。改成 `sealed interface` 之后，「舒尔特的一局」和「找一样的一局」是两个不同的类型，各自只带自己那套字段，矛盾态**无法被写出来**。

代价与收益：`PlayScreen.kt` 的 `when` 因此变成穷尽的——将来再加规则，编译器会把漏掉的分支顶回来。第 12 轮加第二个游戏时，编译器确实报出了三处「`when` 不是穷尽的」，这也是为什么「加游戏」并不像第 11 轮以为的那样只需动目录。**第 17 轮加第三个游戏时，编译器又报出了三处**（都在 `ui/play/PlayVoice.kt`：`:60` 的 `headline`、`:80` 的 `doneLine`、`:92` 的 `doneNote`）——两次都印证同一条：新增一个 `PlayRound` 实现，代价不落在目录里。

**公共部分刻意不含的东西**（这一条是 DR-09 的直接来源）：

- 错了几次 —— 没有字段，`tap()` 也没有任何一条路径去记它；
- 扣了几分 —— 没有分数的概念；
- 用了多久 —— 用时**不在** `PlayRound` 里，它在 `core/time/AppClock.kt` 现算，只活在 `Finished` 这个界面状态里，页面一关就没了；
- 没有 id、没有时间戳、没有用户字段 —— 于是「把这一局存下来」这件事没有落点。

这不是靠自觉，是**没有可以落的地方**（详见第 5.4 节）。

### 3.3 `CellMark` —— 格子有三种样子

### 3.4 三个 `tap` 实现

`tap(index)` 是纯函数：越界、重复、点错都不抛异常，一律返回一个对象。

#### 3.4.1 `OrderRound.tap` —— 三分支，没有第四种结果

`domain/play/PlayGame.kt:144-150`

```
tap(index):
  1) finished              → return this      // 已经完成，点什么都不动
  2) cells.getOrNull(index) == null
                           → return this      // 越界下标，静默退回
  3) 取 label = cells[index]；rank = order.indexOf(label)
       3a) rank == step        → copy(step = step + 1, hint = NONE)   // 点对
       3b) rank in 0 until step → copy(hint = ALREADY_DONE)           // 点过了
       3c) 否则                → copy(hint = NOT_YET)                  // 还没轮到
```

要点：

- **分支 1 与 2 都是原样返回**，不抛异常、不产生副作用、不改 `hint`。界面永远能安全地调它。
- **3b / 3c 只改 `hint`，不动 `step`。** 点错既不加分也不扣分——`step` 是一个单调不减的量，它在数学上就没有「减小」这条路径（AC-12.3 的结构性保证）。
- 返回类型收窄成 `OrderRound`（不是 `PlayRound`），于是 JVM 测试不必做类型判断就能直接断言 `step`。

#### 3.4.2 `FindPairRound.tap` —— 四分支，点错不清空手上那张

`domain/play/PlayGame.kt:199-206`

```
tap(index):
  1) solved                    → return this                          // 这一局已经了了
  2) cells.getOrNull(index) == null
                               → return this                          // 越界，静默退回
  3) index == firstPick        → copy(hint = ALREADY_DONE)             // 同一张点两次
  4) label != pairLabel        → copy(hint = NOT_THIS_ONE)             // 不是要找的那张
  5) firstPick == null         → copy(firstPick = index, hint = NONE)  // 第一张，拿住
     否则（firstPick != null）  → copy(solved = true,   hint = NONE)   // 第二张，成了
```

要点：

- **点错（分支 4）不清空 `firstPick`。** 用户不需要先把错的取消掉再重新选——手上那张牌一直拿得住。这是有意的（KDoc 在 `PlayGame.kt:196-197`）。
- `stepsToFinish` 恒为 `2`（`:175`）：一局就是对两次，写死而不是算出来，因为这个游戏的对数永远是 1 对。
- 分支 3 用 `index == firstPick` 判断「同一张」而不是比较文字：盘面上有两张字相同的牌，文字比较会把「另一张同字牌」也当成重复点。

#### 3.4.3 `SubtractRound.tap` —— 四分支，答对就换下一道

`domain/play/SubtractSeven.kt`（第 17 轮新增）

```
tap(index):
  1) finished                  → return this                            // 5 道都算完了
  2) cells.getOrNull(index) == null
                               → return this                            // 越界，静默退回
  3) 这一格的数 == current - deduction
                               → copy(step = step + 1, hint = NONE)      // 答对，走到下一道
     否则                       → copy(hint = NOT_THIS_ONE)              // 答错，换一句提示
```

要点：

- **分支 3 的两个出口都不读时钟**：答对只把 `step` 加一，答错只改 `hint`。这条直接对应 ADR-018 的筛选规则第 ② 条（判对错、判结束都不许读时钟）。
- **答错不改 `step`、不改题目顺序**：题面停在原地，用户接着点别的选项就行。这和 §3.4.1 的「点错只改 `hint`」是同一个形状——三个 `tap` 实现里，改动范围最大的那一步永远是「只动 `hint`」。
- 返回类型收窄成 `SubtractRound`（不是 `PlayRound`），于是 JVM 测试不必做类型判断就能直接断言 `step` 与 `hint`。
- **`markOf` 恒返回 `PLAIN`**（见 §3.10），所以这个 `tap` 不需要维护任何「哪一格被标记过」的状态。

### 3.5 `PlayGame` —— 一个游戏是什么

`domain/play/PlayGame.kt:221-242`

| 字段 | 位置 | 类型 | 含义 |
| --- | --- | --- | --- |
| `id` | `:222` | `String` | 稳定标识（`schulte-5x5` / `find-pair-4x4` / `subtract-seven`），不随文案改动 |
| `name` | `:223` | `String` | 显示名（`舒尔特方格` / `找出一样的` / `算一算`） |
| `howTo` | `:225` | `String` | 一句话说清怎么玩（会被词表扫描） |
| `columns` | `:231` | `Int` | 一行摆几个格子；摆法是游戏自己的事 |
| `longestSeconds` | `:239` | `Int` | **估时**（界面照实说成「大概 N 分钟」，第 22 轮），不是目标、不是及格线，**更不是会中断这一局的期限** |
| `deal` | `:241` | `(Random) -> PlayRound` | 出局函数：给定随机源，摆出一局。纯函数，同一个 `Random` 出同一局 |

**为什么是 `data class` 而不是 `interface`。**

出处是 `docs/02` 第 2.2 节正文与 `docs/01` NFR-14（「只有一个实现的接口不写」）。一个「游戏」需要被提供的东西就是上面这 6 项，用 `data class` 表达即**已经表达了全部契约**，再包一层 `interface PlayGame { … }` 只是把 6 行字段抄成 6 行抽象成员，然后在下面写一个 `object XxxGrid : PlayGame`——两个文件说同一件事。

> **第 12 轮更正**：第 11 轮本文把这条出处标成了「`docs/02` 约束 C-04」，而 `docs/02` 的 C-04 实际是「用户点头之前不提供帮助」。源码里的那处交叉引用已在第 12 轮改为「`docs/02` 第 2.2 节、`docs/01` NFR-14」（`PlayGame.kt` 的类 KDoc），GAP-09 由此关闭。

**「加一个游戏要改多少」—— 分档结论**（源码 KDoc 也写了这一条）：

| 情形 | 要改的地方 |
| --- | --- |
| 规则**已经存在**（再来一个舒尔特式的、或者再来一个找一样的） | 只往 `PlayCatalog.games` 里多写一条 `PlayGame(...)` + 同包一个 `object` 里的 `deal` |
| 规则**是新的** | **三处**：一个 `PlayRound` 实现（新的局面形状）+ 一条目录项 + 界面上的一个分支 |

第 12 轮走的正是第二条路。因此第 11 轮那句「加第二个游戏只需多写一条、不新增类型」经实测**部分成立**：六个字段确实一个没动 ✔，但**必须新增类型** ✘——`PlayRound` 得从 `data class` 变成 `sealed interface`。完整的取舍记在 `records/03` 的 ADR-016。

**第 17 轮走的还是第二条路**（规则是新的），代价与第 12 轮同形：一个 `PlayRound` 实现（`SubtractRound`）+ 一条目录项（`PlayCatalog.games`）+ 界面上的分支。但这一次有一处**不同**：界面分支不是「想起来才改」，而是**编译器逼出来的**——`PlayVoice.kt` 里三个 `when` 加了 `SubtractRound` 之后就不再穷尽，漏一个就编不过；而 `PlayScreen.kt` 一行都不用动（它只问 `cells`/`markOf`/`columns` 这些公共成员，见 §4.4）。这是第 12 轮改框架换来的东西：**「加游戏」的界面代价从「想起来才改」变成「不改就报错」**。

**`longestSeconds` 为什么是估时、而不是倒计时的期限。**

界面上没有任何地方把它渲染成「还剩 N 秒」。它只有两个用途：

1. `PlayVoice.promise(game)`（`PlayVoice.kt:76-77`）把它折算成一句「一局大概 N 分钟就完了」；
2. `PlayVoice.minutes`（`:126`）用它做 `(longestSeconds + 59) / 60` 的向上取整。

一个跳动着的倒计时本身就是催促，而这个模块想给人的只是「手上有件事做」。

**第 22 轮补的结论（本节此前写的是「上限」）**：这一局**没有任何东西会在超时后把它停下**——`ui/play` 与 `domain/play` 两层里没有 `delay(`、没有 `LaunchedEffect`、没有倒计时，`AppClock` 只在完成时算一次用时（第 22 轮 `grep` 实测）。所以屏幕上那句话不能说「最多」，只能说「大概」：说「最多」就是一句没人兑现的话，用户慢慢点，它就从他头顶上的一句话变成一道催促。同一批文案里「最多一天一次」之所以站得住，是因为它旁边真有 `maxGapMinutes = 1440` 兜着（`InterventionWindow.kt:26`，并在 `:47` 做 `coerceAtMost`）——**有机制兜底的「最多」才配写在屏幕上**。取舍记在 `records/03` ADR-020。

### 3.6 `SchulteGrid` —— 第一个实现

`domain/play/SchulteGrid.kt`（50 行）

| 成员 | 位置 | 值 |
| --- | --- | --- |
| `ID` | `:20` | `"schulte-5x5"` |
| `SIDE` | `:23` | `5` |
| `numbers` | `:26` | `private`，`(1..25).map { it.toString() }` |
| `game` | `:28` | `PlayGame(id = ID, name = "舒尔特方格", howTo = "格子里是打乱的 1 到 25，按从小到大的顺序挨个点一遍。点错了也不要紧，接着点就是。", columns = SIDE, longestSeconds = 180, deal = ::deal)` |
| `deal(random)` | `:45` | `OrderRound(gameId = ID, cells = numbers.shuffled(random), order = numbers)` |

与第 11 轮相比**只有一处**差别：`deal` 的返回类型由 `PlayRound` 写成 `OrderRound`（`:45`）。函数体一个字没改——收窄类型是为了让测试拿到带 `step` 的具体类型。

### 3.7 `FindPair` —— 第二个实现

`domain/play/FindPair.kt`（66 行）

| 成员 | 位置 | 值 |
| --- | --- | --- |
| `ID` | `:22` | `"find-pair-4x4"` |
| `SIDE` | `:25` | `4` |
| `words` | `:34-39` | 20 个二字日常物件：桔子 苹果 白菜 豆腐 茶壶 蒲扇 毛衣 布鞋 象棋 毛笔 藤椅 凉席 算盘 棉被 雨伞 桂花 月饼 核桃 花生 石榴 |
| `game` | `:41-48` | `PlayGame(id = ID, name = "找出一样的", columns = SIDE, longestSeconds = 120, deal = ::deal)` |
| `deal(random)` | `:57-65` | 见下 |

**`deal` 怎么摆一局**（恰好一对，位置随机）：

```
1) pool = words.shuffled(random).take(SIDE * SIDE - 1)   // 15 个互不相同的字
2) pairLabel = pool[random.nextInt(pool.size)]            // 从这 15 个里挑一个当「要找的那张」
3) cells = (pool + pairLabel).shuffled(random)            // 凑成 16 格，整体再洗一次
```

两点：**第二张是复制出来的**，所以盘面上恰好只有一对同字（15 个字 + 一个重复）；**用 `shuffled(random)` 而不是 `shuffled()`**，是为了给定 `Random` 就能造出确定局面——JVM 测试靠这一点逐格断言。

**为什么第 12 轮选它做第二个游戏**（KDoc 也写了）：

- **动作最少**：没有计时、没有翻牌记忆、没有数字输入。当时认为剩下三个顺延的游戏（记一记 / 反应速度 / 连续减七）都会破坏「领域层不认识时钟」这条红线，得先解掉那个问题才好做。
- **它测的是结构**：它的规则形状与舒尔特方格不同（没有顺序、有「拿住一张」的中间态），于是能真正压到框架的类型上——这正是 ADR-016 要回答的问题。

> **第 17 轮更正（出自 `records/03` ADR-018）**：上面「剩下三个都会破坏红线」这条判断**只对两个成立**。第 17 轮把三个候选逐个过了一遍筛选规则（①全部交互说得成一个「点某一格」②判对错、判结束都不读时钟），结论是：**记一记顺延**（翻牌记忆本身要「翻回去」这个动作，说不成一个点格子）、**反应速度判退**（它的核心就是「多久之内点」，不读时钟就没有这个游戏）、**连续减七落地**——因为「从 100 每次减 7、从三个数里点对的」这套交互既说得成「点某一格」，判对错也只是比数，压根不需要知道现在几点。于是它作为「算一算」成了第 17 轮的第三个游戏（见 §3.10）。这条更正同时写进了 `records/02` RC-014。

**牌面字是怎么挑的**（KDoc）：两字日常物件（不认字的老人也能认出图景感）、四列下不挤成两行、彼此不互为子串（测试会查）、并且整体过了宣称词表。

### 3.9 `ClaimWords` —— 宣称词表的单一来源（GAP-07 已关闭）

**GAP-07 的来龙去脉。** AC-11.1 是**全 App** 的规则，但第 11 轮结束时仓库里有**两张**各自定义的表：

**判据是朴素子串**（`text.contains(it)`），不是分词、不是正则。这个选择是**故意**的，KDoc `:13-14` 写明了后果：

> 因此自己也不能写否定式：一句「这不叫练脑子」照样会被扫出来。这是存心的——顺着读的人只会记住那几个字，而扫的代价只是换个说法。

`allowedWords` 的用途不是参与判定（它不在 `checkWords` 的默认参数里），而是**写给后来者的注释**：把「大脑体操」显式列出来，是为了防止有人顺手把「大脑」两个字加进 `banned`——那会把允许的说法一起扫掉。

### 4.3 状态机的转换

`ui/play/PlayViewModel.kt`

```
           choose(game)                start()               tap(i) 且 next.finished
Choose ─────────────────► Ready ─────────────► Playing ───────────────────────────► Finished
   ▲                        │                      │                                   │
   │  chooseAgain()         │                      └── tap(i) 且 !finished ──────────────┘
   └────────────────────────┘                          留在 Playing，只换 round，不回退
   （这条路只在规则页）

                离开页面（返回）：ViewModel 销毁，状态一起消失
```

| 转换 | 触发 | 位置 | 动作 |
| --- | --- | --- | --- |
| 初值 `Choose` / `Ready` | 构造 | `playStartState()` `:154-159` | `if (games.size == 1) Ready(first, canChooseAgain = false) else Choose(games)` |
| `Choose → Ready` | `choose(game)` | `:86` | 记下选中的游戏，`canChooseAgain = true` |
| `Ready → Choose` | `chooseAgain()` | `:102` | 退回选择页（第 23 轮加，只在规则页生效） |
| `Ready → Playing` | `start()` | `:116` | `game.deal(Random.Default)` 摆一局 + `clock.now()` 记 `startedAt` |
| `Playing → Playing` | `tap(i)`，未完成 | `:133-141` | `round = round.tap(i)` |
| `Playing → Finished` | `tap(i)`，完成 | `:133-141` | 先算 `secondsSince(startedAt)`，再置 `Finished` |
| 任意 → 消失 | 返回键 / 退出 | — | ViewModel 随页面销毁，不留任何痕迹 |

**「只有一个游戏就直接进 Ready」这个判断现在写成一条纯函数**（`playStartState()`，`:154-159`，KDoc `:148-153`），构造时的初值（`:67`）与 `chooseAgain()`（`:102`）共用它。第 23 轮之前这段判断直接嵌在属性初始化里（当时的 `:70-74`），既没有测试也走不到。它的意思是：第 11 轮只有舒尔特方格时，用户点「玩一会儿」直接看到规则页；第 12 轮有两个游戏，才多出一次选择。这条分支留着不是为了兼容什么，而是它本身就是对的——只有一个选择时不该让人选。

**三条状态转换各挡一道。** `choose` / `chooseAgain` / `start` / `tap` 四个动作都在开头判一次「现在是不是该我出场」（`if (mutableState.value !is X) return`）：从规则页再挑一次游戏、或者在玩到一半点「换一个游戏」，都不会悄悄改掉手上这一局。挡住之后，调用方不必自己记得这件事。

**取时钟只有两个时点**：`start()` 一次、完成那一次。中间每一次点击都**不读时钟**——所以「用了多久」完全不受点击快慢的影响，也不会因为时钟被拨动而在中途发生变化。

**`secondsSince()` 的实现**（`:144-145`）：

```kotlin
Duration.between(start, clock.now()).seconds.coerceAtLeast(0L).toInt()
```

`coerceAtLeast(0L)` 处理的是「取整到秒之后出现负数」这种边角：`Duration.between` 本身按纳秒算不会负，但秒级截断之后，若用户在极短的一瞬完成一局，`seconds` 可能是 0；而如果系统时钟在这期间被回拨，结果就是负的。负的用时在界面上是没意义的东西，按 0 处理。

**凭什么不需要 `viewModelScope`。** 这一页**没有**任何挂起调用、没有协程、没有 `Flow` 收集之外的后台工作：

- 没有 repository（不存在读写）；
- 没有 `delay`（没有倒计时）；
- 状态载体就是 `MutableStateFlow`（`:67`），赋值是同步的（`state` 由 `:69` 暴露为只读）。

既然没有异步工作，也就没有需要取消的东西——`viewModelScope` 在这里只会是一个没人用的字段。过滤器/持久化一旦接进来，它才需要被加上，而不是现在预埋。

三处布局决策，每一处都在源码里写了理由：

1. **提示行始终占着位置**（`:170-174`）。点错时它才有字。若让它「有字才出现」，整张卡片会在用户点错的一瞬间往下跳一下——而用户的眼睛正盯着下面那片格子。
2. **格子用 `heightIn(min = 56dp)`，不用 `aspectRatio(1f)` 也不用固定高度**（`PlayCell` 的 KDoc）。大字号的字会比正方形高，正方形会把字裁掉一截，跟 `ui/common/ElderComponents.kt` 弃用 Material `TopAppBar` 是同一个原因。宁可变成竖长方形，也要让字完整。三档字号的实测数据见 `records/04` 第十二节。
3. **点过的格子压暗但照样能点**（`PlayCell` 的 KDoc）。把点击关掉看着更清爽，代价是用户点了一下毫无反应——那比一句温和的提示糟得多，而这一下正是 AC-12.3 要接住的误触。

**第 23 轮加的一条：规则页上的退路只在规则页**（「换一个游戏」，`ReadyPanel` 的 KDoc `:126-138`）。玩到一半不摆它，是因为那时每一格都在等人点，多一个按钮就是多一次「这个是不是要我点」，而在玩那一局的退路顶上的返回键已经是了；结束卡上不摆它，是因为 AC-11.3 规定那张卡只允许有一个按钮、且必须是**离开这一页**的那个。这一页可以往回走，是因为这一刻这一局**还没摆出来**（`start()` 才摆）——退回去不丢任何东西，也没人在等一个结果。取舍见 `records/03` ADR-021。

`cols` 从 `game.columns` 取而不是写死 5（`:217`）：第 12 轮加 4×4 的「找出一样的」时，摆格子的**布局**一行都没动（`columns` / `chunked` / `weight` 三件事都不用改）；真正改过的只有一处**判据**——`PlayCell` 的入参从 `passed: Boolean` 换成 `mark: CellMark`，`PlayGrid` 里把 `rowIndex * game.columns + columnIndex` 提成一个 `val index`（`:226`）。用 `chunked` 切行之后，格子数与行宽之间就没有隐含的整除前提了（KDoc 在 `:200-212`）。

**第 36 轮更正**：上表第 3、4 行此前写的是 `:130` 的 `SectionTitle(text = "手上想有点事的时候")` 与 `:131-133` 的 `ActionRow(text = "玩一会儿", …)`；这两行从第 16 轮（`5e09cef`）起就已经过期——那一轮把首页文案收进 `HomeVoice`，`git show 5e09cef` 里正是 `-SectionTitle(text = "手上想有点事的时候")` / `+SectionTitle(text = HomeVoice.sectionPlay)` 与 `-text = "玩一会儿"` / `+text = HomeVoice.playAction`（`HomeScreen.kt` 此后只在第 18 轮因无障碍标签动过一次），本轮按当前源码重出。这一页这次**没有改代码**：变的只是它所引用的那个常量——`HomeVoice.playAction` 从自己写字面量改成指向 `PlayVoice.title`（见 4.4 节末尾与第 8 节 GAP-04 行）。

### 4.7 `A11y.kt` —— 语义标签只有五个入口（第 18 轮）

`ui/common/A11y.kt`（**58 行**，第 18 轮新建）把全部无障碍语义收在**五个** `Modifier` 扩展里。它们一个字节的可见文字都不发，只往 Compose 语义树里放标签；系统把语义树转成平台层 `AccessibilityNodeInfo` 给读屏软件（TalkBack）念。

| 修饰符 | 交给系统什么 | 挂在哪 |
| --- | --- | --- |
| `asScreenTitle(state: String? = null)` | `heading()`；`state` 非空时再给一个不显示的 `stateDescription` | `ElderComponents.kt:110`（`ElderHeader` 的表头 `Text`）。四屏各一：首页 / 对话页 / 游戏页 / 设置页 |
| `asSectionTitle()` | `heading()` | `ElderComponents.kt:142`（`SectionCard` 的标题）、`:157`（`SectionTitle`） |
| `announcesWhenItChanges()` | `liveRegion = LiveRegionMode.Polite` | `PlayScreen.kt:168`（题面）、`:179`（提示行）、`:193`（结束语） |
| `gridOf(rows, columns)` | `collectionInfo = CollectionInfo(rows, columns)` | `PlayScreen.kt:217`（棋盘 `Column`），`rows` 由 `(cells.size + columns - 1) / columns` 现算 |
| `gridCell(row, column)` | `collectionItemInfo = CollectionItemInfo(row, 1, column, 1)` | `PlayScreen.kt:276`（单个格子） |

三条设计口径，都是**取舍**，不是「顺手加的」：

1. **`heading()` 与 `stateDescription` 合成同一个 `semantics {}`。** `asScreenTitle` 因此只有一个块（`A11y.kt:32-35`），页码作为参数传进来而不是叠第二个块。**能说清的只有一条理由**：标题与页码从此只有一处入口，不会各自漂移。**不能说清的那条要如实标出来**——「同一节点上叠两个 `semantics` 块会让语义节点分裂成两个」这句话**本项目没有实测过**（没有 A/B 对照过两种写法在语义树与平台层各是什么样），所以本轮的选择是**根本不去碰这个不确定的行为**，而不是「已知会分裂」。这一句在第 18 轮末被收窄过一次，收窄经过见 `records/04` 第十六节与 `records/03` ADR-019 第 2 条。
2. **播报区只在「同一位置文字被替换」处用。** 提示行（`PlayScreen.kt:175-180`）**始终占着位置**，点错时才有字——节点一直都在、变的只是字，所以「读这行」有明确的触发时刻。反过来，首页问候语与「说两句」的结果卡是**新出现的节点**，而「新节点是否会请求朗读」这件事本项目**没有实测过**，因此**刻意不加** `liveRegion`（见 ADR-019 第 3 条）。
3. **行列从 0 开始，每格跨度 1。** `gridCell(row, column)` 传的是下标，不是「第几」；「第 3 行第 2 列」这句话由读屏软件自己拼。

装饰性图标显式写 `contentDescription = null`，并在附近留 `a11y-decorative: 理由` 豁免标记，由源码级守卫 `A11yPlacementTest` 的第二条规则盯着（见第 7.3 节）。全仓**没有**加任何 `onClickLabel`：本项目的按钮文字本身已经说清动作，再加一层标签是多出来的维护点。

### 5.4 DR-09「不落库」为什么是结构性保障

需求里写的是「不保存历史成绩」，但**「不保存」不能靠自觉**——真正能守住它的写法，是让写这件事**没有地方发生**：

| 检查 | 结果 |
| --- | --- |
| `ui/play` 是否 import 任何 `data` 层的类 | 否 |
| `PlayViewModel` 的构造参数 | 只有 `clock: AppClock` |
| `PlayViewModel` 里有无 repository 字段 | 无 |
| `PlayRound` 是 `sealed interface`，公共的七件事里有无 `id` / 时间戳 / 错误计数 / 用时字段 | 无（用时只活在 `Finished` 这个 UI 状态里，随页面消失） |
| `domain/play` 与 `domain/voice` 里有无存储写入的线索 | 无 |

最后一行用 import 复核过：`domain/play` 加上 `domain/voice` 一共只有 3 行 import，全部是 `kotlin.random.Random`。这一层没有存储依赖，也就没有地方写下任何一局的结果。

结论：**这一层没有「上次多少秒」这个数据可以拿出来比较**，因为它从来没有被写下来过。

### 5.5 转屏、重建与「中途退出」

`PlayRound` 现在是 `sealed interface`，两种实现都是 `data class` 且 `tap()` 返回**新对象**，界面手里那个不会被悄悄改；状态的唯一载体是 `PlayViewModel` 里的 `MutableStateFlow`（`:60`）。所以设备旋转时 Activity 重建、`ViewModel` 存活，正在玩的这一局原样还在——第 12 轮改了类型的形状，但**不可变性这条结论没有变**。

第 12 轮的走查（`build/walk12d.log`）把「中途退出」这条路用第二个游戏重跑了一遍，逐字证据：

### 7.8 第 27 轮：把测试收尾顺序做成一条会红的规则

（承接 §7.1~§7.7 的分层口径。）第 26 轮审收尾顺序时留下一笔账：`PlayScreenTest` 里那条走 `AppContainer` 的注销路径，「关库发生在界面组合退场之前还是之后，代码里看不出来，也没有任何东西会因此变红」。第 27 轮把这笔账还了，**`app/src/main` 一行未改**。

**新文件** `app/src/androidTest/java/com/fortheelder/ui/TestTeardown.kt`（3,058 字节 / 68 行）——`androidTest` 里**第一个不是测试类的 Kotlin 文件**。它导出一个顶层函数：

```kotlin
fun 关库排在组合之后(databaseName: String, container: () -> AppContainer): TestRule
```

用法是**套在 compose 规则的外面**：

```kotlin
private val compose = createComposeRule()   // 去掉 @get:Rule

@get:Rule
val rules: RuleChain =
    RuleChain.outerRule(关库排在组合之后(TEST_DB) { container }).around(compose)
```

收尾顺序靠 `RuleChain` 自己的机制（**内层先收**）而不是靠用例代码的记忆：宿主 Activity 先被 compose 规则销毁（组合销毁 → `ViewModelStore.clear()` → `viewModelScope` 取消），之后才轮到这条规则关库。`finally` 里的三步固定为：**断言前台上本应用 Activity 数为 0** → `container().database.close()` → `deleteDatabase`。

**为什么屏幕级用例需要它、而视图模型用例不需要**：`TalkViewModelTest` / `HomeViewModelTest` 的 `ViewModelStore` 是手工建的，它们自己把 `viewModelStore.clear()` 写在 `database.close()` 之前；屏幕级用例的视图模型活在 compose 规则自己的 store 里，**外面够不着**，只能靠规则链把顺序交回给框架。

**那条断言**（`要求宿主已经不在前台()`）：`ActivityLifecycleMonitorRegistry` 要求在主线程上问，所以过一遍 `runOnMainSync`，再断言 `getActivitiesInStage(Stage.RESUMED).size == 0`，失败报文点名 `TestTeardown.kt`。

| 它保证什么 | 它不保证什么 |
| --- | --- |
| 关库那一刻**前台上没有本应用的 Activity**（⇒ 组合已退场，`viewModelScope` 已取消） | **不保证「在飞的写库已结束」**——那归 ADR-023 的入库策略管 |
| 谁把顺序调回去，**当场变红**，而不是留到某天偶发失败 | **不保证**旧 `@After` 写法「必然出错」；本轮**没能构造出**可观察的数据级失败 |

**反向验证（有真负例）**：把 `TalkStarterTest.kt` 的规则链临时反过来写成 `RuleChain.outerRule(compose).around(关库排在组合之后(...))`（改前备份 `build/bak_TalkStarterTest_27.kt`），只跑该类 → `EXIT=1`、`AssertionError: 关库时前台上还有 1 个 Activity：收尾顺序反了（见 TestTeardown.kt）`、`BUILD FAILED in 25s`（`build/l3_27_neg.log`）；用完即还原，还原后 md5 与备份一致（`3d7f6cbed848f03975cea2008416e325`）。⇒ **「规则能识别反序」这件事本轮有真负例**；其余三个屏幕级用例类**没有各自的负例**。

四个屏幕级用例类跟着改了收尾（`PlayScreenTest` / `TalkInputTest` / `TalkStarterTest` / `A11ySemanticsTest`）：`createComposeRule()` 去掉 `@get:Rule` 注解存成字段、收尾换成上面那条 `RuleChain`、删掉原 `@After`。

本轮 L3 全量 = **18 类 / 125 例**（XML 重算，备份在 `build/l3_27_xml.xml`；`classname` 去重 = 18 ⇒ 新文件**没有**被 runner 误计成测试类）；四层完整数字与五处如实交代见 `docs/06` §3.6。

### 7.10 第 29 轮：偏好也开一个测试口子，收的是 DataStore 实例而不是文件名

（承接 §7.1~§7.9 的分层口径。）§7.9 的表里留了第二笔账：**「`AppContainer` 只给数据库开了测试口子，`settings` 取的是应用也在用的进程单例」，代价是「这台机器上的真实设置会被清掉」**。第 29 轮把这笔账还了，改的还是**测试接线**这一层。

**从两个参数变成四个**。`AppContainer` 原来的签名是 `(context, databaseName)`，现在两份偏好也各收一个口子，四个全是默认参数：

```kotlin
class AppContainer(
    context: Context,
    databaseName: String = ElderDatabase.FILE_NAME,
    settingsData: DataStore<Preferences> = context.applicationContext.settingsDataStore,
    interventionData: DataStore<Preferences> = context.applicationContext.interventionDataStore,
)
```

正式调用点 `main/.../ElderApp.kt:24` 那句 `AppContainer(this)` 一字未动，**默认值逐字等于改动前的取值**（`app/src/main` 的落盘路径一行未改）。

**为什么收「实例」而不是「文件名」**（取舍与 ADR-027 同）：`SettingsDataStore.kt` 只有 14 行，`val Context.settingsDataStore: DataStore<Preferences> by preferencesDataStore(name = "settings")`；`InterventionStore.kt:26` 同法写死 `name = "intervention"`。**委托属性没法参数化名字**——要收文件名就得改成自造一个「按名字缓存的工厂」，那会**动到正式落盘路径**，是数据丢失级风险。收实例则默认值原样保留，正式路径零改动。

**为什么「节流」那份也要收**。§7.9 记过「时钟固定不了」：`AppContainer.clock` 写死是系统钟，而「说什么」同时取决于钟点与节流（`InterventionStore` 是**进程单例、没有清空口**）。只隔离 `settings` 的话，5 个屏幕级用例写过的节流状态照样落在这台设备的真实存储上。

**为什么不跟库那条一样放进 `@After` 收尾**。库那条能收尾是因为 `deleteDatabase` 能在进程外把文件抹掉；DataStore 不行——`@After` 跑在 compose 规则收摊**之前**，那一刻收集器还挂在 DataStore 上。所以新加的 `TestTeardown.kt: 自己的存储(context, 标签)` 改用**默认作用域 + 每例一个新名字**（`System.nanoTime()`），两份文件分别落在 `context.cacheDir`，用例结束后实例无引用、靠 GC 回收，文件也不事后删（靠系统/`pm clear` 收）。

跟着改 `@Before` 的是 5 个类：`ui/settings/SettingsScreenTest.kt`、`ui/talk/TalkInputTest.kt`、`ui/talk/TalkStarterTest.kt`、`ui/play/PlayScreenTest.kt`、`ui/a11y/A11ySemanticsTest.kt`，一律 `AppContainer(context, TEST_DB, 存储.settingsData, 存储.interventionData)`。`SettingsScreenTest` 另删掉了 `@After fun 把共用的设置清回出厂状态()` 与 `@Before` 里的 `resetToDefaults()`。

**关键证据（量的是这台设备上应用真正的那两份偏好文件，不是测试自己那份）**：

| | 种子后（真实文件） | 跑完同一个类之后 | 结论 |
| --- | --- | --- | --- |
| **改前** | `settings.preferences_pb` **143 字节** / md5 `5e06c361e629cacdfb4564baaa655d1a` | **0 字节** / md5 `d41d8cd98f00b204e9800998ecf8427e` | **用户真实设置被设备测试清空**（缺陷复现） |
| **改后** | `settings.preferences_pb` **143 字节** / md5 `5e06c361e629cacdfb4564baaa655d1a`（与改前种子**逐字节一致** ⇒ 种子可复现） | **143 字节** / md5 不变；`intervention.preferences_pb` 49 字节 md5 `0c94a5656737e961093eec9c8a05dd02` 同样不变 | **两份都逐字节没动** |

两跑跑的都是 `com.fortheelder.ui.settings.SettingsScreenTest`（7 例，`OK (7 tests)`）。**这条证据不是用 gradle 驱动的**：`connectedDebugAndroidTest` 跑完 AGP 会把两个 APK 连应用数据一起卸掉，那样量不到，所以改用 `adb install -r <test apk>` + `adb shell am instrument -w -e class ...` 直接驱动（跑的还是同一份 test APK）。另外要照实说两点：① 改前那一跑里 `app-debug.apk` 的 mtime **没变**（仍是第 28 轮那颗），因为新旧 `AppContainer` 的默认值都指向真实 DataStore，**这处主代码差异对本次测量行为上是中性的**，真正被换掉的是 test APK——这一点是**推理**，不是直接量到的；② `intervention.preferences_pb` 里带时刻相关字段，**跨种子的 md5 会变**（改前那次种子是 `c7bc0179…`），所以它只能做「同一种子内前后对比」，不能拿「两个种子的 md5 相同」当证据。

### 7.11 第 30 轮：回执不设倒计时，各住自己那张卡

（承接 §7.1~§7.10。）§7.10 还的是测试接线的账。第 30 轮改**设置页两条回执的生命周期**，它同时是一处真实用户可见的缺陷修复。

**毛病一：靠 2 秒倒计时把回执撤掉。** 改前 `SettingsScreen.kt` 里有 `SAVED_HINT_MILLIS` 加一个 `LaunchedEffect(hint)` 配 `delay(...)`：保存称呼之后弹出「称呼已保存。」，2 秒后自己消失。两头都损：

1. **抓不稳**。第 27 轮走查就这么栽过——`uiautomator dump` 一次几百毫秒，加上 `sleep`，往往赶在那句话自己走掉之前 dump 不到，断言于是忽红忽绿。测不稳的东西在真机上同样不稳。
2. **对慢一点的用户有损**。半句话读不完就等于没出现过。目标用户是 55~65 岁刚退休人群，这正是最不该用倒计时的一群人。

**毛病二：字号回执长在称呼卡里。** 第 28 轮给字号三档加了回执，但它被摆在称呼卡那张卡片的尾部。于是在字号卡点「更大」，跑出来的「字号已改成「更大」。」出现在**上一张卡**下面，与刚点的按钮隔着一整张卡——位置本身就是错的。

**改法（三处）**：

1. **删掉常量与它的副作用**：`SAVED_HINT_MILLIS`、`LaunchedEffect`、`delay` 全部下线。
2. **两个独立槽位**：改前一个共用变量被两条路径写，现在拆成 `addressReceipt`（称呼那条）与 `fontReceipt`（字号那条），互不干扰。
3. **清除条件改成「下一次动手」**：回执不再自己走掉，而是这一页接下来**任何输入动作**时撤掉；离开这一页再回来也不在（内存态）。

| 位置 | 做什么 |
| --- | --- |
| `SettingsScreen.kt:86` | `onValueChange` 里 `addressReceipt = null` —— 一打字就把上一次的回执撤掉 |
| `SettingsScreen.kt:97` | 保存落库成功 → `addressReceipt = SettingsVoice.addressSaved` |
| `SettingsScreen.kt:103-104` | `addressReceipt?.let { ChangeReceipt(it) }`，摆在称呼卡尾注 `addressHint` **之前** |
| `SettingsScreen.kt:121` | 点某一档字号 → `fontReceipt = SettingsVoice.fontSizeChanged(option.label)` |
| `SettingsScreen.kt:140-141` | `fontReceipt?.let { ChangeReceipt(it) }`，摆在字号卡提示语之后、尾注 `fontStackNote` **之前**（⇒ 回到它所属的那张卡） |
| `SettingsScreen.kt:196-203` | `private fun ChangeReceipt(text: String)`：`bodyMedium` / `color = primary` / `fillMaxWidth()`，共 6 行 |

**代价（照实说）**：

- **不自动消失**：用户不动它，它就在那儿。是否反而显得啰嗦，**没有拿目标用户验过**（已进 `docs/07` 风险表与 CHANGELOG 的 `Unverified`）。
- **清除条件是「输入框里有动作」**，不是「点了屏幕别处」。点空白处那行小字还在。
- **内存态、不落盘**：进程被杀、或离开这一页再回来，回执就没了。这是有意的——它是「刚刚那一下」的回执，不是状态。

**指向**：取舍与四种备选见 **ADR-028**。

**证据甲（L4 走查，`build/screens30.log`，`EXIT=0` / `RESULT=PASS`）**。本轮新增 `font-size-picked` 一段，量屏幕上真实节点的坐标，而不是「字符串在不在」：

### 7.12 第 31 轮：`AppContainer` 收下时钟，屏幕级用例第一次能固定「现在」

（承接 §7.1~§7.11。）§7.11 还的是两条回执的账。第 31 轮还的是**一条从第 26 轮就挂着的欠账**：屏幕级用例固定不了「现在」。

**问题。** 第 26 轮写 `HomeViewModelTest` 时在 KDoc 里留了一句「首页那句晨昏问候该由 `HomeScreenTest` 来验」，当时写不成：`AppContainer` 的时钟是写死的 `SystemAppClock`，而屏幕级用例既拿不到 `refresh()`、也换不掉钟 ⇒ 任何一条「早上的话是早上那句」的断言都会**随运行时刻忽红忽绿**（走查脚本为此专门绕着走，测试里则根本不敢写）。第 28 轮的 **ADR-026** 于是做了个反向决定：**不开这个口子**，把「时钟写死」这个限制本身做成被测行为，交给 `SettingsScreenTest` 里那条安静时段用例去证。

**这一轮，口子的成本结构变了。** `AppContainer` 到第 29 轮已经收过三个口子（`databaseName`、`settingsData`、`interventionData`，都挤在构造参数表上），三个都是**同一个形态**：带默认值的构造参数，默认值指向应用自己在用的那一份（`ElderDatabase.FILE_NAME` / `context.settingsDataStore` / `context.interventionDataStore`）。第四个口子与它们**逐条同形**，代价只是「多一个参数」；而关着它要一直付的账是「**首页那句问候语在设备上一次都没被验过**」。于是开口子。

**位点**：

### 7.14 第 33 轮：把两处同名声明收成一处，并给新类补反向证据

§7.13 结尾留了三句话——注释不成立、第四个口子只在一条链路上被依赖、**没有任何断言能区分「公开属性被打坏」与「构造参数被打坏」**。本轮把三句一起结掉：**先改代码把缺陷消掉，再补一个能钉住这件事的用例类，最后用两处注入式变异证明它不是摆设**。

#### 缺陷的形状与修法

第 31 / 32 轮的 `AppContainer` 有**两处同名的 `clock`**：

```kotlin
class AppContainer(
    ...
    clock: AppClock = SystemAppClock,   // 第 31 轮加的口子：一个 plain 构造参数
) {
    ...
    val clock: AppClock = clock         // 第 31 轮加的公开属性：初始器取的是上面那个参数
```

第 32 轮的 M3 把下面那行的初始器换成 `SystemAppClock` ⇒ **公开属性**改了，**九处内部接线一处没改**（类体里的无限定名 `clock` 解析到构造参数）。于是「替换这一个值就等于把整棵对象图的时间一起挪了」这句承诺**只在 `HomeViewModel` 一条链路上成立**，而这件事在编译期与 L1~L4 四层里**都没有任何东西会拦**。原因是**有两处可以单独改**。

修法就是**把两处收成一处**：让构造参数本身就是那个公开属性，于是不存在「第二处」：

```kotlin
class AppContainer(
    ...
    /**
     * 全应用唯一的「现在」。……
     * 第 32 轮之前这里有两处同名声明……（KDoc 从类体挪到这里，并改掉那半句）
     */
    val clock: AppClock = SystemAppClock,   // 只此一处：既是口子，也是公开属性
) {
```

改动只在 `app/src/main/java/com/fortheelder/core/AppContainer.kt` 一个文件：`:75` 加 `val`；删掉类体里原先的 `val clock: AppClock = clock` 及其 KDoc（KDoc 挪到构造属性上方并改对了后半句）。类体里那九处 `clock` 从此无歧义地指向**同一个属性**，也就是那只被注入的钟。

### 7.15 第 34 轮：把「关库」从「按顺序做」升级成「等收尾落地」——顺带用实测推翻自己先写的那版修法

§7.14 结尾照实写着一句欠账：**L3 全量首跑那次崩溃根因未修，也没做最小复现**，而且「第 30 轮一次、第 33 轮一次」已经是同一条栈的第二次出现，照第 30 / 32 / 33 三轮的老口径，「L3 全绿」只是那一跑。本轮把这句话消掉，做法分三步：**先做最小复现把抖动变成可点的数字，再量清窗口的真实形状，最后才动手改**——结果第一版改法被自己的实测推翻，留下的是第二版。

#### 缺陷的形状：关库那一刻，观察者还挂在库上

读法：`viewModelStore.clear()` 触发 `viewModelScope` 取消，Room 的 `CoroutinesRoom.createFlow` 在协程退栈时调 `removeObserver`，而 `removeObserver` 内部要跑一次 `syncTriggers`（一个 `inTransaction`）⇒ **摘观察者这件事本身要碰数据库**。第 30 轮起那条「关库排在组合之后」的规则只保证**顺序**（先 `clear()`、后 `close()`），**不保证**中间那次 `removeObserver` 已经跑完。

#### 最小复现：把「偶发」变成可点的数字

`build/r34/repro.sh <次数> <标签>` 就是「装了测试包之后循环跑 `TalkViewModelTest`」这一个动作。30 次的结果：**1 次进程崩溃 + 1 次用例失败**，两次不是同一回事：

- 第 13 次：上面那条崩溃（`elder-test-talk-vm.db`）；
- 第 10 次：`java.io.FileNotFoundException: /data/user/0/com.fortheelder.debug/cache/talk-vm-93333403983327.preferences_pb: open failed: ENOENT`（`OkioStorage.kt:227` ← `DataStoreImpl` ← `Dispatchers.IO`）——**收尾里删 DataStore 文件时，IO 线程上那条读还没跑完**。同属「收尾与在飞任务赛跑」，但与库无关，所以后来是另一个助手治的（见下）。

#### 窗口的真实形状：70~130 ms，而且是确定性的 2 → 0

先量「`clear()` 返回时库里还挂着几个观察者」（探针类 `TalkTeardownProbe.kt`，只读地数 `InvalidationTracker` 上的 `observerMap`）：

- `clear()` / `cancel()` **返回时 = 2**；
- 之后**只靠时间流逝**自己归零：每 50 ms 采样一次，`t = 17 / 18 / 71 ms` 都还是 2，`t = 136 ms` 已经是 0 ⇒ 落地落在 **70~130 ms** 之间。
- 线程栈给出原因：那一刻 `arch_disk_io_0` / `arch_disk_io_1` 两条线程正卡在 **阻塞查询** 里（`AnchorDao_Impl$5.call` / `WishDao_Impl$10.call`，Room 开库 + 查询约 100 ms）。
- 为什么只有两条线程在飞、而且是共享池：`ElderDatabase.open` **没有给 Room 自定义 executor** ⇒ `database.queryExecutor` 就是 ArchTaskExecutor 的共享 IO 池（`Executors.newFixedThreadPool(4)`，线程名 `arch_disk_io_0` 到 `arch_disk_io_3`）。

#### 第一版修法（屏障）**被实测推翻**——这一段是本轮最该留的话

先写的修法很直白：**往 `database.queryExecutor` 排几个空任务、等它们回来**，想着「排到队尾就说明前面那些任务跑完了」。实测：

- 连着 **4 轮**「排 4 个任务 + `CountDownLatch` 等回」，跑 5 次（`build/r34/probe_AfterDrain_1..5.log`）⇒ **5/5 每轮观察者数都还是 2**；
- 换成「4 轮 `Instrumentation.waitForIdleSync()` + 排空执行器」，跑 3 次（`probe_AfterIdle_1..3.log`）⇒ **同样无效**。

原因是线程栈直接给出来的：那两条真正要跑完的任务**已经占着两条线程**，而我排的空任务落在**空闲**线程上，**屏障原理上就够不着在飞的那两条**。⇒ 这不是调参能救的，`waitForIdleSync` 也不行（它管的是主线程消息队列，跟这个池无关）。这一版**一次都没有生效**，如实留在这里，免得以后有人再走一遍。

#### 最终改法：等「库里挂着的观察者归零」

观察者计数才是与「现在能不能安全关库」**直接对应**的不变量，而且它是**确定性的**（2 对 0）：计数为 0 时 `removeObserver` 已经跑完、`syncTriggers` 已经做完，关库不可能再撞上它。改法落在**测试收尾**（`TestTeardown.kt`），**生产代码一个字没动**——生产里 Room 实例**永不 close**，这个坑本来就是测试自己的。

三处改动，都在 `app/src/androidTest/java/com/fortheelder/ui/TestTeardown.kt`：

**(1) 数观察者（`:126`，私有，反射）**：

```kotlin
private fun 库里挂着的观察者数(database: RoomDatabase): Int {
    val 追踪器 = database.invalidationTracker
    val 字段 = try {
        追踪器.javaClass.getDeclaredField("observerMap")
    } catch (没有: NoSuchFieldException) {
        throw AssertionError(
            "InvalidationTracker 上找不到 observerMap 字段，Room 版本变了要重写这段（见 TestTeardown.kt）",
            没有,
        )
    }
    字段.isAccessible = true
    val 表 = 字段.get(追踪器) ?: return 0
    return 表.javaClass.getMethod("size").invoke(表) as Int
}
```

两处刻意为之：字段名是 `observerMap` 而**不是** `mObserverMap`（Room 2.6.1 的实参名）；字段类型是 `androidx.arch.core.internal.SafeIterableMap` 而**不是** `Map`，强转会 `ClassCastException`，所以只能问它的 `size()`。拿不到字段**当场抛**而不是悄悄返回 0 —— 后者会让下面那个等待退化成空转。

**(2) 等落地（`:159`）**：

```kotlin
fun 关库前等收尾落地(database: RoomDatabase, 上限毫秒: Long = 5_000) {
    val 截止 = System.currentTimeMillis() + 上限毫秒
    while (true) {
        val 还剩 = 库里挂着的观察者数(database)
        if (还剩 == 0) return
        if (System.currentTimeMillis() >= 截止) {
            throw AssertionError(
                "关库前等了 $上限毫秒 ms，库里还挂着 $还剩 个观察者：收尾没跑完（见 TestTeardown.kt）",
            )
        }
        Thread.sleep(5)
    }
}
```

等不到就**打红**并把还剩几个写进消息，而不是让库在未知状态下被关掉。这跟第 29~33 轮那条一贯口径一致：**与其靠注释提醒，不如让它当场断言**。

**(3) 规则 `关库排在组合之后`（`:45`）的收尾多一步（`:54`）**：

```kotlin
} finally {
    要求宿主已经不在前台()
    关库前等收尾落地(container().database)
    container().database.close()
    InstrumentationRegistry.getInstrumentation().targetContext
        .deleteDatabase(databaseName)
}
```

顺序是「先断言宿主已退场 → 再等观察者摘完 → 再关库 → 最后删库文件」。`AppContainer.database` 是 `by lazy`，所以 `container()` 调两次安全（已读源码确认）。

**另一条链路：`取消后等收完`（`:182`）**治的是上面那次 DataStore `ENOENT`——删文件前先等已取消的作用域真的收干净：

```kotlin
fun 取消后等收完(scope: CoroutineScope, 上限毫秒: Long = 5_000) {
    val 任务 = scope.coroutineContext[Job] ?: return
    try {
        runBlocking {
            withTimeout(上限毫秒) { 任务.join() }
        }
    } catch (超时: TimeoutCancellationException) {
        throw AssertionError("作用域取消后 $上限毫秒 ms 仍没收完（见 TestTeardown.kt）", 超时)
    }
}
```

它和 (2) 是**两个不同的不变量**，别混：一个看「协程收完没有」，一个看「库上还挂着几个观察者」，后者才是关库的直接前置条件。`TalkViewModelTest` 与 `HomeViewModelTest` 的 `tearDown()` 现在都是「`clear()` → `cancel()` → `取消后等收完(storeScope)` → `关库前等收尾落地(database)` → `close()` → `deleteDatabase` → 删 DataStore 文件」。

改法本身也要能被证伪，所以新加 `app/src/androidTest/java/com/fortheelder/ui/TestTeardownTest.kt`（3 例，设备级）：

### 7.16 第 35 轮：给「首次读撞上首次写」这条竞态装上护栏，并用**同一次运行里**的 A/B 对照把「修好了」变成可点的数字

第 34 轮把那个偶发崩溃拆成了两条：一条是 Room 的「收尾与在飞任务赛跑」（已修，见 §7.15）；另一条是 DataStore 的
`java.io.FileNotFoundException: …: open failed: ENOENT`（`build/r34/pre10.log`）。**当时第二条被当成「测试删文件时的收尾噪声」记下来**。
本轮把它的性质改了：**它是产品侧的真缺陷**——全新安装、第一次打开应用就会走到，与测试无关。

#### 先分清「哪一次读」和「为什么那次读会中招」

第 34 轮已经拿到崩溃现场（`build/r34/pre10.log` 第 4 行）：

```
java.io.FileNotFoundException: /data/user/0/com.fortheelder.debug/cache/talk-vm-93333403983327.preferences_pb:
    open failed: ENOENT (No such file or directory)
Caused by: android.system.ErrnoException
```

注意文件名带随机后缀（`talk-vm-93333403983327`）⇒ 它是一只**刚建好的空文件**，崩溃就发生在**该文件的第一次读**。
本轮把「崩溃的必要条件」拆成三层，逐层用可核对的证据钉住：

**第一层：读为什么不等写。** `DataStore` 的读侧拿的是**非阻塞**的 `tryLock`（`OkioReadScope.readScope`），
所以交错是可能的——读不会排队等写完成。这一条解释了「为什么能撞上」，但不解释「撞上为什么不是常态」。

**第二层：撞上之后，异常为什么没被正常路径吃掉。** `OkioReadScope.readData()` 的原文（官方 sources jar，
`build/r35/srcokio/commonMain/androidx/datastore/core/okio/OkioStorage.kt`）：

```kotlin
override suspend fun readData(): T {
    checkClose()
    return try { fileSystem.read(file = path) { serializer.readFrom(this) } }
    catch (ex: FileNotFoundException) {
        if (fileSystem.exists(path)) { throw ex }
        serializer.defaultValue
    }
}
```

这段代码把话说得很死：**文件不存在时读一次，得到的正常结果就是「默认值」，不是异常**（设备探针 P-A：连续 50 次，50/50 返回默认值，
`fileExists=false`）。异常要逃到用户手上，**只可能**走 `if (fileSystem.exists(path)) { throw ex }` 这一条——也就是
**`open` 失败的那一刻文件不存在，而 `exists()` 查的那一刻文件已经存在**。探针 P-B 证明这条分支在实际解析到的产物组合下**确定活着**：
把它读的路径先建成目录（`madeDir=true exists=true`），读出来的就是 `outcome=java.io.FileNotFoundException|…: open failed: EISDIR (Is a directory)`。

写入侧把窗口压到极窄：`atomicMove` 在 okio 3.4.0 里就是一句 `File.renameTo`（Linux 上原子，**不会留出「目标消失」的窗口**）。
所以这个窗口只能是**「读开始得早了一拍，而写在读的两次系统调用之间恰好落地」**，宽度是微秒量级。

**第三层：那次读是在哪条线程上跑、为什么能撞进去。** 崩溃栈落在 `kotlinx.coroutines` 的
`Builders.common.kt:164`，对照 kotlinx-coroutines 1.9.0 的源码（`build/r35/kx/commonMain/Builders.common.kt`），
`:164` 正是 **FAST PATH #2**：

```kotlin
:152    newContext.ensureActive()
:154    // fast path #1: context is the same
:160    // FAST PATH #2: the interceptor is the same  ⇒ startUndispatchedOrReturn
```

`withContext` 在**调度器相同**时会**就地 undispatched 执行**，不重新派发。`storeScope` 与用例的
`runBlocking` 都跑在 `Dispatchers.IO` 上 ⇒ 那次读是**原地跑**的，与写者共享同一批 IO 线程，
「读得早一拍」因此有了落地的机会。探针 P-C 把次序也钉住了：在 `storeScope.cancel()` **之后**再发起的读，
拿到的是 `JobCancellationException`（`afterScopeCancel=kotlinx.coroutines.JobCancellationException`），**根本走不到打开文件**——
所以崩溃那一次读必然是在 `cancel()` **之前**就进了 `withContext`。

**把三层并起来，成因链只有一条**：读与写在同一条 IO 路径上交错，`open` 先失败、`exists()` 后看到文件，
于是 `FileNotFoundException` 逃出来。**抛出这个异常时，文件一定已经写好了**——数据没坏，读也没读错，**只是读得早了一拍**。

#### 修法：读侧加一层「只重试一次」的护栏

新增 `app/src/main/java/com/fortheelder/data/datastore/ReadRaceGuard.kt`（49 行，纯 LF）：

```kotlin
internal fun Flow<Preferences>.guardFirstReadRace(): Flow<Preferences> =
    retryWhen { cause, attempt -> cause is FileNotFoundException && attempt == 0L }
```

两个判定条件都不是随手写的：

- **只接 `FileNotFoundException`**。文件真损坏走的是 `CorruptionException`，不是这个类型，**不会被这层接住**——
  如果为了「多救一点」把范围放大到 `Exception`，就会把损坏、权限、磁盘满一起吞成静默重试。
- **`attempt == 0L`，只重试一次**。让「重试也失败」照原样抛出去。连续两次都撞上同一个微秒级窗口的概率可以忽略；
  真抛出来那多半是别的问题（磁盘满、权限错），不该被这层反复掩盖。

**「重试会重新读盘」这一点是有源码依据的，不是想当然。** `DataStoreImpl.kt:494-512` 的 `RunOnce`：

```kotlin
/**
 * Helper class that executes [doRun] up to 1 time to completion. If it fails, it will be retried
 * in the next [runIfNeeded] call.
 */
internal abstract class RunOnce {
    suspend fun runIfNeeded() {
        if (didRun.isCompleted) return
        runMutex.withLock {
            if (didRun.isCompleted) return
            doRun()                 // 抛异常时 didRun 仍是未完成态
            didRun.complete(Unit)
        }
    }
}
```

`didRun.complete(Unit)` 只在 `doRun()` **正常返回**之后才执行 ⇒ 抛异常后 `didRun` 仍是未完成态，
**下一次收集会重新跑一遍 `doRun()`、真的重新读盘**，而不是把缓存的失败再抛一次。
`readState(requireLock)` 在 `:218-219`，`internalDataFlow`（冷流，`:101` 起）在 `:127` 把原异常抛出，
`data`（`:150`）是 `channelFlow`、每次收集重跑 `internalDataFlow`，`readDataAndUpdateCache`（`:288`）
在缓存是 `ReadException` 时**不会**提前返回 ⇒ 重试路径通到盘上。

**接在哪些入口上**（4 处，也就是本轮读盘的**全部**入口）：

| --- | --- | --- |

#### 代价与边界

### 8.2 「APK 字节数总是一样」—— 第 17 轮解释并关闭

第 16 轮把它记成一条 Known Issue：第 12、15、16 三轮的 APK 都是 **10,971,528** 字节，新增了源文件却一个字节都没长，当时**解释不了**。第 17 轮做了逐条目比对，结论是**这不是巧合，是构造上的必然**，这条已知问题可以关闭。

做法：把改文案前的产物 `build/keep17-apk-0ef75004.apk`（记为 A）与改文案后的产物（记为 B）解开，逐条目对 `raw size` / `compress_size` / 本地记录长 / 起始偏移。脚本 `build/apkcmp17.py` + `build/apkcmp17b.py`（纯用 `zipfile` 读中央目录，不依赖 `unzip` 能不能装），输出 `build/apkcmp17.log`（24,972 字节）。实测：

- 条目数 **175 → 175**，无增无删；`sum(compress_size)` A=10872387 → B=10872384，**差 −3**；文件大小两边都是 **10,971,528**。
- **只有一个条目的内容变了**：`classes6.dex`（本轮改的那句引导页文案落在它里面）。raw size 两边都是 104,720，`compress_size` 44888 → **44885**（−3）。
- 那 −3 个字节从哪儿补回来了：下一个条目是 `lib/arm64-v8a/libandroidx.graphics.path.so`（**未压缩**存放），它前面的 extra field 是一长串 0 的 4096 对齐填充。该条目的本地记录长 16176 → **16179（+3）**，起始偏移 10348608 → **10348605**。
- 本地记录总长 A = B = **10,951,648**；尾部（中央目录 + EOCD）= **19,880**；两者相加正好 10,971,528。

所以机制是：**压缩后的字节差被紧随其后的对齐填充等量吸收**——只要差值小于那个条目剩余的填充余量，APK 的总字节数就**必然**不变。字节数相同**不能**说明产物没变；判据只能是 md5（本轮 A=`0ef75004cbeb63734fb33d2842011e4a` → B=`5b08e169a6501c9a328ef134356f3dcb`）。附带一条正面证据：`classes15.dex` 里能查到 `subtract-seven` 1 次、`算一算` 1 次、`SubtractSeven` 15 次，说明第 17 轮的代码确实进了这个包。

**两条守卫能看见的边界（四条，照实写）**

1. 只认 `val 名字: List<String> = listOf("…")` 这一种写法（正则 `val\s+(\w+)\s*:\s*List<String>\s*=\s*listOf\(([^)]*)\)`）。写成 `arrayOf` / `setOf` / `buildList`、从 `res/` 读、或者把禁词拆成两个字分别判，**它都看不见**。
2. 判「这是不是另一张表的复写」的门槛是**与在册表重合 ≥2 个词**；只抄 1 个词的私表扫不到。
3. 少于 2 个汉字的表直接跳过（`words.size < 2`）⇒ 单字禁词不在视野内。
4. 它管「表有几张、词对不对」，**不管「有没有人在用」**：某处把 `CopyRules.hit` 的逻辑抄一遍但不建表、或者建了表却没人调，它都不会红；`domain/` 里除了这几张词表，其余文案（例如目录正文本身）仍只靠各自的结构检查与人工评审，**那一层没有机械守卫**。

**把第 36 轮那两条「未查明」对上（本轮新增的对账）**

- **「10,971,528 vs 10,987,912 差 16,384」查清：不是功能差异，是 zipalign 给第一个未压缩原生库做的 16 KB 页对齐。** 五个包（本轮 `app-debug.apk`、`build/apk_r36_clean1.apk`、`build/apk_r36b_clean1.apk`、`build/apk_r34_clean1.apk`、`build/apk_r32_clean1.apk`）**都是 175 个条目、条目名与顺序全同、中央目录 extra 总长为 0**；按物理布局算空隙，两两之间**只有 1 处不同**——下标 17 的 `lib/arm64-v8a/libandroidx.graphics.path.so` 本地头 extra 长度 r36 = 15,875 → r37 = 599（−15,276）。真读本地头（`struct.unpack("<IHHHHHIIIHH")`）证实 **8 个 `.so` 的 data 起始偏移全都 `%16384 == 0`**：r37 落在 10,354,688、r36 落在 10,371,072，**差正好一页**。账平：文件差 −16,384 = 压缩总量差 −1,108 + 对齐填充差 −15,276。第 32/33/34 轮与 r37 同为 10,971,528（同一页），第 35/36 轮越到下一页。脚本 `build/r37/apkcmp37{,b,c,d}.py` 与四份日志。
- **「第 36 轮那 485 字节落在 zip 哪一处」查清。** `apkcmp37d.py` 比同轮两种构建模式的包：本地头区结束位置**完全相同**（10,968,032）、**空隙差 0 处**、中央目录 + EOCD 余量都是 19,880；差异只在 `classes6/7/8/10/12/13.dex` 六个条目的 raw/comp **内容真不同**（`sum comp` 差 +485，方向以缓存还原版为大），同时那个 `.so` 的填充 −485（15,875 → 16,360）把它抵掉，所以两者总字节数相同。⇒ **485 字节在包内的落点闭合**；**仍然没查明的是**：同一份源码为什么在两种缓存状态下这 6 个 dex 的内容真的不同（D8/R8 的确定性）——**这一条不许说成已查清**。
