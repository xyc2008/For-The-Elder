## 1. 测试目标与策略

### 1.1 测试目标

本项目要回答的不是「功能调用成功了吗」，而是三个更窄的问题：

1. **这条链路在设备上是真的走通了，还是只是编译过了？** —— 判据是装机走查的逐条断言与设备用例的 XML 报告。
2. **没测的地方有没有被写成「已测」？** —— 判据是第 8 节与 `records/CHANGELOG.md` 的 `Unverified` 一节。
3. **守卫会不会自己失效（假绿）？** —— 判据是每个机械守卫都带「先红后绿」记录与防假绿断言。

### 1.2 测试分层

| 层 | 名字 | 跑在哪 | 本例工具 | 最新规模（第 18 轮实测） |
| --- | --- | --- | --- | --- |
| L1 | 单元测试 | JVM，无 Android 框架 | JUnit 4 + `kotlinx-coroutines-test` | **29 类 / 370 例**，0 失败 |
| L2 | 构建与打包 | JVM（Gradle） | `:app:assembleDebug` | APK **11,052,250** 字节 |
| L3 | 设备仪器化测试 | 模拟器（AndroidJUnitRunner） | `androidx.test` + Compose UI Test + Espresso | **16 类 / 102 例**，0 失败 |
| L4 | 装机走查 | 模拟器（外挂脚本） | `adb` + `uiautomator dump` + `input tap` | **88 行断言日志**，逐条 `ASSERT ok` |

**为什么 L3 与 L4 同时存在**：L3 用测试框架的语义定位器点控件，**看不见点击落在哪个像素**；L4 用 `uiautomator` 转储真实界面树，能发现「按钮被裁到屏幕外」这类**布局**问题——引导第 3 页的次按钮被裁掉只剩 14px（第 6 轮）与算一算棋盘的行列数写错（第 18 轮），分别只有 L4 能抓到。两者不互相替代。

### 1.3 「先红后绿」纪律

任何新增的机械守卫与边界用例，必须先给出**它红过**的证据，再给出它变绿的证据。没有先红记录的守卫视为可疑——因为无法区分「守卫生效」与「守卫根本没执行」。

仓库里落过这条纪律的实例：

| 守卫 | 先红 | 后绿 |
| --- | --- | --- |
| `UiCopyPlacementTest`（`ui/` 层文案不许硬编码） | 搬迁前同一命令报 **138 处**违规，逐条人工看过、无误报，全文落盘 `build/offenders16.txt` | 搬迁后通过 |
| `PlayStaysClocklessTest`（`domain/play` 不许有钟） | 第 17 轮随新增游戏书面走查 | 通过 |
| `A11yPlacementTest`（语义只许从 `A11y.kt` 出） | 第 18 轮书面走查 | 通过 |

### 1.4 三条防空转的硬性做法

1. **强制真跑**：JVM 与打包一律加 `--rerun-tasks`。不加的话 Gradle 报 `UP-TO-DATE`，那样「通过」只是缓存结论，不是本次执行结论。
2. **数字取自 XML 报告，不取自 Gradle 控制台的「BUILD SUCCESSFUL」**。控制台不告诉你例数，报告告诉你 `tests / failures / errors / skipped`。
3. **守卫缺输入时直接失败，不许静默跳过**。`UiCopyPlacementTest` / `A11yPlacementTest` 拿不到 Gradle 传入的源码路径时 `error(...)` 失败，而不是 `return`——否则守卫会在 CI 或新环境下悄悄变成「零扫描、零违规」。

### 3.2 L1 覆盖不到的边界（转 L3 的原因）

- **Room DAO 在纯 JVM 跑不了** → 建表、迁移、唯一索引、`INSERT OR IGNORE` 全部进 L3。
- **Compose 渲染与字号** → 合成 density 的渲染级断言只能在设备上跑。
- **平台广播接收（`BroadcastReceiver`）** → 必须由系统投递，只能在设备上验。

### 4.1 编译期错误回归清单

以下只在写下时错、未进入任何交付物，记在此处供后人避坑：

| 错法 | 报什么 | 处理 |
| --- | --- | --- |
| `prefs[Long键] = nullable Long` | 类型不被允许 | 拆成 `if (x != null) prefs[k] = x.toEpochMilli() else prefs.remove(k)` |
| 新增 `sealed interface` 分支后漏 `when` 臂 | `'when' expression must be exhaustive` | 三处 `when` 各补 `is SubtractRound ->`（第 17 轮加第三个游戏时） |
| `Unresolved reference`（漏 import） | 编译失败 | 补 import |

**共同的教训**：本项目用 `sealed interface` 表达「一局的状态」，好处是漏分支**编译不过**而不是运行时静默走错分支；代价是每加一个游戏要改的 `when` 位置必须一次找齐。

### 5.2 两个真实的「同进程」坑（都不是产品缺陷）

仪器化用例与**应用同进程**，由此踩过两个坑，各修一次，值得完整记下：

1. **应用自己的采集器把用例的断言污染了**（第 7 轮）。`ElderApp.onCreate` 已按用户设置挂上进程级采集器，而用例里的 `input keyevent 26` 发给的是**系统**——两个采集器同时收到同一广播，一个用注入时钟写、一个用真实时钟写，断言读到三条记录。处理：`setUp()` 先 `container.rhythmCollector.stop()`，把写库的人收敛成一个。
2. **用例轮流 `deleteDatabase("elder.db")` 把产品库删空**（第 8 轮）。测试进程里 `AppContainer` 的 Room 实例长期存活，库文件被删空重建 → `SQLiteException: no such table: wish`，`Tests 63/71 completed`。处理：`ElderDatabase.open(...)` 与 `AppContainer(...)` 各加一个**默认参数**（唯一生产调用点未改），每个测试自带库名（`elder-test-*.db` 共 5 个）。

**这两条的共性**：真机上只有一个采集器、只有一个库；这两类失败**只存在于测试环境**。所以它们进第 9 节「缺陷清单」时，必须标成「测试侧」。

## 6. L4 装机走查（手工端到端用例）

走查不是手点的，是**脚本驱动的可复现流程**：`python build/walk18.py`（第 18 轮）在已装 APK 的模拟器上依次转储界面、断言可见文字、`input tap` 推进，把每一步的转储写进 `build/screens18.log`（88 行），末行必须是 `OK`。每次走查前补 `pm install -r -t` + `force-stop` + `KEYCODE_HOME`（第 18 轮实测：仪器化测试跑完会卸载 APK、前台会被 `com.android.camera2` 占着）。

**走查覆盖不到语义树**：`uiautomator dump` 只吐 17 个节点属性，看不到 `semantics{}` 挂的任何东西——无障碍那部分只能靠 L3（`records/04` 16.5）。

### 6.2 走查三条纪律

1. **正负断言成对**：不只断言「应出现」，还要断言「不应出现」（如「不含『两个小游戏』」）。单向断言抓不到「旧文案没删干净」。
2. **末行 `OK` 是唯一成功信号**：断言失败即中止并留日志，脚本不返回「大概通过」。
3. **脚本失败要先怀疑脚本**：第 17、18 轮各有三次失败，**逐条定性后全部是脚本自身**的错误（断言顺序错、把第二道题面误当上一道答案、日志 `_flush()` 写错变量导致文件恒为 0 字节；以及第 18 轮那两处环境问题）。产品侧只在第 17 轮真的抓到一个（引导页「两个小游戏」→ 三个）。

### 6.3 崩溃判据

`adb logcat -b crash -d`。**第 18 轮如实说明**：这一轮读缓冲区之前没有先清一次，读到的是 **0 行**，因此这句话只能保证「读到的时候是空的」，不保证「整轮期间一条都没进过」。第 10~12 轮的记录都是「走查前后各清一次、两次都空」，口径更强。

### 6.4 性能基线（第 21 轮实测，GAP-03）

第 21 轮是**纯测量轮**：`./gradlew :app:assembleDebug` 报 `UP-TO-DATE`（`38 actionable tasks: 38 up-to-date`），被测 APK 就是第 18 轮那份构建——`md5 84327b14218630002a6e4a26721333b6` / 11,052,250 字节。因此本节数字**可以**与本文其余各节的 L2 数字直接并列。

**NFR-07（冷启动 ≤ 2.5s）—— 本环境满足**

- 9 次启动全部 `LaunchState: COLD`，**942~1495ms**，中位 **1178ms**，均值 1157.3ms。原始输出：`build/coldstart21.log` + `build/perf21.log` + `build/perf21b.log` + `build/burst21.log`。

**NFR-08（滚动不掉帧）—— 本机型不可判**

- 原判据说的「首页滚动」在本机型**没有适用对象**：首页与「挑一个」各只渲染 **1 帧**，一屏放得下、不可滚动。

**两套数字并列的口径纪律**（同 `records/04` 第 19.8 节）：`framestats` 只保留最近约 119~120 帧，所以 n=388 是「三段窗口末尾样本的合并」，不是全窗口帧数；`gfxinfo` 汇总的 `50th` 与 `framestats` 的 `50%` 统计对象不同，**两套并列写、不取平均、不互相校准**。

## 11. 判定标准

一轮迭代要算「测试通过」，必须同时满足：

1. **L1 全绿**：`testDebugUnitTest --rerun-tasks` 的 XML 报告 `failures=0 errors=0 skipped=0`。
2. **L2 通过**：`assembleDebug` `BUILD SUCCESSFUL`，并记下字节数与 md5。
3. **L3 全绿**：`connectedDebugAndroidTest` 的 XML 报告 0 失败 0 错误 0 跳过。
4. **L4 走查末行 `OK`**，且正负断言成对。
5. **崩溃缓冲区为空**（清一次再跑、跑完再读一次），措辞与操作强度一致。
6. **每条未验的项写进第 8 节与 `records/CHANGELOG.md` 的 `Unverified`**，不写成「已覆盖」。
7. **没有假绿**：新增守卫有先红记录，且缺输入时直接失败。

**明确不算通过的情形**：只有 `BUILD SUCCESSFUL` 而没读 XML 报告；跑了 `assembleDebug` 但没 `--rerun-tasks` 却报出确定数字；走查只断言「应出现」；把估算值写成实测值。
