# 07 · 风险管理计划

| 项目 | 内容 |
| --- | --- |
| 系统名称 | For-The-Elder（懂节制的陪伴者——面向 55-65 岁刚退休人群的低打扰生活节奏陪伴 App） |
| 应用包名 | `com.fortheelder`（debug 变体 `com.fortheelder.debug`） |
| 版本 | 0.1.0（versionCode 1）；数据库 schema 版本 3 |
| 文档编号 | 07 |
| 编写轮次 | 第 14 轮 |
| 事实来源 | 本项目 13 轮迭代里真实出现过的问题 + `records/03` ADR-001~ADR-016 + `records/02` RC-001~RC-011 + `docs/01` GAP-01~GAP-09 + `records/04` 的实测数字 |

**一句话说明本文件的性质**：这里写的每一条风险，都能在仓库里指到一个编号或一条命令。凡是「还没验」的，一律写在「残余风险」里，不写成「已缓解」。

## 0. 本项目的风险结构与参照项目完全不同

参照项目（旅装 WeatherWear）的 `docs/07` 一共 16 条风险，其中 6 条是「外部依赖不可用」类：天气 API、12306 非官方接口、高德地图要自备 Key、内容平台不许抓取、LLM 编造内容、网络不可达。

本项目**一条这样的风险都没有**，因为对应的能力面根本不存在：

| 能力面 | 本项目状态 | 可复现的判据 |
| --- | --- | --- |
| 网络 | 零调用 | `grep -rnE 'http://\|https://\|java\.net\.URL\|Socket\|OkHttp\|Retrofit\|HttpURLConnection' app/src/main/java/` → 宽口径 **1 行**，是 `domain/engine/intent/IntentScan.kt` 的 KDoc 文字；窄口径（不含 `Socket`/`io.ktor`）**0 行** |
| 权限 | 0 个 | `grep -cE 'uses-permission\|<receiver' app/src/main/AndroidManifest.xml` → **0** |
| 第三方 SDK | 0 个 | `app/build.gradle.kts` 的 `dependencies` 只有 AndroidX / Compose / Room / DataStore / 两个测试库（详见 `docs/08` §1.2） |
| 服务端 | 无 | 没有 `INTERNET` 面，没有 Key，没有后端地址 |
| 大模型 | 无 | 意愿识别用词表规则（ADR-010），明确不加载 native 库、不用模型 |

**所以风险往哪集中**：不在「别人给我的东西坏了」，而在**「我自己推断的对不对」「有没有真人验过」「文档还准不准」**这三处。13 条风险里有 6 条属于「没有真实用户数据」，3 条属于「没在真实条件上跑过」，2 条属于「文档/纪律」，2 条属于「未来动作可能破坏现有立场」。

这不是更安全，是**能做的事更少**：一个不联网、不申请权限、不弹通知的 App，出错的方式确实少，但**能被证明有用的方式也少**——这一点本身就是 R-09。

## 1. 风险管理方法

### 1.1 流程

```
识别 → 判级（可能性 × 影响）→ 定级 → 制定应对 → 指派触发信号 → 跟踪复评
```

每个风险条目固定写四段：**表格（来源/类别/描述/触发条件/定级/应对/监控信号）→ 已落实措施 → 残余风险 → 修订历史（并入文末）。**

### 1.2 定级标准

**可能性（P）**

| 级别 | 含义 |
| --- | --- |
| 高 | 本环境已实测发生，或由所选方案在结构上必然发生 |
| 中 | 有条件发生，或部分用户会碰到 |
| 低 | 需要特定条件凑齐才发生 |

**影响（I）**

| 级别 | 含义 |
| --- | --- |
| 高 | 功能不可用 / 数据丢失 / 用户被误导并因此卸载 |
| 中 | 功能可用但结果不准，或后续开发被误导 |
| 低 | 文案、观感层面的瑕疵 |

**等级矩阵**

| P \ I | 高 | 中 | 低 |
| --- | --- | --- | --- |
| **高** | 红（立即处理） | 橙（计划处理） | 黄（接受并记录） |
| **中** | 橙（计划处理） | 黄（接受并记录） | 绿（监控） |
| **低** | 黄（接受并记录） | 绿（监控） | 绿（监控） |

### 1.3 应对策略类型

| 策略 | 含义 | 本项目实例 |
| --- | --- | --- |
| **规避** | 改设计，让风险不可能发生 | 用词表代替模型，从结构上没有「编造」这一说（R-01） |
| **减轻** | 降低可能性或影响 | 阈值一律往「宁可不说」的方向取（R-02）；介入上限 24 小时而非永久沉默（R-09） |
| **转移** | 把后果交给外部机制承接 | 本项目**没有可转移的对象**——没有服务端、没有第三方，也没有通知通道；这是有意的 |
| **接受** | 承认识别到，明确不处理并记录理由 | GAP-06（没有通知通道，是明确不做，不是待做项） |

### 1.4 「接受」在本项目里的特殊地位

本项目大量使用**接受**，而且接受得很硬：

- 进程不在就收不到广播 → 接受（ADR-009，代价写明「本轮没有量化」）。
- 词表外的说法听不懂 → 接受（RC-006 写明「这是已知的、刻意的漏，不是缺陷」）。
- 一整天不打开应用就什么都不做 → 接受（GAP-06，写成「明确不做」）。

之所以敢接受，是因为这些「不做」的方向全部指向同一个产品立场：**对 55-65 岁人群，一次不合时宜的打扰比少说一句话伤害大得多**（RC-008 原文）。风险管理的任务因此不是「把接受项都消灭」，而是**把每一项接受的代价写清楚，并盯住它不要变成「没用」**——那就是 R-09。

## 2. 风险登记册

### R-01 意愿识别靠词表，词表外的说法一律听不懂

| 项 | 内容 |
| --- | --- |
| 来源 | 本项目实测（第 7 轮 ADR-010、第 8 轮 RC-006） |
| 类别 | 功能正确性（漏识，不是错识） |
| 描述 | FR-06「从用户说的话里听出他想做什么」由本地词表匹配实现。`domain/engine/intent/IntentLexicon.kt` 实测有 **19 个兴趣提示词、4 个否定标记、13 个兴趣主题、7 个状态短语、2 个请求短语**，三张 `IntentTerm` 表共 **111 条短语**。没有模型、不联网、不加载 native 库，所以用户说的不在词表里，结果就是 `NotRecognized`。第 8 轮已把这条写进需求，并写明代价：`「下棋挺好的」` 这类话识别不出来。 |
| 触发条件 | 用户用词表外的说法表达意愿（词表外主题，如口琴、太极剑；或绕一句的说法） |
| P | 高（这是选型的必然结果，不是意外） |
| I | 中（不是答错，是没反应；用户会说「我说了它没懂」） |
| 等级 | **橙** |
| 应对 | 规避 + 减轻（结构上不猜 + 给一个不依赖识别的出口） |
| 监控信号 | 用户反馈「我说了它没听懂」；同一句话被反复输入而始终 `NotRecognized` |

**已落实措施**

1. **不猜**：`IntentScan.scan()` 返回 `sealed interface`，认不出来就是 `NotRecognized`，调用方**必须**处理这个分支——不返回「最接近的一条」。设备走查里刻意留了一句识别不出的话，用来证明它不是来者不拒（`records/04` 10.6）。
2. **不逐词消解否定**：否定标记只在兴趣上生效，按整句丢弃。做一半的句法分析会产生「看起来很聪明」的错误结果（ADR-010 第 2 条）。
3. **把出口做进界面**：「说两句」页有示例句按钮，用户不认字也能点出一句话；列表里点「我现在想了解一下」可以自己把兴趣记下来，完全不依赖识别（RC-006 / RC-007）。第 12 轮走查第 13 次通过，走的正是「点选示例句」这条路（`build/walk12e.log`，`grep -c "ASSERT ok"` = 41，0 FAIL）。
4. **留原话当纠错线索**：证据存用户原话片段，不存归一化后的规范词（ADR-010 第 3 条）。
5. **词表钉在单测里**：`IntentScanTest` 逐条断言正例与反例，边界（否定、请求、状态）各有用例。

**残余风险**

| 项 | 说明 |
| --- | --- |
| 覆盖率没有数据 | 「真人的自然说话方式能覆盖多少」**没有数据**（第 8 轮已如实记下）。19 个兴趣提示词是手写的，不是从语料统计出来的。 |
| 中文手工输入这条路从未验过 | 设备上只能靠 Compose 的 `performTextInput` 把字符直接注入文本框，**不是**真实输入法（GAP-02，见 R-07）。也就是说「用户用中文输入法打字 → 识别器读数」这条链上有一段没有任何人走过。 |
| 兴趣主题只有 13 个 | 词表外主题零识别，属设计内行为，不是缺陷。 |
| 措辞纪律没有人工评审 | `TalkVoice` 的措辞只由两张禁用词表扫描守住，挡不住一句没进词表的、同样空洞的新承诺（`docs/01` §9「仍未验证」原文）。 |

### R-02 作息推断的全部阈值都是推导值，没有任何真实用户数据支撑

| 项 | 内容 |
| --- | --- |
| 来源 | 本项目实测（第 5~6 轮 ADR-006 / ADR-007 / ADR-008） |
| 类别 | 功能正确性（推断偏） |
| 描述 | FR-03 / FR-04 的作息画像由 `RhythmInference` 统计得出，带一整套手写阈值：`cutoverHour=4`、`minDays=3`、`minPresencePerDay=20`、`minAwakeMinutes=360`、`bucketMinutes=30`、`quietDensityRatio=0.35`、`minQuietSignalsPerDay=0.5`、`minIdleMinutes=60`、`edgeGuardMinutes=45`、`chargingSpreadMinutes=90`、`chargingLookbackMinutes=240`。这些数字**每一个都是从需求推导的估计值，没有真实用户数据支撑**（`records/04` 原文），也只在本环境用「按电源键」造出来的信号上跑过。 |
| 触发条件 | 用户的实际节奏与阈值假设不符：午睡两小时被当成空窗；或长期达不到「3 天 + 每天 20 条」，画像永远停在 `NotEnoughData` |
| P | 高（阈值是推导的，必然有偏） |
| I | 中（推断偏 → 说话时机偏 → 打扰或沉默） |
| 等级 | **橙** |
| 应对 | 减轻（宁可不说，也不要猜错） |
| 监控信号 | 用户反馈「它在我午睡的时候说话」；`daily_rhythm` 表长期为空 |

**已落实措施**

1. **每个阈值都写清取舍**：`RhythmConfig` 的每个字段都有 KDoc 说明它拿什么换什么（例：`minPresencePerDay = 20` 是「这天几乎没碰手机」与「这天正常用了手机」之间的线，定太低会把稀疏得像噪声的一天当成正常作息，把整幅画像拉歪）。
2. **宁可不说**：数据不够时返回三态里的 `NotEnoughData`，而不是一个硬猜的值（ADR-007：用三态不用可空值）。
3. **床边留白**：起床后、睡前各留 `edgeGuardMinutes = 45` 分钟不判空窗——「误判空窗会导致一次不该来的打扰」，所以这里的默认方向永远是不说。
4. **空窗门槛抬高**：`minIdleMinutes = 60`，半小时的间隙一天里有的是，不值得打扰。
5. **纯函数**：`RhythmInference` 不看「现在几点」、不引用任何 Android API，因此能用合成数据把边界情况全跑一遍（AC-04.1 / AC-04.2，`RhythmInferenceTest`）。
6. **界面不谎报**：「样本不足时说不知道」被写成了验收口径，不是实现细节。

**残余风险**

| 项 | 说明 |
| --- | --- |
| 阈值未校准 | 没有任何真实用户数据参与过校准。它们保证的是「不乱报」，**不代表贴合目标用户的真实使用频率**（`records/CHANGELOG.md` Unverified 原文）。 |
| 空窗的实际价值未验 | 找到的空窗是不是用户真的「没事做」，**需要真人参与**才能确认（`records/04` 原文）。 |
| 只在模拟器造的信号上跑过 | 真实信号来自真机、真实充电习惯、真实锁屏设置。`isPresence` 还把 `SCREEN_ON` 当成「人在场」，理由写的「目标用户里相当一部分不设锁屏密码」——这条假设同样没有真实数据（`records/01` 第 6 轮）。 |
| 节流上限松紧未验 | `InterventionConfig`：`minGapMinutes=30` / `backoffStepMinutes=180` / `maxGapMinutes=1440`。「低打扰」产品里 24 小时这个上限是否偏松，**没有目标用户数据支撑**（`records/CHANGELOG.md` Unverified 原文）。 |

### R-03 进程不在就收不到广播：采集天生不连续，丢多少没量化

| 项 | 内容 |
| --- | --- |
| 来源 | 本项目实测（第 6 轮 ADR-009） |
| 类别 | 数据完整性 |
| 描述 | 作息信号靠五条系统广播（`SCREEN_ON` / `SCREEN_OFF` / `USER_PRESENT` / `ACTION_POWER_CONNECTED` / `ACTION_POWER_DISCONNECTED`）在**运行时**注册采集。manifest 里没有任何 `<receiver>`，也不申请 `RECEIVE_BOOT_COMPLETED`，没有前台服务、没有 `WorkManager`。**进程不在，广播就收不到**。于是信号在「关机期间」和「杀进程之后」两段是断的。 |
| 触发条件 | 厂商电池优化/后台清理杀掉进程；用户长时间关机；用户随手清掉后台 |
| P | 高（结构上必然发生） |
| I | 中（样本量低于常驻采集方案；极端情况下连续几天都攒不够 `minDays`） |
| 等级 | **橙** |
| 应对 | 接受 + 减轻（把代价写清楚 + 把清理挂到启动路径 + 让功能不依赖它） |
| 监控信号 | 冷启动次数明显少于一天一次；`daily_rhythm` 长期为空；用户报告「作息一直说不知道」 |

**已落实措施**

1. **代价写清楚，不藏**：ADR-009 明写「这个代价本轮没有量化」，并把它记进 `records/01` 第 6 轮的遗留里。丢的事件主要是「关机期间」和「杀进程之后」，而这两段恰好是信息量最低的（人在睡觉）。
2. **权限仍为 0**：三条广播与两条充放电广播都是系统广播，动态注册就能收到，**不需要任何权限**——既然不需要，就不申请。
3. **注册用 `RECEIVER_NOT_EXPORTED`**：走 `ContextCompat.registerReceiver`，兼容 API 26~34 的差异。
4. **`start()` 做成幂等**：每轮冷启动会重新注册一次，不做幂等会导致同一事件落两条。
5. **例行清理挂启动路径**：`pruneIfDue()` 同一天只清一次；信号与画像各保留 30 天（`SIGNAL_RETENTION_DAYS` / `RHYTHM_RETENTION_DAYS`）。
6. **不采集也照常能用**：拒绝引导第 3 页后，画像退回「按普通人的作息猜」，其余功能全部可用，且界面文案与代码分支对齐——第 6 轮设备实测：拒绝后首页仍显示「夜深了 / 不着急，什么时候想说都行。」。
7. **返回值不造假**：广播回调返回 `Job?`（「这个 action 我认，并且已经排了活」/「认不出」），不返回条数——落库是异步的，返回条数只能是 0 或编造（ADR-009 第 4 条）。

**残余风险**

| 项 | 说明 |
| --- | --- |
| 丢事件量未知 | 没有量化数据，因此**无法判断**作息画像在真实稀疏使用下的置信度。 |
| 可能长期 `NotEnoughData` | 「3 天 + 每天 20 条」在真实用户身上是否容易达到，没有数据；达不到时用户只会看到「还看不出来」，不知道原因。 |
| 厂商后台策略未验 | 只在 AVD `Elder_API35` 上跑过，国产 ROM 的后台清理策略完全未验（同 R-06）。 |
| 无法后台清理 | 定期清理只能挂在启动路径上；用户长期不开应用时，过期数据会留着。 |

### R-04 性能基线只在模拟器上测过（NFR-07 / NFR-08 / GAP-03）

| 项 | 内容 |
| --- | --- |
| 来源 | 本项目实测（第 4 轮起登记；**第 21 轮首次实测**） |
| 类别 | 性能 |
| 描述 | `docs/01` 的 NFR-07（冷启动到首页可交互 ≤ 2.5s，模拟器基线）与 NFR-08（首页滚动不掉帧，无连续 > 2 帧超 32ms）在第 10~18 轮一直顺延。**第 21 轮做了第一次实测**（API 35 模拟器 / `sdk_gphone64_x86_64` / swiftshader 软件渲染 / 1080×2400 / density 420）：冷启动 9 次全 `LaunchState: COLD`、942~1495ms（中位 1178ms）⇒ NFR-07 在本环境满足；NFR-08 原话的「首页滚动」在本机型无适用对象（首页与「挑一个」各 1 帧、一屏放得下），能滚的活动窗口（设置页）三窗口合并 n=388、50% 35.3ms、>16.7ms 383/388、>33.3ms 223/388 ⇒ **本模拟器上不可判**。 |
| 触发条件 | 目标用户手里的低端机；APK 体积（debug **11,052,250** 字节 / release 未签名 **7,550,437** 字节，后者是第 12 轮数字） |
| P | 中（Compose 单页 + 零网络；本环境实测启动在 1s 量级，但**仍然没有一台真实中低端机**） |
| I | 中（慢会直接影响 55-65 岁用户的第一印象；但不会出错） |
| 等级 | **黄**（不因一次模拟器实测而降级：真机与旧系统仍未知） |
| 应对 | 接受并记录——**已测的部分给数字，没测的部分不写估算**；真机测量是唯一能关闭它的路径 |
| 监控信号 | 任何一次真人试用里出现「打开要等一下」；或拿到真机后的复测 |

**已落实措施**

1. **缺口写进需求**：`docs/01` GAP-03 明确写着「**不做任何估算或推断**——没有数据就是没有数据」。这本身是本项目的写作纪律：宁可在文档里留一条红字，也不写一个看起来专业的假数字。
2. **结构上不存在网络等待**（推断，非实测）：全 App 零网络调用，首页只读本地 DataStore 与内存态，没有任何一次「等接口」。
3. **单 Activity + Compose**：没有多 Activity 切换、没有 Fragment 事务。
4. **APK 体积有实测值**：debug 与 release 两个数字都逐字节量过（第 12 轮 `--rerun-tasks` 两次一致）。

**残余风险**

| 项 | 说明 |
| --- | --- |
| 真机上的数字仍然不存在 | 第 21 轮的数字只覆盖一台 API 35 模拟器（`sdk_gphone64_x86_64`、swiftshader 软件渲染）。NFR-07 在本环境满足，但**真机与 Android 8~14 上的冷启动仍然没人测过**；NFR-08 的判据在本模拟器上连中位数都压不到 32ms 以下，因此**无法判真也无法判假**。 |

### R-08 零权限、零网络是产品立场，任何一次功能扩展都可能把它破掉

| 项 | 内容 |
| --- | --- |
| 来源 | 本项目实测（第 6 轮 ADR-009、第 9 轮 RC-008） |
| 类别 | 产品立场 / 平台政策 |
| 描述 | 「权限数 = 0」「`<receiver>` = 0」「网络调用 = 0」是本项目的三条硬判据，也是给用户看的承诺。它们不是「暂时没加」，是**有意的设计**：一个「懂节制」的陪伴应用，自己先变成一个一直在后台偷看屏幕状态、或者需要打电话权限的东西，说不过去。风险在于：功能一扩展（加通知、加联网取内容、加云备份、加统计 SDK），这三条会被悄悄破掉，而**用户界面上的承诺文案不会自动跟着变**。 |
| 触发条件 | 任何人提出「加个通知提醒」「联网抓点兴趣内容」「接个统计看看用户怎么用」「加个云备份免得换机丢」 |
| P | 中（当前没有排期，但只要迭代就会有人提） |
| I | 中（破功本身不崩，但会让整套承诺与文案失真，也会触发 R-13） |
| 等级 | **黄** |
| 应对 | 规避（把判据做成可复现命令）+ 减轻（把「不做」写成正式条目） |
| 监控信号 | `grep -cE 'uses-permission\|<receiver' app/src/main/AndroidManifest.xml` 不再是 0；`grep` 网络符号出现新的业务代码命中 |

**已落实措施**

1. **三条判据都能一条命令核**（见本文 §0 表格），且每一轮收尾都复核。
2. **「不做」被写成正式条目**：GAP-06 明确是「**明确不做，不是待做项**」，理由写了两条——与两条硬判据直接冲突；对 55-65 岁人群，一次不合时宜的通知比少说一句话伤害大得多。
3. **「介入」被收窄并留痕**：RC-008 把 FR-05 收窄为「打开应用时是否迎上来说话」，本版本不建通知通道，且明确写了「本版本不建」而不是「暂未实现」。
4. **早期设想也标了边界**：`docs/01` NFR-10 记着「仅唤醒式联网用于抓取兴趣内容」这条早期设想**在代码里没有任何实现**，且与 NR-01（不推销）冲突，落地前必须先走 `records/02` 变更。
5. **权限的可核对性已经实际用过**：第 11~12 轮的四类静态扫描里，权限/receiver 计数是其中一类（`grep -cE 'uses-permission|<receiver'` → 0）。

**残余风险**

| 项 | 说明 |
| --- | --- |
| 一旦加通知就同时破两条 | 通知需要 `POST_NOTIFICATIONS` 并在清单里注册 receiver，两条硬判据一起作废；那时必须先走 `records/02` 变更并重估本风险。 |
| 平台政策会变 | 目标 SDK 抬高（当前 `targetSdk 35`）后，平台可能要求新的声明；当前无影响，但「零权限」这条不是我们能永久保证的。 |
| 无障碍标签还没加 | **已做（第 18 轮）**：语义标签全部落在 Kotlin 里（`ui/common/A11y.kt` 一组修饰符），`AndroidManifest.xml` 与 `res/` 一个字节没加，权限数仍为 0、`<receiver>` 仍为 0，所以这道风险**没有被触发**。剩下的尾巴是「没有人真的用耳朵听过读屏朗读」，见 `records/04` 第十六节的 Unverified 段。 |

### R-09 产品立场风险：把「不打扰」做成「没用」，用户会卸载

| 项 | 内容 |
| --- | --- |
| 来源 | 本项目实测（第 9 轮 ADR-013，原文即本风险的识别） |
| 类别 | 产品价值 |
| 描述 | 本项目把 NR-02（不打扰）推到了极限：没有通知通道（GAP-06）、介入只在用户打开应用的那一刻发生（ADR-013）、静默采集、权限 0。代价是**用户一整天不打开应用时，它什么都不做**。ADR-013 里已经写下了这条风险的判断：「一天一次已经足够低；再低就退化成『几乎不说话』，**那种应用用户会直接卸载**。」 |
| 触发条件 | 用户装完、走完引导，之后不再主动打开；或打开后发现「没什么可做」 |
| P | 高（这是产品立场的必然副作用，不是意外） |
| I | 高（卸载 = 产品失败） |
| 等级 | **红** |
| 应对 | 减轻（在「不打扰」与「有用」之间给出可测的落点）+ 接受 |
| 监控信号 | 用户一个周期内一次都没打开应用；或第一次打开后 3 天内没有第二次 |

**已落实措施**

1. **上限而不是永久沉默**：`maxGapMinutes = 1440`（一天一次封顶），理由是「用户没有任何办法把一个永久沉默的陪伴者叫回来——它看起来坏了，而用户不会知道是自己『不理它』导致的」（ADR-013 原文）。退避序列可算：30 → 210 → 390 → … → 1440 分钟封顶。
2. **三条不依赖权限的主动入口常驻首页**：「说两句」「玩一会儿」「起点卡」。用户主动开口不需要任何权限、任何通知。
3. **一句问候也不白说**：问候引擎在设备上实测过（冷启动时的问候、节流后转「先不重复招呼了」），并且修过一个真实时序问题——`ON_START` 补判但冷启不重复判（用 `leftSinceLastOpening` 判「真的先离开过」），否则第一句话会一闪而过。
4. **拒绝采集后功能照常**：界面文案与代码分支对齐（`AppContainer.startProcessWork()` 在 `collectRhythm == false` 时不调 `start()`，问候引擎照常工作），有设备实测。
5. **不锁流程**：每一屏有退路；游戏一局玩完就结束，明确不设「再来一局」、不留历史最好成绩（RC-010），避免用「再来一局」把人留在应用里充当活跃数据。
6. **节流状态机有单测**：`ignoredStreak` 的增长、上限、以及「用户接话后回退」都钉在 JVM 单测里。

**残余风险**

| 项 | 说明 |
| --- | --- |
| 「值不值」没有数据 | 整个价值判断建立在「用户会自己打开应用」这一条假设上，而这条假设**从未被真人验证**（同 R-05）。 |
| 上限松紧未验 | 24 小时上限是否偏松，没有目标用户数据支撑（同 R-02）。 |
| 引导页是唯一的第一印象 | 引导页三页（RC-005）之后没有第二次说服机会；引导页文案在第 12 轮刚修过一次事实错误（GAP-08）。 |

### R-11 一句功效宣称就能把产品推向医疗口径

| 项 | 内容 |
| --- | --- |
| 来源 | 本项目实测（第 12 轮收口 GAP-07） |
| 类别 | 合规 / 文案 |
| 描述 | 面向 55-65 岁人群时，任何一句「改善记忆力」式的说法都可能被当成功效承诺，也可能让 App 在应用商店里落进医疗/健康类目，进而带来资质要求。AC-11.1 是全 App 规则：不得出现功效与医疗宣称词，只允许「玩」「试试」「大脑体操」。 |
| 触发条件 | 新增任何用户可见文案（界面、引导页、应用名、商店描述） |
| P | 中（词表是黑名单，只能挡住已经想到的词） |
| I | 高（被当成功效承诺是**对用户的失真**，比文案丑严重得多） |
| 等级 | **橙** |
| 应对 | 规避（词表单一来源）+ 减轻（可复现扫描 + 单测钉住） |
| 监控信号 | 扫描命中数不再等于词表自身的行数；或有人提出「加一句听起来更有吸引力的说法」 |

**已落实措施**

1. **词表单一来源**：`domain/voice/ClaimWords.kt`。`banned` 声明在 `:21`（15 个词，条目在 `:22-36`），`allowedWords` 在 `:40`，`checkWords` / `violations` 两个入口在 `:42` 起。GAP-07 的核心问题（两张表重叠但不一致）已在第 12 轮消除，`domain/play/PlayWords.kt` **已删除且不留转发壳**。
2. **可复现扫描，数字写死**：15 个词在 `app/src/main/java/` 只命中 **15 行**，全部落在词表定义行；`app/src/main/res/` **0 行**——即用户可见文案 0 命中。
3. **词表本身有单测**：`ClaimWordsTest` **7 例**把词表内容与扫描函数一起钉住。
4. **界面描述同一口径**：游戏描述统一写成「不算分也不排名次」；引导页在游戏数 1→2 之后同步改成「有两个小游戏」（GAP-08 的修补顺带做了口径统一）。**第 17 轮又改一次**：游戏数 2→3 之后这句再次对不上（选择页已是 3 张卡），已改成「有三个小游戏」（`ui/onboard/OnboardVoice.kt:44`），并在装机走查里加了两条断言（`有三个小游戏` 必须出现、`两个小游戏` 必须不出现，见 `build/screens17.log`）。这条风险真正的含义是：「游戏有几款」属于**会随功能漂移的文案**——每加一个游戏，引导页、用户手册、速查卡都要回头改一遍；第 12 轮与第 17 轮各漏过一次，两次都是靠人工比对发现的，目前**没有**机器守卫能自动发现这类漂移（现有守卫 `UiCopyPlacementTest` 只管文案放在哪个文件，不管数字对不对）。

**残余风险**

| 项 | 说明 |
| --- | --- |
| 黑名单挡不住没进词表的说法 | 词表能挡的只有已经想到的词。`docs/01` §9 已写明：`TalkVoice` 的措辞**没有人工评审**，挡不住一句没进词表的、同样空洞的新承诺。 |
| 词表内容的判断是人定的 | 允许词只有三个（「玩」「试试」「大脑体操」）；再多一个，就是一次没有第二人复核的判断。 |

### R-12 数据库迁移在真实旧库上出错，数据无备份

| 项 | 内容 |
| --- | --- |
| 来源 | 本项目实测（第 10 轮 `MIGRATION_2_3`、ADR-003） |
| 类别 | 数据安全 |
| 描述 | 数据库已到 schema 版本 3，迁移逐条写在 `Migrations.kt`，导出文件 `app/schemas/.../3.json` 在仓里。若将来写错一条迁移，或旧库结构与该文件不一致，用户已有的锚点与作息信号会丢失，或被 Room 直接拒绝打开（`Cannot find schema file` 这类问题在设备测试里真实出现过，排查记在 `docs/08` §8.2）。更要紧的是：本 App 的数据**只在这台手机上、卸载即消失**（ADR-003 `allowBackup="false"`），**没有备份可以回退**。 |
| 触发条件 | 下一次动 schema（版本 4 及以后）；或包的调试/正式变体共用了同一个库文件 |
| P | 低（当前无待做迁移，且已有测试覆盖） |
| I | 高（用户数据永久丢失，且用户不会知道原因） |
| 等级 | **橙** |
| 应对 | 减轻（迁移与 schema 都进仓 + 设备侧真跑迁移 + 隔离测试库） |
| 监控信号 | 用户报告「打开就闪退」或「记录没了」；设备测试报 `Cannot find schema file` |

**已落实措施**

1. **迁移逐条写在代码里，schema 导出进仓**：`MIGRATION_2_3` 现成，`3.json` 可核对。
2. **迁移在设备侧真跑**：`MigrationTest` **5 例**在模拟器上真实执行迁移，不是 JVM 侧模拟。
3. **测试库与产品库物理隔离**：ADR-012 规定仪器化测试必须用自己的库文件，不能和产品的 `elder.db` 共用一个文件——这条正是为了防「测试把产品库搞坏」。
4. **取舍已写成 ADR**：ADR-003 写明 `allowBackup="false"` 并且**刻意不写备份规则文件**——换机就丢，是「隐私换可移植性」的自觉选择，不是忘了配。
5. **界面如实告知**：「您的称呼、字号这些设置只存在这台手机里。卸载应用时它们会一起消失，我们这边不会留有副本。」（该文案已在设备上实测在屏，`records/04`）。
6. **保留期硬限制**：信号与画像各保留 30 天，启动路径上 `pruneIfDue()` 清理。

**残余风险**

| 项 | 说明 |
| --- | --- |
| 迁移只在测试库上跑过 | 没在「一个真的用了一个月、三张表都有数据的旧库」上跑过。 |
| 无备份 | 迁移出错等于永久丢数据；这是 ADR-003 的自觉代价，但它把 R-12 的影响从「中」顶到了「高」。 |
| 升级路径未验 | 从未做过一次「装旧版本 → 覆盖安装新版本」的实测。 |

### R-13 行为数据的隐私（全部本地、零上传，但它仍然是行为数据）

| 项 | 内容 |
| --- | --- |
| 来源 | 本项目实测（第 2 轮 ADR-003、第 6 轮 ADR-009、第 7 轮 ADR-010） |
| 类别 | 隐私 |
| 描述 | `elder.db` 里存的是「几点亮了屏、几点插了电、什么时候算安静」这类**行为痕迹**，以及用户说过的话的**原话片段**（ADR-010 第 3 条有意保留原话）。它不含位置、通讯录、设备标识，也没有任何上传通道。风险不在泄漏路径（没有路径），而在「数据就在本地库文件里，能拿到设备的人就能读」。 |
| 触发条件 | 有人物理接触设备并读到 `elder.db`；或将来引入任何上传面（后端、分析 SDK、云备份） |
| P | 低（需要物理接触；且 App 本身不联网，没有远端泄漏面） |
| I | 中（行为痕迹与原话片段属个人信息） |
| 等级 | **绿** |
| 应对 | 规避（零上传 + 零备份）+ 接受（本地库未加密） |
| 监控信号 | 引入任何自有后端、第三方分析 SDK 或云备份；或清单里出现网络相关权限 |

**已落实措施**

1. **零上传**：网络调用 0（见 §0 判据），权限 0，接收器 0。
2. **零备份**：`allowBackup="false"` 且不写备份规则文件（ADR-003），卸载时数据一起消失。
3. **界面如实告知**：文案原文见 R-12 第 5 条，已在设备上实测在屏。
4. **保留期硬限制**：信号与画像各保留 30 天，过期即删。
5. **采集需要用户点头**：引导流程第 3 页是「先问后采」的同意闸门（RC-005），拒绝后全部功能照常可用（ADR-009 第 5 条，有设备实测）。
6. **不存规范词**：兴趣证据保留原话片段，是为了让用户能指着它纠错（ADR-010 第 3 条）——这条是功能取舍，同时也意味着原话确实落库，所以它被写进本条而不是藏起来。

**残余风险**

| 项 | 说明 |
| --- | --- |
| 本地库未加密 | 未使用 SQLCipher。对行为痕迹这类数据，加密不是必须的，但确实没有做。 |
| 原话片段长期留存 | 兴趣证据长期保留、不设保留期（RC-007 有意如此：用户能在列表里指着它纠错）。这是功能与隐私之间的一次明确取舍，方向偏功能。 |
| 未来上传面会改变定级 | 只要引入任何上传面，本条的 P 与 I 都要重判，届时 R-08 一并复评。 |

## 5. 本版本刻意不登记的风险（诚实清单）

下面这些在参照项目里是**主要**风险，在本项目里一条都不成立。写出来是为了说明「不是漏了」，也为了让将来引入对应能力时知道该在哪儿补条目。

| 不登记的类别 | 为什么不成立 | 哪一天要补 |
| --- | --- | --- |
| 外部服务超时/限流/被屏蔽 | 零网络调用（§0 判据），没有任何外部服务 | 引入任何后端或开放接口时，新增一条「外部依赖不可用」，并按参照项目 R-02 的写法给降级层 |
| 第三方 Key 未配置 | 依赖里没有任何需要 Key 的 SDK | 引入地图/天气类 SDK 时 |
| 内容平台不允许抓取 | 只做本地功能，不抓任何平台内容；唯一相关设想（「仅唤醒式联网抓取兴趣内容」）在代码里零实现，且与 NR-01 冲突（`docs/01` NFR-10） | 该设想立项时，先走 `records/02` 变更 |
| 大模型编造内容 | 不用模型（ADR-010），结构上没有「生成」这一说；输出全部来自用户自己输入的原话与手写词表 | 引入任何模型时，本条必须与 R-01 一起重判 |
| 通知打扰用户 | 没有通知通道，是明确不做（GAP-06 / RC-008） | 该决定被推翻时，本条与 R-08 同时改写 |
| 服务端数据泄露 | 没有服务端 | 出现服务端时，R-13 的 P 与 I 全部重判 |
