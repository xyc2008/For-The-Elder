## 1. 立项背景

需求文档给出的核心判断是：市面上的老年 App 大多在做两件事——**健康管理**和**子女远程看护**，而 55–65 岁刚退休这批人的真实痛点是别的：

> 精准锁定 55-65 岁、刚退休、有一定智能机基础但面临"时间突然变多、感到失落"的过渡期老人。
> 切入场景是他们每天"不知道干嘛"的空窗期，而非刻板的健康管理。

也就是说，本项目的立项理由不是「老人需要被管理」，而是「老人退休后失去了工作这个天然的时间锚点，一天的时间结构塌了」。这是一个人生阶段的过渡期问题，不是医疗问题。

需求文档同时给出了产品的差异点，本项目的全部设计取舍都以它为准绳：

> 在互联网都在抢夺用户时长的时代，我们做"反沉迷、不打扰、不制造焦虑"的产品。
> 通过"不推销、尊重意愿"，在老年群体中建立极深的信任感。

## 2. 项目目标

### 2.1 业务目标

1. 让刚退休的用户在一天里**至少有一个属于自己的、被记住的生活锚点**（例如每天傍晚去走一圈）。
2. 让 App 的每一次出现都**有理由、有余地**：不确定用户想不想说话时，就不说话。
3. 让用户相信这款 App **不图他的时间和钱**。

### 2.2 交付目标（工程口径）

| 编号 | 目标 | 验收口径 |
| --- | --- | --- |
| G-01 | 可构建 | `./gradlew :app:assembleDebug` 成功产出 APK |
| G-02 | 可测试 | `./gradlew :app:testDebugUnitTest` 全绿 |
| G-03 | 可安装可运行 | APK 能装到 `Elder_API35` 模拟器并跑通核心链路，无崩溃 |
| G-04 | 文档齐备 | `docs/00`–`docs/09` 存在且描述与代码一致，引用到具体文件与行号 |
| G-05 | 过程可追溯 | 每轮迭代在 `records/01-迭代记录.md` 有「目标 / 产出 / 问题与解决 / 验证」四节 |
| G-06 | 无假功能 | 不存在点了没反应、写死数据、无实现的空壳入口 |

G-06 是本项目的硬约束，直接来自用户要求「不断完善功能，不要存在假功能」。它的工程含义是：**任何进入导航的入口都必须是通的**。一个功能没做完，它的入口就不出现在界面上，而不是放个 `"敬请期待"`。

## 3. 范围

### 3.1 范围内（In Scope）

| 模块 | 内容 |
| --- | --- |
| 无感作息感知 | 用手机使用行为（解锁频率、充电时段）推断用户空闲规律，找出「介入窗口」。不使用穿戴设备。 |
| 陪伴式意愿发现 | 不弹问卷、不要求填标签。在闲谈中接住用户的话茬，**只有用户说「愿意」才提供帮助**。 |
| 主服务：陪伴 + 兴趣陪伴 | 表达意愿后给低门槛尝试选项，并持续轻推，帮用户立起生活锚点。 |
| 辅模块：趣味脑力互动 | 注意力/执行功能的游戏化设计，作为插件存在，严格剥离医疗宣称。 |
| 适老化基础能力 | 应用内独立字号档位、大触控目标、低认知负荷的信息层级。 |
| 隐私与反沉迷 | 数据本地存储、不索取无关权限、主动节流不打扰。 |

### 3.2 范围外（Out of Scope，明确不做）

| 不做的事 | 原因 |
| --- | --- |
| 血压/心率/睡眠等健康指标记录与解读 | 需求文档明确本品「而非刻板的健康管理」；且一旦涉及健康解读就会滑向医疗宣称。 |
| 脑力训练的「延缓认知衰退」等疗效宣称 | 需求文档要求「严格剥离医疗宣称，定位为'趣味大脑体操'」。 |
| 子女远程监护面板 | 与「不替您判断身体状况」及信任定位冲突。 |
| 签到、打卡、连续天数排行榜 | 与「不催您、不会记您几天没来」直接冲突。 |
| 任何形式的商品推荐、广告、付费引导 | 与「零推销」冲突。 |
| 账号体系与云端同步 | 尚无必要，且会把本地数据变成需要保管的资产。 |

### 3.3 明确的负面需求（Negative Requirements）

负面需求同样是需求，必须被验收。本项目有 5 条：

- **NR-01 零推销**：产品内不得出现任何商品、服务、课程、广告的推荐位。
- **NR-02 不打扰**：不得在用户未主动打开 App 时以任何形式发出提示（无通知栏、无角标、无悬浮窗）。
- **NR-03 不制造焦虑**：不得展示任何「您已 N 天未使用」「今日目标未完成」类文案或图形。
- **NR-04 不替用户判断**：不得给出身体、心理、财务方面的判断或建议。
- **NR-05 不索取无关权限**：权限只在功能真正需要时才申请，且申请前必须说明用途。

`NR-02` 尤其需要说明：它意味着本项目**刻意不使用** `POST_NOTIFICATIONS` 权限，也**刻意不使用** WorkManager 的前台唤起能力。节流调度的产出是「App 下次被打开时该说什么」，而不是「在某个时刻把用户叫起来」。理由见 `records/03-架构决策记录.md`。

## 4. 目标用户与画像

| 维度 | 描述 |
| --- | --- |
| 年龄 | 55–65 岁 |
| 状态 | 刚退休或退休 1–3 年内 |
| 设备能力 | 会用微信、会扫码、会视频通话；不熟悉「设置」深处；不会为自己改系统字号 |
| 生理特征 | 老花、手抖、指腹触控面积大、对高对比度文字更敏感 |
| 心理特征 | **不愿被当成"老人"**；对推销高度警惕；对「填问卷」「做测试」有抵触 |
| 核心场景 | 白天某段时间无事可做、心里发空；或者晚上想起以前喜欢做的事 |
| 一句话诉求 | 「别烦我，但你得记得我。」 |

画像带来的两条设计铁律：

1. **不能用「老人模式」这类称呼**。App 内的字号设置标题是「字的大小」，不是「长辈模式」。
2. **不能用问卷收集偏好**。所有偏好只能从用户主动说出的话里获得。

## 5. 关键假定与约束

### 5.1 假定

| 编号 | 假定 | 若假定不成立的影响 |

## 9. 验收准则（项目级）

项目在以下条件同时成立时才算达标：

1. `./gradlew :app:testDebugUnitTest` 通过，且测试数量随功能增长（无「删测试求绿」）。
2. `./gradlew :app:assembleDebug` 通过并产出 APK。
3. APK 安装到模拟器后可走通核心链路：**作息感知 → 意愿发现 → 兴趣陪伴 → 脑力互动**，全程无崩溃（`logcat -b crash` 为空）。
4. `docs/00`–`docs/09` 全部存在，文档中引用的文件路径与行号在仓库中真实存在。
5. `records/01-迭代记录.md` 中的每一轮都有四节，且「验证」一节只写实际执行过的检查；未执行的检查明确标注「未验证」。
6. 不存在占位功能：全仓库搜索不到 `TODO`、`FIXME`、`敬请期待`、`not implemented` 之类的未实现标记出现在用户可达路径上。
7. 已完成 10 轮迭代并成功 `git push` 至少一次。

第 6 条的检查方式已固化，见 `records/04-质量与验证记录.md`。

## 10. 风险概要

完整清单见 `docs/07-风险管理计划.md`。最高风险三条：

| 编号 | 风险 | 应对 |
| --- | --- | --- |
| R-01 | 「不打扰」与「有用」互相削弱，App 变得可有可无 | 把价值压在「被记住」而非「被提醒」上；用生活锚点做留存，不用提醒做留存 |
| R-02 | 作息感知在模拟器/开发机上无法验证真实准确性 | 引擎与采集器解耦：引擎吃纯数据、可在 JVM 单测里用合成数据充分验证；采集器只做「如实上报」 |
| R-03 | 意图识别在无网/低算力设备上不准 | 全部推理可离线；无法判断时一律走「不提供帮助」的安全分支，宁可少做也不误判 |
